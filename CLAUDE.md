**Most of this file is dated incident history, and a claim naming a specific column, file or count is a fact with a shelf life.** The RULES here are durable; the INSTANCES illustrating them decay, because the renames and repairs this file teaches you to perform are performed on the very things it cites. A 2026-08-05 audit against live `information_schema` found seven claims stated as live defects that were already fixed — two of which a documentation sweep had acted on, spending real effort establishing that the target was clean. So: **verify before you act on any specific identifier here.** One query, one `ls`, or one `git show` settles it, and a claim's age is not a proxy for its truth.

That audit also got one wrong in the other direction, which is worth more than the seven it got right. It reported the `wagers` 42703 below as already repaired, on the strength of the column name resolving and the file's most recent commit looking plausible — but the defect was live in production and stayed live for another day. **Checking a column against `information_schema` verifies the NAME and says nothing about whether any particular commit fixed the code**, so an audit that mixes the two oracles will mark live defects repaired at exactly the rate it corrects stale ones. Whenever this file credits a hash with a fix, the claim rests on a diff someone has to have read. Where a passage is history it now says so; treat an undated specific as unverified rather than current. ## Project Overview

This is **xo.football**, an open-source fantasy football league management platform featuring live auctions, advanced analytics, betting market integration, and comprehensive data views. Built with React/Redux frontend and Express.js/PostgreSQL backend.

## Development Commands

- `yarn start` - Frontend development server only
- `yarn start:api` - API development server only

**Code Quality:**

**Build & Deploy:**

- **`yarn deploy:all` — the deploy path. Use this unless you have a specific reason not to.** Runs `preflight:deploy && deploy && build && deploy:dist && deploy:sourcemaps`: pre-flight gate, then backend to both hosts, then the frontend bundle and its sourcemaps. It exists because the individual steps below are each independently skippable and the skip is silent — the recurring production incident here is a PARTIAL deploy, someone shipping `deploy:dist` for the frontend and never running `deploy` for the backend (or the reverse). On 2026-07-16 both backend checkouts sat 6 commits behind since the last `yarn deploy` while the client `dist` had been rebuilt that same day; the app hosts drifted again to 4 behind by 2026-07-29. Running every step in one command is what makes the sequence un-skippable. It is human-gated on purpose — nothing auto-deploys these hosts, because they run the live API and the import workers and reloading them unattended is the wrong risk. Being a superset of a backend-only deploy costs one webpack build and one rsync; take that over reasoning each time about whether your change reaches the SPA.
- `yarn preflight:deploy` - The gate `deploy:all` runs first (`scripts/preflight-deploy.sh`). Refuses to deploy from a dirty working tree (`yarn build` would bundle a concurrent session's edits into production), from a HEAD that is ahead of or behind `origin/master` (the hosts `git pull` origin, so an unpushed commit deploys the prior state), or with an unpushed `private` submodule commit (the hosts `git submodule update --init private`, and `private` is a nested submodule that `sync-all` does not push). Read-only — it fetches and compares, nothing else. Safe to run on its own to check whether a deploy would be honest.
  **`yarn deploy:all` EXITS 0 WHEN THE PRE-FLIGHT GATE REFUSES, so the exit code cannot tell a completed deploy from one that never ran.** On 2026-08-14 a deploy refused with `HEAD is 1 commit(s) BEHIND origin/master` — a sibling had pushed while the worktree was installing — and reported `exit=0` with a normal-looking tail; the hosts never moved and the change was reported as shipped. Read the OUTPUT (`grep -c 'REFUSING TO DEPLOY'`) and then the hosts, never the status. Two checks settle it: both hosts at `origin/master` (`ssh league "cd /root/league && git rev-parse --short HEAD"`, same for `digitalocean-0`), and — the one that matters more — **the bundle the served HTML references must exist on disk**: `curl -s https://xo.football/ | grep -oE 'main\.[a-z0-9]+\.js'` against `ssh league 'ls /root/league/dist/'`. Checking the served HTML's CONTENT is not enough, because Cloudflare will happily keep serving a deleted `/dist` asset from the edge (the `immutable` note above) and the page renders for you while it is broken for anyone without that cache entry.

**And note the deploy ORDER is reload-then-rsync: `deploy` (pm2 reload) runs BEFORE `build && deploy:dist`.** Anything the API caches from `dist/` at startup is therefore captured from the PREVIOUS build. The SPA-fallback middleware (`libs-server/middleware/render-html.mjs`) cached `dist/index.html` on first read and pinned production to a superseded, content-hashed bundle that `deploy:dist` had already deleted — every visitor without an edge-cached copy got a blank app, and the recovery was a second `pm2 reload` after the rsync. It now keys the cache on mtime, covered by `test/api.render-html-middleware.spec.mjs`. When you add anything that reads `dist/` at startup, assume it will see the old build.

- `yarn build` - Build production bundle
- `yarn analyze` - Build with bundle analyzer
- `yarn deploy` - **API + workers only**: on each host, `git pull` from `origin/master`, `yarn install`, and `pm2 reload` the app (main) / import workers (worker-1). Does **NOT** rebuild or rsync the frontend `dist/` bundle. Frontend changes (any file under `app/`, `webpack/`, `libs-shared/` consumed by the SPA, or routes/components) require running `yarn build && yarn deploy:dist` separately — **which is exactly the split that keeps producing partial deploys, so prefer `yarn deploy:all` above.** Reach for bare `yarn deploy` only when you have positively established your change is backend-only (`api/`, `libs-server/`, `scripts/`, `jobs/`). **Push to `origin/master` before running `yarn deploy`** — the servers pull from origin; an unpushed local commit will deploy the prior origin state and leave production on stale code. (`yarn deploy:all` refuses in that situation; bare `yarn deploy` does not check.)
- `yarn deploy:dist` - Frontend-only deploy: rsyncs locally-built `dist/` to `/root/league/dist` on the main server (excludes `*.map` — sourcemaps are never served publicly). No API restart. Pair with `yarn build` to refresh the SPA bundle.
- `yarn deploy:sourcemaps` - Ships the build's `*.js.map` files to the **private** path `/root/league/sourcemaps` on the main server (never the public `dist/`). The `/api/errors` route resolves minified client stack frames against these maps server-side (`libs-server/symbolicate-stack.mjs`), so emitted `log_error` signals carry original `file:line:col` instead of minified chunk coordinates. **Always pair this with `yarn build && yarn deploy:dist`** — a frontend deploy that ships new chunk hashes without the matching maps silently degrades symbolication to raw minified stacks for the new chunks. Full frontend deploy: `yarn build && yarn deploy:dist && yarn deploy:sourcemaps`.
- `yarn load:main` - Update code and deps on the main server and `pm2 reload` the API app
- `yarn load:worker1` - Update code and reload worker processes on worker server 1

Deploy targets (SSH hosts): `league` (main: API + frontend), `digitalocean-0` (odds/plays import workers)

**`yarn build` reads the working tree, not the pushed ref — never build a frontend deploy from a dirty shared checkout.** `yarn deploy` is safe against local dirt (each host `git pull`s from `origin/master`), but `yarn build` bundles whatever is sitting in the tree, so a sibling session's uncommitted edits ship straight to production. This is not hypothetical: a 2026-07 frontend deploy for the RFA column rename coincided with another session's uncommitted changes to `libs-shared/get-draft-window.mjs`, which reaches the SPA through `libs-shared/index.mjs`. Check `git status` before `yarn build`; if the tree is dirty with work that is not yours, build from a throwaway worktree pinned to the pushed ref (`git worktree add ~/user-base/tmp/<name> origin/master`, symlink `node_modules`, then `yarn build && yarn deploy:dist && yarn deploy:sourcemaps` from there, then `git worktree remove`). Do not stash a sibling's work to clean the tree.

**A fresh worktree does not inherit submodules, so `yarn deploy:all` from one refuses with `private submodule is not initialized; the hosts deploy it`.** The recipe above omits the step: run `git submodule update --init private` in the worktree first (it clones ~fresh, so give it a moment), then verify its HEAD matches the main checkout's before deploying. Confirmed 2026-08-04 on the trade-review rename deploy — preflight caught it cleanly, but it reads as a deploy-config problem rather than a missing worktree step.

**`yarn deploy:dist` ships whatever is already in `dist/` — a clean `git status` does NOT mean it is safe to run.** This is the companion hazard to the one above, and the check for it is different. `dist/` is a build artifact directory: it survives commits, it is not cleaned by anything, and it can hold a sibling session's _finished build of an undeployed change_ while the source tree is spotless. Running `deploy:dist` then ships that change to production early, out of its own sequence and possibly ahead of the schema or push it depends on. This is not hypothetical either: on 2026-07-28 the tree was clean while `dist/` held a built bundle of the rookie-draft hourly-window rework, which had its own gated deploy sequence and must not have shipped early. **Before any `deploy:dist`, compare the local bundle against what production actually serves** — `ls dist/main.*.js` locally against `grep -o 'main\.[a-z0-9]*\.js' /root/league/dist/index.html` on the server. A local hash that does not match production's means `dist/` holds something undeployed; find out whose it is before shipping. If your change is backend-only (`api/`, `libs-server/`, `scripts/`, `jobs/`), skip the frontend steps entirely — `yarn deploy` alone is what you want.

**Verifying a frontend deploy over HTTP: assets live under `/dist/`, and every path OUTSIDE `/dist/` returns `index.html` with a 200.** The SPA catch-all means `curl https://xo.football/main.<hash>.js` answers `200` with 11KB of `index.html` rather than the bundle — so a verification that only checks the status code passes identically whether the asset exists, is stale, or was never deployed. On 2026-07-29 a `kickoff_at` frontend deploy was "confirmed" three ways by this shape: the new bundle, the superseded bundle, and a `.map` all returned 200, which read as success, success, and a public sourcemap leak. All three were `index.html`. Check `content_type` and body, not `%{http_code}` — the real URLs are `https://xo.football/dist/main.<hash>.js` (`application/javascript`, ~376KB). Read the referenced hash out of the deployed page (`curl -s https://xo.football/ | grep -oE 'src="[^"]*"'`) rather than guessing the path.

Since 2026-07-30 the `/dist` mount is `fallthrough: false` with its own 404 handler (matching `/static` and `/docs`), so **a missing asset under `/dist/` now 404s instead of falling through to the catch-all.** Before that fix an absent chunk was answered `200 text/html` with index.html's body, and the browser parsed `<!doctype html>` as JavaScript and reported `SyntaxError: Unexpected token '<'` with no filename and no request_url — naming neither the asset nor the deploy that dropped it (signal #123576). This changes the sourcemap check's observable: `/dist/main.<hash>.js.map` now returns **404**, where it previously returned `text/html`. Both results prove the same thing — maps are not publicly served, because `deploy:dist` excludes `*.map` — but the passing observable is now a 404, not an HTML body. A `.map` that returns `200 application/json` is still the real leak to watch for.

**Confirm a shipped bundle by executing its behavior, not by grepping the source for the fix.** "The new source contains the fix" and "the deployed bundle no longer has the defect" are different claims, and only the second is what a deploy verifies. For a defect that is a silent no-op rather than a crash — a comparator returning `NaN`, a filter matching nothing — nothing in the logs or the status codes will ever distinguish them. The durable check is to fetch the bundle production actually serves, extract the minified construct from it, and run it against a real production payload: the 2026-07-29 `kickoff_at` gamelog sort was confirmed by pulling `(e,t)=>new Date(t.kickoff_at)-new Date(e.kickoff_at)` out of the served JS and sorting a live 61-row response with it, showing the old comparator yielded `NaN` and the shipped one ordered correctly. Note that `/api/players/:pid/gamelogs` has **no `ORDER BY`** — the server returns rows unordered and the client comparator is the only thing sorting them, which is why this class of defect is display-only yet fully invisible server-side.

**Probing an API route unauthenticated proves NOTHING about whether it deployed: the blanket 401 at `api/index.mjs` answers identically for a route that exists and one that does not.** `curl -X POST https://xo.football/api/leagues/1/pause` returning `401 {"error":"Authentication required"}` reads as "the route is live and gating correctly" — but on 2026-08-13 the negative control `/api/leagues/1/pause-nonexistent` returned the exact same 401, so the check was vacuous. `/api/docs/swagger.json` is auth-gated too, so reading the deployed swagger for a new component fails the same way. Two checks that DO discriminate: read the host's git HEAD plus the pm2 process uptime (`ssh league "export PATH=\$HOME/.nvm/versions/node/<v>/bin:\$PATH && pm2 list"` — pm2 is not on a non-interactive PATH), and exercise a behavior that differs from the default, which for the pause meant opening one on a DORMANT league (league 2, zero teams in the current year) and watching the same anonymous POST flip 400 -> 423 -> 400 across pause and resume, never touching league 1 with its live draft. This is the same shape as the `/dist` catch-all trap above, relocated to the API.

**Executing the deployed behavior is necessary and not sufficient: the INPUT has to be able to tell the old rule from the new one, and real production data usually cannot.** A behavioral check runs the shipped code against real rows, agrees with expectation, and reads as the strongest possible verification — while proving nothing, because the two rules return the same answer on that input. On 2026-08-09 the Amendment XL wildcard-berth deploy was "confirmed" by seeding league 1's real 2025 standings through the deployed `get_playoff_seeding`: the field came out `7, 12, 4, 2` under `head_to_head_berth_count = 2` and `7, 12, 4, 2` under a forced 0, so the run was vacuous. It is not a quirk of one season — the record ladder and the points-for ladder agree in **six of league 1's seven seasons**, because the best records below the byes are usually also the highest scorers, so picking any single real season had about a one-in-seven chance of discriminating. The fix is to run the check as a PAIR against a control with the feature disabled and require the two to DIFFER, which turns "did it work" into a question the run can actually answer; sweeping all seven seasons then found 2021 as the one real discriminator, and a synthetic case built to disagree (best records below the byes are also the worst scorers) pinned the exact predicted split. This is the fixture-with-two-identical-columns trap from the testing section, relocated to a verification oracle over production data, where it is harder to see because nothing about the data looks contrived.

**A component's strings are NOT in `main.js` — routes are code-split, so grepping the main bundle for your change returns a confident zero on a deploy that fully succeeded.** This is the false-negative twin of the trap above, and it fires on the cheapest check anyone reaches for first. On 2026-08-03 a verified-good deploy of the restricted free agency nomination card answered `0` in `main.js` for `until bids close`, `until the window opens` and `Nomination needed`, while the CSS class name `restricted-free-agency-nomination` WAS present — the class reaches main through the style import, the JSX strings live in the lazy route chunk. The three strings were all in `5453.9c112e32.chunk.js` and `8274.c17f0b54.chunk.js`. So grep the whole deployed directory rather than the main bundle, and read the host as the oracle: `ssh league "cd /root/league/dist && grep -l -- '<string>' *.js *.css"`. Sweep `*.css` too — extracted stylesheets are their own chunks, so a style-only change appears in no `.js` file at all. The same run also re-proved the documented "validate a negative pattern first" rule: `rfa-nomination__compact` returned nothing because the real class is `rfa-nomination--compact`, and a double-underscore guess is indistinguishable from a missing deploy.

**Cloudflare sits in front of xo.football, so a probe of an already-published asset URL can be an edge hit rather than origin truth.** `/dist` assets are served `Cache-Control: public, max-age=31536000, immutable`, so once an edge node has a hash-named asset it keeps answering `200` for it long after `deploy:dist` deleted that file from `/root/league/dist`. On 2026-07-30 the superseded `main.f1d67453.js` and its chunks still returned `200 application/javascript` from the edge (`cf-ray` present) while all three were provably `deleted` on the host. So an edge `200` proves nothing about what origin holds, and "the old bundle is still being served" is the expected reading, not a failed deploy. A probe is origin-truthful when its URL is one the edge has never cached a success for — a brand-new content hash, or a path that does not exist — which is why the `9999.deadbeef.chunk.js` and `.map` 404 checks above stay valid. For anything about origin state (did a file actually ship, did it actually get deleted) read the host directly: `ssh league 'ls /root/league/dist'` or `grep` in that directory, and treat that as the oracle over any `curl`.

**A data-view fix is not live for users when the deploy lands — redis keeps serving the pre-fix value to whoever requests the same payload, and the entry can outlive the deploy by DAYS, not hours.** `api/routes/data-views.mjs` caches the whole result set under a hash of the request body (`where`/`columns`/`sort`/`offset`/`prefix_columns`/`row_axes`), with the TTL the columns' `get_cache_info` agree on. **Do not assume 12 hours.** The tiers in `libs-server/data-views/cache-info-utils.mjs` run `ONE_DAY` / `TWO_DAYS` / `ONE_WEEK` / `THIRTY_DAYS`, and the from-plays family routinely lands on `one_week` — a 2026-08-04 scan of production found live keys at ~599,000s remaining out of 604,800. So "the deploy was more than 12 hours ago, the cache must have turned over" is an unsafe inference and has to be replaced by reading the key. The cache is in redis, so `pm2 reload` does not clear it and there is no bypass parameter. This cuts both ways on verification: a probe with a payload nobody has requested before gets a fresh key and honestly executes the deployed emitter, while re-running the exact payload the page sends can return a pre-fix entry and read as a failed deploy. After fixing a column, verify with a deliberately novel payload, then check whether a stale entry still exists for the real one — `ssh league "for k in \$(redis-cli --scan --pattern '/data-views/*'); do redis-cli --raw get \"\$k\" | grep -q <column_name> && echo \"\$k \$(redis-cli ttl \"\$k\")\"; done"` — and delete only the affected keys if any hold the old value. Confirmed 2026-07-31 on the `player_league_extended_salary` extension-ladder fix, where a single key held the column and it was the verification probe's own fresh entry.

For a SAVED view, skip the scan and compute the key directly — it is exact, and TTL alone cannot tell you a key's age without knowing which tier it came from. Feed the stored `table_state` to `get_data_view_hash` over `{where, columns, sort, offset, prefix_columns, row_axes, user_id}` (`user_id` is `null` for anonymous; it does not change the hash for a view with no viewer-scoped column), then `redis-cli exists` / `ttl` that one key. Note the script must live INSIDE `/root/league` for the `#libs-server` import map to resolve, and `get_data_view_hash` is a DEFAULT export. Used 2026-08-04 to clear the from-plays alias-collision deploy: the view's key held no entry at all, so no purge was needed.

The same on-host trick is the way to verify a column's emitted SQL in production without a credential: `/data-views/debug` bypasses redis but requires an admin bearer token (`userId === 1`), whereas importing `get_data_view_results_query` from `#libs-server/get-data-view-results.mjs` and printing `query.toString()` executes the deployed emitter honestly, generates no load, and writes nothing.

**The same redis cache INVERTS the verification advice for a CLIENT-side data-view defect: a novel payload hides the bug, and only the real one reproduces it.** The paragraph above says probe with a payload nobody has requested so the deployed emitter honestly executes; that is correct for a column's SQL and exactly wrong for anything in the SPA's request/response handling. On a cache MISS the request is queued and `handle_non_auth_request` (`api/sockets/data_view.mjs`) collapses a second request from the same client into the first, so only one result comes back; on a cache HIT both answer immediately and overlap. A 2026-07-31 defect that rendered every row of a saved view twice — two requests per direct link (`app/core/data-views/sagas.js`), plus a reducer keying its append decision on `request_id`, which is the VIEW id and not a per-request identity (`app/core/data-view-request/reducer.js`) — reproduced at 2x on a warm cache and was perfectly clean on a cold one, on the same view minutes apart. Verify a client-path fix on the payload the page actually sends, after warming it, and treat "it looked fine on a fresh probe" as no evidence at all.

Two related traps when counting rendered rows in a browser to prove such a thing. **The SPA delivers data-view results over the WEBSOCKET, not `POST /api/data-views/search`** — that route exists and answers correctly, so a network capture filtered to it shows nothing and reads as "no requests fired". Hook `WebSocket.prototype.send` and a `MessageEvent.prototype.data` getter, both of which apply to an already-open socket, rather than patching the `WebSocket` constructor (too late by the time you can evaluate). And **the table renders ~25 rows per scroll and pads the end with empty `.row` elements**, so a raw `querySelectorAll('.row').length` overcounts; key the duplicate check on the player NAME cell, never on the row-number cell, which is generated per rendered row and is unique by construction — that mistake returns a confident zero duplicates over a table that is entirely duplicated.

**When you write a grep to prove a defect is ABSENT, validate the pattern against an occurrence you know exists first.** A negative grep that cannot match is indistinguishable from a clean result, and it reads as proof. Concrete instance from 2026-07-30: `remove:[a-zA-Z_$]{1,4}\.removeTag` was used to assert the fixed bundle no longer contained the broken dispatch map, and it reported `absent` on both the fixed AND the broken chunk — the minified namespace is `h.CB`, whose `.` is not in the character class, so the pattern could never match anything. The check was vacuous in exactly the direction that looks like success. Anchor negative checks on the bare identifier with surrounding context (`grep -ohE '.{28}removeTag.{12}'`) and read the hits, rather than encoding a guess about the minified shape into the pattern.

**Deploy tree topology:** the main host runs a **single** `/root/league` clone. The long-lived PM2 app (`server.mjs`, registered from `/root/league` via the absolute `script` path in `server.pm2.config.js`) and all scheduled scripts (crontab invokes `/root/league/scripts/*.mjs`; SSH-in wrappers `cd /root/league`) share that one tree; `digitalocean-0` mirrors the shape for its import workers. `yarn deploy` = `yarn load:main && yarn load:worker1`, each a `git pull` + `yarn install` + `pm2 reload` on its host. (Historically the main host carried a second `/root/league/source` pm2-deploy tree; in 2026-07 a `pm2 start` from the wrong tree silently served a months-old bundle, so the layout was collapsed to one tree and pm2-deploy was dropped — see `user:text/league/league-server.md` § Deployment Topology.)

**Submodule policy:** Only `private` is initialized on the production servers. The `data` submodule is **dev-only** — it is a large git-lfs reference dataset and git-lfs is not installed on production. Never run plain `git submodule update --init` (without an explicit path) on a production server; always target `private` specifically. The `load:main`, `load:worker1`, and `load:logrotate:main` scripts use `--init private` for this reason.

**A commit that bumps the `data` gitlink breaks `yarn deploy` on every host, and `submodule.data.active=false` does NOT prevent it.** `git pull` defaults to `fetch.recurseSubmodules=on-demand`, which fetches any submodule whose gitlink CHANGED — and under git 2.43 that path does not consult `submodule.<name>.active`, so the hosts (which have `active=false` set and an empty `data/` directory, exactly as the policy above intends) still tried to reach `git@github.com:mistakia/league-data.git` and failed. It presents identically to the `private` case below: the superproject fetch prints a reassuring `d429910ed..ba25f64c9 master -> origin/master`, then `fatal: Could not read from remote repository` / `Errors during submodule fetch: data`, the merge never runs, and the `&&` chain skips `yarn install` and `pm2 reload`. The host simply stays where it was. Hit 2026-08-05 on `1ccd93480`, which refreshed the glossary coverage reports and bumped the gitlink as a side effect; the fix is `git config fetch.recurseSubmodules no` in each host's checkout, now set on `league`, `digitalocean-0` and `base-storage`. Nothing is lost by it — `load:main` and `load:worker1` already run an explicit `git submodule update --init private`, so recursive fetch was never what supplied the one submodule production needs.

**An unpushed `private` commit breaks `yarn deploy` for EVERY session, and the error names neither the cause nor the repo you are working in.** `private` is a nested submodule that `sync-all` does not recurse into, so a commit there reaches origin only if someone pushes it directly. Push the gitlink bump to `origin/master` without pushing `private` and the host's `git pull` aborts with `fatal: remote error: upload-pack: not our ref <sha>` / `Errors during submodule fetch: private` — the superproject fetch SUCCEEDS and prints a reassuring `master -> origin/master`, but the merge never runs, so the host stays on the old commit and the `&&` chain skips `yarn install` and `pm2 reload` entirely. Nothing says "your deploy did not land"; check `ssh league "cd /root/league && git rev-parse --short HEAD"` rather than trusting the deploy output. This is not necessarily your commit — on 2026-08-03 a Sleeper-importer deploy hit it on an unrelated session's vendor-proxy commit, which had been referenced by pushed `master` for hours. Verify `git -C private rev-list --count origin/main..HEAD` is 0 **before** deploying, not after the failure, and when it is not, `git -C private push origin HEAD:main` — the commit is already public by reference, so leaving it unpushed is the broken state, not the safe one.

**Running a script host-side against the live database:** `NODE_ENV=development` does not work — `config/config-development.json` names a LOCAL database (`127.0.0.1` / `league_development`) with a blank password, so `#db` connects nowhere useful. Use the production config (sops-decrypted at load) redirected onto the `base db` league SSH tunnel:

```bash
NODE_ENV=production LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=15432 node scripts/<script>.mjs
```

The tunnel's local port comes from `config.databases.instances.league.tunnel.local_port` in user-base and is what `base db query league` already uses, so a working `base db query league` means the tunnel is up. Never pass a credential on the command line.

**Nothing destructive runs against a target it has not verified — `db/guard-destructive-target.mjs` refuses on the live server's own `current_database()`, never on `NODE_ENV`.** The label is exactly what could not be trusted: until 2026-08-08 the tracked `config-development.json` named `38.242.199.45` / `league_production` / `league_writer`, so `NODE_ENV=development` already pointed at production and the only thing between it and a dropped database was a blank password field. The worst path was never a backup script — `test/global.mjs`'s `mochaGlobalSetup` enumerates `pg_tables` and issues `DROP TABLE ... CASCADE` on every table in `public`, so the suite run under a development config would have dropped production. The guard refuses unless the database is `league_test` / `league_development` / `league_local` / `league_test_<slug>` **and** the host is loopback, and it fails closed on a missing connection, an unreadable server, or an unrecognized name. There is no bypass flag, deliberately: an env escape hatch set once in a shell profile is the same hole in a new shape.

Two consequences worth knowing before you debug a refusal. It is the single chokepoint for the whole suite, so every spec's teardown — including the unqualified `knex('users').del()` ones — runs only after it has passed; a refusal exits **1 in about a second** rather than throwing, because a throw out of `mochaGlobalSetup` leaves the pool holding the event loop and hangs indistinguishably from the four documented suite hangs. And `scripts/dev-smoke.sh` is the one consumer that legitimately points a non-production `NODE_ENV` at production; it is read-only by construction (`default_transaction_read_only=on`), reaches no destructive call site, and now states that targeting as explicit `LEAGUE_DB_DATABASE` / `LEAGUE_DB_USER` overrides rather than inheriting it from a tracked config.

`db/gates/check-destructive-db-guard.mjs` is the static half: no non-production config may name `league_production` or a remote host, and every file in `DESTRUCTIVE_ENTRYPOINTS` must import the guard. It needs no database and no base ref, so it is in CI and in `yarn check:cluster`. Add a file to that list when you add a path that can `DROP`, `TRUNCATE`, or restore over a database — a listed file that no longer exists is itself a finding, so the list cannot go stale through renames.

**Testing:**

Nearly every spec is an integration test against a real Postgres, so the suite needs a database before it will run at all. `compose.test.yaml` ships one:

```bash
yarn test:db:up     # throwaway Postgres 16 on :5433, waits until healthy
yarn test:local     # starts the DB and runs the full suite against it
yarn test:db:down   # stop and remove the container
```

**`yarn test` and `yarn test:db:up` do not point at the same database, so starting the container and then running `yarn test` HANGS INDEFINITELY rather than failing.** `yarn test` blanks `LEAGUE_DB_HOST`/`LEAGUE_DB_PORT`, and `db/index.mjs` only overrides on a truthy value, so the connection falls back to `config-test.json` — **127.0.0.1:5432**. The container publishes on **5433**. On a machine already running something on 5432 the pool neither connects nor errors: mocha sits at ~0% CPU emitting nothing, because `--reporter min` prints only at the end. On 2026-08-05 that read as a slow suite for 53 minutes before the CPU time (2.4s elapsed against 53 min wall) gave it away; `yarn test:local`, which sets port 5433 explicitly, then ran the same suite in 2 minutes. **Use `yarn test:local` — never `yarn test:db:up && yarn test`.** Check `ps -o etime,time` on the mocha pid before assuming a long run is progressing; this presents identically to the malformed-schema hang documented under "Building a candidate schema by hand" below.

**A bare `yarn test` with no database fails with `role "league_test" does not exist`.** That is a missing test DB, NOT a broken or unrunnable suite — start it with `yarn test:db:up` rather than concluding the tests cannot run here. `test/global.mjs` drops all tables and reloads `db/schema.postgres.sql` on every run, so schema edits are exercised by simply running the suite.

**`league-test-pg` is a SHARED container and `test/global.mjs` drops all tables, so two concurrent worktree sessions running `yarn test:local` will stomp each other mid-run.** Every worktree's `compose.test.yaml` names the same `container_name: league-test-pg` on the same `:5433`, so `yarn test:local` from a worktree does not get an isolated database — it gets whichever one is already up. The failure is not a clean error: a sibling's `DROP`/reload lands partway through your run and surfaces as unrelated missing-relation failures. When more than one cluster is live (check `base thread list --running`), start your own instance on a distinct port and point the suite at it rather than sharing:

```bash
docker run -d --name <slug>-pg -e POSTGRES_USER=league_test -e POSTGRES_PASSWORD=league_test \
  -e POSTGRES_DB=league_test -p 54XX:5432 \
  -v "$PWD/db/test/init-roles.sql:/docker-entrypoint-initdb.d/10-init-roles.sql:ro" postgres:16
LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=54XX TZ=America/New_York NODE_ENV=test TEST=all \
  node node_modules/mocha/bin/mocha.js --exit --require test/global.mjs
```

**In a fresh worktree, invoke mocha's real entrypoint — the `node_modules/.bin` shims are broken there.** `.yarnrc.yml` sets `nmMode: hardlinks-global`, so `node_modules/.bin/mocha` is a hardlinked COPY rather than a symlink; its `require('../lib/cli/options')` then resolves against `node_modules/lib`, which does not exist, and both `yarn test` and `npx mocha` die with `Cannot find module '../lib/cli/options'`. The package is fine — `node_modules/mocha/lib/cli/options.js` is present. Run `node node_modules/mocha/bin/mocha.js` instead. Note also that a fresh worktree needs its own install first, and the bare command is blocked fleet-wide: use `sandbox-install yarn install`.

To run one spec against an already-running DB:

```bash
LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 TZ=America/New_York NODE_ENV=test TEST=all \
  npx mocha --exit --reporter min --require test/global.mjs test/trade.spec.mjs
```

- Test patterns: `yarn test --reporter min test/common.*.spec.mjs`
- Grep patterns: `yarn test --reporter min --grep "should login successfully"`

## Architecture Overview

### Frontend (`/app/`)

**React/Redux with Immutable.js state:**

- Domain-driven modules in `/app/core/` (players, leagues, teams, auction, etc.)
- Each module contains: `actions.js`, `reducer.js`, `sagas.js`, `index.js`
- Centralized selectors in `/app/core/selectors.js` using reselect
- Redux-Saga for async operations and WebSocket handling
- Components in `/app/views/components/` with co-located styles (`.styl`)
- React Router v6 with nested league routes: `/leagues/:lid/...`

**A typo'd action-creator name in `mapDispatchToProps` fails SILENTLY, and it has shipped twice.** Every connected component here uses the object form (`const map_dispatch_to_props = { remove: roster_actions.remove_tag }`), which redux passes to `bindActionCreators` — and that function copies only values that are `typeof 'function'`, skipping everything else without warning. So a reference to a creator that does not exist resolves to `undefined`, gets dropped from the props object entirely, and produces **no connect-time warning, no lint error, and no build failure**. The component renders normally; the only symptom arrives when a user fires the handler, as `TypeError: this.props.<name> is not a function`, reported through `window.onerror` with null `filename`/`lineno`/`request_url` because the browser has no usable stack for it.

The recurring cause is the project's camelCase → snake_case action rename passing over a call site: on 2026-07-30 `remove-tag-confirmation/index.js` still referenced `roster_actions.removeTag` (real name `remove_tag`, signal #123469) and `stat-qualifier-filter/index.js` still referenced `stat_actions.updateQualifier` (real name `update_qualifier`, never reported — it needs the qualifier filter opened to fire). Note that `PropTypes.func` does not catch it either; the prop is simply absent, and an absent non-required prop is valid.

When touching a dispatch map, verify each referenced name exists on the actions module rather than trusting it — `grep -nE "^\s+<name>[:(]" app/core/<domain>/actions.js`. A same-named saga or a `SCREAMING_CASE` type constant is not the creator: `removeTag` existed as both a saga export and `REMOVE_TAG`, which is exactly what made the wrong name look plausible. There is currently **no automated guard** for this class — but the reason stated here until 2026-08-07 was wrong in the direction that discourages writing one. A connected component does resolve `@core`/`@components` aliases mocha has no harness for, which blocks a BEHAVIORAL spec; it does not block a SOURCE scan. `test/app.connected-component-prop-contract.spec.mjs` covers the adjacent defect that way — a component destructuring a prop no producer supplies — and needs no harness at all. That gate cannot see THIS one: a typo'd creator leaves the map's KEY declared while only its VALUE is undefined, so the prop reads as provided and `bindActionCreators` drops it at runtime. Resolving each dispatch value against its actions module is the fix, and it is the same parse the existing gate already does.

**But "app/core is not Node-importable" is too broad a reading of that, and it has already discouraged coverage that was free to write.** The blocker is the `@`-prefixed aliases specifically. A module importing only `#`-prefixed specifiers and bare package paths resolves natively, because both this repo and `react-table` declare the matching `imports` field in their `package.json` — **101 of the 231 files under `app/core/` are in that group** and need no harness at all. `app/core/data-views/parse-table-state-from-url.mjs` was believed untestable on this basis and carried zero coverage while holding the entire blast radius of the `splits` -> `row_axes` URL defect; it in fact imports under plain `node` unchanged, and `test/data-views.parse-table-state-from-url.spec.mjs` covers it today with no harness. Before concluding a module in this tree cannot be specced, try importing it — `node -e "import('#app/core/<path>.mjs').then(...)"` costs one command and answers definitively. The remaining 130 files that do reach for `@core`/`@components` are the real harness backlog.

**An Immutable `Record` SILENTLY DROPS any key its declaration does not list, so a new API/database field reaches the client as `undefined` no matter how correctly it is plumbed everywhere else.** `new League({...})` copies only declared keys; `createLeague` additionally destructures an explicit field list, so a field must be added in BOTH places (`app/core/leagues/league.js`) plus the constructor call. Nothing warns: not lint, not the build, not PropTypes, and not the reducer — `create_default_league` can set the value, `getLeague`'s `SELECT *` can return it, and the Record discards it between them, which is exactly what makes the plumbing look correct. On 2026-08-02 the five new `seasons` playoff-format columns were wired through the API, the selector and the shared primitive but never declared on the Record, so `get_playoff_seeding` received `playoff_team_count: undefined` and threw — inside `mapStateToProps`, which renders the standings page and the league-home dashboard blank. Same family as the `mapDispatchToProps` trap above: an absent key, no diagnostic, symptom far from cause. When adding a column the SPA reads, grep `app/core/<domain>/<model>.js` for a sibling field and confirm it appears three times, and prefer degrading in the selector over throwing — a throw in `mapStateToProps` is a blank page, and it is also the state of every league between a frontend deploy and a not-yet-applied migration.

**A league field reaches the SPA on TWO payloads, and wiring only `get-league.mjs` leaves it inert for exactly the people who are logged in.** `GET /leagues/:leagueId` is the obvious wire and it is half of one: the leagues reducer rebuilds the whole record from the `/api/me` payload on `AUTH_FULFILLED` (`state.set(l.uid, createLeague({...l}))`), and `GET_LEAGUE_FULFILLED` does the same from the other route, so whichever response lands last wins and a field present on only one is absent, present, or racy depending on timing. `api/routes/me.mjs` builds its own `db('leagues')` query and inherits nothing from `libs-server/get-league.mjs`. On 2026-08-13 the league-pause fields shipped on `get-league.mjs` alone, so an anonymous visitor saw the pause banner and every member did not — the inverse of the usual auth-shaped bug. Attach on both routes from ONE implementation (`get_pause_state_by_league_id` is the shape: the single-league reader delegates to the batch one) rather than writing the query twice.

This is the same absent-key family as the traps above, with one addition worth internalizing: **no server spec can see it.** The suite drives the API over HTTP and never loads a reducer, so `/me` returning a correct-looking league passes everything; only a browser against a real store shows the field never arriving. The gate that does work is a spec asserting the field on BOTH route payloads (`test/league-pause.spec.mjs` § "pause state on the league wire"), which is cheap and needs no harness — copy it when adding a league field the SPA reads.

**Two more members of that family sit on the REQUEST path, and on 2026-08-12 both shipped in one feature — each independently enough to make a new button do nothing.** They are worth knowing together because the plumbing looks complete at every site a reviewer would grep.

**An api service function's return value is merged FLAT into the fetch init, so a `method` nested one level down is silently dropped and the request degrades to a GET.** `api_request` does `merge(default_options, apiFunction(opts), ...)` and then `fetch(options.url, options)`, so `{ url, opts: { method: 'POST' } }` sends a GET — valid JavaScript, no lint error, a clean build, and the only symptom is a 404 from a route that answers POST. Every other entry in `app/core/api/service.js` spreads `...POST(data)`; copy the sibling rather than hand-writing the options. `test/app.api-service-verb-contract.spec.mjs` is the gate.

**`create_api_actions` and `create_api_action_types` are BOTH required, and exporting only the first leaves every reducer case as `case undefined`.** The creators are what a saga calls; the type constants are what a reducer switches on, and they come from the second helper spread into the domain's `<domain>_actions` object. Export the creators alone and `actions.X_FULFILLED` is `undefined`, so the saga dispatches a real string that matches nothing: the store never updates and a FAILED case can never set its error. With `ignore_error: true` on the saga — the shape used wherever a refusal renders inline — that combination gives the user no feedback whatsoever. `test/app.action-type-registration.spec.mjs` asserts the pairing across every `app/core/**/actions.js`.

The general rule both teach: **an `rg` count proves a token is present, not that it is wired.** Both defects satisfied a plan whose per-step verify was a grep count, and neither is reachable from the server suite, which drives the API over HTTP and never loads a reducer. A client-path change needs a browser pass on `yarn dev:live`, or a source-scan spec of the kind above — and note that both gates here had to discriminate on POSITION rather than presence, since the broken form of the first one contains the word `method` and would pass any grep for it.

**`player_map.get(key, default)` is not a null guard, and it reads exactly like one.** Immutable substitutes `notSetValue` only when the key is ABSENT; a key present with an explicit `null` returns `null`. Several reducer branches write explicit nulls when clearing a field — `DELETE_RESTRICTED_FREE_AGENCY_TAG_FULFILLED` sets `bid` and `restricted_free_agency_conditional_releases` — so `get('restricted_free_agency_conditional_releases', [])` handed the RFA dialog a null it then iterated, crashing the page for a real user on 2026-08-01 (signal #123965). Coalesce with `|| []` / `?? 0` when the field is one a reducer clears; a 2026-08-01 sweep of the other array-defaulted reads (`championship_round`, `deltas`) found no second live instance, but nothing prevents the next one. Clearing a field to the empty shape the API already returns — every players route coalesces this one with `|| []` — is the better half of the fix, since it keeps client state in the shape every read site expects.

**`current_season` is a `Season` INSTANCE, so a module-level constant reached through it is `undefined` — and as a comparator's `notSetValue` that yields `NaN`, which `sort` reads as "equal".** `libs-shared/constants/index.mjs` re-exports both the instance and a pile of bare constants, so `current_season.default_points_added` looks like every other `current_season.*` read and resolves to nothing; the real export is `default_points_added` (`-999`) from `source-constants.mjs:104`. The draft board sorted on it (`app/views/pages/draft/draft.js`) and 274 of the 396 players in the 2026 rookie class have no `pts_added['0']`, so their comparisons returned `NaN`, those rows held their arrival order, and the page shipped looking unsorted with no error anywhere. Same family as the three traps above — an absent key, no diagnostic, symptom far from cause — but the mechanism is namespace confusion rather than a dropped prop, and `NaN` is the worst of the group because a comparator swallows it silently instead of throwing. The sibling auction selector had it right the whole time (`app/core/selectors.js:47,253`). Before reaching for a constant on `current_season`, confirm it is a `Season` property (`libs-shared/season.mjs`) and not a bare export — and treat any `notSetValue` feeding arithmetic as worth checking at runtime, since a wrong one cannot fail loudly.

**The `teams` store is keyed by YEAR and nothing loads a year but the app's own, so a page rendering any other season shows blank teams — and a page that dispatches none of four specific actions shows blank teams in EVERY season, including the current one.** `get_team_by_id_for_year` falls back to `new Team()` (`app/core/selectors.js:84`), which renders as empty rather than throwing, so this is the same absent-key/no-diagnostic family as the traps above with an even quieter symptom: a `TeamName` that is simply not there. Two independent halves, and the second is the one that surprises. `load_teams` (`app/core/teams/sagas.js`) takes `year` from `get_app` and ignores its caller, so it can only ever populate the app year — but it is also only ever _reached_ from `LOAD_TRANSACTIONS`, `LOAD_WAIVERS`, `LOAD_MATCHUPS`, `LOAD_ROSTERS`, `LOAD_TEAMS`, `SELECT_YEAR` and `AUTH_FULFILLED`. A new page that dispatches none of them gets no teams at all: the restricted free agency history shipped on 2026-08-02 with every team blank in all six seasons, and the current-season case looked identical to the historical one, which is what made "the store has no 2024 teams" read as the whole story. `load_teams_for_year` now takes an explicit year for this; watch your page's load action from `team_sagas` rather than assuming another page's fetch has warmed the store, and note the request-history key is `GET_TEAMS_${leagueId}_${year}` while `initTeams` fetches with no year at all, so the current season's key is literally `..._undefined`. The same hole exists for players — a historical roster names players no league page has ever loaded — with `load_missing_roster_players` as the pattern to copy.

**`PlayerName` renders a FRAGMENT of two siblings, not one element, so its container's `display` decides whether a player's own status/tag chip stays attached to it.** The second element (`.player__name-label`) carries the PSP/cutlist/status/`PlayerTag` chips. In a block parent it starts its own line — a tagged player put his PUP or Q chip on a row beneath the position badge. In a flex row it is a separate flex item that can wrap away from the name it belongs to, so a list of players needs each one in its own wrapper, not the bare component. `.player__name` also carries `flex 1`, which makes it expand to fill any flex parent unless overridden. None of this is visible in the JSX at the call site, which reads as a single component. When laying out more than one `PlayerName`, or one beside other content, wrap each in its own flex element and override `flex` on both children.

**Every floating surface takes its z-index from the named scale in `app/styles/variables.styl` — a bare number is the bug, and `yarn check:z-index-scale` fails CI on one.** MUI stacks dialogs, popovers, menus and autocomplete popups all on ONE layer (1300) and breaks the ties by DOM order, which works only as long as no app surface is raised above 1300. This app hand-rolls its nav drawer, its context menu and several dropdowns, so their values shared that space with MUI's under no declared ordering, and every collision was historically fixed by nudging one surface upward — each nudge silently jumping over every MUI layer in between. `6d8490f78` raised the selected-player drawer to 1400 to clear the nav drawer at 1300, which put it above every `Dialog`: from then on the place-bid, sign-free-agent, waiver and poach confirmations opened BEHIND the panel that launched them. Nothing failed — the dialog rendered, took focus and worked, it was just not visible, which is the same absent-symptom family as the traps above.

Two rules the scale encodes and a literal cannot. **A surface that is always opened FROM another surface belongs above everything that can open it** — `$z_popper` sits above `$z_dialog` rather than beside it, because ten confirmation dialogs here contain a `Select` or an `Autocomplete` and a naive "dialogs on top" ordering hides their own dropdowns. And **a value below 100 is local, not global**: it orders siblings inside one component, so the guard ignores it. The scale is injected into every `.styl` by stylus-loader (`webpack/webpack.config.base.mjs` `stylusOptions.import`), so no import is needed anywhere. When a new surface does not fit an existing layer, add a layer to the scale rather than picking a number — the point is that the whole ordering is reviewable in one file.

**The dangerous case is a MUI overlay that carries no literal at all**, since a value living in `theme.zIndex.*` is invisible to any sweep of this repo. `Snackbar` defaults to 1400: it ties the selected-player drawer and loses to every dialog, and it survived the first pass of the guard precisely because there was no number to find. `general.styl` now pins each such component onto the scale, and the guard asserts the pin exists rather than trusting the list — extend `MUI_OVERLAYS_REQUIRING_A_PIN` when the app starts using another one. The remaining blind spot is a stacking-context trap, which is static-undetectable: an ancestor with `transform`, `filter`, `opacity < 1`, `will-change` or `contain` makes a descendant's z-index local regardless of which layer it names. A 2026-08-04 sweep found none — every overlay here portals to `document.body` or is `position: absolute` — so a new one would be a new trap.

**A new route needs an entry in `libs-shared/page-routes.mjs` or it ships `noindex` with the home page's copy.** `app/index.html` carries double-brace tokens that the API's SPA fallback (`libs-server/middleware/render-html.mjs`) fills per request from that table — a crawler never runs the app, so the served HTML is the only head it reads, and a path the table does not know is deliberately treated as a typo rather than given the site defaults under its own canonical. The same table drives the client-side `@components/page-head` effect, which is what keeps the browser tab correct after an in-app navigation, so the two cannot drift. Three things that are easy to get wrong: the tokens must NOT be filled at build time (one bundle serves every route); do not write a brace token into a comment in `app/index.html`, because the dev build keeps comments and it then reads as an unfilled placeholder; and a per-route title sourced from the database must be safe to show an anonymous visitor — league names are, saved data-view names are not, since `user_data_views` has no public flag.

**A full page load and an in-app navigation to the SAME URL do not produce the same app state, so verifying a route by typing its address cannot see this whole class of defect.** `app/views/components/app/app.js` reads the route's league id in a `useEffect` whose dependency list is `[init]` — it runs once on mount, and until 2026-08-14 nothing else could move `app.leagueId`. So `/leagues/1` was correct when loaded directly and rendered the DEFAULT league under that URL when reached by clicking a link: the landing page's only call to action, with a sidebar still reading "League not connected" and no league links at all. Every server-side oracle was green throughout, because the server was never asked. `SELECT_LEAGUE` (`app/core/app/actions.js`, with a `load_league` watcher in `app/core/leagues/sagas.js`) now carries the matched route's league, so the two paths agree.

Two things generalize past the one fix. **Any state derived from the route at mount is a candidate** — a mount-only effect is the shape to grep for, and `app.year`/`app.teamId` are reached the same way — so when you add route-derived state, drive it from the route rather than from `INIT_APP`. And **a browser check has to CLICK the path a user takes**: the two anonymous defects fixed the week before (standings, data views) were both found and verified by direct `page.goto`, which is exactly the method that reads this one as working. Drive the real link with `page.click` and compare against a `goto` of the same URL; a disagreement between them IS the bug.

**`useNavigate()` returns a NEW function identity whenever the matched route changes** — its own deps include the resolved pathname and the match array — so an effect that lists `navigate` in its dependency array re-runs on every in-page navigation, not just on mount. On 2026-08-14 the trade-review page's list-load effect listed it, so toggling a row (which navigates between the two sibling routes `/trade-review` and `/trade-review/:trade_uid`) re-fired `load_trade_review` and dropped the page back onto its full-width spinner every time. Keep `navigate` out of a data-fetch effect's deps: an absolute redirect like `navigate('/', { replace: true })` does not need a fresh identity, so split it into its own effect keyed on `[lid, navigate]` and key the fetch on `[lid]` alone.

### Backend (`/api/`)

**Express.js with PostgreSQL:**

- Modular routing: `/api/routes/` with domain-specific files
- Route index exports all route modules from `/api/routes/index.mjs`
- JWT authentication with `express-jwt`
- WebSocket support via `/api/sockets/` (auction, scoreboard, data_view, external-league-import)
- Node-cache for performance optimization (10-min TTL)
- Database access via Knex.js ORM at `req.app.locals.db`

**Twenty routers mount BEFORE the blanket auth guard, so each of their routes must self-enforce.** `api/index.mjs` mounts `docs`, `status`, `errors`, `stats`, `players`, `projections`, `plays`, `schedule`, `sources`, `auth`, `leagues`, `teams`, `markets`, `percentiles`, `seasonlogs`, `cache`, `data-views`, `u`, `wagers` and `selection-combinations` above the `if (!req.auth) return 401` catch-all, which therefore covers only what mounts after it (`scoreboard`, `me`, `settings`). Most of those routers are legitimately public NFL data, but any route in one of them that reads USER-owned rows needs its own `req.auth` check, and the guard's presence in the file makes it easy to assume otherwise. `GET /api/data-views` had neither an auth check nor a mandatory filter for that reason and returned every saved view on the platform to an anonymous caller until 2026-07-31 (`216c1a5d0`). Its sibling `GET /api/plays/views` still has the identical shape against `user_plays_views`, latent only because that table is empty. When adding a route to any pre-guard router, check whether it touches user-owned data and enforce ownership in the handler.

**`GET /api/wagers/:user_id` was the second live instance, and its shape is worth recognising because the ownership check WAS there — it just could not fire.** The handler computed `public_only = req.auth && req.auth.userId && req.auth.userId !== user_id`, which is correct for an authenticated caller and silently false for an anonymous one, so a caller with no token was treated as the OWNER and received private wagers. Reading that line in isolation it looks like a privacy filter; the defect is only visible once you know the router mounts pre-guard and `req.auth` is therefore routinely absent. Measured before the 2026-08-06 fix (`2f0ca9a0f`): user 1 holds 64,513 wagers, none of them public, every one reachable unauthenticated up to the 1000-row default limit. **A predicate gated on `req.auth` being PRESENT is inverted on a pre-guard router** — anonymous is the untrusted case, not the exempt one, so write the condition so that absent auth falls into the restricted branch (`!req.auth || req.auth.userId !== user_id`).

### Database

**PostgreSQL with comprehensive schema:**

- 80+ tables for fantasy football operations (leagues, rosters, trades, waivers)

**`db/` is split by LIFECYCLE, not by subject matter — read `db/README.md` before adding a file to it.** Everything under `db/` is "about the schema", so subject matter separates nothing; what separates them is whether a file is ever edited again and whether it carries a verdict.

| Directory  | Rule                                                                                  |
| ---------- | ------------------------------------------------------------------------------------- |
| `adhoc/`   | Dated `YYYY-MM-DD-<slug>`, written once, run once, **never edited**. History only.    |
| `gates/`   | Pass/fail verdict AND an entry in the `check:cluster` manifest. State file beside it. |
| `tools/`   | Durable, and **must not** carry a verdict wired to a run.                             |
| `checks/`  | Registered data checks. Carry a verdict that **must not** fail their own run.         |
| `archive/` | Tooling whose cluster closed. Kept for reference, not run.                            |

**A standing DATA condition is a registered check, not a cluster gate — `db/checks/registry.mjs` is where it goes, and `yarn check:cluster` is where it must not.** The two carry opposite dispositions and that is the whole reason they are separate: a cluster gate makes a FINDING fail the run, which is right for "did this push break something", while a data check's exit code carries DETECTOR HEALTH only — a finding rides a self-closing signal and a red run means the check could not answer. Putting a data check in `gates/` is what makes a standing condition nobody introduced defer **every** session's push to `mistakia/league`, which `db/gates/check-conflated-player-rows.mjs` does today. The line: **a gate is triggered by a CODE change; a check watches a STANDING condition.** A conflated player row can arise with no code change at all.

Adding one is a row in `db/checks/registry.mjs` carrying its query, grain, optional precondition, threshold, calibration prose and repair command; `scripts/run-data-checks.mjs` runs the whole registry weekly, `libs-server/data-check.mjs` grades it, and `db/checks/parked.json` holds every suppressed finding under a required `adjudicated` or `baselined` disposition. Findings travel on ONE convention — a `log_error` signal with a pinned `fingerprint_override` of `data-check-findings-<check_id>`, `data-check-parked-stale-<check_id>` or `data-check-ungradeable-<check_id>`, each paired with a resolve on the clean branch — so a check removed from the registry must have all three keys closed in the same change or any open row becomes permanently un-closeable. They are three keys rather than one because the conditions can be true independently, and dedup collapses a second emit under an already-open row into a no-op. The design rules are canonical in `user:guideline/software/design-data-checks.md`; the registry's header carries the mechanical how-to-add.

If you would ever edit it, it is not an adhoc migration. If it answers pass/fail but no runner invokes it, it is a gate nobody runs — the failure this repo keeps repeating. If it exits non-zero by design on standing debt, it is a tool and wiring it into CI produces a permanently red master, which defers **every** session's push to `mistakia/league`. Before relocating anything under `db/`, check the path depth: most of this tooling resolves the repo root as `path.join(__dirname, '..', '..')` and then filters scan directories through `fs.existsSync`, so a move to a different depth silently empties the scan set and reports zero findings at exit 0. The five directories are deliberately at the same depth.

**Schema Change Workflow:**

1. Author the SQL in `db/adhoc/YYYY-MM-DD-<slug>.sql`, including a `-- STATUS: PENDING` line in the header
2. Run it against production with `yarn db:exec db/adhoc/<file>.sql` (wraps the file in a single transaction with `ON_ERROR_STOP=1`)
3. Export the updated schema using `yarn export:schema`
4. Commit both the adhoc file (audit trail, banner now rewritten to APPLIED) and the schema diff

**Renaming a VIEW column needs `ALTER VIEW ... RENAME COLUMN`; `CREATE OR REPLACE VIEW` cannot do it.** Replacing a view may add trailing columns or change their expressions, but it refuses to change an existing output column's NAME — `ERROR: cannot change name of view column "<old>" to "<new>"`, with a HINT naming the right verb. Plans reach for `CREATE OR REPLACE VIEW` because it is the familiar shape and because it genuinely avoids the drop-and-recreate dependency problem; it just does not perform a rename. Prefer `ALTER VIEW` on its own merits anyway: it moves the one alias without restating the whole `SELECT`, so there is no restated body that can silently drift from what is live. Caught 2026-08-04 on `view_trade_asset_flow.market_value_at_trade`, where the task entity had specified the unusable form; `db:exec` runs the file in one transaction so the failed apply rolled back cleanly and production never saw a partial change. That column name is the pre-rename one and no longer exists — the rename landed in `0d2af7fd4` and the view now carries `keeptradecut_value_at_trade`.

**Do not wrap an adhoc file in `BEGIN`/`COMMIT`** — `db-exec.sh` already runs it as a single transaction, and a nested `BEGIN` only emits `WARNING: there is already a transaction in progress`. Some older files in `db/adhoc/` carry the redundant pair; they are not the pattern to copy. 5. The exported schema file (`db/schema.postgres.sql`) is the source of truth; `db/adhoc/` is the append-only history of how it got there

**The status banner is machine-owned — `db:exec` refuses a `db/adhoc` file without one.** It rewrites `-- STATUS: PENDING` to `-- STATUS: APPLIED <date> against league_production` in place on success, so there is no window where the apply has happened and the file still reads pending, and it REFUSES a file already marked APPLIED (`--reapply` overrides). That refusal is the real point: three headers advertised applied work as pending until 2026-07-27, one of them a non-idempotent two-`DROP COLUMN` file that a second run would have failed or half-applied. Commit the rewritten header in the same commit as the apply; the script prints the command.

**Dry-run a data migration before applying it: copy the file, replace the tail with a deliberate `RAISE EXCEPTION`, and run the copy through `db:exec`.** The wrapper is `--single-transaction` with `ON_ERROR_STOP=1`, so a forced abort at the end rolls the whole thing back while still executing every statement against production data — which is the only way to find a constraint violation that no amount of reading the SQL surfaces. On 2026-08-04 a 189-row duplicate-person merge dry-ran twice before it was correct: first it violated `player_nfl_player_id_unique`, because copying an identifier onto the surviving row while the donor row still holds it puts two rows at the same value for the duration of the statement (fix: snapshot the donors, delete them, then fill from the snapshot); then a pre-delete guard caught a table missing from the re-point list. Both would have aborted the real apply mid-file. Two things to get right: strip your own `BEGIN`/`COMMIT` (the wrapper supplies the transaction, and an explicit `COMMIT` inside it defeats the rollback), and keep the dry-run copy OUTSIDE `db/adhoc/`. That last point used to read "give the copy a `-- STATUS:` banner that is not `PENDING`", which cannot be done: `db-exec.sh` applies the banner rule only to files under `db/adhoc/`, and there it accepts exactly two values — it refuses `APPLIED` outright and refuses anything that is not `PENDING` with "carries no machine-readable status banner". So a dry-run copy in that directory either cannot run or is indistinguishable from the real file. Put it under `tmp/` and pass the absolute path; the banner check does not apply and the unconditional `RAISE EXCEPTION` is what makes it unmistakable. Cheap enough to be the default for anything that deletes rows.

**The server sets `statement_timeout` to 40s, so a large `ALTER TABLE` is CANCELLED partway and the rehearsal cannot warn you.** This is the one failure mode a scratch-database rehearsal is structurally blind to: the scratch database carries the SCHEMA and none of the rows, so every rehearsed DDL is instant by construction and exits 0 no matter how long the real one would take. On 2026-08-08 the `nfl_plays.updated` retype — 1,483,118 rows across 27 partitions at 8,489 MB — died at 42s wall on `canceling statement due to statement timeout`. It rolled back whole (`db-exec.sh` is `--single-transaction` with `ON_ERROR_STOP=1`), so the failure is clean rather than partial, but it lands in the middle of an apply window with the companion file already applied.

The 40s is `statement_timeout` in the server's `postgresql.conf` — `boot_val 0`, `reset_val 40000`, `source configuration file`. There is **no role-level or database-level override** (`pg_db_role_setting` carries only `search_path` and `log_min_duration_statement` for `league_writer`) and `db-exec.sh` passes no `PGOPTIONS`, so nothing outside the file can raise it. Put the override in the DDL file itself, where it is transaction-local and reverts when the transaction ends:

```sql
SET lock_timeout = '30s';
SET statement_timeout = 0;
```

**Set `lock_timeout` in the same breath, and do not leave it at 0.** Once the statement is QUEUED for `ACCESS EXCLUSIVE` it blocks every new reader behind it, so an unbounded wait to ACQUIRE is strictly worse than failing — 30s to acquire, unlimited to execute, which is the asymmetry you want. Estimate whether you need this from the table's real size (`pg_total_relation_size`) rather than from the rehearsal's timing, and treat any rewrite of a table above roughly a gigabyte as needing it.

**A `VALUES` list restoring a wide table types every column from the FIRST row, so a backup replay of a sparse table fails on a column that is `NULL` everywhere.** Postgres infers `text` for an all-`NULL` column and then rejects it against the real type — `column "jnum" is of type smallint but expression is of type text` — naming one column when the problem is the whole list. Cast every value in the first row (`CAST(NULL AS int2)`, `CAST(2001093004 AS int4)`, ...) and the remaining rows coerce to it. Hit 2026-08-04 replaying 256 `player_gamelogs` rows across 106 columns, 57 of them null on every row; the rollback-only dry run caught it before the real apply.

**The cluster gates run as ONE command — `yarn check:cluster`.** Every durable gate below is in its manifest (`scripts/check-cluster-gates.mjs`), ordered cheapest-first, and a gate whose prerequisite is missing SKIPS LOUDLY naming what it needs rather than being silently absent from the run. Add `--base <pre-cluster-ref>` to include the gates that diff against a base revision; `--list` prints the manifest and each gate's oracle without running anything. This exists because the recurring failure here was never a gate returning the wrong answer — it was a gate nobody ran, and the invocation list living only in this file is what made skipping one invisible. The 18 renamed param keys that dropped filters on 45 saved views are the standing example, and this file's own verdict on them is that what was missing was running the check at all.

It fails on more than findings. **A gate that declares an always-on negative control must print one, and a control reporting STAYED GREEN fails the whole run even when that gate exited 0** — which turns the "never accept a green you have not shown can go red" rule from a convention each gate keeps privately into something checked from outside. The runner's own verdict rule is driven by synthetic controls on every invocation, for the same reason.

**Four things it cannot decide for you, and they are the whole judgment half of a cluster.**

- **A skipped gate is not a passed gate.** The run says so in its summary; believing it is on you. Same for the count it prints of gates that carry no negative control — 8 of 13 today — whose greens are unproven by construction.
- **Whether a finding is a defect or accurate history.** A doc site describing what a rename DID is correct; only live instruction counts. That call needs someone who knows what the cluster did, which is the deciding reason none of this is in CI.
- **Which findings to read first.** `check-data-view-sql-validity` ranks by reachability tier, not by how broken the SQL looks; ranking by severity once put a dormant seasonal path above a route that had been 500ing for a year.
- **Whether the green is yours.** Several gates read the WORKING TREE — its schema file, its prose, its column definitions — so a sibling mid-cluster turns them red on findings belonging to nobody in your push. When the shared tree is dirty, run from a clean worktree at your HEAD.

And it stops at the repo boundary: a cluster is not done when its gates are green, it is done when the sweep is DEPLOYED. Nothing here can see what production is executing.

**Run `node db/gates/check-schema-conformance-ratchet.mjs` before pushing any commit that adds a table or column — it is CI-only, so a fully green local suite tells you nothing about it.** The ratchet is a separate CI step and nothing in `yarn test`, `yarn lint`, or the SQL-validity gate exercises it, so the first signal is a red master. On 2026-08-02 a new `scoring_format_projection_calibration` table shipped with columns `n`, `r`, `slope` and `position` — three bare names of five characters or fewer plus a reserved word — against a local suite that was green at 2600 passing. The cost is not yours alone: a red master makes the sync-all pre-push guard defer **every** push to `mistakia/league`, so unrelated sessions pile up behind a failure invisible in their diffs, and clearing it needs `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh`. The check takes about a second. When it fires on a table you just added, that is new debt and the fix is renaming the columns — **never `--rebaseline`**, which is reserved for a deliberate audit widening. Full-word snake_case; no bare name of five characters or fewer (an underscore is what conforms `slope` -> `fit_slope`); no reserved words (`position`, `timestamp`, `order`, `desc`, ...). Post a bulletin naming the cause if you do turn master red, so siblings do not debug your gate.

**A conformance COUNT is a reading off an INSTRUMENT that is versioned in this repo, so a number measured on a branch cut before an audit change is taken against a different ruler — and it looks exactly like stale arithmetic in the plan.** `db/tools/audit-schema-conformance.mjs` gains rules over time; a worktree branched before one of those commits runs the narrower audit and reports a smaller total, with nothing in the output naming which instrument produced it. On 2026-08-08 the footballoutsiders retirement measured 25 total violations against a plan that said 45, and the session wrote a `[correction]` onto the task entity declaring the plan's arithmetic stale. The plan was right: the branch was cut at `41dd78ffc`, which predates `cc50e2a49` (widened the audit past its three blind spots) and `e15841c77` (rebaselined for it), so `external_id` and `timestamp_type` did not yet exist as rules. After merging master the numbers landed exactly as planned — 45 before, 21 after, 24 cleared. Worse than the wrong number was the near-miss: `--rebaseline` run on the narrow instrument had written a 1-entry baseline, which merged would have silently dropped 20 real violations. **Merge master and re-measure before citing any conformance number, and never rebaseline from a branch you have not just merged** — the same "verify before you act on any specific identifier here" rule this file opens with, applied to the measuring device rather than to the measurement.

**The ruler moved again on 2026-08-08: `60495ef2d` took the audit from 16 to 24, and every one of the 8 is `external_id`.** It closed the third and worst blind spot in `conforms_external` — a bare two-token `/^[a-z0-9]+_[a-z0-9]+_id$/` that applied no vocabulary check to EITHER token, so any `qualifier_noun_id` conformed by construction. That one is categorically worse than the two `cc50e2a49` repaired: those made a column INVISIBLE, so the count was an acknowledged floor, while this one reported non-conforming columns as CLEAN — five of the eight are `gsis_it_id`, a name the audit's own `known_bad_external_ids` roster already listed and the permissive shape was overriding. The entity-type vocabulary is now DERIVED from the schema's own table-name tokens rather than hand-listed as `player|team|game|league|site`, so a new entity type conforms on arrival. **Decompose a widening's delta by TABLE as well as by rule when you report it** — 8 findings by rule is 7 tables by table (`nfl_games` carries two), and this program has already shipped a by-rule total into three artifacts as if it were a by-table one. `test/db.schema-conformance-external-id.spec.mjs` is the regression test for the class, and it is the shape to copy for this tool: it spawns the real audit against a synthetic schema through the new `--schema-file` flag, so it pins reported OUTPUT rather than an internal shape a refactor could move. Note that flag does NOT change the `LEAGUE_SCHEMA_FILE` caveat stated further up — the tool still ignores the environment variable, and the ratchet gate still spawns the audit without the flag, so a candidate schema must still be copied over the tracked path.

**A writer that names a column which does not exist passes the whole suite, because `test/global.mjs` loads the SAME `db/schema.postgres.sql` that is missing it.** The two halves of the check fail together, so a green suite is not evidence the writer can execute against any database — and the number is reassuringly large while it happens. On 2026-08-04 `dd48ce077` shipped `generate-league-format-player-seasonlogs.mjs` writing `points_added_net_rank`, `points_added_net_position_rank`, `points_added_net_per_game_rank`, `points_added_net_per_game_position_rank` and `points_added_net_cap_dollars`; none of the five existed, 2947 tests passed, and the commit was pushed and deployed. It would have thrown `column ... does not exist` on the generator's next run and taken the stats pipeline with it (`libs-server/stats-pipeline.mjs`). The gap is that no spec runs that generator, so nothing ever executed the insert. **When a commit adds a column to an insert object, check the column exists in `db/schema.postgres.sql` — a `git show HEAD:db/schema.postgres.sql | grep` costs one command** — and prefer running the generator itself over trusting the suite — where it has a `--dry` flag, which builds the full insert and logs samples without writing. **Check for the flag rather than assuming it: only 98 of the 240 scripts have one, and it is absent from several of the highest-risk generators.** A 2026-08-05 validation pass reached for it on `generate-rosters`, `generate-league-formats`, `calculate-league-careerlogs`, `process-projections`, `project-lineups`, `import-rotowire-practice-report` and `generate-nfl-team-seasonlogs` and **none of the seven had it**, so the intended validation could not run as written. The fallback that needs no execution and no writes: extract the insert payload's keys and check each against `information_schema` for the target table, plus the `onConflict` target and the `merge()` list. That is what found three nonexistent columns in `generate-player-snaps` (2026-08-05, `6ba0d1d02`). Note this is the exact inverse of the deploy-lag rule further up: there, committed code was ahead of a deployed schema; here, committed code was ahead of the schema file that both production AND the suite derive from, which is why neither could see it.

**`db:exec`'s `CONCURRENTLY` guard greps the whole FILE, so the word in a comment refuses a file that must stay transactional — and the suggested fix is dangerous there.** The guard exists because `CREATE/DROP INDEX CONCURRENTLY` cannot run inside a transaction block, and it prints `Re-run with --no-transaction`. But it cannot tell a statement from prose: on 2026-08-03 a file whose header said "no `CONCURRENTLY` anywhere, because TRUNCATE empties both tables first" was refused, and that file was a `TRUNCATE` plus two `ADD COLUMN`s plus an index swap — precisely the shape that must be atomic. Taking the suggestion would have run a destructive statement with no rollback. Reword the comment to avoid the literal token (say "no non-blocking index build is needed here") rather than passing `--no-transaction`, and state in the header that the transaction is required. Reach for `--no-transaction` only when a real `CONCURRENTLY` statement is present and every statement is independently re-runnable.

**Before reaching for `PUSH_TO_RED_MAIN`, check whether the red is a FLAKE and just re-run the job — that clears the block for everyone instead of pushing past it.** `PUSH_TO_RED_MAIN` is the remedy when master is genuinely broken and your commit is the repair; it is the wrong tool when CI failed on a known-flaky shape, because it leaves master red and every other session still deferred. The tell that you are looking at a flake is in this file already: a duplicate-key violation (`rosters_players_pkey`, `transactions_pkey`) is the documented downstream symptom of an EARLIER test exceeding its budget, whose abandoned queries then collide with the next test's fixture reset — so the named spec is the victim, not the cause. Confirm by running the same spec locally against the same tree; if it passes, `gh run rerun <run-id> --failed` is the whole fix. Hit 2026-08-07, where sync-all was logging `red_main_skip league` and holding six commits from three sessions behind one flaked `test/players.routes.spec.mjs` case at `7345a655a`; the re-run went green and the queue drained on the next cycle. Read the sync telemetry to find out you are in this state at all — `telemetry/sync/<date>.jsonl` in user-base records `red_main_skip <repo>`, and nothing else announces that your push is being deferred rather than simply not having happened yet.

**A green master is NOT evidence your commit was tested, and a missing `Test` run is NOT flakiness — GitHub scans the ENTIRE commit message for `[skip ci]`, body included, so you cannot WRITE ABOUT the token without triggering it.** This was recorded here as an unexplained intermittency until 2026-08-08, when three consecutive misses resolved to one cause with no residue. `Test` is a bare `on: push`, the workflow is `active`, and every commit in that window whose message contains the literal token anywhere got no run while every commit without it got one — a perfect correlation across eight shas.

Two ways the token lands in a message nobody meant to skip.

- **A merge commit inherits it from the branch.** `git merge` writes a `merge.log` body listing the merged commits' subjects, so a single branch commit ending in `[skip ci]` propagates the skip to the merge — and the merge is the commit that lands the whole cluster. `3501e4f27` merged the timestamptz retype (16 production column retypes, ~50 consumer files) and was skipped this way, by the subject of `4ed9f92de` quoted in its own body. **Check `git log -1 --format=%B` of the merge before pushing it**, not the subject line.
- **Explaining the token invokes it.** Twice, a commit written specifically to RESTORE a suppressed run defeated itself by naming `[skip ci]` in its prose. `41dd78ffc` was an empty commit whose body reads "The preceding commit carried [skip ci]"; `10407feaf` reads "this commit carries no [skip ci]". Both were skipped. Describe the mechanism without the literal — "carried a skip token" — or the remedy commit becomes another instance of the disease.

The cost is quiet: the retype cluster reached production with nothing having run the suite in CI, and the only evidence it worked was a local run. Two standing consequences. Reading the branch's latest CI status answers a question about someone else's commit, so **query the runs API for your own head sha** (`gh api "repos/mistakia/league/actions/runs?head_sha=<sha>"`) when it matters that your change was exercised; a lone run with event `dynamic` is CodeQL, and CodeQL running is not a proxy for `Test`. **Pass the FULL 40-character sha** — `head_sha` is matched exactly, so an abbreviated one returns an empty `workflow_runs` array at exit 0, which is indistinguishable from the suppressed-run state this very check exists to detect (`git rev-parse <short>` first; confirmed 2026-08-14, where two commits that each had a green `Test` read as having no run at all). And an **empty commit is a poor CI trigger** — it changes no paths and, as above, tempts you into writing the very token you are undoing; prefer sequencing the real work so the head commit carries content.

**Applying DDL to production opens a window in which ANY other session's `yarn export:schema` can commit your change for you — the one-commit rule is not yours alone to keep.** The recipe says apply, export, and sweep land in one commit precisely so master never has a schema declaring a column its code cannot name. But `yarn export:schema` dumps the whole live database, so between your apply and your commit, an unrelated cluster that exports for its own reasons will pick your column up and ship it without your sweep. That is not hypothetical: on 2026-07-29 the `nfl_games."timestamp"` -> `kickoff_at` retype was applied and its sweep still in progress when `872cfb8f` (an unrelated `projections` rename) regenerated the schema, and master went red on six tests — two in `historical-injury-index-sql.mjs`, four inserting the old column in `test/teams.reserve.spec.mjs`. The retyping session had done nothing wrong and had not yet committed anything. Two consequences worth planning around: keep the apply-to-commit window as short as you can and do not start a long consumer sweep with the DDL already applied if you can sequence it otherwise; and when it does happen, recognise the shape immediately — a schema/code disagreement on master that you did not commit — because the sync-all pre-push guard then refuses every push to the repo INCLUDING the commit that repairs it, and clearing it needs `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh` (never a bare `=1`, never a direct push). The corollary for the exporting session: `yarn export:schema` is never a private act in a shared tree, so read the diff for columns that are not yours before committing it — though note the exporting session cannot solve this for you, since an export that refused to carry foreign DDL would produce a schema file disagreeing with the live database, a worse failure than the one it prevents. The window closes only at the applying end. **Which DDL opens it: renames and drops, not additive changes** — with one exception that is not about the DDL at all. A new table or column makes the schema a superset of what the code needs, so nothing fails to resolve; a rename removes something committed code still names. The exception is an additive column that widens a table's GRAIN, where the damage is done by the BACKFILL rather than by the `ALTER`: adding `pff_player_seasonlogs.season_type` on 2026-08-14 was harmless until 12,616 scoped rows were written, at which point the deployed emitter's `left join ... on pid and season_year` — correct against the old grain, and unchanged — began matching three rows per player and every `player_pff_*` data-view column fanned out 3x in production. The `ALTER` and the deploy were minutes apart; the fan-out window was the twenty minutes between the backfill and the deploy, and no gate can see it because the committed code is right and the deployed code is right for the schema it was written against. **Sequence a grain-widening backfill immediately before its deploy, never as a separate step afterwards**, and check the redis cache for entries written inside the window (`/data-views/*` payloads whose pid list has duplicates). The same 2026-07-29 window fired three times in one afternoon and only once did damage — the `kickoff_at` retype above — while the same mechanism carried two other clusters' new tables to master harmlessly. Left unrepaired it is not merely a red CI: production ran the conformed schema against stale code for an hour, and the two live GET routes naming the dropped column (`api/routes/players.mjs`, `api/routes/stats.mjs`) began returning 500s once real traffic reached them. This is strictly stronger than the deploy rule further down — a deploy can lag safely, a commit cannot.

**The way to sequence it otherwise: build a CANDIDATE SCHEMA and sweep against that, so production is untouched until everything is green.** Load the committed schema into a scratch database on the `:5433` container, apply your `db/adhoc` files to it, then dump it through `scripts/export-schema.sh`'s own flags and `awk` post-processing (see the "Building a candidate schema by hand" note below — a raw `pg_dump` is not a drop-in substitute and fails as a mocha hang). Copy that over `db/schema.postgres.sql` in a throwaway worktree and run the whole cluster there: consumer sweep, full suite, `check-data-view-sql-validity`, the ratchet, eslint, prettier, and golden regeneration. Only then apply to production, `yarn export:schema`, commit, and deploy — a window of minutes with no debugging inside it, instead of hours. The 2026-08-05 shorthand cluster (204 renames + 9 drops, 434 files) ran this way and its apply-to-deploy window was **eight minutes**; it also caught three defects that the apply-first order would have found in production instead — a PL/pgSQL trigger body that would have failed every `league_formats` write, a silent absent-key on the roster read path, and a data-view param emitting a dropped column. Two things this does NOT get you: `audit-schema-conformance.mjs` ignores `LEAGUE_SCHEMA_FILE` and reads the tracked path (hence copying over it in the worktree — setting the variable reports the TRACKED numbers, which reads exactly like a migration that did nothing), and the candidate dump will differ cosmetically from production's in `CHECK`-constraint array spelling when the two `pg_dump` versions differ, which is not drift. **And a third: a candidate schema makes your LOCAL suite green on code that CI cannot run.** CI reads the tracked `db/schema.postgres.sql`, so if you commit schema-dependent code in one commit and the export in the next, the first commit is red on GitHub no matter how green it was locally — and because the red-main pre-push guard then blocks every league push fleet-wide, the fix sitting in your very next local commit cannot push itself. That happened on 2026-08-13 with `league_pauses`: the guard queried a table the tracked schema did not declare, ~35 specs failed on `relation "league_pauses" does not exist`, and clearing it needed `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh`. **Ship the DDL, the export, and the code that depends on them in ONE commit** — the same one-commit rule the note above states for the apply, for the same reason, at the other end.

**Run `check-saved-view-param-coverage.mjs` as part of that gate list, not as an afterthought — a renamed PARAM key is the one failure this whole recipe otherwise misses.** The suite, the SQL-validity gate and the goldens all pass over it, because the defect lives in `user_data_views.table_state` rather than in any file. The 2026-08-05 cluster renamed 18 keys in `nfl-plays-column-params.mjs` and shipped without a matching rule in `data-views-saved-view-migration.mjs`, silently dropping filters on **45 saved views** (`qtr` 25, `dot` 7, `route` 7, `dwn` 5, `wp` 5) — found only after the deploy. The rule for that file is stated at length further down; what was missing was running the check at all, so treat it as a required gate whenever a cluster touches a param registry.

**Both param-coverage gates are KEY-anchored, so neither can see a renamed param VALUE — and a value rename has no gate at all.** `check-saved-view-param-coverage` walks `Object.keys(node.params)` and `check-data-view-url-param-coverage` walks `parsed.searchParams.keys()`, so both stay green across a value rename whether or not any migration rule exists. Running their negative controls does not help: those prove the gates work on KEYS. This is the reach-versus-class distinction stated further down, arriving on the surface where it is easiest to miss, because a plan that says "run both param gates" reads like coverage. The 2026-08-08 run-direction rename hit it — `team_rush_left_end_dvoa` and its four siblings are VALUES of the `dvoa_type` param on `team_unit_dvoa` (`app/core/data-views-fields/team-dvoa-table-fields.js`), not param keys and not column ids, so `LEGACY_URL_PARAM_ALIASES` was the wrong remedy too: that map aliases top-level `table_state` keys, and an entry for a value would have been inert. The working shape is a VALUE map in `data-views-saved-view-migration.mjs` (`SCORING_FORMAT_HASH_TO_ID` is the precedent — it is likewise a value mapping) plus wiring it into `parse_table_state_from_url`, since the URL path runs only the nfl-week migration and would otherwise rewrite nothing at all. The gate has to be a spec proven red at the pre-fix revision; `test/data-views.dvoa-type-value-migration.spec.mjs` is the shape, asserting through the two public entry points rather than importing the rename map so its red is a value that was not rewritten rather than a missing export. **Before trusting a gate a plan names, check that your defect is in its class — three column-shaped things live in `table_state` (param keys, column ids, param values) and only the first two have gates.**

**Its sibling `check-data-view-url-param-coverage.mjs` covers the OTHER data-view surface, and it is the one a rename forgets — a shared short URL cannot be rewritten, so a missed key there is permanent.** The saved-view gate checks the params nested inside a column; this one checks the top-level query-string keys of the production `urls` table against `SHARE_LINK_URL_SCHEMA` plus `LEGACY_URL_PARAM_ALIASES`. The distinction that made the June 2026 `splits` -> `row_axes` rename fail is that **a URL query string carries no version field**, so it never enters the versioned migration chain in `libs-shared/data-view-storage/migrations.mjs` — the rename did ship a `v2_to_v3` rule and 188 of 682 production URLs still rendered at the wrong grain for six weeks, three of them emitting unexecutable SQL. Run it alongside the saved-view gate on any cluster touching a top-level `table_state` key:

`yarn check:cluster` runs it, supplying the production environment itself and skipping loudly when the tunnel is down.

The only remedy for a reported key is a permanent entry in `LEGACY_URL_PARAM_ALIASES` (`app/core/data-views/parse-table-state-from-url.mjs`); there is no migration to write, because the link is immutable. Two things worth copying from it. Its accepted-key sets are **imported rather than grepped**, which is the direct fix for the failure that blinded the saved-view gate — a presence-grep cannot tell a consumer from prose about one, so a comment naming a legacy key made that key unreportable. And its URL population is **five routes, not one**: `/leagues/:lid/players-table` is a `<Navigate>` redirect preserving `location.search`, so scoping to `/data-views` alone misses 159 of the 863 URLs. Its negative control is deleting the `splits` alias and confirming the gate reports it — take that as seriously here as everywhere else in this file.

**Two ways a rename hides from the gates you are running.** First, **a golden cannot catch a miss its emitter SHARES**: if the emitter still produces the old name and the golden still expects it, they agree and the fixture passes — two goldens survived the 2026-08-05 sweep that way, and one was `skip_query_match`, so it could never have failed on SQL at all. After regenerating, grep the goldens for every old table-qualified name; that grep, not the suite, is the gate. Second, **the audit cannot show you the members it did not flag**: renaming some members of an obvious sibling set splits it. `wins`/`ties` are four characters and flagged while `losses` is six and invisible, so four tables were about to ship `regular_season_wins / losses / regular_season_ties`. When a class renames part of a set, check the whole set against `information_schema` rather than against the audit output.

**A build-and-swap that RENAMES the old table instead of dropping it turns `check-schema-conformance-ratchet` red, and the baseline cannot absorb it.** Retaining the old table under a new name is the right call for a large migration — `db-exec.sh` runs a file as one non-interactive transaction and exits, so there is no post-commit recovery short of a full restore. But the conformance baseline keys every violation on `table.column`, so the rename mints brand-new keys for the SAME non-conforming columns the baseline already carried, and the ratchet reports them as new debt. The 2026-07-31 keeptradecut restructure retained `keeptradecut_rankings` as `keeptradecut_rankings_pre_valuations` and the ratchet went to exit 1 on `.d`, `.qb` and `.v` — none of which was new. The blast radius is the whole repo, not your cluster: a red master makes the sync-all pre-push guard defer **every** push to `mistakia/league`, so unrelated sessions' commits pile up behind a gate whose cause is invisible in their diffs (four were parked within six hours). Two rules. Do **not** `--rebaseline` — the entries vanish when you drop the table, so you would write stale ones and bury a real regression landing in the same window. And plan the retention window in hours, not days: the drop is what clears it, so verify fast and drop, or post a bulletin naming the cause so siblings do not debug your gate.

**`CREATE TABLE ... AS SELECT` produces a table with no statistics — `ANALYZE` it in the same file.** The planner sees a fresh CTAS relation as tiny regardless of its real size, so a swap that puts 2.3M rows behind a name the API reads on every page load ships with plans derived from nothing until autovacuum eventually gets to it. The 2026-07-31 restructure's DDL omitted this and it had to be run by hand immediately after the apply. Any build-and-swap file should end with `ANALYZE <new_table>;` before the rename, alongside the constraints and grants.

**A staging table left in `public` on production breaks `yarn export:schema` for EVERY session, not just yours.** `pg_dump` takes `ACCESS SHARE` on every table it can see, in one `LOCK TABLE` naming all of them, so a scratch table owned by a role the export role cannot lock fails the whole dump with `permission denied for table <staging>` — not a partial export, no schema file written, and the error names a table that has nothing to do with whatever the exporting session was working on. A 2026-07-29 projection backfill loaded six `projection_backfill_*` tables as `postgres` and every subsequent export failed until they were dropped. Two rules: create bulk-load staging with the same role that runs the export, or drop it in the same session that created it — and never leave it in `public` across a commit boundary. If an export suddenly fails naming a table you have never heard of, this is why; `\dt public.*` and ask whose it is rather than debugging your own change.

**A `debug.enable()` call REPLACES the enabled namespace set — it does not add to it.** So a helper's own instrumentation is silently unreachable unless the entry-point script lists its namespace. `record-league-format-projection-value-history` logs the change rate that is the entire cost model for the projection-value history store, and it had logged **zero times** in production — including through the run that seeded 468,930 rows — because neither `process-projections.mjs` nor `process-projections-for-league-format.mjs` named it in their `debug.enable(...)`. Nothing fails; the metric just does not exist, which is the worst shape for an instrument whose job is to detect silent degradation.

**The remedy is NOT "name the namespace at the entry point" — that was this file's advice until 2026-08-03 and it cannot work.** Two mechanics defeat it. First, ESM evaluates every import before the importing module's body, so a `debug.enable` at the module scope of any imported file runs BEFORE the entry point's own line — and since enable REPLACES the set, the last import to run owns the process. Second, under `debug` 4.4.3 a call made after a logger has been constructed can turn that logger OFF but **cannot turn it back ON**, so once a library has clobbered the set the entry point is structurally unable to repair it. Both were measured on the production host: with `DEBUG` naming `insert-prop-markets`, the logger reads `enabled=true` at import and still `enabled=false` after an `enable()` call that explicitly names it.

The prop write path was dark in production for exactly this reason, and it cost five deploys and three wrong diagnoses on 2026-08-03. `jobs/import-live-odds-worker.mjs` imports the draftkings, pinnacle and prizepicks scripts in that order; `import-prizepicks-odds.mjs` ran last and set the namespaces to its own three, naming neither the worker nor `insert-prop-markets`. The worker's own unconditional `debug.enable('import-live-odds-worker')` then ran after it and restored exactly one namespace — its own — which is precisely why the worker logged normally while everything else stayed silent and every configuration change looked correct. Removing that line without replacing it took the worker's stderr to **total silence**, a strictly worse state that shipped to production for an hour.

So: **`debug.enable` at module scope in anything importable is the bug.** Every call site in `libs-server/` (14), `libs-shared/calculate-standings.mjs`, and the three importable odds scripts is now guarded as `if (!process.env.DEBUG) { debug.enable(...) }`, which makes an explicit `DEBUG` authoritative and leaves each module's list as the default for a bare CLI run. Keep that shape when adding one, and note `libs-shared` is isomorphic — use `globalThis.process?.env?.DEBUG` there, since the SPA bundle has no `process`. `private/` still carries unguarded module-scope calls; they are outside the odds worker's import graph today and are the next instance waiting to happen.

**Do NOT "fix" the importable-module hazard by moving `debug.enable` into `main()` — that silences the script entirely, and it exits 0 while printing nothing.** The guarded module-scope form above is the shape to keep; deferring the call to `main()` reads like a stricter version of the same rule and is not. A logger constructed at module scope (`const log = debug('x')`, which is every script here) is not reliably re-enabled by an `enable()` that runs later in `main()`, so a cron line carrying no `DEBUG` produces an **empty log file** — the job runs, does its work, exits 0, and writes nothing anyone can read. Measured on the league host 2026-08-05: `audit-keeptradecut-liquidity-coverage.mjs` and `import-keeptradecut-liquidity.mjs` both printed zero bytes with the call in `main()` and printed correctly with `DEBUG` set explicitly, which is what made the cause obvious.

The durable fix for anything whose log IS its audit trail — a scheduled job, an oracle, a one-shot repair — is **`console.log`/`console.error` for every outcome line**, reserving `debug` for chatty per-item detail. Namespace resolution is a runtime negotiation with the whole ESM import graph; an oracle's verdict must not depend on winning it. This is the same reasoning already given for `db/adhoc` scripts further down, and it generalises to every `scripts/*.mjs` a crontab invokes. Note the failure is invisible to the test suite (specs assert on return values, not stdout) and to a local run with `DEBUG` set — only running the job the way cron runs it, with a clean environment, exposes it.

**Diagnose this by instrumenting `debug.enable`, never by reading configs.** Monkeypatch it to print its argument and caller, then load the real import graph — it names the clobbering call site in one command. The whole 2026-08-03 detour came from verifying configuration (the pm2 env was correct in `/proc/<pid>/environ` every single time) and inferring behaviour from it, when the observable was one `grep` away: the error log contained exactly ONE namespace, which is a fact about precedence rather than about whether any config was right.

**Column renames must sweep query call sites, not just the DDL.** A rename lands green while leaving code that still names the old column, because most such references only fail when their code path actually executes. The 2026 `year`/`seas_type` -> `season_year`/`season_type` conformance left four seasonlog and careerlog generators still filtering on `nfl_games.year` and `ng.seas_type`; each threw Postgres 42703 at runtime and had silently aborted every scoring and league format seasonlog build until it was found by a backfill months later. After renaming a column, grep the old name across `scripts/`, `libs-server/`, `jobs/`, and `api/` and run the affected generators once, rather than trusting the schema export to be the whole change. Beware unqualified object-literal predicates (`.where({ year, seas_type: 'REG' })`) — they read as local variables and do not grep like column references.

**The rename's other half: an UNQUALIFIED predicate that was fine before can become AMBIGUOUS after, and the failing query is one nobody edited.** Conforming a column to a name a joined table ALREADY carries collapses the accidental disambiguation the old name provided, so Postgres rejects the whole statement with 42702 `column reference "<new>" is ambiguous`. The 2026-08-05 season_grain conform hit this in `libs-server/restricted-free-agency-bids-query.mjs`, whose builder filtered a bare `.where('season_year', year)`: its three callers join `restricted_free_agency_nominations`, which had been conformed to `season_year` by an earlier cluster, so the predicate was unambiguous only while the bids table still said `year`. That single line was **83 of 165 suite failures** — a shared query builder multiplies one defect across every caller, which is also why the failure count read like a scattered regression rather than one site. Note the sweep itself is what introduces it, so no pre-rename grep of the old name can find it: the check is to list each renamed table's join partners and grep for unqualified predicates naming the NEW column. Loud on execution, so the suite catches it — but only where a spec exercises the path.

**A routes-scoped alias grep does not see the websocket layer.** When a rename ends a wire alias-back, `api/routes/**` is the obvious place to sweep and it is incomplete: three of the nine `year`-to-`season_year` alias-backs removed on 2026-08-05 lived in `api/sockets/auction.mjs`, on the broadcast path that hands bid and transaction shapes to the client. Sweep `api/sockets/` alongside `api/routes/` for anything that shapes a response.

**`db/gates/check-renamed-column-consumers.mjs` is the gate for that sweep, and its two halves are wired differently on purpose.** GATE 1 — every `'<table>.<column>'` literal in server code must resolve against `db/schema.postgres.sql` — needs no rename list and no base ref, so it cannot drift and cannot go red on a sibling's in-flight migration; it runs in CI. GATE 2 answers the harder question: did THIS change remove a column whose old name a consumer still reads. It diffs the schema against a base ref, so **run it by hand per cluster** and give it the pre-cluster revision:

`yarn check:cluster --base <pre-cluster-ref>` runs it; `node db/gates/check-renamed-column-consumers.mjs --gate 2 --base <pre-cluster-ref> --unadjudicated` is the direct form when you want the unadjudicated set.

**Give it a ref that resolves, and check that it did.** Handed a base ref git cannot resolve, this gate prints a one-line `SKIPPED: could not read db/schema.postgres.sql at <ref>` in the middle of its output and then exits **0** with `GATE OK` — so a typo, or a ref that has since been garbage-collected, reads as a passed gate from every angle except the one line. `yarn check:cluster` resolves the ref itself and treats an unresolvable one as a missing prerequisite, which is the only reason a run through it cannot be fooled this way.

It is deliberately NOT in CI. A gate finding turns master red, and a red master defers **every** session's push to `mistakia/league`; gate 2's findings also need per-site adjudication by someone who knows the cluster, which CI cannot do.

**The thing to understand before trusting a gate-2 green: it is anchored on the affected TABLE, not on the column name.** A silent defect here is a query selecting an affected table WHOLESALE (no explicit projection, and a `.select('*')` wildcard counts) whose row loses the old key with no error while a consumer still reads it — an explicit projection naming a dropped column raises 42703 and is loud instead. Findings are adjudicated per `(table, column)` in `renamed-column-consumer-adjudications.json`, which records the QUERY site list reviewed so a new query site is reported rather than inherited. **That promise does not extend to READ sites, which is where this class of defect actually lives** — see the SPA paragraph below before writing an adjudication reason.

**Anchoring on the table buys reachability for FROM-target queries and loses it for JOINED ones — a table reached through `.join`/`.leftJoin` is invisible to gate 2, no matter how literal its name is.** This is stronger than the table-name-in-a-constant caveat and was undocumented until 2026-08-06. The candidate set comes from `db('<table>')` FROM-target literals only, so a query that says `db('rosters_players').leftJoin('transactions', ...)` puts `transactions` outside the gate's reach entirely. That is how `72346e579`'s rename of the transactions salary column shipped a live defect: `libs-server/get-league-rosters-from-database.mjs` never appeared in the candidate set — at `--base 62ca45544` the gate produces 36 sites for that pair and that file is not among them — so the pair was adjudicated already-swept off a single producer, players arrived with `value: undefined`, and `NaN || 0` at `libs-shared/roster.mjs:97` rendered every team's salary space as the raw $200 cap. The gap is general: 22 join-only sites across the same window. **A gate-2 green does not mean a joined consumer was checked.**

**That REACH gap is now covered by `check-knex-column-resolution`, with a number rather than an inference — 175 of 178.** Measured 2026-08-07 by instrumenting the resolver to separate tables that entered scope through a join from the FROM target: **178 (file, table) pairs where the table is join-reached, 175 with at least one resolved column reference**, leaving 3 uncovered (`generate-seasons.mjs::seasons`, `process-nfl-plays-player.mjs::player`, `resolve-player-match.mjs::player_aliases`). Two caveats worth carrying. The instrumentation has to be gated to the primary scan — the negative controls re-run `run_scan` with a source override and contaminated the first reading by 5x. And this covers REACH only: the silent wholesale-key-loss class is gate 2's, and reach and class are independent, exactly as the paragraph below establishes.

**But do NOT close that by widening `from_re` to join literals — it was measured on 2026-08-07 and does not work.** The obvious remedy reads as a one-line change and this file recommended it for a day. At `37cc9f36b~1` with `--base 8f1abd79d~1`, adding `.join`/`.leftJoin` to `from_re` takes the candidate set from 259 to 284 sites and reopens **37 adjudications** — the exact cost the gate's own header predicts — while still reporting the live defect it was aimed at **zero** times. The reason is that the defect was never gate 2's class: `compute-roster-slot-metrics.mjs` carried explicit projections at both sites (`.select('tid', 'pid')`, `.select('r.tid', 'g.pid')`), so gate 2 skips them correctly. Gate 2 catches the SILENT loss of a key from a wholesale row; a stale column in a predicate is the LOUD 42703 class, which is gate 1's question. Generalising: **before widening a gate's reach, check that the defect you are aiming at is in that gate's CLASS** — reach and class are independent, and a reach fix aimed at a class miss costs a full re-adjudication and buys nothing.

**`db/gates/check-knex-column-resolution.mjs` is the gate for that class, and it is the fourth anchor: a column reference that names no table LITERALLY, resolved through the statement that binds it.** Gate 1 reads only `'<realtable>.<column>'` literals, which leaves the three shapes this codebase writes constantly — an ALIAS-qualified `'r.year'` where `r` is bound by `.join('rosters_players as r', ...)`, an object-shorthand `.where({ lid, year })` that reads as a local variable, and a BARE STRING `.where('status', x)` that names no table at all. It builds each statement's alias environment from its FROM target, its `.from(...)` calls and every join, then resolves each reference against `db/schema.postgres.sql`. An unqualified or bare reference is resolved ONLY when exactly one table is in scope; with a join present the name is genuinely ambiguous and guessing a table would invent findings, so those are counted as unchecked and printed. It needs no rename list and no base ref, so it is CI-eligible on gate 1's terms and is in the CI step; `yarn check:cluster` runs it with no prerequisite. Its ten negative controls run on every invocation and **four of them assert the gate stays SILENT**, because half of what it does is decide a token is not a column reference.

**The bare-string half has two traps worth knowing before you extend it.** The predicate family's FIRST argument is a column and every argument after it is a VALUE — `.where('type', 'TRADE')` binds a string second — while every argument of the list family (`.groupBy`, `.onConflict`, `.merge`) is a column. Reading past argument 0 for the predicate family resolves DATA as columns, silently, on a corpus where transaction types and season types are all lowercase strings. And a bare reference to an OUTPUT ALIAS the statement declares for itself is correct SQL that must be excluded: `.count('* as count')` then `.orderBy('count')` resolves against the projection, not the table. On this corpus that exclusion is the difference between **9 findings and 1** — the 8 it removes are all that shape. Because an exclusion removing 8 of 9 findings is indistinguishable from a collector that finds nothing, one of the four silence controls asserts exactly it; do not add such a filter here without the paired control.

**It carries no coverage-floor number, and the reason generalises to every gate here that is tempted by one.** It shipped with three — 200 files, 800 statements, 1500 references — and they were deleted on 2026-08-07 as redundant rather than ratcheted. The controls already cover the case they were written for: each of the first four has to FIND real corpus material of its shape before it can mutate it, so **emptying the corpus, making statement extraction return nothing, or making alias binding always fail turns all four red with NO MATERIAL** — measured all three ways. What the floors could not see is the failure that is actually reachable, ONE root going dark, because `walk_files` treats an unreadable directory as empty: moving `jobs/` aside leaves the three floors printing `GATE OK`, since `jobs` is 4 statements of 1493. They were also 22%, 54% and 45% of live coverage, loose enough that a scan could silently halve and still pass, and loose for the ordinary reason a hand-maintained number always ends up loose — an exact match turns unrelated commits red. Coverage is asserted instead **per corpus root**, derived from `ROOT_EXPECTATIONS`: every root must contribute at least one file and at least one knex statement, except `libs-shared`, which must contribute exactly zero because it is isomorphic and reaches the SPA bundle. That last one is an architectural assertion rather than an exemption — a knex statement there is a defect. Nothing in the declaration is a measurement, so ordinary churn moves nothing, and this is the same conclusion `check-api-response-shapes` reached from the other direction: when a control has to work anyway, a hand-maintained minimum adds nothing to the catastrophic case and fires on the ordinary one.

Its first run on master found **four live 42703s that every other gate was green over**, which is the argument for it: `teams.year` in `compute-optimal-metrics.mjs` (the sibling file in the same directory as the one `37cc9f36b` had just fixed, same generator, same cluster, missed by the same sweep), `nfl_team_seasonlogs.year` in `filter-prop-pairings.mjs`, `league_scoring_formats.scoring_format_id` in `load-simulation-data.mjs` (whose own sibling function 130 lines up writes the correct `.where({ id: ... })`), and `users.reset_token` in `POST /auth/reset-password` — a column that has never existed on `users`, so that route had been throwing on every call. All four were repaired rather than adjudicated, so the gate ships with an **empty adjudication surface**: there is no `knex-column-resolution-adjudications.json`, and the absence is the correct end state rather than an omission.

**`private/` is in NO consumer gate's corpus, so a rename touching the PFF or odds importers has no gate at all — and every gate still prints `GATE OK`.** `ROOT_EXPECTATIONS` here is `api`, `libs-server`, `libs-shared`, `scripts`, `jobs`; `check-renamed-column-consumers` and `check-rename-alias-residue` scan the same roots, and the only gate that reaches into `private/` is `check-plays-column-repoint`. This is the code analogue of the `yarn test:private` note further down — that paragraph establishes private SPECS are local-only, and the stronger fact is that private SOURCE is unreachable by the consumer gates entirely. Measured 2026-08-07 on the residual position/team conform, where the writers for three of the seven renamed columns live in `private/` and a full green gate sweep said nothing about any of them. The oracle that works is the candidate-schema recipe above plus, for a writer no spec executes, a throwaway round-trip probe under `tmp/` that calls the real exported function against the candidate database — `log_unresolved_player` reverted alone raises 42703 naming both the insert and the `do update set` halves, which is the only thing that distinguishes a moved payload key from a well-formed one that cannot execute. **When a cluster touches `private/`, budget for hand-verification and do not report a gate sweep as coverage of it.**

**`db/gates/check-rename-alias-residue.mjs` is the third gate, and it covers that class from the other side — run it on every rename cluster.** It anchors on the **alias-back site**, which needs neither a FROM-target literal nor a distinctive word, so it works for `value` exactly as well as for `rid`. The discriminator is that the alias TARGET name is a column the table actually LOST in the schema diff, which separates a rename alias-back from ordinary join disambiguation (`waivers.uid as wid`) and takes the corpus's alias literals down to a handful. It reads both anchor forms — a qualified `'<table>.<new> as <old>'` and an unqualified `'<new> as <old>'` resolved from the enclosing `db('<table>')` statement (including one held in a builder binding), which is not pedantry: `libs-server/get-roster.mjs:48` writes the unqualified form and a qualified-only scan misses one of the two producers. The BARE side reads the matching three shapes — qualified, unqualified, and wholesale `'*'` — so a `select('*')` producer counts against an aliasing one. Findings come in three classes with their own verdict questions — SPLIT PRODUCERS (aliased at one site, bare at another: the shape `72346e579` left on the transactions salary column), ORPHANED ALIAS (the new name is ALSO read as an in-memory key somewhere, so two vocabularies disagree: the `practice.*` shape), and UNIFORM (correct today, reported as a standing hazard). Adjudicate per `(table, column, file)` in `rename-alias-residue-adjudications.json`; an entry suppressing nothing is itself a finding — **but only when the run's base ref put that entry's column in the lost set, and until 2026-08-07 that qualifier was missing.** Every unused entry was reported STALE with the remedy "the site is gone, so the entry must go too", which made staleness a property of the caller's `--base` rather than of the tree: at `--base 62ca45544` (243 lost columns) all 15 entries were used and the gate read OK, while at `8f1abd79d~1` (27) and `c801b5a11` (0) all 15 read as stale over sites all live in the working tree. Acting on that output deletes load-bearing suppressions. An entry outside the run's lost set is now **NOT EXERCISED** — printed with a count, no verdict — so read that count before treating a green run as an audit of the file: covering all 15 needs a base ref spanning every rename window they were written for. `yarn check:cluster --base <ref>` runs it. **Unlike gate 2 it treats an unresolvable base ref as exit 2, not as a pass.**

**A UNIFORM verdict from this gate was untrustworthy until 2026-08-06 and is not any more — but the reason it was is the durable lesson, because the same asymmetry is easy to reintroduce.** An adversarial review falsified the oracle three ways on the day it shipped. The bare-producer half read only QUALIFIED `'table.column'` literals while the alias half read two anchor forms, so a producer projecting the row WHOLESALE (`select('*')`, or an unqualified bare projection) contributed nothing and a genuine SPLIT PRODUCERS case was reported as UNIFORM — "every producer aliases back, correct today" — with an empty bare-producer list. An alias-back against an imperative builder (`const query = db('x')`, then `query.select('col as alias')`) resolved to no table and was dropped silently. And `REGISTRY_PATH_MARKERS` matched `'data-view'` as a substring of the whole path, excluding 132 files including 13 real query emitters. All three are fixed, along with six smaller defects — comment prose counted as alias sites, a case-sensitive fast path, a partition-terminator miss that hid six tables, and a default `--base` that guaranteed exit 1. **The general rule: when a gate anchors on a pairing, the two sides must read the same shapes, and an asymmetry between them fails toward a confident green.** On the real corpus the repair reclassified six of fifteen findings out of ORPHANED ALIAS into SPLIT PRODUCERS, naming four bare producers no run had printed; none was a live defect, all four were opened and read the physical name.

Three things about it worth carrying. **The stale-adjudication rule is a real backstop, mutation-proven:** broadening `REGISTRY_PATH_MARKERS` to exclude every file still turned the gate red through 15 stale entries, so an already-adjudicated column cannot go quietly dark even when the scan is fully blinded. **`--base` is required and has no default** — there is no invocation that silently diffs against nothing. **A rename does NOT reach into PL/pgSQL function bodies, and no grep of this repo can find the ones it breaks.** Postgres rewrites the parsed trees behind views, indexes and constraints on `ALTER TABLE ... **An `onConflict([...])` target list is a column reference that does not look like one, and no gate here covers writer SQL.** A rename sweep that updates the inserted object keys and misses the upsert's conflict target produces valid-looking JS that Postgres rejects at execution with `column "<old>" does not exist`. **A BARE column reference inside a `.merge()` expression is ambiguous, and Postgres rejects the whole statement — insert half included.** The DO UPDATE expression's namespace holds both the target table and `excluded`, so `db.raw('total_checks + 1')` raises 42702 `column reference "total_checks" is ambiguous` rather than resolving to the stored value the author meant. Qualify every bare column in a merge raw with the table name (`draftkings_category_activity.total_checks + 1`); reaching for `excluded` instead is a different statement, and for a "keep the old value unless ..." CASE it is the wrong one — `excluded` would wipe the field on every no-op check.

**The red-at-the-broken-revision rule has a consequence worth stating outright: EXTRACTING a pure function to make it testable destroys the proof.** The extracted file does not exist at the broken commit, so the spec fails there on module-not-found rather than on the defect — a red that proves nothing, and one that reads exactly like a real one in a terminal. The two goals are in direct tension: a spec either covers the code that was broken, or it covers code you wrote after the fact. **The companion hazard runs the other way: DROPPING a unique constraint breaks every `ON CONFLICT` that names it, on code you have not deployed yet — so the outage lands between the apply and the deploy, not after it.** `ON CONFLICT (a, b, c)` requires a unique index on exactly those columns, and Postgres resolves it at execution, so the moment the constraint goes the still-running old code fails every upsert with `no unique or exclusion constraint matching the ON CONFLICT specification`. The apply is instant and the deploy is human-gated, which makes that window hours rather than seconds. The fix is to make the two oracles OVERLAP rather than hand off: add the new unique index in the first file and drop the old constraint in a second one applied immediately after the deploy verifies. Both spellings of the upsert resolve for the whole window, so there is no moment where deployed code cannot find its conflict target. Two things to get right. Gate the second file on what the HOST is running (`ssh league 'cd /root/league && git rev-parse --short HEAD'`), not on what is committed or pushed — this is the same "a cluster is done when it is DEPLOYED" rule further down, and here it is load-bearing rather than hygienic. And treat the second file as an immediate post-deploy step rather than as cleanup, because the overlap is not free in the other direction: a retained constraint is strictly stricter than the digest that replaced it, so once the new code is live it rejects rows the new oracle considers distinct. Reproduced on a scratch database — an insert differing from an existing row only in `defensive_touchdowns` raised a duplicate-key violation on the retained constraint that `ON CONFLICT (config_digest)` did not catch, which is a 500 for a commissioner editing a DST value. **A RETYPE GATE'S FINDING COUNT IS NOT THE CLUSTER'S BLAST RADIUS, and reading it as one is how the 2026-08-08 lifecycle retype nearly shipped two silent data-corruption defects.** `check-retyped-column-arithmetic` reported 13 findings over 6 files for the fifteen-column lifecycle retype; the real consumer surface was roughly 90 changes across ~50 files. The gate was not wrong — every one of its 13 was real — but its class is a resolvable epoch expression in a predicate or a read, and **four other classes carry the same defect while lying outside it by construction**. Budget for all four on any retype:

- **INSERT PAYLOADS.** A payload is neither a predicate nor a read. 24 sites across 18 files here — trade accept/reject/cancel, waiver submit/cancel, RFA bid submit/cancel, poach submit/process, tag cancel. All fail LOUDLY, so the cost is a stopped write path rather than bad data, but an unswept one takes the app's whole transactional surface down. Note several were reached only through a DERIVED variable (`const timestamp = Math.round(occurred_at.getTime() / 1000)` feeding `processed: timestamp` 160 lines later), which no grep of the epoch idiom finds.
- **THE SPA.** `SCAN_ROOTS` omits `app`. Beyond the obvious `dayjs.unix()` renders, the expensive shape is a value the SPA sends BACK as a query bound: `getScoreboardUpdated` returned `0` when no plays were loaded, which becomes `where updated > 0` against timestamptz and breaks the live scoreboard on the FIRST register of every session. A column can be SPA-visible through the write path even when nothing in `app/` renders it — do not conclude "not SPA-visible" from a read sweep alone.
- **MIXED-UNIT MERGE STREAMS, and these are the dangerous ones.** A Date pushed into a stream of epoch seconds that is then sorted or compared numerically. Both instances were SILENT and neither was adjacent to anything the gate flagged: `walk-transactions.mjs` compared `earliest_trade * 1000` on a value that is now a Date, so the synthetic pre-trade ownership window was never created and every pick traded before its endowment lost its first leg; `refresh-extension-state.mjs` pushed `restricted_free_agency_bids.processed` raw into a reset stream keyed on epoch seconds, misordering every extension-ladder reset. The second one's own comment asserted the opposite, accurately when written — a dated unit claim in a comment is exactly the thing a retype falsifies.
- **WRITE-BOUNDARY AND RAW-SQL CONVERSIONS BECOMING DOUBLE CONVERSIONS.** `to_timestamp(?)` wrappers and `TO_CHAR(TO_TIMESTAMP(col), ...)` were correct against an epoch integer and are now either a type error (`function to_timestamp(timestamp with time zone) does not exist`, which fails the whole statement) or a float misread (`invalid input syntax for type double precision: "58450-09-27..."`). Grep `to_timestamp` and `epoch_to_timestamptz` against the retyped columns as its own sweep step.

Two procedural rules follow. **Read the sibling lines around every site the gate names** — the five `walk-transactions` findings it reported all had an unflagged `sort_ts:` assignment one line above, and the worst defect in the file was 40 lines below them. And **treat an ordering-shaped test failure as a possible real defect until you have bisected it**: five lineage failures reading `expected 2 to equal 1` looked exactly like specs asserting a stale contract, and reverting only that file against HEAD is what proved they were not. The full suite against a candidate schema, compared against a control run at HEAD, is the oracle that found both silent defects — no gate did.

**Check a proving join for its own false matches before believing what it proves.** A join used as evidence — "this table's data all exists over there, so the drop is lossless" — is itself a query that can be wrong, and when it is, the error hides in the aggregate. On 2026-07-29 two separate approved instructions rested on joins missing a discriminating column. The `schedule` drop was to be preceded by backfilling 2 "unique" `surf` values; the finding behind it joined on `(season, week, v, h)` without `season_type`, and since `schedule` holds no preseason at all, its regular-season week-1 rows had matched **preseason** week-1 rows for the same teams. Both values already existed on the correct rows, and performing the approved backfill would have invented surface data for two games the source never described. The tell was never visible in a count — it took looking at the individual rows the join had paired, and re-matching on `(season, teams, nearest date)` to absorb the OAK/LV code drift and postseason renumbering that broke the naive form.

**A retype must preserve UNIT semantics, and re-deriving a number with a different query shape does not test the population it was scoped to.** Two lessons from one defect, both live for the remaining retype clusters. First: `b09fdbce` restated `to_timestamp(gm."timestamp" - 7*86400)` as `kickoff_at - interval '7 days'` and described the forms as equivalent. They are not — a day-unit interval on a `timestamptz` is calendar arithmetic in the session timezone (production is `America/New_York`), so across the November fall-back it spans 169 hours. Hour units are absolute; day, week, and month units are not. When a retype moves epoch-integer arithmetic onto a `timestamptz`, state offsets in hours (`interval '168 hours'`, pinned in `8684b569`) and assert the calendar form is ABSENT, or the drift is invisible: it fires for one week of every season and no other, which is a seasonal artifact rather than a uniform widening. Second, and the more general one: the impact of that drift was first measured at **155 flipped rows and re-derived with a differently-shaped query that agreed**, but both shapes omitted the `player_gamelogs gl_inner` join the CTE actually performs, so both measured a population the CTE never sees — the real figure is **5**, and 580 of the 616 "extra" changelog rows belong to players with no gamelog for the game whose window they fell into. Independent derivation only catches an error the derivations do not share, and scoping is exactly what two readings of the same SQL will share. It is also not what a positive control fixes by default: the control used here (a game on the fall-back date) validated the timestamp arithmetic, which was never in doubt. Aim the control at the step that could be wrong, and anchor it on the artifact you are making the claim about — name a row, predict its value, then look for it in the output table. Doing that surfaced both the corrected count and an unrelated defect, because the predicted row was not in the table at all.

**An executed-result oracle is only as good as where its expected values came from.** The result-equivalence fixtures are the gate meant to catch semantics that valid SQL cannot, but their `expected_rows` are hand-written, and one authored by reading the current output is a screenshot rather than an oracle. `game-opponent-range-year-offset-fanout-result-equivalence.json` asserted `game_is_home: true` for a subject team its own `seed` SQL places at `away_nfl_team` in both games, so it executed happily and blessed an inverted flag alongside four query-match goldens. Derive an oracle's values from the fixture's seed data, and note that `update-data-view-snapshots.mjs` only rewrites `expected_query` — regeneration structurally cannot repair an oracle, so a wrong one must be hand-corrected.

**A regenerated data-view golden cannot catch a rename you missed.** `scripts/update-data-view-snapshots.mjs` overwrites `expected_query` with whatever the current code emits, so a golden regenerated from buggy code agrees with the buggy code and the suite goes green over a live defect. This is not hypothetical: the 2026-07 plays/snaps conformance left `build_role_union_period_cte` emitting `nfl_plays.year` against the renamed table — a 42703 on every data view carrying a rate type — and eight regenerated goldens blessed it. Auditing the regeneration diff does not help either, because that only proves each _change_ was intended; it says nothing about an old name that stayed _unchanged_. After regenerating, grep the goldens for the old names directly (they escape quotes, so match `nfl_plays\\".\\"<old>`), and treat executed result-equivalence — not query-match — as the gate.

**A golden carrying `skip_query_match: true` asserts NOTHING about its SQL — regenerating one is bookkeeping, not coverage.** The mocha harness branches on that flag: when set, it logs the SQL diff to the working-tier catalog for hand review and continues, so `expected_query` is inert and the fixture cannot fail on a query change. The trap is that every other signal still looks like coverage — the file lives in `test/data-view-queries/`, `data-view-test-cli.mjs` _does_ compare it and prints `✓ Queries match!`, and `--update` rewrites it — so a session fixes a defect, regenerates the one golden that exercises the shape, sees green, and has added no gate at all. On 2026-07-31 the week-row-axis fix landed against exactly this: `keeptradecut-value-year-week-split.json` was the only golden in the corpus requesting a `week` param, and it is `skip_query_match`. Check the flag before treating a fixture as your gate; when it is set, the coverage has to be a spec asserting on the generated SQL (or a result-equivalence fixture), and the honest proof is that the new test **fails at HEAD** — run it in a clean worktree at HEAD and confirm it goes red before trusting it green in your tree.

**Beware the inverse grep error: a pattern that matches as a SUBSTRING of a longer identifier, making dead code look live.** The documented hazard above is a pattern that cannot match; this is one that matches too much, and it reads as confirmation rather than as a zero. Grepping the goldens for `week_timestamp` to check whether a join was exercised returns 11 files — nearly all of them hits on the _table_ name `nfl_year_week_timestamp`, which contains the column name as a substring. Anchoring on a delimiter (`\.week_timestamp`, `"week_timestamp"`) returns 3. Anchor a reachability grep that way and confirm the emitted SQL, not just the file list.

**The third variant is the worst, because delimiter-anchoring does not fix it: the token is complete and correctly spelled, but appears in a DIFFERENT SYNTACTIC ROLE than the one you are testing for.** A column name that is also a data-view column id, a wire key, or a constant will be in the bundle no matter what the code does with it, so its presence proves nothing about the migration you are verifying. On 2026-08-06 a frontend deploy meant to clear the roster-salary rename was "confirmed" by `grep -oh player_salary` over the deployed `dist/` returning 130 hits across ten chunks — with a positive control that passed. The claim was worthless: `player_salary` predates the migration as a data-view column id, which the bulletin tracking that deploy had explicitly warned about. **Anchor on the syntactic role, not on the token**: the migration moved Immutable reads, so the discriminating patterns are `get("player_salary")` and `get("player_salary",0)` (14 and 4 hits, the second being exactly the `notSetValue` form the source uses) against **zero** `get("value")`. Positive form present in the shapes the source actually has, negative form absent — that pair is the proof, and either half alone is not. Corollary: when a bulletin or task note tells you a specific verification is invalid, it is recording a trap someone already fell into; read it before choosing your oracle, not after.

As of 2026-05, the anchored count was **zero** and the join was genuinely unreachable: `group_tables_by_supported_row_axes` intersects the request `row_axes` against the column's `source.grain` identity, so a `player_year`-grain column never saw a `week` axis and its week branch could not execute. A plan had been written to fix a type error in that branch. **That is no longer true** — the keeptradecut restructure declared `supports_row_axes: ['year', 'week']`, which made the branch live and put the column into three goldens. The grep technique is the durable lesson here; the counts are dated.

**Never conclude a column is absent from a pattern-filtered `information_schema` query.** The same failure class as the grep note below, in the one place it reads as authoritative. On 2026-07-29 a session checked whether `projections` retained dated history with `information_schema.columns WHERE table_name='projections' AND column_name ~ 'time|date|year|week'`, got no timestamp back, and reported that no point-in-time projection history existed anywhere. The column is `generated_at`, which contains none of those four substrings. It is `NOT NULL` and part of the unique key, so the table had been appending 4.69M rows across 2,064 daily snapshots for two years. The wrong conclusion drove a design decision -- projections demoted to live-only, their benefit "asserted rather than measured" -- that had to be reversed. List a table's columns in full before concluding a capability is missing; a pattern filter is for reading convenience on a table you already know, never for proving a negative.

**Grep proves the absence of a string; only EXPLAIN proves the query is valid.** The golden-grep above is necessary but not sufficient, and on 2026-07-27 it missed a live defect twice. Correlated-subquery predicates are emitted as raw SQL against a generated CTE alias, so they appear _unquoted_ and _hash-named_ — `t22c9a76f62c8a62fec52ad076663a982.year IN (2024,2025)` — and match neither `nfl_plays\\".\\"<old>` nor any table-qualified pattern. A reviewer sweeping for `prop_markets_index.year` plus a fixed alias list that omitted `pmi.` likewise returned a confident zero on `pmi.year` in `update-market-settlement-status.mjs`, which had thrown 42703 on every game finalize for four days.

The gate that does work is now committed as **`db/gates/check-data-view-sql-validity.mjs`**, and it must run per cluster on any grain-column rename:

`yarn check:cluster` runs it once the `:5433` container is up (`yarn test:db:up`).

It provisions its own database on the shared :5433 container (so it cannot collide with a sibling's suite run), loads `db/schema.postgres.sql`, generates SQL for all 551 data-view columns across the plain and `year_offset` range shapes, and `EXPLAIN`s each of the 1102 statements in about five seconds. Run ad hoc on 2026-07-27 it found six defects that 232 goldens and a fully green 2214-test suite did not; on its first committed run it found two more, both pre-existing (`player_pro_bowl_selections` naming a physical column that does not exist, and a `NaN` interpolated raw into the keeptradecut `year_offset` range SQL).

**Run it from a clean worktree at your HEAD, not from the shared tree — it reads the working tree, so a sibling's uncommitted edits are indistinguishable from your defects.** The script imports the column definitions live and loads `db/schema.postgres.sql` off disk, both from whatever is sitting in the checkout. So a sibling mid-cluster — emitter already renamed, DDL still `PENDING`, schema export not yet regenerated — makes the gate fail on _their_ transient inconsistency, reported against column names that have nothing to do with your change. On 2026-07-31 a schedule-route cluster ran the gate and got `GATE FAIL: 8` on `espn_team_win_rates_index.nfl_team does not exist`; HEAD had the correct `key_columns: { team: 'team' }` and the `nfl_team` was an uncommitted edit belonging to the live time-series-feeds session, staged ahead of its own `db/adhoc/2026-07-31-conform-espn-win-rates-feeds.sql`. The findings were real SQL failures and entirely not the running session's — and read as a pre-existing defect worth reporting. The tell is a finding on a table your cluster never touched; the check is `git status` plus `git show HEAD:<emitter>` against your tree. Get the honest number the same way you would for a build: `git worktree add ~/user-base/tmp/<name> HEAD`, symlink `node_modules`, run there, `git worktree remove`. It costs one command and the gate still provisions its own database, so it cannot collide.

**A bare import that is not in this repo's `package.json` still resolves — from user-base's ROOT `node_modules`, one level up — and no gate here catches it.** Node walks parent directories, so a package absent from `repository/active/league/node_modules` is found at `/Users/<you>/user-base/node_modules` and everything looks fine from the real checkout. It breaks only where that ancestor is missing: a worktree under `/tmp`, a CI checkout, a production host. `league-import/espn.mjs` imported `node-fetch` this way until 2026-07-31, and a `/tmp` worktree therefore killed the **whole suite at load** with `ERR_MODULE_NOT_FOUND` before a single test ran — while the SQL-validity gate and individual golden specs still passed, because neither loads `test/importer-espn.spec.mjs`. So `/tmp` appeared to work right up until you asked for the number that mattered.

That import is gone (the file now uses Node's global `fetch`), and `node-fetch` was the only such package — every other unresolved bare specifier in the tree is a webpack alias or a Node builtin. A worktree at `/tmp` runs the full suite green today. The recipes above still say `~/user-base/tmp/` because it costs nothing and keeps the scratch under one root; that is preference now, not a constraint. What is worth keeping is the check: **before adding an import, confirm the package is in this repo's `package.json`** — a parent-resolved dependency produces no error, no lint failure, and no gate finding on the machine you develop on.

**Read its findings by reachability, not by how broken the SQL looks.** Every finding carries a tier — `system_view` (ships in a default view, so it is on a page-load path), `saved_view`, `golden`, `catalog_only` — and the report sorts by it. Ranking the 2026-07-27 findings by severity alone inverted the call: a dormant seasonal path was ranked BLOCKER above `GET /api/markets/players/:pid`, which had been returning 500 on every call for a year. A `catalog_only` failure still fails the gate; the tier orders triage, it does not excuse anything. Feed the `saved_view` tier from production with `--saved-view-columns` (see `check-saved-view-param-coverage.mjs --column-ids`).

To validate a single golden by hand, extract its `expected_query` and run `EXPLAIN` against the container directly (`docker exec -u postgres -i league-test-pg psql -U league_test -d league_test`; the `postgres` and `league_writer` DB roles are GRANT targets and cannot log in, so `-U league_test` is the only usable login role).

**A renamed column PARAM silently drops the filter — sweep saved views at apply time, not authoring time.** `apply_play_by_play_column_params_to_query` iterates the param registry and skips any key it does not recognise, so a param renamed code-side leaves every saved view still persisting the old key with a filter that is quietly ignored: no error, no failed test, just a wrong answer. `db/gates/check-saved-view-param-coverage.mjs` finds them against production:

`yarn check:cluster` runs it against production when the tunnel is up.

The remedy for anything it reports is a rule in `libs-shared/data-views-saved-view-migration.mjs`, which rewrites persisted params at read time. A one-shot SQL migration written when the rename is AUTHORED cannot cover a view saved between that check and cutover — which is precisely the hole the 2026-07-24 plays/snaps saved-view migration left. This check found 196 orphaned occurrences across 13 saved views from a 2025-07-24 rename that shipped with no saved-view migration at all.

**That rule runs CLIENT-side, so the fix is not live for users until a FRONTEND deploy — a backend deploy changes nothing.** `run_migrations` is reached only from `app/core/data-views/sagas.js` (via `libs-shared/data-view-storage/storage.mjs`), so the rewrite happens in the browser before the request is sent. `yarn deploy` ships the module to the hosts and no user is helped. Sequence `yarn build && yarn deploy:dist && yarn deploy:sourcemaps`, and confirm the map reached the bundle by grepping the deployed directory on the host for a legacy KEY that exists nowhere else (`ssh league "cd /root/league/dist && grep -oh 'avsk:.\{0,22\}' *.js"`), with a positive control. One upside of the client-side placement: the migrated request carries the new keys, so it hashes to a fresh redis key and no cache purge is needed. Confirmed 2026-08-05 fixing the 18 shorthand param renames (`038e45768`).

**Two traps in the coverage check itself, both of which make a CORRECT fix look broken.** Its recognition test is a presence-grep whose tokenizer requires three characters or more, so a two-character legacy key (`wp`, `cp`, `ep`, `db`) could never match and reported as an orphan with a correct rule in place; it now imports `MIGRATED_PARAM_KEYS` from the migration module and recognises migrated keys exactly. And a param whose key doubles as its column may legitimately KEEP its key while its column moves — resolution is `column_name || param_key` and saved views persist the key — so `dot` is still a live registry key even though its column is now `depth_of_target`. Adding a rename rule for that shape CREATES an orphan rather than fixing one; check the registry before writing a rule.

**A third trap ran the other way and was far worse: until 2026-08-05 the check tokenized COMMENTS, so prose naming a legacy key marked it recognised and the gate could not report it at all.** The two traps above make a correct fix look broken, which is loud. This one made a broken state look fixed. The presence-grep cannot distinguish a consumer from prose ABOUT a consumer, and the prose that names a legacy key is by construction written in exactly the files it scans — so the migration module's own incident note (`across 45 saved views (qtr 25, dot 7, route 7, dwn 5, wp 5)`) plus an aside in `player-fantasy-points-from-plays-column-definitions.mjs` between them made `qtr`, `dot`, `route` and `dwn` permanently unreportable. The comment documenting the incident is what blinded the gate to the incident. Verified by deleting the `qtr` rule and re-running: still `GATE OK`, over 289 occurrences across 25 saved views. Comments are now stripped before tokenizing, which costs nothing legitimate because a legacy key requires a rule and `MIGRATED_PARAM_KEYS` recognises those exactly.

**So never accept a green from this check without a negative control.** Delete one live rename rule, re-run, confirm it reports, and put the rule back — it takes two minutes and it is the only thing that distinguishes "no orphans" from "cannot see orphans". That is the same positive-control discipline this file already requires of any sweep whose zero would let you skip work, and this gate had gone un-controlled since it was written.

**`await` on a knex QueryBuilder EXECUTES it, so an async helper that returns one hands you rows and every SQL-shape assertion silently passes over an array.** A builder is a thenable, so `const q = await build_query()` resolves the builder itself rather than returning it, and `q.toString()` is then `'[object Object]'` (or `'[object Object],[object Object]'` for a result set). Assertions written as `expect(sql).to.include(...)` fail with a message about `[object Object]` that reads like a broken expectation rather than a broken harness; assertions written as `expect(sql).to.not.include(...)` **pass vacuously**, which is the dangerous half. This cost two separate detours on 2026-08-05 — first in a new builder spec, then again in an ad-hoc verification script where it produced `per-game stage emitted: false` for a feature that was working correctly and nearly sent the session to debug the emitter. Have the helper return the builder inside a wrapper (`return { query: build_period_cte(...) }`) or make it synchronous; a helper whose only async work is resolving inputs should resolve them first and return the builder plainly.

**A verifier that reads a GENERATED file is only as current as the last generation — its OK is vacuous until you regenerate.** `scripts/verify-named-format-catalog.mjs` iterates `libs-shared/named-format-catalog.mjs`, which is written by `yarn generate:formats`. On 2026-08-05 that file was eight weeks stale, so a newly added named format was absent from it entirely and the verifier reported `OK` while asserting nothing whatsoever about the new format. Regenerating first turned the same command into two real errors. This is the same family as the negative-grep and `skip_query_match` traps above, with the staleness living in an input artifact rather than in a pattern: before trusting a green from any generated-input gate, confirm the thing you are verifying actually appears in the generated input (`grep -c <new-id> <generated-file>`), then run the negative control. Note the control itself can be vacuous for a third reason — prettier reformatting can break a mutation pattern, so a `perl -0pi` control that reports "no failure" may never have applied; verify the mutation landed before reading its result.

**`apply_scope_to_query` resolves physical column names by table name; do not hardcode them.** `libs-server/data-views/physical-season-columns.mjs` maps physical tables to their conformed `season_year` / `season_type` columns, and `apply_scope_to_query` consults it by default, so an emitter that simply omits `year_column` gets the right name instead of the vocabulary `year`. Any cluster that conforms a physical table an emitter targets must register it there — `test/libs-server.physical-season-columns.spec.mjs` scans `libs-server` for `apply_scope_to_query` call sites and fails the suite when a table one of them names carries `season_year` but is absent from the map. Note the criterion is that an emitter targets the table, not that the table carries the column: 70 base tables carry `season_year` and only the handful an emitter names belong in the map. A call site passing a variable rather than a literal cannot be resolved statically, so those are pinned in a reviewed list and a new one fails until it is reviewed. Tables with no season-type column at all (`nfl_snaps`, the `nfl_plays_*` participant tables) are declared explicitly and throw rather than falling back, so a `seas_type` predicate against them is a loud error rather than a runtime 42703.

**A cluster is not done when its sweep lands — it is done when the sweep is DEPLOYED.** Every gate above examines the working tree or master; none of them can see what production is actually executing. So an applied DDL plus a correct, committed, undeployed consumer sweep leaves production running stale code against a conformed schema, and the whole suite stays green while it does. This is not hypothetical: on 2026-07-29 production was 20 commits behind with `practice` already conformed to `season_year`/`season_type` while the deployed `historical-injury-index-sql.mjs` still queried `practice.seas_type` — a 42703 waiting on that script's next cron fire in early September. Treat the DDL apply and its consumer deploy as one unit, and before declaring a cluster complete check what production is on:

```bash
ssh league "cd /root/league && git rev-parse --short HEAD"           # against origin/master
ssh digitalocean-0 "cd /root/league && git rev-parse --short HEAD"   # odds/plays import workers
ssh base-storage "cd /home/user/league && git rev-parse --short HEAD" # seasonal Underdog ADP ingest
```

**Check all THREE checkouts — `base-storage` is the one that bites.** It is a functional code checkout running a production importer, and no deploy step touches it: it is outside the `yarn deploy` fan-out entirely. **It is no longer unattended, though — since 2026-07-29 it fast-forwards itself hourly at `:40` (`~/bin/update-league-checkout`, logged to `/var/log/league/update-league-checkout.log`) and again immediately before the seasonal ADP import.** So a nonzero behind-count here is expected to self-clear within the hour, and the thing to check is whether the currency job is still RUNNING — read that log rather than treating any drift you observe as a manual remediation. Confirmed working 2026-08-07: a checkout 6 commits behind converged on its own 12 minutes later. **Do not read the "238 commits behind" below as a current figure** — it is the pre-automation incident, and quoting it as live state is a mistake that has already been made once.

On 2026-07-29 it was 238 commits behind: its `find_player_row` still named `player.formatted` after the rename to `formatted_name`, so every player lookup threw. Because the Underdog best-ball ADP importer catches per-player lookup failures and counts them as unmatched, the run produced zero inserts, exited 0, and reported success **daily for three weeks** while writing nothing — the rename's blast radius reached a host the sweep never considered, and the exit-code oracle could not see it. A rename sweep that checks only `league` is not complete. See [[user:task/league/keep-base-storage-league-checkout-current.md]].

Note the cron schedules make this class of defect latent until the season starts (`0 9 * 1,2,9-12 2` for the injury index), which is the same shape as the prop-settlement 42703 — offseason silence is not evidence that a sweep landed.

**"A deploy can lag safely" is true only for BACKEND consumers. Rename a column the SPA reads and the deploy lag is a live user-facing outage, while every server-side oracle stays green.** The API does not break: routes here `SELECT *`, so the response simply carries the new key and `/api/status` keeps answering 200. The browser breaks, because the deployed bundle still reads the old key. On 2026-08-05 the boolean-prefix sweep renamed `leagues.hosted` to `is_hosted`, and between the apply and the frontend deploy a logged-in user lost Auction, Draft, Matchups, Schedule, Standings, Stats, Transactions, Waivers, Restricted Free Agency, Trade Review and the whole team section — the menu gates on `Boolean(league.hosted)` (`app/views/components/menu/menu.js`). The blast radius runs well past the menu because an Immutable `Record` drops the undeclared key at the reducer boundary, so `app.js`'s auction banner, `league-team`'s summary panel, `trade-action` and `editable-league` (both of which then treat the league as external) and every roster action surface degraded together — the same silent absent-key family documented above.

So for any rename touching a column the SPA reads, **the frontend deploy is part of the apply, not a follow-up**: sequence `yarn build && yarn deploy:dist && yarn deploy:sourcemaps` immediately behind the DDL rather than at the end of the cluster, and treat a 200 from the API as no evidence whatsoever. The cheap check for whether you are in this case is to grep `app/` for the old bare name before applying — if the SPA names it at all, the window is user-visible. Note this inverts the usual priority: the commit is what must not lag for backend consumers, but for SPA-visible columns the _deploy_ is the urgent half.

**`db/gates/check-api-response-shapes.mjs` is the gate for that class, and it is the first thing here that reads the swagger response schemas at all.** `api/swagger` declares response schemas across 53 route files and nothing validated a response against them, which is exactly why the `leagues.hosted` window above was invisible server-side and why the season_grain wire question had to be settled by reading routes by hand. Two halves, wired differently on purpose. GATE 1 compares the spec to ITSELF — every `required` name and every `$ref` must resolve against the schema's own resolved properties. It needs no database and no base ref, cannot go red on a sibling's in-flight migration, and cannot produce a false positive. GATE 2 compares the spec to the SCHEMA FILE, for handlers that echo a wholesale single-table read to `res.send`: there the response key set IS the table's column set, so a documented non-column is a field that is never emitted. Run both per cluster; it takes about a second and needs no container.

`yarn check:cluster` runs both gates. `node db/gates/check-api-response-shapes.mjs --gate 1` is the spec-only form, safe anywhere and the one to reach for from a dirty tree.

**Its ORACLE choice is the load-bearing decision, and the intuitive answer is the wrong one.** Executing each route against the test container and validating the body sounds stronger. It is weaker: in a fresh test database nearly every list route answers `[]`, which validates vacuously against `type: array`, so an executed gate runs green across the whole surface while structurally unable to see a renamed column — the failure this file already records three times. Its power would be bounded by fixture coverage rather than by the spec. For the wholesale-read shape, `db/schema.postgres.sql` states the key set completely, so the static comparison is a COMPLETE oracle for those routes and strictly better than execution. What static analysis cannot do is the rest of the surface, which is why the run always prints the denominator.

**Read the coverage line before the findings — gate 2 reaches 5 of 109 operations, and that is the honest number.** The other 104 have a response the analysis cannot determine: an explicit projection, a join, or a `res.send(rows.map(...))` that builds a new object per row. The run lists every uncovered operation with its reason, because a gate over part of a surface that READS as full coverage is worse than no gate. Two things keep that number honest rather than decaying. The chain analysis is an ALLOWLIST of shape-preserving knex methods, not a denylist of projecting ones — the first draft was a denylist, `map` was not on it, and the gate reported five confident findings against a route whose response carries none of that table's columns; with an allowlist an unrecognised method makes a route uncovered, which is the safe direction. And the NEGATIVE CONTROL runs on every invocation rather than behind a flag: three mutations, each asserted to be reported, and a control that stays green fails the run.

**That control is also what detects the gate going blind, which is why there is deliberately no coverage-floor constant.** The gate-2 control needs a covered route to mutate, so if the handler analysis ever stops finding any, it reports STAYED GREEN and the run exits 1 — the catastrophic case is already covered by a mechanism that has to work anyway. A hand-maintained minimum would add nothing there and would fire on the ordinary case instead: giving a covered route an explicit projection is a perfectly good change that drops coverage by one, and the only remedy would be editing a magic number, which is the ritual `--rebaseline` teaches you to distrust. The same reasoning removed an adjudications file: under the allowlist a covered route's response IS the table's columns, so a documented non-column is a defect by construction and an exception file would have been a hook for a case that cannot arise.

It found the two known stale-doc defects unaided plus three the season_grain cluster had not identified — `Transaction` documenting five non-columns, `PlacedWager` documenting `id`/`status` where the columns are `wager_id`/`wager_status`, and `api/routes/leagues/settings.mjs` referencing a `#/components/responses/Unauthorized` that does not exist. All are repaired (`948e6e5d8`, `e5fe62bd0`) and the gate is green. It also surfaced one finding that was NOT a docs defect: `api/routes/wagers.mjs` filtered `whereIn('status', wager_status)` against `placed_wagers`, which has no `status` column — a live 42703 that `check-renamed-column-consumers` gate 1 could not see, because that gate resolves `'table.column'` literals and this was a bare `'status'`. **That one is now FIXED** in `2f0ca9a0f`, deployed 2026-08-06. The bare-literal blind spot it exposed in gate 1 is **now covered** by `check-knex-column-resolution`'s bare-string half (`6a6521858`), whose first run on master found a live 42703 of exactly this shape: `scripts/validate-charting-import.mjs` called `.whereNotNull('sumer_id')` on `db('player')` where the column is `sumer_player_id`, fixed in the same commit.

**A caution about that fix line, which read `23e73d14b` here until 2026-08-06: it credited a commit that never touched the predicate.** `23e73d14b` edited `api/routes/wagers.mjs` in the same window — it moved `placed_at` onto a `Date` for the timestamptz retype — and `git show 23e73d14b:api/routes/wagers.mjs` still carries `whereIn('status', wager_status)` at line 350. So the file recorded a live 42703 as repaired for as long as the wrong hash stood, which is the same shape as the named-but-absent spec above: every signal says covered except the one that counts. **Verify a fix attribution by reading the commit's diff for the specific line, not by trusting that a commit touching the right file in the right window is the right commit.** One command settles it: `git show <hash> -- <file> | grep <predicate>`.

**The same route held a second defect no name-resolution gate could ever have found: `.where('public', true)` against `placed_wagers.public`, which is a `smallint`.** The column exists, so gate 1, the proposed bare-predicate gate, and any `information_schema` sweep all resolve it happily — it is the bound VALUE that is wrong, and pg rejects it at execution with `invalid input syntax for type smallint: "true"`. That broke every authenticated caller viewing another user's wagers, alongside the 42703 that broke every `wager_status` filter. Two rules. When a rename sweep or a schema conform passes over a route, check the bound value's type against the column's, not just the column's existence — a `smallint` flag read as a boolean is the common shape here, since several older tables spell booleans that way. And note the whole class is invisible to static analysis: only executing the predicate against a real schema distinguishes it, which is why the spec for this route seeds rows and runs the round trip rather than asserting on the query builder.

**Why it survived: this handler catches and returns 400, not 500.** `catch (error) { res.status(400).send({ error: error.message }) }` turns a server-side schema failure into what reads as caller error, so neither the status code nor any error-rate alarm distinguishes "you sent a bad filter" from "this route cannot execute its own query". A route whose catch-all maps every exception to 4xx has no observable for its own breakage; prefer 500 for anything the caller could not have caused, and treat a 400 carrying a Postgres error string as a server defect wearing a client's status code.

**Two swagger traps the gate cannot remove, both of which make a CORRECT-looking repair wrong.** First, **a schema can be defined TWICE under one name and swagger-jsdoc merges the definitions silently** — once in `api/swagger/config.mjs` and again in a route's `@swagger` JSDoc block. `WaiverClaim` and `Transaction` were both in that state until 2026-08-05. So a property the merged spec carries may live in a file you are not reading, and a finding can name a key you cannot find where you are looking. Collapse to one definition rather than editing whichever copy you found.

Second, and more expensive: **a component schema shared by two operations means a documented non-column may be a real emission by the OTHER route.** `WaiverClaim` was the 200 of both `GET /waivers/report` (a wholesale read, so gate-2-covered) and `POST /waivers` (uncovered — it sends the inserted row plus `data.release`, which lives in `waiver_releases`). Acting on the finding, a repair deleted `release`, leaving `POST /waivers` documented as not emitting a field it does emit and contradicting its own 200 example — with no gate able to see it, since that route is uncovered. The remedy is to SPLIT the schema (`SubmittedWaiverClaim`, and `Transaction` / `TransactionWithDraft` before it), never to delete the property from a shape two routes share. Gate 2 now names the sharing operations on every such finding, but the check it cannot do for you is reading what the other route actually sends.

**Not in CI, and gate 2 should stay out.** It reads the working tree's schema file, so a sibling mid-cluster turns it red on findings that are not yours — run it from a clean worktree at your HEAD, exactly as for `check-data-view-sql-validity`. Gate 1 is genuinely CI-eligible now that it is green: spec-only, about a second, no database, and structurally unable to go red on someone else's migration, which is the same reasoning that put gate 1 of `check-renamed-column-consumers` in CI and kept its gate 2 out. `--gate 1` runs only gate 1's controls for exactly that reason.

When a rename does turn up a bad golden: **fix the code first, regenerate second, EXPLAIN third.** Regenerating first only re-blesses the defect. And declare `key_columns: { pid, year }` on any data-view source whose CTE projects `season_year` — `param-utils.mjs` silently defaults `year_column` to `'year'` when a source omits it, which is a rename that no grep of the source tree will ever surface.

Before regenerating, prove the golden is the thing that is wrong. A golden that disagrees with your change may be encoding semantics you just broke: on 2026-07-27 a `.year BETWEEN` predicate that was invalid without a year split turned out to be **valid and load-bearing** with one (the CTE projects `season_year as year` only when a year row axis is present), and the golden that failed was the only signal. The fix was to guard the predicate on `year_reference`, not to regenerate. Confirm the delta is exactly what you intended by reversing your change on the generated string and checking it reproduces the old golden byte for byte.

**String-level reversal only works for a change that SUBSTITUTES text — for one that adds structure, reverse the code instead, in a worktree at HEAD.** A change that appends a UNION arm, a CTE, or a join cannot be undone by deleting the matching text: on 2026-07-30 two new role-union arms were stripped by splitting the generated SQL on `union all` and dropping the arms naming the new roles, which also deleted the trailing `) as "role_union" inner join "nfl_games" ...` that belonged to the last arm, and the "reversal" then differed from the golden at char 0 on several fixtures. The rig looked like it had found a problem when it had only mangled the SQL. The reliable form costs one command: `git worktree add ~/user-base/tmp/<name> HEAD`, symlink `node_modules`, run the golden spec there against its own database, and confirm it is **fully green**. That proves the committed goldens encode current-master behaviour, so every failure in your tree is your change alone — which is the claim you actually need before regenerating, and it holds no matter what shape your change takes. Pair it with reading the first divergence point of each failing golden to confirm the inserted text is only what you added.

**A golden that embeds a clock-derived value must be a template, not a literal.** `expected_query` is run through `libs-server/process-expected-query.mjs`, which evaluates it as a template literal with `current_season`, `constants`, `all_years`, `last_3_years`, and `next_week` in scope (`next_week` mirrors the `next_week_opponent_total` branch of `get-data-view-results.mjs`). Any golden containing `${` is also skipped by the regeneration script, so templating is what protects a fixture from being re-blessed. `pff-team-grades-next-week-opponent.json` was a literal `"week" = 0` until 2026-07-28, when the date rolled over, the derived week moved to 1, and the golden broke on master with no code change; it is now `"week" = ${next_week.week}`.

**`scripts/update-data-view-snapshots.mjs` rewrites every fixture that currently mismatches unless you name the ones you want.** Pass filenames (`node scripts/update-data-view-snapshots.mjs some-fixture.json`) — unfiltered, it will also bless unrelated drift from a sibling session's uncommitted edits in this shared tree. Always `git status -- test/data-view-queries/` after regenerating and revert anything you did not intend to touch. The script runs outside `test/global.mjs` and so has no clock mock of its own; both it and the suite honor `LEAGUE_MOCK_DATE`, which pins the clock for a regeneration or a verification run.

**It DOES connect to the database for some fixtures, and without the connection env it silently regenerates only part of the corpus.** The script is widely described as pure `.toString()` on the query builder — true for most fixtures, false for the ones whose emitter resolves a format through `#db`. Run bare on 2026-08-05 it wrote 11 fixtures and printed `error <name>: role "league_test" does not exist` for 10 more, then reported a normal-looking summary line; re-run with `LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 LEAGUE_DB_DATABASE=<your-db>` it wrote 20. The per-fixture errors scroll past above a summary that reads like success, so a rename sweep can regenerate "all" the goldens and leave half of them stale. Always pass the DB env, and check the updated count against `git status -- test/data-view-queries/`.

**Regenerating goldens cannot fix a fixture's `setup` SQL — those are hand-edited.** Result-equivalence fixtures carry raw statements like `INSERT INTO nfl_games (esbid, season_year, week, season_type, v, h) VALUES (...)` in their setup block. `update-data-view-snapshots.mjs` only rewrites `expected_query`, so a rename sweep that regenerates every affected golden still leaves the setup SQL on old column names, and the fixture then fails at seed time rather than at compare time. The 2026-07-29 `nfl_games` conform hit exactly this in 9 fixtures. After any rename, `grep -rn "INSERT INTO <table>" test/data-view-queries/` as a separate step.

**Grep the goldens for the BARE quoted projection, not just the table-qualified form.** The emitters produce both shapes, and a sweep keyed to one silently misses the other. The documented pattern `nfl_games\".\"<old>` finds table-qualified references, but CTE builders like `rate-type-per-game.mjs` project `"h" as "team"` with no table prefix — so 7 affected goldens looked clean under the table-qualified grep and were caught only when the suite failed on them. Sweep both: `\\"<old>\\" as \\"` as well as `<table>\\".\\"<old>`.

**Verify a clock-derived golden across a week boundary, not just against today.** Regenerating until green only re-blesses whatever the clock says now. Run the suite at several mocked instants spanning PRE/REG/POST — e.g. `LEAGUE_MOCK_DATE=2026-09-22T12:00:00Z LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 TZ=America/New_York NODE_ENV=test TEST=all node_modules/.bin/mocha --exit --require test/global.mjs --reporter min test/libs-server.data-view-queries.mjs`.

Format identities (`league_scoring_formats.id`, `league_formats.id`) are opaque -- snake_case slugs for the named catalog, `gen_random_uuid()` for the long tail. Never reintroduce a content-derived hash as an identifier -- see `user:guideline/schema/avoid-content-derived-identity.md`.

**The two tables now dedup differently, and the scoring one is the exception.** `league_formats` still uses a `UNIQUE` index across its full config tuple, so adding a roster metric there is a normal additive `ALTER TABLE ADD COLUMN` plus an index rebuild. `league_scoring_formats` cannot: its tuple reached 44 columns when kicking and DST scoring became configurable on 2026-08-04, against a Postgres `max_index_keys` of 32, so the full-tuple index is no longer buildable at all. Dedup there is `config_digest`, a `GENERATED ALWAYS AS (md5(...)) STORED` column with a unique index on it alone, and the upsert's conflict target is `ON CONFLICT (config_digest)`. `id` is untouched and nothing references the digest, which is what keeps this outside the guideline's prohibition.

**`libs-shared/scoring-columns.mjs` is the single source for what a format can score, and adding a scoring column means adding a registry entry — not editing five lists.** It replaced four enumerations that had to agree by hand: `base_fantasy_stats` / `kicker_fantasy_stats` / `defense_fantasy_stats` in `constants/stats-constants.mjs`, `SCORING_COLUMNS` in `find-or-create-format.mjs`, the unique tuple, and `scoring_field_labels`. All of those now derive from it, `calculate-points.mjs` loops it, and `test/libs-shared.scoring-registries.spec.mjs` asserts it against the exported schema in both directions — including that every registry column appears in the digest expression, since an omission there silently merges two distinct formats onto one id with no error anywhere.

Three things about the registry that are not obvious from reading it. The three stat lists are **derived, not deleted**: they feed `all_fantasy_stats`, which `format_base_gamelog` uses to filter which columns are persisted to `player_gamelogs`, so an entry losing its `stat` silently stops that column being written. An entry may carry a `stat` with no `column` (`field_goals_made` is deliberately never scored -- it is the total the five distance bands partition, and scoring both double-counts) or a `column` with no `stat` (the two DST thresholds parameterise a rate rather than reporting a value, so they must stay out of `all_fantasy_stats`). And **`default_value` is load-bearing in two places, not documentation**: `find-or-create-format.mjs` fills an absent config key from it rather than writing `null`, and `calculate-points.mjs` falls back to it when a `league` object does not carry the column. Both exist because every new column is `NOT NULL` and many callers hold a partial config -- the named format definitions declare only the base columns, and the external-league mapper structurally cannot carry kicking or DST keys. Drop either fallback and the failure is silent in opposite directions: an explicit NULL on write (an explicit NULL does NOT fall back to the column DEFAULT), and every kicking and DST stat scoring zero on read.

**Kicking scores PER-YARD at 0.1 in production, not in 3/3/3/4/5 distance bands.** The old code branched on `if (stats.field_goal_yards)` and the band arm was unreachable whenever that stat was populated, which it always is -- 2025 REG kickers: 453 gamelogs with band counts, all 453 also with field goal yards, ZERO with bands alone. The backfill therefore sets the per-yard rate to 0.1 and every band to 0, and "correcting" it to the bands would silently cut every kicker's score. Scoring is now additive (bands plus the per-yard term) so a banded league sets the bands and zeroes the rate. `test/libs-shared.scoring-format-equivalence.spec.mjs` checks all 65 production formats against a fixed stat-line corpus and is mutation-checked.

**Before sourcing a from-plays role off an `nfl_plays` pid column, MEASURE that column against production — it has been effectively empty three times out of three, and the role passes every gate while returning nothing.** The pid column is the obvious source and the cheap one, so the instinct is to reach for it and move on. But the join is valid, the SQL EXPLAINs, the suite is green, the goldens regenerate, and the column simply produces no rows: return touchdowns resolved 4 of 732 valid stat rows, two-point conversions 2 of 2,221, field goals 0 of 931 and extra points 2 of 1,210. Two of the three read as obviously fine beforehand — a two-point conversion IS a rush or a pass, and a field goal obviously has a kicker — which is exactly why reading the schema is not a substitute for counting. The measurement is one query:

```sql
SELECT ps.stat_id, count(*) AS valid_stat_rows, count(p.<pid_column>) AS rows_with_pid
FROM nfl_play_stats ps
JOIN nfl_plays p ON p.esbid = ps.esbid AND p.play_id = ps.play_id
WHERE ps.is_valid = true AND ps.stat_id IN (<ids>)
  AND p.season_year = 2025 AND p.season_type = 'REG'
GROUP BY 1 ORDER BY 1
```

Scope it on `nfl_plays` rather than joining `nfl_games` — the games join times out through `base db query`. When `rows_with_pid` is near zero, the role has to take the `nfl_play_stats` attribution shape plus the EXISTS gate widening, which is what `libs-server/data-views/nfl-play-stats-attribution.mjs` exists for; its header carries the per-role evidence.

**A registry-driven scoring path and a hand-written one must have their COVERAGE compared by a spec, because nothing else can see the gap.** `calculate-points.mjs` scores every column in `libs-shared/scoring-columns.mjs` by construction — it loops the registry — while the from-plays path hand-writes each term into a generator. So a column nobody remembered to add scores correctly on one path and silently ZERO on the other, with no error, no failing golden and no red gate. `passing_completions` was in that state for as long as the from-plays path has existed: 2 of the 65 production formats score it at 0.50 and 0.20, so a 350-completion quarterback was under-reported by up to 175 points a season. It was found by writing a spec, not by any gate. `test/libs-server.fantasy-points-path-parity.spec.mjs` is the shape to copy — assert the coverage MAP rather than an executed residual (the suite's seeded database has no real season, so a residual measures the fixtures), require every gap to be declared with a reason, and carry a positive control so a matcher that stops matching cannot report perfect parity over a path scoring nothing.

**That spec no longer reads source text — it IMPORTS `from_plays_scored_columns`, which the scoring module derives from its two role tables.** So a column is covered exactly when a term or a role names it, and moving code cannot change the map. What that replaced is worth keeping in mind whenever a gate is built on matching rather than on data. The spec used to read two files by PATH and run three regexes over them, which coupled it to file layout in a way nothing declared: the import graph does not change, no module fails to resolve, and the matcher simply stops finding terms that still exist and still work. Extracting the generators into their own module (`815f092d6`) hit exactly that, and only the positive control made it visible. Worse, its broadest pattern was any single-quoted lowercase token, so any unrelated string could have counted as coverage — the same over-permissive tokenizer that made `check-saved-view-param-coverage` unable to report the orphans it existed to find, and the reason a matcher-based map needs a negative control that a derived one does not.

**Adding a scoring column to the from-plays path means adding a term to a role in `libs-server/data-views/fantasy-points-scoring-expressions.mjs`.** The three roles `nfl_plays` names with a pid column (passing, rushing, receiving) carry declarative `terms`; the seven `nfl_play_stats`-sourced roles carry a `scoring.columns` list. Terms have three `kind`s — `rate` (`<expr> * <value>`), `flat` (`<value>`, for a role whose join already restricts each row to one event), and `conditional` (a `CASE`) — plus an `always` flag for terms emitted even at 0. **Those exist to reproduce the previous hand-written output character for character, not as a general expression language**: the split between always-emitted and emitted-only-when-nonzero is what keeps 248 goldens from moving, so match an existing term's shape rather than inventing one. Read values as `scoring_format[column] || 0`, deliberately not through the registry's `default_value` fallback — a format row missing a column must keep emitting 0 here or existing SQL changes.

## Key Development Patterns

### ES Modules

- All server-side files use `.mjs` extension
- Import path aliases configured in `package.json` imports field:
  - `#config` → `./config.js`
  - `#db` → `./db/index.mjs`
  - `#libs-server` → `./libs-server/index.mjs`
  - `#libs-shared` → `./libs-shared/index.mjs`
  - `#constants` → `./libs-shared/constants/index.mjs`

### Configuration

- Environment-based config: `config.js` loads `config.{NODE_ENV}.js`
- Separate configs for development, production, test environments

### Code Style

- Prettier config: single quotes, no semicolons, no trailing commas
- ESLint: extends standard, camelcase off, curly off
- Components use functional patterns with hooks

### Scripts & Jobs

**Located in `/scripts/`:**

- Data imports: projections, odds, player data, NFL games/plays
- League processing: waivers, matchups, trades, roster operations
- Calculations: points, values, baselines, percentiles
- Maintenance: backups, auditing, cleanup

**Background jobs in `/jobs/`:**

- `finalize-week.mjs` - End-of-week processing (scheduled via crontab-worker-1.cron)
- `import-live-odds-worker.mjs` - Continuous odds import with per-bookmaker throttling (PM2)
- `import-live-plays-worker.mjs` - Continuous live play import with per-game finalization (PM2)
- `refresh-projection-cache-worker.mjs` - Rebuilds projection cache slices a commissioner's settings edit emptied (PM2, main host)

**`is_main` is FALSE under pm2, so every pm2-managed job needs `|| process.env.PM2_HOME` or it silently does nothing.** pm2 fork mode execs its own `ProcessContainerFork.js` and leaves `process.argv[1]` pointing at THAT, while `is_main` is a verbatim `===` against `fileURLToPath(import.meta.url)`. So `main()` never runs — and the process does not exit or crash, because importing `#db` builds a knex pool whose reap interval holds the event loop open. pm2 reports a healthy `online` process at steady RSS that has never executed a line of its own logic. `refresh-projection-cache-worker` shipped that way on 2026-08-09 and ran for hours; both live-import workers already carried the clause, which is the only reason they work. **The trap is that reading it from OUTSIDE confirms the wrong thing**: `/proc/<pid>/cmdline` shows `node /root/league/jobs/<worker>.mjs`, because pm2 rewrites the process title, and that is what made `is_main` look like it passed. Measure `process.argv` from INSIDE a pm2 child instead — a three-line probe started under pm2 settles it. The companion symptom is zero-byte pm2 logs, which reads as an observability gap and is not one; a control app started under pm2 on the same host writes its log files normally.

**Cron schedules in `/server/crontab-*.cron`** for different server roles

**`yarn deploy` does NOT update cron — the crontab is a separate deploy.** A code deploy ships the scripts but leaves the schedule and its ARGUMENTS untouched, so a script whose flags changed will keep running under the old ones with no error anywhere. On 2026-07-29 an external-league importer was deployed with new `--import_limit`/`--resync_limit` budgets while the installed crontab still passed a removed `--limit 250`; the job would have run weekly with stale arguments indefinitely. Ship both: `yarn deploy` then `server/deploy-crontab.sh league server/crontab-main`. Note the installed file is machine-built (`base crontab build`, which injects `JOB_SCHEDULE`/`JOB_SCHEDULE_TYPE`), so never hand-edit `~/crontab/*` on the host — and before deploying, diff the installed job lines against the source with the injection stripped, since the crontab directory is shared and carries every session's committed changes, not just yours.

**A league-host cron job has NO `scheduled-command` entity, so never address its signals to one.** The league host runs no `schedule-processor`, which makes a `scheduled-command` entity for one of these jobs inert — and since base's processor executes `enabled: true` entities, creating one for a job this crontab already runs invites a second concurrent execution. Two scripts nonetheless set `SIGNAL_SOURCE = 'user:scheduled-command/league/<name>.md'` against an entity that has never existed, so every signal they raised addressed nothing and triage had no entity to open; both are fixed as of 2026-08-04 (`process-projections.mjs` in `d2bca6f21`, `generate-dst-market-projections.mjs` in `d84b46073`). Pick the replacement shape by what actually invokes the script, and do NOT reach for `cron:` reflexively — naming a schedule that does not exist is its own defect. A job in `server/crontab-main/*.cron` takes the host-cron shape `cron:<job>@league`, matching the fleet's `cron:check-host-resources@database`. A script nothing schedules takes the emitter-named shape `script:<repo-relative-path>` (cf. the fleet's `script:scripts/import-3dep-dem.mjs`), which names the script rather than its scheduler and so stays correct if it is later put on a schedule — that is what the DST generator got, since it is committed deliberately unactivated and appears in no crontab. Either way the failure and success dedup keys both derive from `SIGNAL_SOURCE`, so they move together. The entities under `user:scheduled-command/league/` are a DIFFERENT population: jobs migrated OFF this host onto base's scheduler, carrying `working_directory: /Users/trashman/user-base`. Note that nothing validates a URI embedded in a code string — `base entity validate-references` does not reach it — which is why both defects survived so long.

**A fixed sleep between requests does not rate-limit anything.** It ADDS to network latency rather than bounding a rate, so the achieved rate depends entirely on which host runs the job — and the fast host is always the one that ships. Measured 2026-07-29 on the Sleeper importer with a fixed 120ms sleep: round trip was ~670ms from a workstation (~76 req/min) but ~43ms from the production VPS, which would have run the identical code at ~350 req/min, roughly 4x the vendor's conservative published figure. The workstation measurement looked reassuring and was pure artifact of a slow link, which is the real trap: it is easy to "verify" a throttle somewhere it will never run. Pace against elapsed time instead — hold a `next_request_at` timestamp and advance it from `max(now, next_request_at) + interval`, so the ceiling is deterministic on any host and a slow response cannot bank credit toward a later burst. See `scripts/import-sleeper-external-league-trades.mjs`.

**A timestamp populated on only ONE row of a group makes `Number(null)` → `0` read as "infinitely overdue" rather than as an error — give the group a row of its own.** `restricted_free_agency_bids.announced` was written onto the nominating team's own bid and only that bid, because the announcement is a property of the PLAYER's window and not of a bid row; every competing bid carried `announced = null` for its whole life. `process-restricted-free-agency-bids.mjs` read it per bid, so a competing bid's null coerced to epoch 0, landed roughly 41,000 windows in the past, and came due the instant it was submitted: league 1 processed its second 2026 nomination at 10:10 ET on 2026-08-02 instead of 16:00 ET, three minutes after the winning bid was placed, and cut a player off the winning team's cutlist to make room. Nothing threw, and the script's own shortfall oracle was blind to it in both directions because it filtered `whereNotNull('rfab.announced')` — excluding exactly the rows that were mis-firing.

The structural fix landed 2026-08-02: `restricted_free_agency_nominations` holds one row per `(league_id, player_id, season_year)` carrying `original_team_id`, `nominated_at`, `announced_at`, `processed_at` and `winning_bid_id`, and the bid columns that duplicated them are gone. Read window state through `libs-server/get-restricted-free-agency-nominations.mjs`; the null that could be misread no longer exists, because the field has exactly one home per auction. Note this also removed a live inconsistency the denormalized form had already produced: two of the 166 historical auctions carried disagreeing `player_tid` values across their own bids, from a player traded before the auction ran.

Three rules survive the fix. When a field is populated on one member of a group, resolve it through the GROUP key rather than off the row in hand — and prefer giving the group its own row over agreeing to read the field carefully. Refuse a falsy value explicitly (return `Infinity`) rather than letting it flow into date arithmetic, the same silent-`NaN` family as the `current_season` comparator trap above. And note the suite could not have caught this: `test/scripts.restricted-free-agency.spec.mjs` gave its competing bids an `announced` value they never carry in production, so the fixtures encoded the wrong shape. Fixtures now seed through `test/utils/insert-restricted-free-agency-bid.mjs`, which makes that shape unwritable rather than merely unwritten. When a live incident contradicts a green suite, check whether the fixture builds a row the writer never builds.

**The companion lesson is about the outcome column: never store a presentation string where a code belongs.** `restricted_free_agency_bids.reason` carried whatever English was in scope at settlement — two hardcoded sentences plus `error.message` — so the database's vocabulary was an accident of exception text, and 262 of 280 losing bids across five seasons read `player no longer a restricted free agent`, which is true of every ordinary loss and distinguishes none of them. It is now `outcome`, a closed set defined once in `libs-shared/constants/restricted-free-agency-constants.mjs` (`won` / `matched` / `outbid` / `lost_tiebreak` / `roster_limit_violation` / `player_ineligible` / `processing_error`), with `outcome_detail` carrying a message only for the error case and nothing branching on it. Failures attach their code at the throw site via `libs-server/restricted-free-agency-bid-error.mjs` so no caller matches on message text — a reworded throw would otherwise change the stored outcome silently. Historical rows were reclassified from each auction's resolved state, which recovers the distinction the text never recorded.

**A bare `.merge()` on an upsert asserts EVERY column the insert names, including ones another pipeline owns.** A generator that hardcodes a constant for such a column silently reverts the owner's writes on every run, and nothing fails — the row is simply wrong afterward. `generate-player-gamelogs.mjs` hardcodes `is_active: true` (correct for a player with counting stats) while `player_gamelogs.is_active` is owned by `import-nflverse-weekly-rosters.mjs`, which maps game-day roster status onto it (ACT -> true; INA / RES / DEV -> false). With a bare `.merge()` the UPDATE half reverted every game-day-inactive flag the run touched: regenerating one 2014 game flipped six. Fixed by merging every column except that one — `GAMELOG_COLUMNS_NOT_MERGED` — which keeps the insert value for a new row and leaves an existing one to its owner. (The column was `active` when this was written; the 2026 boolean-prefix conform renamed it to `is_active` in `6ac331d4c`.) Before adding a column to any upsert here, ask which script is the writer of record for it — the INSERT and the UPDATE halves of an upsert do not need the same column set, and for a foreign-owned column they must not have it.

**A second class of column belonged in the same hold-back, and the fix was to remove the cause rather than keep the hold-back: one that re-encodes a value with no controlled vocabulary.** `player_gamelogs.player_position` and `player_seasonlogs.player_position` both copy `player.primary_position`, and until 2026-08-04 none of the three had a canonical value set — `player.primary_position` held 43 distinct values, the gamelog column 39, with `OLB` and `LB`, `T`/`G`/`C` and `OL`, `SS`/`FS`/`CB` and `DB` all naming the same position under different importers' spellings. Merging therefore rewrote a stored value to a DIFFERENT SPELLING OF ITSELF, which reads as a correction in a diff and is churn: a 277-game backfill would have changed the position on 1,183 rows, including 111 `K`->`P` and 87 `P`->`K` flips in opposite directions on the same run. It is no longer held back. The vocabulary is now the 25 values in `libs-shared/constants/position-constants.mjs`, enforced by a `CHECK` constraint on every position column in the schema and by `normalize_position` throwing at each write site, so a merge can only write the value already stored. `is_active` remains held back, for the foreign-ownership reason above. (Both position columns were spelled `pos` when this was written; a later conform renamed them to `player_position`.) **The general rule survives its instance:** an uncontrolled vocabulary is a reason to control the vocabulary, not a reason to permanently except a column from its upsert.

**Validate a generator change against the PRIOR GENERATOR, not against production — these tables are upsert-only, so production carries rows no current input supports.** The instinct is to diff new output against the live table, and it conflates your change with every accumulated mis-attribution and every newer field nobody backfilled. Measured both ways over the same 277 games on 2026-08-04: prior-generator-vs-new was 21,634 unchanged / 291 changed / 0 added / 100 removed, and every delta was explainable; production-vs-new was 3,503 changed / 1,522 added / 8,240 removed on identical code, with the extra volume being stale `pos` spellings, un-backfilled `receiving_first_downs`, and gamelogs whose supporting play stats no longer resolve to that player. Extract the old file with `git show <commit>^:scripts/<script>.mjs`, import both, and diff their collectors. Then read the production diff separately, as the answer to "what will the write actually touch" — a different and equally necessary question. Note the corollary: a `removed` row in either diff is NOT removed from the database, because nothing here deletes; it just stops being regenerated.

**`player_gamelogs.nfl_team` cannot validate a writer that writes it — use `nfl_play_stats.nfl_team` as the oracle.** The stored team is produced by the code under test, so scoring against it measures the sum of your error and its own, and the second term dominates. Measured 2026-08-04 while replacing the snap-path team fallback: the candidate resolver scored **4.4% wrong against `player_gamelogs`** and **0.021% against `nfl_play_stats`** — nearly every disagreement was the stored value, not the resolver. Game `2016081153` is CAR @ BAL and carried gamelogs for TEN, SF and BUF; Rick Wagner, a Ravens tackle, was stored as CAR. `nfl_play_stats.nfl_team` is the feed's own statement of the PLAYER's team rather than the possession team — a defensive player's tackle rows carry his own side — so it is independent of `nfl_snaps`, of `player_gamelogs`, and of any gamelog writer. Two guards make it usable: drop any oracle row whose team is neither side of its own game (such a value is wrong on its face and cannot be ground truth), and remember it only exists for players who recorded a counting stat, which is exactly the population a snap-only gamelog is NOT in — so it validates the method without being able to repair the rows.

**Comparing `player_gamelogs.nfl_team` against `nfl_games.home_nfl_team`/`away_nfl_team` reports ~33,000 false positives unless BOTH sides go through `fixTeam`.** `nfl_games` keeps the abbreviation the franchise carried at the time (`SD`, `STL`, `OAK`) while `player_gamelogs` stores the conformed one (`LAC`, `LA`, `LV`), so every Chargers game before 2017 and every Rams game before 2016 looks like it has no team in common with its own gamelogs. The raw predicate returns 33,224 rows and reads as mass corruption; the normalized one returns 477, and the pre-2015 remainder is entirely relocation drift with no defect in it at all. The failure is worse than a wrong number because it is directionally convincing — the raw counts cluster in exactly the old seasons where you would expect legacy data problems. Normalize before counting, and treat "team is neither side of the game" as a genuinely useful corruption predicate only in its `fixTeam` form.

**`is_main` compares `process.argv[1]` VERBATIM against the resolved module path, so a script invoked by a relative path silently does nothing and exits 0.** Node sets `argv[1]` to the path as typed, not the resolved one, while `is_main` resolves its `import.meta.url` side — so `node db/adhoc/repair-something.mjs` never enters `main()`. It is not an error and prints nothing; it is indistinguishable from a run that had no work to do. The `scripts/` convention survives this only because cron and the SSH wrappers invoke absolute paths. Everything under `db/` — `adhoc`, `gates`, `tools`, `archive` — is run by hand from a relative path, which is why those files call `main()` bare (`db/gates/check-schema-conformance-ratchet.mjs`, `db/gates/check-data-view-sql-validity.mjs`) — follow that, and treat a one-shot data repair that produced no output as unproven rather than as a no-op. Related: give such a script `console.log`, not `debug` — the ESM import graph clobbers the namespace set before a module-scope `debug.enable` runs, and a repair that writes thousands of rows while printing nothing has destroyed its own audit trail.

**A cross-table invariant is only real if the producer writes both tables in ONE transaction — and every writer here autocommits statement by statement.** A consumer that treats "row A implies row B" as impossible will throw the moment it reads between a producer's two writes, and the evidence is gone by the time anyone looks: both rows are present and correct, so the error message describes a state that no longer exists and reads as data corruption rather than a race. On 2026-08-02 `calculate-team-daily-ktc-value` died on `no restricted free agency signing found for HOU__2026-08-02` because `process-restricted-free-agency-bid.mjs` inserted the RFA tag transaction while its CALLER marked the bid `succ` in a separate statement afterwards. Note this was not luck: a 17:00 ET announcement plus `restricted_free_agency_window_hours=12` minus `restricted_free_agency_processing_lead_hours=1` puts the processing deadline at 04:00 ET, which is the exact minute the valuation job's cron fires, so the two collided on every announcement in that window. Fixed by committing the transaction insert and the bid marking together (`db.transaction`), which the consumer's read ORDER then makes sufficient — it reads `transactions` first, so a visible tag guarantees a visible signing; reversing those two reads would reopen the hole with the producer still atomic. Two rules: when a consumer asserts a cross-table invariant, verify the producer commits both sides atomically before trusting the assertion, and when splitting a success outcome across statements, guard the later one (`whereNull('processed')`) so a throw raised after the commit cannot roll the record back to the broken state. The suite cannot see any of this — a serial test never interleaves — so the gate has to be a test that pins WHERE the write happens, not one that checks the end state.

**A knex `.select()` that omits a column the code later reads yields `undefined`, and an index lookup keyed on that `undefined` MISSES silently — so a whole code block can be dead for years without ever erroring.** This is the same absent-key/no-diagnostic family as the `mapDispatchToProps` and Immutable `Record` traps above, but on the server and far more expensive, because the symptom is not a wrong value in one field — it is an entire branch that never runs. The 2026-08-02 follow-on triage of the same `calculate-team-daily-ktc-value` incident found its `db('transactions').select('tid', 'pid', 'type', 'timestamp', 'year')` never selected `uid`, while the loop below keyed the trade lookup on `trades_index[transaction.uid]`. Every lookup was `trades_index[undefined]`, so the trade-application block had never executed. Trade transactions are type `TRADE`, which the roster switch ignores, so that block was the _only_ thing moving a traded player: 349 players across 196 accepted trades had never changed teams, and fixing the one-word select changed 11,614 of the table's 12,346 rows (mean absolute 12,565, max 104,325). Nothing failed for years — the map lookup returned `undefined`, the `if (trade && ...)` guard read it as "not part of a trade", and the script exited 0 every night. Two rules. When a query feeds an index lookup, check that the key column is in the `.select()` list, since a missing one is indistinguishable from a legitimate miss at the call site. And prefer an explicit throw over a truthiness guard on a lookup that is supposed to hit — `if (trade && !processed[trade.uid])` cannot tell "this transaction is not a trade" from "I never selected the key", which is exactly what let this survive.

**The same replay had two more silent roster holes, and the pattern is general: a transaction type that MOVES a player but is absent from the switch leaves the roster permanently wrong, with the strays hidden inside `ignored_tran_types`.** `POACHED` was handled as an add to the poaching team while nothing removed the player from the team he was poached from, so he contributed his full value to a team that no longer held him for the rest of history. At the 2026-08-11 snapshot the replay carried **291 players against the 243 actually rostered**, 50 of the 54 strays having been poached, which moved a team's Article XXII deposit by up to $37 in a $2,000 pool. Fixed in `00fe563b3` as the one-roster-per-player invariant — remove the player from every roster before any add — rather than a `POACHED`-only removal, so a future add whose departure the log does not state cannot reopen it.

Two rules, and the second is the expensive one. **Reconcile the replay's roster against an independent point-in-time source rather than assuming it** — `roster_asset_holding` scoped with `period_start <= date AND (period_end IS NULL OR period_end > date)`, which is a different walker over the same log and disagrees where either is wrong. Scoping it to holdings open TODAY instead manufactures phantom disagreements for anyone who joined after the date, which reads exactly like a defect. And **fixing one half of a two-sided flow can activate a DORMANT bug in the other half**: `SUPER_PRIORITY`, the reclaim an original team makes once the poaching team releases the player, was equally unhandled and equally invisible — with the poach unapplied the player never left, so nothing had to bring him back. Shipping the poach fix alone would have silently deleted two players from their rosters (fixed together, `1d413e3f8`). Reconcile the full residual to zero before calling such a fix done; "54 strays down to 2" is not the same claim as "the rosters are right".

**A fraction column typed `numeric(p,p)` — scale equal to precision — cannot represent 1.0, and the ceiling is invisible until the day a single row reaches 100%.** All the digits sit after the decimal point, so `numeric(5,5)` spans only ±0.99999 and a legitimate `1.0` raises `numeric field overflow`, which aborts the entire `batch_insert` rather than the one row. `league_team_daily_values.ktc_share` was `numeric(5,5)` and survived only because league 1 has 12 teams and its maximum share was 0.52125; the moment the 2026-08-02 fix started emitting rows for zero-value teams, the 2020 league-inception day where one team held all the ranked value produced a share of exactly `1.00000` and would have killed the job on every run. Widened to `numeric(6,5)`, which keeps the five decimal places and adds the one integer digit. When adding any share/rate/percentage column, give it a precision strictly greater than its scale.

**A `--esbid`-style narrowing flag has to filter the collection the writes are derived FROM.** The same script's flag filtered only `unique_esbids`, which feeds the routes / dropbacks / snap loads, while every gamelog was built from an unfiltered `playStats` — so it wrote the whole week and logged one game. It also compared a numeric column against a yargs `type: 'string'` option, so the filter matched nothing and reduced the auxiliary loads to zero games while the full-week write proceeded regardless. Two rules for a scoping flag on a backfill tool: filter the source collection, not a derived index, and throw when the scope selects nothing rather than falling through to the unscoped write.

**No future-week roster slice is ever served, so one that exists can only drift — and a `rosters.find(r => r.tid === tid)` over a week-DESC list silently picks it.** `get-league-rosters-from-database` returns every week of the year ordered `week` DESC, so a bare `find` on `tid` resolves to the HIGHEST week, never the one the client renders (`getRosterRecordByTeamId` clamps to `min(fantasy_season_week, finalWeek)`, as does every other consumer — the scoreboard and matchup selectors, `simulate-matchup`, and `load-team-starters`, which computes future lineups from the CURRENT roster pool rather than reading a future slice). On 2026-08-03 that attached a team's live restricted free agency bids to a week-1 slice nobody reads while the week-0 roster it renders charged the pre-bid salaries, so the bid dialog quoted a max bid of -$75 against a $200 cap — $52 under the truth, with no error anywhere, because `Roster` prices `bid ?? value` and the bids simply never arrived. The same family as the absent-key traps above: the `find` returns a real roster, just the wrong one.

The slice should not have existed at all. `generate-rosters` takes `current_season.week + 1`, and `current_season.week` reads **0 for the entire offseason**, so the forward slice is materialized the day the previous season ends and then freezes at whatever week 0 held that night. It is now held until Week 1 is within `FORWARD_SLICE_LEAD_DAYS` of `regular_season_start` (which is itself two Tuesdays before the opener), and the orphan-slice oracle reports any populated week beyond the one a run is responsible for. Two rules: qualify a roster lookup by week, never by `tid` alone; and when a job derives a target from `current_season.week`, check what that expression reads in the offseason before trusting it.

### Testing

- Mocha with Chai assertions
- Test files: `test/*.spec.mjs`
- Global setup in `test/global.mjs` drops all tables, loads schema, runs seeds
- MockDate for time-dependent tests
- Environment: `NODE_ENV=test`, timezone: `America/New_York`

**That timezone is the NODE process's — the test container's Postgres SESSION timezone is `Etc/UTC`, while production's is `America/New_York`.** Both were read live on 2026-07-31 (`SHOW timezone` against `:5433` and against `league_production`). So any SQL whose result depends on the session TZ evaluates differently in the suite than in production, and a fixture asserting the production behaviour cannot pass locally — it is not a bug in the fixture. The concrete case: `date_trunc('day', <date column>)` yields a timestamp WITHOUT time zone, which Postgres resolves against a `timestamptz` in the session TZ, so the keeptradecut year-split boundary lands on NY local midnight in production and on UTC midnight in the suite. This is invisible until a `timestamptz` is on the other side of the comparison, which is why the retype cluster surfaced it and years of integer-epoch columns did not. When a comparison's correctness depends on the session TZ, pin a TZ-agnostic property instead (that fixture asserts the boundary is the _unshifted_ start of the day, so a shift in either direction fails it) and record the session-TZ dependence as the real fragility — a `SET TIME ZONE` in the query, not in the fixture, is the only thing that removes it.

**The JS-side analogue: on a tz-aware dayjs object, `.add(n, 'day')` followed by `.hour(h)` silently shifts every result by an hour once the range crosses a DST transition.** The timezone plugin applies the UTC offset captured when the object was BUILT, so setting the hour after advancing across a transition resolves against the wrong offset. Nothing throws and the first few values are correct, which is what makes it ship: the 2026-08-01 restricted-free-agency windows computed 17:00 ET boundaries correctly through Oct 31 and 16:00 from Nov 1 onward, caught only because a spec asserted the wall-clock hour across the fall-back rather than just the spacing. The shape that works is to advance the calendar date in UTC (no DST, so pure day arithmetic) and then resolve the wall-clock time in the league timezone for that date — `dayjs.utc(anchor.format('YYYY-MM-DD')).add(days, 'day').format('YYYY-MM-DD')`, then `dayjs.tz` on the composed `"<date> <time>"` string — see `libs-shared/get-restricted-free-agency-window.mjs`. Any window/clock feature doing local-hour arithmetic (draft windows, RFA windows, free agency) needs a spec that pins the wall-clock hour on both sides of a November boundary; spacing-only assertions pass straight through the defect.

**A NEW time column must be `timestamptz` even when every column beside it is a bigint epoch.** The conformance ratchet keys on `table.column`, so the legacy neighbours are baselined and silent while the new one is a fresh violation — following local convention is exactly what trips it. `seasons.restricted_free_agency_first_window_at` shipped as bigint alongside `restricted_free_agency_period_start`/`_end` and turned master red on 2026-08-01; the fix is the retype, never `--rebaseline`. Budget for the retype's second half: `Number(date_value)` yields milliseconds and `dayjs.unix(date_value)` yields a nonsense year, and neither throws, so every read site has to move to `dayjs(value)` in the same change. Both survivors here were log/fallback paths that no test covered — grep the column name across the repo after a retype rather than trusting a green suite.

**The suite does not run on Node > 22 — honor `.nvmrc` (22.22.1) before debugging anything else.** mocha 11.0.1's bundled yargs is CJS loaded from an ESM context, so on Node 26 every invocation dies at load with `ReferenceError: require is not defined in ES module scope` before a single test executes. The failure is not a database problem and names no spec, so it reads like a broken harness or a broken change; it reproduces identically on an untouched spec, which is the cheapest way to tell it apart from your own work. Nothing in `yarn test`, `yarn test:local`, or a direct mocha invocation checks the running Node version, and a shell that has drifted off the pinned version gives no other signal. Run `node --version` first, and `. "$HOME/.nvm/nvm.sh" && nvm use` to pin it (`nvm use` is not inherited across Bash tool calls, so re-source it in each one).

**Adding a value constraint to a production column breaks the suite in two places that are not the code you changed.** Both surfaced on 2026-08-04 when the position vocabulary got its `CHECK` constraints, and neither is specific to positions. First, `db/fixtures/test/player.sql` is a **production dump**, so it carries whatever the column held before the backfill — 714 rows spelled an absent `tertiary_position` as empty string, and others carried the retired `OT`/`OG`/`SS`/`FS`/`SAF`. A backfill that conforms production silently leaves the fixture non-conforming, and the constraint then rejects the seed rather than any test's own data. Second, `test/libs-server.data-view-queries-result-equivalence.mjs` isolates each fixture's seeded players by giving them a value **no shared fixture uses** and filtering the data view on it — six invented position sentinels (`ZZ`, `QC`, `ZF`, `ZK`, `ZQ`, `ZW`, `ZY`). Constraining the column outlaws exactly that technique, and the replacement has to be a real vocabulary member the shared fixtures happen to leave free, which is a weaker guarantee: assert it stays unclaimed rather than trusting it. Before adding a `CHECK`, grep the fixtures and seeds for the column, not just the writers.

**When repairing fixture data, match on the COLUMN NAME, never on the literal.** The same 2026-08-04 change nearly shipped a subtle break because `'ZZ'` was simultaneously the position sentinel and the team sentinel, and a `player_gamelogs` seed happened to list them adjacently as `..., 'ZZ', 'ZZ', ...` (`nfl_team`, `pos`). A string replace on the pair rewrote the team too, which broke the join to `nfl_plays.offense_nfl_team` and turned six equivalence tests from red-for-the-right-reason into red-for-a-new-reason. Parse the `INSERT INTO t (cols) VALUES (vals)` and zip the two lists; the fixtures are uniform enough that this is a five-line script.

**Local test database requires Postgres >= 15.** `db/schema.postgres.sql` uses `NULLS NOT DISTINCT` (Postgres 15+); loading it against an older server fails in `test/global.mjs` with `syntax error at or near "NULLS"`. `config/config-test.json` connects to `127.0.0.1:5432`; `db/index.mjs` honors `LEAGUE_DB_HOST`/`LEAGUE_DB_PORT`/`LEAGUE_DB_USER`/`LEAGUE_DB_PASSWORD`/`LEAGUE_DB_DATABASE` overrides (note: the `yarn test` script blanks `LEAGUE_DB_HOST`/`LEAGUE_DB_PORT`, so to target a non-default port invoke mocha directly rather than through `yarn test`).

**With nothing listening on :5432, `yarn test` HANGS rather than failing.** The connection pool retries until its timeout instead of surfacing `ECONNREFUSED`, and `--reporter min` prints nothing until the run ends, so a suite that will never start is indistinguishable from a slow one — on 2026-07-30 this ate a 15-minute background task before anyone checked. If a `yarn test` run produces no output for more than a minute, check `psql -h 127.0.0.1 -p 5432 -c 'select 1'` before debugging the suite, and use the `:5433` container path below.

**A reachable :5432 does not clear this — the hang also happens when the server is up but lacks the test ROLE, and the documented `select 1` check does not discriminate it.** A Homebrew Postgres on :5432 has no `league_test` role (only the `:5433` container creates the roles, via `db/test/init-roles.sql`), so `test/global.mjs` dies immediately on `role "league_test" does not exist` and then hangs exactly as it does with nothing listening. The `select 1` probe answers `FATAL: database "<you>" does not exist` — reachable server, unrelated-looking psql quirk — so the documented check passes while the suite is already dead. On 2026-07-31 this ran for two hours and was nearly reported as an unverified test result. Two rules: probe with the credentials the suite actually uses (`psql -h 127.0.0.1 -p 5432 -U league_test -d league_test -c 'select 1'`), not a bare `select 1`; and prefer the `:5433` container path unconditionally, giving your run its own database (`LEAGUE_DB_DATABASE=league_test_<slug>`) so it neither collides with a sibling nor depends on local role state. The same suite that hung for two hours on :5432 ran green in **2 minutes** on the container.

If your local default Postgres on :5432 is < 15, use the bundled throwaway PG16 (`compose.test.yaml`, listens on :5433). It auto-creates the roles the schema GRANTs to (`postgres`/`league_writer`/`league_reader`) via `db/test/init-roles.sql`, so no manual `docker exec` step is needed:

```
yarn test:db:up      # start the PG16 container (blocks until healthy)
yarn test:local      # start DB + run the full suite against :5433
yarn test:local test/auth.spec.mjs   # ...or a single spec / mocha args
yarn test:db:down    # stop and remove the container (data volume persists)
```

To run mocha directly against the :5433 container (e.g. a custom reporter or `--grep`), set the port override and the standard requires yourself — `yarn test:local` is just this with `test:db:up` chained in front:

```
LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 TZ=America/New_York NODE_ENV=test TEST=all \
  node_modules/.bin/mocha --exit --require test/global.mjs --reporter min test/<file>.spec.mjs
```

**A new spec and the `export` it imports must land in the SAME commit — split across two, the first one turns master red for every session.** An ESM missing-export is a `SyntaxError` at module load, so it does not fail one spec: mocha dies before any test runs and the whole suite exits 1. Splitting is easy to do by accident, because the spec passes locally the entire time — the working tree has the `export`, and only the committed tree does not. On 2026-08-03 a prune spec landed in `b59e4ed1d` with its `export` following in `5cd4859de`, and CI went red in between on `SyntaxError: The requested module '../scripts/generate-prop-pairings.mjs' does not provide an export named 'prune_stale_prop_pairings'`. The cost is not local: a red master defers every push to `mistakia/league` for every session. When a commit adds a spec, `git show HEAD:<module>` and confirm the symbol is exported there, or use one explicit pathspec covering both files.

**Every spec lives FLAT in `test/`, named `test/<area>.<name>.spec.mjs` — a spec in a subdirectory is silently not a test.** Mocha's default spec glob is one level deep (`./test/*.{js,cjs,mjs}`) and nothing widened it, so 13 spec files and 205 tests under `test/libs-shared/`, `test/libs-server/`, `test/data-view-storage/` and `test/data-views/` had never run in `yarn test` or in CI; two had been failing the entire time, including the one governing injured-reserve eligibility. They were flattened on 2026-08-03 (2710 passing before, 2915 after — exactly +205). `yarn check:test-collection` now fails on any `*.spec.mjs` or `*.test.mjs` under `test/` that mocha does not collect, and runs in CI before the database setup; an intentional exclusion needs a listed reason in `scripts/check-test-spec-collection.mjs`.

**Do NOT "fix" that with a `spec` glob in `.mocharc.yml`.** It is the obvious tidier move and it is wrong twice over. Mocha MERGES rc `spec` into the command line's positional arguments rather than being overridden by them (`lib/cli/options.js` recombines `args.spec` into `args._`), so an rc glob silently widens every script that passes its own path — `test:private` and `test:data-view-queries` each resolve to the entire main suite (measured: a one-file script collecting 375 files). Overlapping globs also double-collect, since `collect-files` does not dedupe: `'test/*.mjs'` plus `'test/**/*.spec.mjs'` resolves to 376 files, 196 unique, running most specs twice. Both measured against mocha 11.0.1.

**`ignore` in `.mocharc.yml` is the rc spelling of `--exclude`, and since 2026-08-03 that is where CI's exclusion lives** (`test/importer-espn.spec.mjs`, which hits the live ESPN API). Unlike `spec`, it stays exclusionary under a positional argument, so it is safe there. It carried a SECOND entry until 2026-08-05 naming `test/libs-server.get-players-table-view-results-debug.mjs`, a file that has never existed at any revision — added in `d468e3ca8` in June 2025, most likely a misremembering of the `get-players-table-view-results{,-2,-3}.mjs` family, all three of which are now gone. It excluded nothing for fourteen months while reading as a deliberate exclusion. `yarn check:test-collection` now fails on any literal `ignore` entry with no file behind it, the same staleness rule it already applied to its own `INTENTIONALLY_UNCOLLECTED` list; globs are left alone, since one legitimately matches nothing. This inverts advice that stood in this file until then: a direct `mocha` invocation used to run MORE specs than CI, because the excludes were argv-only and every direct-mocha recipe here omitted them. That gap was not merely a count — spec files draw from a shared player pool through `selectPlayer`, so excluding two files changes which player every later spec is handed and therefore which cross-file collisions occur, and on 2026-08-02 a locally-green 2649 turned master red on `teams.restricted-free-agency` "remove a nomination". Any invocation that loads the rc now inherits the exclusions, so local and CI collection agree by construction and the recipes below need no `--exclude` flags. A run that passes `--no-config` loses both them and the 10s timeout.

The underlying defect that time was a fixture gap: the per-league fixture resets each table by name, so a NEW table is silently absent from the reset and its rows outlive `league()` into the next spec file. **That class now has a gate — `db/gates/check-league-fixture-reset-coverage.mjs`, in CI and in `check:cluster`** — so add the table to `db/fixtures/reset-league-tables.mjs` in the same change, or adjudicate it with a reason; the omission still cannot fail locally in any reliable way, which is why the gate is static rather than a residue check. Note the residue oracle is the one that does NOT work here: `league_pauses` left no leftover rows at all (its spec cleans up after itself), so "run the suite and look for stray rows" would have been green over the very incident that motivated the gate.

Three things that fell out of building it, each a fact a plausible design would have gotten wrong. **An FK-walk from `leagues` is structurally impossible** — the schema carries exactly TWO foreign keys referencing `leagues` and none between the trade/waiver/poach child tables and their parents, so a bare `league_id` with no FK is the norm rather than `league_pauses` being odd. **A bare league-column rule over-fires badly** (46 tables carry `lid`/`league_id`/`tid`/`team_id` against 20 then in the list), which is how a gate gets silenced. And **four reset entries are scoped only through a parent ROW ID** (`waiver_releases`, `poach_releases`, `trades_transactions`, `restricted_free_agency_releases`), so any rule reading columns for a league reference misses them; the working derivation is a fixed point that seeds on a direct scoping column and then propagates through `<X>id`/`<X>_id` naming an already-scoped table.

**The list lives in ONE file now.** It was duplicated in `db/fixtures/user.mjs`, which had drifted seventeen tables behind — the same remember-to-edit-a-list defect, duplicated, with no gate on the second copy. `db/fixtures/matchups.mjs` was likewise a matchups reset that nothing imported, which is why `matchups` leaked while appearing to be handled.

**The test container is a shared singleton — check for a concurrent run before trusting a result.** `mochaGlobalSetup` drops every table and reloads the schema, so a sibling session starting the suite mid-run pulls the tables out from under yours. It does not fail cleanly: you get a scatter of `relation "player" does not exist` and duplicate-key errors across unrelated specs, which reads like a real regression in whatever you happened to be editing. On 2026-07-28 this produced a 65-failure run that was entirely an artifact of two sessions sharing :5433. Check `ps aux | grep [m]ocha` first, and re-run alone before concluding anything. Better than waiting for the container to go idle: give your run its own database on the same container, which removes the collision entirely and does not disturb the sibling. `db/index.mjs` honors `LEAGUE_DB_DATABASE`, and `mochaGlobalSetup` loads the schema into whatever database it is pointed at, so `docker exec -u postgres league-test-pg psql -U league_test -d league_test -c 'CREATE DATABASE league_test_<slug> OWNER league_test;'` then adding `LEAGUE_DB_DATABASE=league_test_<slug>` to the direct-mocha invocation above runs the full suite in isolation (drop it when done). This turned a contaminated 68-failure run into a clean one on 2026-07-28. For the same reason, treat single-run timings as unreliable — this is a shared workstation and load averages above 50 are normal, so compare a change against a baseline measured back-to-back, not against a number from an hour ago.

**A contaminated-looking run can also come from INSIDE your own change: a spec that mutates a module-level singleton corrupts every LATER spec file, and the failures land nowhere near the cause.** This presents identically to the shared-container collision above — a scatter of failures across unrelated specs, plus fixture-seed duplicate-key errors — but no amount of checking for a concurrent run or giving yourself a private database will clear it, because the collision is in-process. Mocha loads every spec into ONE process, so `libs-server/player-cache.mjs`, which exports a singleton instance, is shared state across files: a spec that clears `is_initialized` to force a reload leaves it uninitialized and every later `find_player` throws `not initialized`, while a spec that leaves it LOADED hands a later file a cache built before that file seeded its own fixtures. On 2026-08-05 the first draft of the player-cache spec did both and took the suite from 3136 passing to **2717 passing and 73 failing**, with only 4 of the 73 in the file responsible.

The distinguishing move is a **control run**: a worktree at HEAD carrying none of your files, its own database, same container, same minute. That is the only thing that separates "the environment is contaminated" from "my change broke 69 other specs" — and the two readings point at opposite actions. Here the control returned 3136 passing / 0 failing, which made the attribution immediate. Run it before reporting any full-suite number you did not personally watch go green, and treat a large failure count in a file you did not touch as YOUR bug until a control says otherwise.

**Once you have run a control, the shell's working directory is the control worktree — and the next suite run silently measures HEAD instead of your tree.** The Bash tool's cwd persists across calls, so a `cd` into the control worktree stays in effect for every later command; the mocha invocation is byte-identical either way and reports a perfectly plausible green. Nothing in the output names which tree it ran in. On 2026-08-05 that turned a re-run meant to reproduce a failure into a clean 3197-passing control repeat, and the failure "disappeared" — the tell was the COUNT, which matched the control exactly rather than the working tree's expected total. **Know your expected test count before you run** (control total plus the tests you added) and check it against the summary line; a run that reports the control's number ran the control. Cheapest guard is to `cd` back explicitly and echo `pwd` in the same command as the suite. The same trap ruins instrumentation: a `perl -0pi -e` meant for a spec in your tree edits the control's copy instead, so the debug output never appears and the spec looks untouched.

**Sharper form of the same trap: cwd persists from the last command that SUCCEEDED, so a compound `cd <dir> && <cmd>` whose `<cmd>` FAILS leaves you in the previous directory.** The `cd` itself worked, which is what makes the next relative-path command read as though it ran where you sent it. On 2026-08-07 a `cd <repo> && node <script>` that exited 1 on a deliberate anchor guard was followed by a bare `grep -n` — which ran in the worktree from three commands earlier and returned that file's contents, briefly reading as though the repo file already held work that was only in the worktree. Nothing in either output names a directory. Use absolute paths for anything whose answer you are going to act on, rather than trusting an earlier `cd` to still be in force.

**Third member of the family, and it corrupts a CONTROL rather than a test run: a control anchored on a RELATIVE ref silently moves to the wrong commit, because sibling sessions push to this branch while you work.** `HEAD~1` is not a fixed point in a shared checkout. On 2026-08-07 a gate's positive control restored `HEAD~1` of two component files to prove the gate went red on a defect just repaired one commit earlier; two unrelated sessions committed in the interim, so `HEAD~1` had become a POST-fix commit and the control reproduced the fixed tree. It reported no finding, which reads exactly like a gate that cannot see the defect it was written for — the worst direction, since the natural response is to go weaken the gate until it "works". The tell was the restored source not containing the old identifier at all; the fix was `git rev-parse` on the fix commit and anchoring the control on `<hash>~1`. **Resolve any base ref to an explicit hash once, at the start, and use the hash** — this is the same rule `check-renamed-column-consumers` gate 2 already enforces by treating an unresolvable `--base` as a skip rather than a pass, applied to the refs a human types. Corollary for reading git output: `git log`/`git show` on `HEAD~n` mid-session is answering about a branch that may have advanced since your last command.

The fix is snapshot-and-restore rather than a reset method, since the class exposes none: `test/utils/player-cache-isolation.mjs` copies the instance's own fields around a `describe` block and puts them back in `after`. Any future spec touching `player_cache` should use it. The same hazard exists for any other module-level cache a spec reloads — `libs-server/charting-data/player-matching.mjs` has `reset_sumer_id_cache` for exactly this reason.

**The isolated-database recipe has its own silent hang: if `LEAGUE_DB_DATABASE` names a database that does not exist yet, mocha hangs forever instead of failing.** Same mechanism as the two `:5432` hangs above — the connection pool retries rather than surfacing the error, and `--reporter min` prints nothing until a run ends — but it fires on the path this file recommends, and the mistake is easy: launch a loop in the background, create the database a moment later, and the first invocation has already latched. On 2026-08-03 a 40-run loop sat on iteration 1 for **an hour** looking like a slow suite, with the database created 60 seconds after launch. Run the `CREATE DATABASE` and confirm it returned before the first mocha invocation, never concurrently with it. The tell, when you suspect it: `ps -o etime=,command= -p $(pgrep -f 'mocha --exit')` shows a single mocha whose elapsed time equals the whole loop's.

**A fourth hang mode passes every probe above, and the distinguishing observable is on the DATABASE side, not the process side.** All three hangs documented so far are connection-level — nothing listening, no role, no database — so each is caught by probing connectivity with the suite's own credentials. On 2026-08-04 a full-suite run against a correctly pre-created isolated database sat **45 minutes** with no output: the database existed, its schema had loaded (292 tables), `psql` answered normally, and the mocha process was alive the whole time. Every documented check said healthy, which made it read as "slow under load" — the host was at load ~11 with a sibling's mocha running, so that reading was plausible and wrong. The suite was wedged in JS, not executing anything. Sample `pg_stat_activity` for the run's own database: `SELECT count(*), max(now()-query_start) FROM pg_stat_activity WHERE datname='<db>' AND state <> 'idle'`. A genuinely slow suite always has a non-idle backend; this one had **none** — every connection idle while the process burned wall time, which no amount of host load explains. Contention slows the queries you can see; it does not empty the list. Kill it (`pkill -f '<db-name>'`), then `pg_terminate_backend` the leftovers before `DROP DATABASE`, which otherwise refuses with "There is 1 other session using the database". Root cause not established — treat an idle-backend stall as a suite-side hang worth reporting rather than a result you can wait out, and fall back to targeted specs plus a module-import smoke test for the gate you actually needed.

**A fourth hang, and the one that is not your fault: a SIBLING's uncommitted schema edits break `test/global.mjs` seeding, and a failed seed hangs mocha rather than failing it.** Your own isolated database does not protect you — `global.mjs` loads `db/schema.postgres.sql` and the fixtures off the WORKING TREE, so a sibling mid-rename (schema file already conformed, or not yet, against fixtures naming the other spelling) breaks the seed for every spec in the shared checkout. The seed error surfaces as an unhandled rejection, the orphaned work keeps the pool alive, and the run sits until your timeout kills it. On 2026-08-04 a prune spec that had run green in 123ms an hour earlier ate a 900s timeout and a 15-minute background task this way; the tell was `column "is_excluding_quarterback_kneels" of relation "league_scoring_formats" does not exist` — a column belonging to an in-flight `league_scoring_formats` cluster the running session had never touched.

Two things make this expensive. The error appears only AFTER the timeout fires, so while it is hanging it is indistinguishable from the three hangs above, and the natural next move — checking that your database exists, checking for concurrent mocha — clears every documented cause and tells you nothing. And `--reporter spec` does not help: piping through `grep` buffers the output, so redirect to a file (`> /tmp/run.txt 2>&1`) if you want to watch it. The cure is the recipe this file already gives for `yarn build` and the SQL-validity gate, applied to specs: `git worktree add tmp/<name> HEAD`, symlink `node_modules`, copy in ONLY the files you changed, and run there. `git status --short` in the worktree should list exactly your files and nothing else — that is the check that your green is yours.

**`yarn test:private` blanks the port overrides exactly like `yarn test`, so it hangs on :5432 too — and CI never runs those specs at all.** The script is `LEAGUE_DB_HOST= LEAGUE_DB_PORT= ... mocha 'private/test/**/*.spec.mjs'`, which means every `:5433` recipe above is unreachable through it and a private spec run silently latches onto the missing :5432 server. Invoke mocha directly instead: `LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 LEAGUE_DB_DATABASE=league_test_<slug> TZ=America/New_York NODE_ENV=test TEST=all node_modules/.bin/mocha --exit --require test/global.mjs --reporter min 'private/test/**/*.spec.mjs'`. The second half is the one that changes what a spec is worth: `.github/workflows/test.yml` runs `yarn test` and the two `check:*` gates, and nothing anywhere invokes `test:private` — so a spec under `private/test/` is a **local-only** gate that no push, no red master, and no deploy will ever exercise. Write one anyway when it pins a real invariant (2026-08-04 added `private/test/import-gameday-rosters.spec.mjs` for the roster id-resolution rule), but do not count it as coverage the way a `test/` spec counts, and never rely on it to catch a regression a sibling session introduces.

**Mocha exits with its FAILURE COUNT, so a shell-convention reading of the exit code misdiagnoses the run.** `$?` of `127` means 127 failing tests, not `command not found` — and on a rename cluster, where the suite is the primary oracle and three-digit failure counts are normal, that collision is easy to hit. It reads as a broken invocation rather than a result, which sends you debugging your mocha command instead of your change. Confirmed 2026-08-05 on the season_grain sweep, where a background run that had genuinely produced `2510 passing / 127 failing` was first read as having never started. Take the counts from the summary line (`grep -aE '^\s+[0-9]+ (passing|failing|pending)'`) and treat the exit code as a boolean at most; note `--reporter min` prints nothing until the end, so an empty log mid-run is not evidence either way.

**Timeouts are the suite's dominant failure mode, and they lie about their cause.** `.mocharc.yml` sets a 10000ms floor because mocha's 2000ms default is a unit-test budget and these specs query a real Postgres. When a test does exceed its budget, mocha fails it but cannot cancel its in-flight queries, so the abandoned work keeps writing and collides with the next test's fixture reset — surfacing as a duplicate-key violation on a later, innocent spec. Read a `transactions_pkey` error in the suite as a downstream symptom of a timeout, not as the defect. `test/global.mjs` prints unhandled rejections with their Postgres `detail`/`constraint` so the real error is visible rather than swallowed.

**An exact `Math.round(Date.now() / 1000)` assertion against a server-stamped timestamp is a race only where the clock is unfrozen, which is the rare case.** The test server runs in-process, so `MockDate.set` freezes both the clock the handler stamps from and the clock the assertion reads; the two agree no matter how long the request takes, and the equality is a real assertion worth keeping. It races only in a spec that never calls `MockDate.set` — and mockdate is global, so such a file inherits whatever the previous file left, which is why the failure appears in a single-file run and not a full-suite one. `test/trade.spec.mjs` is that file: its `post` block sets no date, and the timestamp assertion failed once in 30 single-file runs on a second boundary, now relaxed to `closeTo(..., 2)`. Every other site matching `grep -rn "Math.round(Date.now() / 1000))" test/*.mjs | grep -E "should.equal|to.equal"` — 45 of them across 14 files, audited 2026-08-03 — sits inside an `it` under a frozen clock. Do not sweep them to `closeTo`; that weakens 45 assertions to fix a flake they cannot have. The corroboration: this flake has been observed live twice, on 2026-07-28 and 2026-08-03, and both instances were in `test/trade.spec.mjs` — never in any of the 45. A sweep of all of them has now been proposed twice and is wrong both times.

**Do NOT let that paragraph absorb the next `test/trade.spec.mjs` failure — the same `Math.round(Date.now() / 1000)` idiom in PRODUCTION code is a different defect, and it is not a flake.** The note above is about an ASSERTION racing a server stamp; the sibling failure is a WRITE rounding `transactions.occurred_at`, which is `timestamptz` with millisecond resolution. Rounding moves the stamp up to half a second in either direction, so a transaction written moments after one stamped from an unrounded `new Date()` orders BEFORE it — and `check-last-transaction` reads `order by occurred_at desc`, so the wrong row answers as the player's latest. On 2026-08-07 that failed `one for one trade of rookies` on **4 of 8 runs** at master, which no clock race explains; six write sites were repaired in `1e1c2b228`. The two are easy to conflate because the filename, the idiom and the intermittency all match. Tell them apart by the ASSERTION that fails: a `closeTo`/timestamp expectation is the flake, while `check-last-transaction.mjs:15` reporting a transaction TYPE mismatch (`expected 4 to equal 3` — those are `transaction_types`, not counts) is the ordering bug. Reach for `gh run rerun --failed` only for the first; the second reproduces on repeat runs, which is the cheapest discriminator.

**`selectPlayer` is `ORDER BY RANDOM()`, so a test that seeds two players without `exclude_pids` gets ONE player some fraction of the time — and the failure reads as a broken assertion rather than a broken fixture.** The eligible pool for the default `RB` draw is about 21 players, so two bare calls collide on roughly one run in twenty. `test/scripts.restricted-free-agency-processing-pause.spec.mjs` seeded both of its backlog auctions that way and failed `expected [X] to not include X` at that rate — an assertion comparing a pid against ITSELF, which is why the preceding `deep.equal` on the same array passed and the whole thing looked like an ordering defect in the settle path. It turned master red once (run 31271424181) and was diagnosed twice as a timestamp-resolution problem before anyone read the two pids as one; measured 2 failures in 30 runs, and 0 in 40 after threading `exclude_pids` (`fd6924780`). The convention is already right in the sibling RFA specs — accumulate the seeded pids and pass them to each subsequent draw. Two things generalize. **An assertion that a value is not equal to itself is a fixture-identity bug, never a logic bug**, so read the two operands before reading the code under test. And a per-run failure rate near 5% with a ~20-row fixture pool is the signature of a random draw, not of a clock or an ordering race.

**The self-comparison tell is ONE shape of this class, not its signature — and reading it as the signature is what made the second instance get diagnosed wrong first.** A collision only surfaces as `expected [X] to not include X` when the spec compares the two draws to each other. When it does not, the collided player simply flows into a REQUEST, and the failure is an ordinary status-code mismatch pointing at the route: `test/draft.spec.mjs`'s `league paused` drew a rookie already drafted by `make selection` and answered `400 player rostered` on its resume leg (`api/routes/leagues/draft.mjs:634`), reading as the pause guard having refused a request it never saw. Nothing in that failure compares a value against itself. The 2026-08-14 dispatch brief for it consequently ranked the draw collision SECOND behind a fixture-reset hypothesis that was disprovable by reading the case — the deciding evidence being that the spec deletes every `league_pauses` row before the failing request and a live pause answers 423, not 400. **The durable tell is structural rather than textual: an intermittent failure in a spec that calls `selectPlayer` without `exclude_pids` while an earlier case in the same file rostered a player from the same pool.** Grep the file for bare `selectPlayer({ ... })` calls before reading the route. Note the pools differ by draw — measured 2026-08-14, the rookie `RB` pool is **34**, not the ~21 the paragraph above cites for the default non-rookie draw, which puts the per-run rate near 3% (observed 11 failures in 250 runs, 0 in 250 after `fd6924780`-style exclusion in `667d6580f`). A case that expects a SUCCESS code is the only one that can expose this; siblings expecting a 400 swallow the collision silently, which is why one case in a file flakes and its neighbours never do.

**`config-test.json` deliberately carries an `email` block with a fake Resend key — do not "clean it up".** It is what makes outbound mail OBSERVABLE in the suite rather than absent. `libs-server/send-email.mjs` builds its Resend client at module load and returns early when `config.email` is unset, so with mail disabled a spec cannot read anything the app emailed and has to restate the sender's logic instead. That is what left the password-reset seam uncovered: `test/auth.spec.mjs` minted the reset token itself, so nothing asserted that `POST /auth/reset-password` and `POST /auth/reset-password/confirm` agree on the secret derivation — a divergence there breaks every real reset link while the suite stays green.

The mechanism to copy: Resend transports over the **global `fetch`**, so replacing `globalThis.fetch` for the duration of a describe block captures the outbound message with no network egress, no test-only branch in the route or the mailer, and no new dependency (there is no `nock` here). The spec then reads the token out of the emailed link and hands it to the confirm route, which checks the two derivations against each other by round trip. Restore the original `fetch` in `after`. Two things that keep it honest: assert the capture is non-empty, since a mailer that silently no-ops would otherwise skip the seam the spec exists to cover; and make the oracle the login that follows, not the 200 — the round trip ends by logging in with the new password and being refused the old one, so a flow that merely returned 200s cannot pass. Note `sendEmail` has exactly ONE call site in the repo (the reset route), which is why enabling mail in the test config reaches nothing else; check that before assuming the same is still true.

**Verifying an undeployed SPA + API change end to end, without `dist/` and without touching production.** `yarn dev:live` is wrong for this — it points the production-mode frontend at the LIVE API, so an undeployed route 404s, and for the reset flow it would email a real user. `yarn dev:smoke` is also wrong where the change WRITES, since its production DB tunnel is read-only. The shape that works costs no build: the SPA's dev bundle hardcodes its API at `MACHINE_IP:8082` (`app/core/constants.js`), so run `webpack serve --config webpack/webpack.config.dev.babel.mjs --port <free>` (webpack-dev-server serves from memory and never writes `dist/`, so it cannot clobber a sibling's build) against your own API on 8082 started with `NODE_ENV=test` and `LEAGUE_DB_DATABASE=league_test_<slug>`. Wrap the API entry in a throwaway under `tmp/` (gitignored, and inside the package so `#` aliases resolve — a script in `/tmp` fails with `ERR_PACKAGE_IMPORT_NOT_DEFINED`) that installs the `fetch` mail capture above before importing `#api`, writing each message to a file; that is a local mail catcher a browser-driven run can read the link out of. `playwright-core` plus the installed Chrome (`channel: 'chrome'`) drives the rest. Used 2026-08-07 to validate request -> emailed link -> confirm -> login. **Check the dev-server port first** — sibling sessions routinely hold 8091 and 8095, and the default is 8091.

### Poaching System

**Practice Squad Poaching:**

Teams can poach players from other teams' practice squads with automatic roster space handling:

- **Normal Flow**: Poached player added to bench, removed from original team
- **Immediate Release Flow**: When poaching team lacks space (after designated releases):
  1. Creates `POACHED` transaction (preserves history)
  2. Immediately releases player to waivers via `processRelease()`
  3. Marks poach as successful (not failed)

**Super Priority System:**

When a poached player is released, `handle_super_priority_on_release()` (in `process-release.mjs`) automatically:

- Creates `super_priority` record tracking eligibility
- **Auto-creates waiver** (type: `FREE_AGENCY_PRACTICE`) if original team has practice squad space
- **Requires manual waiver** if no space available

This preserves transaction history and gives original teams first rights to reclaim poached players.

**Key Files**:

- `/libs-server/process-poach.mjs` - Poach orchestration
- `/libs-server/process-release.mjs` - Super priority handling

- Saved view preferences
- Field definitions in `libs-shared/data-view-fields-index.mjs`

**A CTE identity key that derives its membership from a param registry loses members silently when the registry changes, in a commit that never touches the key.** `get_stats_column_param_key` builds the from-plays table alias by enumerating `Object.keys(nfl_plays_column_params)`. `year`, `week` and `seas_type` were registry members until `64a28f9dc` replaced them with the composite `nfl_week_id` — so the alias key stopped distinguishing them, and two `*_from_plays` columns differing only by year hashed identically, landed in one join group, and shared one CTE built from whichever column seeded the group (`group_column_params` in `get-data-view-results.mjs`). The second column rendered the first's values under its own header: no error, no failing test, a wrong answer. It survived from March to July 2026 because the one golden exercising the shape (`player-target-share-from-plays-different-params`) had blessed SQL containing no predicate at all for its second column's year, and 114 saved views carry per-column `year` on a from-plays column. Fixed 2026-07-31 by keying `year`/`seas_type` explicitly, emitted only when present so unscoped columns keep their hash — the reason exactly one golden changed. Two rules: when adding or removing a member of a param registry, grep for code that enumerates its keys rather than reading it by name, since those consumers change behaviour with no diff of their own; and when a param is both user-facing and resolved a layer up (here `year`, expanded into `nfl_week_id` by `resolve_params_contribution`), it still needs to be in any identity hash, because the scope layer runs after grouping has already collapsed the columns.

**The same collision arrives without any registry: a table that stores several PERIODS in one column needs the period in its alias key.** `league_format_player_projection_values` keeps `'0'`, a numeric week, `'ros'` and `'ros_net'` in one `week` column, and each period column pins its own sentinel in `extra_predicates` / `attach`. Its alias keyed only on year/week/seas_type, so two period columns in one view hashed identically, collapsed into one join group, and that join carried only the SEEDING column's predicate. Measured at `50f63cf5a`: `[week, ros]` emitted `week = 'ros'` for both columns and `[ros, week]` emitted `week = '0'` for both, so one of the two rendered the other period's value under its own header — `market_salary` had the same shape. Nothing caught it because no golden exercised any rest-of-season projected column at all, and each column is provably correct when requested ALONE, which is how anyone would test it. Fixed 2026-08-04 in `67278d518` by keying the alias on the period. Two rules: when a column pins a discriminator its siblings do not share, that discriminator belongs in the alias key, not just in the join predicate; and test a join-group defect with the columns TOGETHER and in both orders, since the single-column case passes either way and the order decides which value wins.

**A discriminator in `source.extra_predicates` does NOT reach the year_offset range path, which emits its own correlated subquery instead of reading the join.** `player_year_offset_range_select` / `team_year_offset_range_select` take `extra_predicates` as an explicit ARGUMENT (`libs-server/data-views/param-utils.mjs`), so a source that declares one and a `main_select_string_year_offset_range` override that does not forward it produce two different scopings of the same column — the join is pinned and the range subquery is not. It fails silently in the worst direction for a `latest_by_year: true` override, whose `ORDER BY <year> DESC LIMIT 1` then picks whichever discriminator value happens to sort last: adding `season_type` to `pff_player_seasonlogs` on 2026-08-14 would have let the text columns (`unit`, `player_position`, `grade_position`) render from a scoped row where every column but `routes` is null, a blank cell rather than an error. **The tell is a golden that regenerates to NO CHANGE** while its siblings all gain the new predicate — `player-pff-unit-range-offset-latest-season.json` was the only one of nine that did not move, which is what surfaced it. When you add a predicate to a source, grep that file for `year_offset_range_select` and forward it.

**A `-999` sentinel RATE cannot tell a wiped year from a year that legitimately has no source, and reading it as damage points at a destructive "repair".** `league_format_player_projection_values` is written delete-then-reinsert by `(league_format_id, year)`, so a broken run replaces a year with sentinels — which is exactly what a year whose scoring format has no `scoring_format_player_projection_points` rows looks like on its own. The healthy baseline is already ~48% sentinel (unprojected and non-fantasy-position players sit in the pool deliberately), so rate thresholds are useless here. On 2026-08-05 four format-years read as 100% sentinel across all 19 weeks and were reported as conclusively wiped; joining values to source showed all four hold **zero** source point rows, so a correct run produces the same output and there was nothing to repair. The discriminating query is the join, not the rate: ask for a pair that is fully sentinel **while holding source rows**, which is the only shape a wipe can take. Re-running the writer against a sourceless year recomputes the identical sentinels, so "repair by re-running" is a no-op there regardless.

**An all-sentinel oracle over that table must count NUMERIC weeks only.** `calculatePlayerValuesRestOfSeason` SKIPS the sentinel rather than propagating it, so the `'ros'`/`'ros_net'` rows land at `0` — a non-sentinel value — even on a run where every real week was sentinel. Counting them leaves two "real" values per player on a fully wiped year and silences the check on precisely the failure it exists to catch. Caught by the spec, not by review, when the first draft of `process-projections-for-league-format.mjs`'s oracle did exactly this.

**A projection rebuild is SECONDS of unbroken synchronous JS, so it can never run inside the API process — and its cost is SEASONAL, which makes the log lie to you.** Measured on production data 2026-08-09: `process_scoring_format_year` blocks the event loop for **244ms** (1,131 players, 22,600 rows; the rest of its ~2.1s wall is IO), while the league-format stage — the 19-week `calculate_projection_values` loop plus `calculatePlayerValuesRestOfSeason` — blocks for **7.6 seconds**. Node is not idle through that; it is CPU. Running it in `server.mjs` would freeze every request, the auction socket and the scoreboard for the duration, which is why the rebuild lives in `jobs/refresh-projection-cache-worker.mjs` rather than in `PUT /leagues/:leagueId` where it started.

The seasonal part is the trap. The cron's `process_league_format` starts its week loop at `first_projection_week_to_recompute({ year })`, which returns `current_season.week` — a high week in-season, so few iterations, and **0 for the whole offseason**, so all 19. Reading `duration_ms` out of `/var/log/league/process-projections.log` with a `tail` therefore returns ~2.4s or ~11.5s for the same format depending only on where in the file you landed, with nothing in the line saying which regime produced it. A design decision was nearly made on the in-season number. Read a WHOLE run, check the timestamps against the current phase, and compare two consecutive runs before quoting a duration — the offseason figures for league 1 are `genesis` ~2.1s and `genesis_10_team` ~11.4s, stable across hourly runs, against ~20 formats at 6-34s each for roughly an eight-minute total run.

### Script Execution

All scripts follow pattern:

```javascript
import { is_main } from '#libs-server'
const main = async () => {
  /* logic */
}
if (is_main(import.meta.url)) {
  main()
}
```

Use `handle_season_args_for_script()` for year/week parameters.

**A script that imports `#db` does not EXIT when its work finishes — the knex pool keeps the event loop alive, so wall-clock duration is not run duration.** The work completes, the last `console.log` sits unflushed in a pipe, and the process lives until something kills it. This is the default outcome of an ad-hoc invocation, not a rare event: a 2026-08-04 census of league-production found **four** leaked `node` processes aged 10 to 56 days, every one a hand-typed `node -e` or a `tmp/*.mjs` throwaway, two of them ad-hoc data-view scripts. The 56-day one had held a Postgres backend authenticated as `league_user` — a role DROPPED in the 2026-07-01 rename — because Postgres never re-checks a role on an already-open session, so no timeout and no credential change could ever have reclaimed it. The same trap corrupts measurement while you are still at the keyboard: in that session two timing scripts appeared to hang for 7 and 15 minutes and were nearly diagnosed as slow query CONSTRUCTION, when construction took 98ms and the queries took 44s — the rest was the process refusing to exit behind a `| tail` that therefore printed nothing. End any script that opens a handle with `await db.destroy()`, and add an explicit `process.exit(0)` when a redis client is also open (`redis_cache` from `#libs-server` holds its own socket, which `db.destroy()` does not close). When a script prints nothing and seems slow, check `ps -o etime= -p <pid>` and its open sockets before believing the work is slow.

### Season Constants

Current season info from `libs-shared/constants/season-constants.mjs`:

- `current_season.year`, `current_season.week` (week is the **continuous counter** from `regular_season_start`, not per-type)
- `current_season.nfl_seas_type` (`PRE`/`REG`/`POST`), `current_season.nfl_seas_week` (resets to 1 in POST), `current_season.stats_season_year` (Super Bowl gap / offseason stable)
- `is_offseason`, `is_regular_season`
- `fantasy_weeks`, `nfl_weeks`

**`current_season.week` reads 0 for the whole offseason, and `isReserveEligible` uses that as a deliberate switch — so QUESTIONABLE is reserve-eligible today and will not be once Week 1 starts.** The last clause of `libs-shared/is-reserve-eligible.mjs` makes ANY `game_designation` qualify when the week is 0, because in the offseason there is no game to be active for; in the regular season only OUT and DOUBTFUL qualify. This reads as a bug and is not one — `submit-reserve.mjs` passes the live `current_season.week`, so no QUESTIONABLE player can reach injured reserve during the season. It cost a gated investigation on 2026-08-03 because the spec asserting it hardcoded `expect(result).to.equal(false)` with no frozen clock, which is right in-season and fails every offseason. Anything asserting on a designation whose answer depends on the season phase must pin the clock on BOTH sides; `current_season.week` is a live getter, so `MockDate.set` inside the test works and a clock-derived expectation is never necessary. Same family as the `--recursive` and golden-template traps: a value that is correct half the year looks like a stable one.

Never reconstruct an `nfl_week_id` locally. Use canonical helpers in `libs-shared/nfl-week-identifier.mjs`: `current_nfl_week_identifier()`, `current_nfl_week_params()`, `nfl_week_offset_params({ offset })`. See `docs/data-views-system.md` "Live current_season semantics" for the choke-point rules.

### Player ID Format

Player IDs are `FNAM-LNAM-<serial>` (e.g., `PATR-MAHO-000123`): a frozen 4+4-letter name prefix (a courtesy snapshot, never recomputed, carries no identity) plus an opaque immutable zero-padded serial from a dedicated sequence that IS the identity. The pid does not depend on `dob`/`nfl_draft_year` and is never regenerated. DST pids are the bare team abbreviation (`NE`). See [docs/player-management.md](docs/player-management.md).
