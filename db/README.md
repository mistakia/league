# db/

The schema, the history of how it got there, and the tooling that keeps code and
schema in agreement. Four directories, and **which one a file belongs in is
decided by its LIFECYCLE, not by its subject matter.**

That distinction is the whole point of the split. Everything here is "about the
schema", so subject matter cannot separate anything. What separates them is
whether a file is ever edited again after it is written, and whether it carries a
pass/fail verdict.

| Directory  | Lifecycle                        | Rule                                                            |
| ---------- | -------------------------------- | --------------------------------------------------------------- |
| `adhoc/`   | write once, run once, never edit | Date-prefixed `YYYY-MM-DD-<slug>`. Append-only audit trail.     |
| `gates/`   | long-lived, edited freely        | Has a pass/fail verdict AND is in the `check:cluster` manifest. |
| `tools/`   | long-lived, edited freely        | Durable, and MUST NOT carry a verdict wired to a run.           |
| `archive/` | frozen                           | Tooling whose cluster closed. Kept as reference, not run.       |

`schema.postgres.sql` is the source of truth and sits at this level. It is
generated by `yarn export:schema`; never hand-edit it.

## The rules, stated so they can be applied without asking

**`adhoc/` — if you would ever edit it, it does not belong here.** This is the
one directory with an append-only contract, and mixing anything else in destroys
it. A file here is run once against production by `yarn db:exec`, which rewrites
its `-- STATUS: PENDING` banner in place and then refuses to run it again. There
is no such thing as a "current" file here; there is only history.

Two things follow that are easy to get wrong. A dry-run copy must live OUTSIDE
this directory (`tmp/`), because `db-exec.sh` applies its banner rule to anything
under `db/adhoc` and there a copy either cannot run or is indistinguishable from
the real file. And a correction is a NEW dated file, never an edit to the old
one.

**`gates/` — a verdict plus a manifest entry.** Both halves are required. A
checker that answers pass/fail but is not in `scripts/check-cluster-gates.mjs`
is a gate nobody runs, which is this repo's documented recurring failure — the
2026 plays/snaps cluster dropped filters on 45 saved views and the verdict on it
was that what was missing was running the check at all. `yarn check:cluster
--list` prints the manifest with each gate's prerequisite and oracle, and that
list is authoritative; it is deliberately not restated in prose anywhere.

A gate's **state file lives beside it** — its adjudications or its baseline. They
move together because one is meaningless without the other, and a gate whose
adjudications drifted to another directory is a gate whose suppressions nobody
can find.

**`tools/` — durable, and deliberately NOT a gate.** Each file here has a
specific reason it must never be wired into a pass/fail run, and the reason is in
its header. `audit-schema-conformance.mjs` exits 1 by design on standing debt, so
it is an ORACLE that `gates/check-schema-conformance-ratchet.mjs` converts into a
verdict against a checked-in baseline. `scan-source-leakage.mjs` is advisory and
its non-zero count is the expected state. `schema-partitions.mjs` is a shared
library. `generate-migration-inventory.mjs` regenerates an inventory.

Wiring one of these into CI would produce a permanently red master, which defers
**every** session's push to `mistakia/league`. That is why the boundary is a
directory and not a convention.

**`archive/` — moving the file IS the record.** When a cluster closes, its
tooling moves here rather than acquiring a paragraph in a README saying it is
spent. Prose describing which files are dead decays; a directory does not. Files
here are kept for reference and are not expected to run — several name columns
that no longer exist, which is correct for a record of a closed migration and
would be a defect anywhere else.

## Why this shape

Until 2026-08-06 all of it lived in `db/adhoc/`: 258 entries, 227 of them dated
one-shots, with the gates and their mutable adjudication files mixed in. The
taxonomy existed, but only as prose in a README, so the append-only contract and
the "edited constantly" reality of the gates were the same directory making
opposite promises.

The split pays for itself immediately in one place worth naming.
`generate-migration-inventory.mjs` used to carry a hand-maintained `TOOL_FILES`
set naming three gate and tool files to exclude from consumer discovery — a list
whose failure mode is that a NEW gate is a new entry nobody remembers to add, and
the omission reads as a real consumer rather than as a miss. `db/gates`,
`db/tools` and `db/archive` are simply not consumer directories, so that
exclusion is now structural and the list is gone.
