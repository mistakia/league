# Run a Schema or Rename Cluster

**When to read this:** Read before any DDL: a rename, a retype, a drop, or an additive change that widens a grain.

Everything from authoring the adhoc file to verifying the deploy. Gates are listed in the order to run them, and each entry says what it cannot see.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

## Authoring and applying an adhoc file

**Schema Change Workflow:**

1. Author the SQL in `db/adhoc/YYYY-MM-DD-<slug>.sql`, including a `-- STATUS: PENDING` line in the header
2. Run it against production with `yarn db:exec db/adhoc/<file>.sql` (wraps the file in a single transaction with `ON_ERROR_STOP=1`)
3. Export the updated schema using `yarn export:schema`
4. Regenerate the derived types with `node db/tools/generate-schema-types.mjs`
5. Commit the adhoc file (audit trail, banner now rewritten to APPLIED), the schema diff, and both regenerated type files

**Step 4 is not optional bookkeeping — skipping it turns master red for the whole repo.** `yarn check:types` is a CI step that compares `db/schema-types.d.ts` against the exported schema and fails with `FAIL: db/schema-types.d.ts is stale`, and the generator writes `db/knex-tables.d.ts` alongside it, so BOTH files belong in the commit. The failure is not confined to the commit that caused it: the sync-all pre-push guard reads the latest run on the branch regardless of workflow, so every session's league push is deferred behind it. On 2026-08-22 the five `contribution_*` tables were applied and exported without regenerating, and 78 `red_main_skip` entries accumulated in the sync telemetry while five commits from three sessions sat unpushed — none of them related to the schema change, and nothing in their diffs pointing at the cause. The tell is that the run fails at the `Type check` step rather than in `Test`, which is the same read-the-step-before-attributing rule [the shipping guide](ship.md) states for install failures. Repair is the one command plus a commit, but it cannot land while the guard is deferring pushes, so it needs `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh` and a bulletin naming the cause.

**Renaming a VIEW column needs `ALTER VIEW ... RENAME COLUMN`; `CREATE OR REPLACE VIEW` cannot do it.** Replacing a view may add trailing columns or change their expressions, but it refuses to change an existing output column's NAME — `ERROR: cannot change name of view column "<old>" to "<new>"`, with a HINT naming the right verb. Plans reach for `CREATE OR REPLACE VIEW` because it is the familiar shape and because it genuinely avoids the drop-and-recreate dependency problem; it just does not perform a rename. Prefer `ALTER VIEW` on its own merits anyway: it moves the one alias without restating the whole `SELECT`, so there is no restated body that can silently drift from what is live. Caught 2026-08-04 on `view_trade_asset_flow.market_value_at_trade`, where the task entity had specified the unusable form; `db:exec` runs the file in one transaction so the failed apply rolled back cleanly and production never saw a partial change. That column name is the pre-rename one and no longer exists — the rename landed in `0d2af7fd4` and the view now carries `keeptradecut_value_at_trade`.

`db/schema.postgres.sql` is the source of truth; `db/adhoc/` is the append-only history of how it got there.

**`league_production` accepts no direct TCP connection, so a read-only query needs the same hop `db:exec` uses.** `db-exec.sh` reaches it as `ssh league` plus `psql -U league_writer -h localhost --dbname=league_production` — Postgres is not exposed off the host, deliberately. Nothing says so at the point where you would reach for a quick count, and the failure mode is misleading in the expensive direction: a `NODE_ENV=production` knex or `pg` client from a workstation resolves DNS fine and then times out at the TCP layer, which knex reports as `Timeout acquiring a connection. The pool is probably full.` On 2026-08-28 that was read as a production outage and reported as one, twice ten minutes apart, while the host was up and answering SSH and the real cause was that the port was never open. Two checks separate them in one command each: `ssh league uptime` proves the host, and a raw TCP connect proves the port. For an ad-hoc read, `ssh league "psql -U league_writer -h localhost --dbname=league_production -tA -c '<sql>'"` is the working shape.

**A new table needs its `league_data_view_reader` grant added by hand, and no gate will tell you.** That role is the login the sandboxed-SQL data-view tier connects as, and its `GRANT SELECT` list is enumerated table by table in the adhoc that created it rather than granted by a schema-wide default — so a table created afterwards inherits `league_reader` (which does come from a default) and nothing else. `yarn export:schema` shows the asymmetry plainly if you look, since every peer table carries both lines. Nothing reconciles that list against the tables the data-view column definitions actually reference, so the omission survives every gate and surfaces as a permission error at query time, in the cutover that starts reading the table rather than in the migration that created it. Caught on 2026-08-28 for `season_projections_index` only because the schema diff was read line by line before committing; the fix is a one-statement adhoc, and the check worth running is `has_table_privilege('league_data_view_reader', '<table>', 'SELECT')` against a peer table as a positive control.

**Do not wrap an adhoc file in `BEGIN`/`COMMIT`** — `db-exec.sh` already runs it as a single transaction, and a nested `BEGIN` only emits `WARNING: there is already a transaction in progress`. Some older files in `db/adhoc/` carry the redundant pair; they are not the pattern to copy.

**The status banner is machine-owned — `db:exec` refuses a `db/adhoc` file without one.** It rewrites `-- STATUS: PENDING` to `-- STATUS: APPLIED <date> against league_production` in place on success, so there is no window where the apply has happened and the file still reads pending, and it REFUSES a file already marked APPLIED (`--reapply` overrides). That refusal is the real point: three headers advertised applied work as pending until 2026-07-27, one of them a non-idempotent two-`DROP COLUMN` file that a second run would have failed or half-applied. Commit the rewritten header in the same commit as the apply; the script prints the command.

**Abandoning a design does NOT disarm its adhoc file — a superseded migration sits in HEAD at `-- STATUS: PENDING`, which is exactly the state `db:exec` accepts.** The banner that makes a file runnable is the same banner that makes it look like ordinary pending work, so a stand-down leaves a loaded weapon behind indistinguishable from the queue. On 2026-08-18 the auction-economy collapse was dropped by operator ruling after the consumer sweep was reverted out of the tree — and `db/adhoc/2026-08-18-separate-auction-economy-from-format-identity.sql` stayed in master for hours afterwards, dropping two columns, deleting ~219,000 analysis rows and rebuilding `league_formats_config_unique`. It survived because the supersede reasoned about the SWEEP: the sweep's worker had reverted its own 31 files and reported so, and that report was generalized to cover a file which predated the worker and was outside its scope. Nobody had reverted it because nobody had ever committed anything but its creation.

Two rules. **Deleting the adhoc file is part of the supersede, in the same change that records the decision** — not a cleanup step, because the window between them is one `db:exec` away from an irreversible apply. And **a fix or revert attribution is a claim about a specific commit's diff**: `git log --oneline -- <file>` on the migration would have shown one commit and no revert in a single command. This is the same trap the top of this guide records for credited fix hashes, in the one place where believing it costs production data rather than time.

**Dry-run a data migration before applying it: copy the file, replace the tail with a deliberate `RAISE EXCEPTION`, and run the copy through `db:exec`.** The wrapper is `--single-transaction` with `ON_ERROR_STOP=1`, so a forced abort at the end rolls the whole thing back while still executing every statement against production data — which is the only way to find a constraint violation that no amount of reading the SQL surfaces. On 2026-08-04 a 189-row duplicate-person merge dry-ran twice before it was correct: first it violated `player_nfl_player_id_unique`, because copying an identifier onto the surviving row while the donor row still holds it puts two rows at the same value for the duration of the statement (fix: snapshot the donors, delete them, then fill from the snapshot); then a pre-delete guard caught a table missing from the re-point list. Both would have aborted the real apply mid-file. Two things to get right: strip your own `BEGIN`/`COMMIT` (the wrapper supplies the transaction, and an explicit `COMMIT` inside it defeats the rollback), and keep the dry-run copy OUTSIDE `db/adhoc/`. That last point used to read "give the copy a `-- STATUS:` banner that is not `PENDING`", which cannot be done: `db-exec.sh` applies the banner rule only to files under `db/adhoc/`, and there it accepts exactly two values — it refuses `APPLIED` outright and refuses anything that is not `PENDING` with "carries no machine-readable status banner". So a dry-run copy in that directory either cannot run or is indistinguishable from the real file. Put it under `tmp/` and pass the absolute path; the banner check does not apply and the unconditional `RAISE EXCEPTION` is what makes it unmistakable. Cheap enough to be the default for anything that deletes rows.

**The rollback is not total: `nextval` is non-transactional, so any sequence the dry run advanced stays advanced.** "Rolls the whole thing back" is true of every row the file writes and false of the sequence counter behind it, which is the one piece of state a `ROLLBACK` deliberately does not restore — Postgres cannot give a value back without serializing every caller of the sequence. So a repair that assigns fresh identity values consumes them on each rehearsal, and running the dry run twice before the real apply leaves two gaps rather than one. That is harmless where the column is an opaque surrogate (2026-08-17, the `jobs` surrogate-key duplicate repair, which draws two `nextval`s), and it is worth thinking about before dry-running anything whose sequence values are user-visible or contiguity-dependent. The practical rule: never assert a post-repair sequence position or a specific assigned id in the file's own post-conditions, because the dry run moves it out from under the real apply — assert the PROPERTY you need (zero duplicates, row count unchanged) instead of the values that establish it.

**The server sets `statement_timeout` to 40s, so a large `ALTER TABLE` is CANCELLED partway and the rehearsal cannot warn you.** This is the one failure mode a scratch-database rehearsal is structurally blind to: the scratch database carries the SCHEMA and none of the rows, so every rehearsed DDL is instant by construction and exits 0 no matter how long the real one would take. On 2026-08-08 the `nfl_plays.updated` retype — 1,483,118 rows across 27 partitions at 8,489 MB — died at 42s wall on `canceling statement due to statement timeout`. It rolled back whole (`db-exec.sh` is `--single-transaction` with `ON_ERROR_STOP=1`), so the failure is clean rather than partial, but it lands in the middle of an apply window with the companion file already applied.

The 40s is `statement_timeout` in the server's `postgresql.conf` — `boot_val 0`, `reset_val 40000`, `source configuration file`. There is **no role-level or database-level override** (`pg_db_role_setting` carries only `search_path` and `log_min_duration_statement` for `league_writer`) and `db-exec.sh` passes no `PGOPTIONS`, so nothing outside the file can raise it. Put the override in the DDL file itself, where it is transaction-local and reverts when the transaction ends:

```sql
SET lock_timeout = '30s';
SET statement_timeout = 0;
```

**Set `lock_timeout` in the same breath, and do not leave it at 0.** Once the statement is QUEUED for `ACCESS EXCLUSIVE` it blocks every new reader behind it, so an unbounded wait to ACQUIRE is strictly worse than failing — 30s to acquire, unlimited to execute, which is the asymmetry you want. Estimate whether you need this from the table's real size (`pg_total_relation_size`) rather than from the rehearsal's timing, and treat any rewrite of a table above roughly a gigabyte as needing it.

**A `VALUES` list restoring a wide table types every column from the FIRST row, so a backup replay of a sparse table fails on a column that is `NULL` everywhere.** Postgres infers `text` for an all-`NULL` column and then rejects it against the real type — `column "jnum" is of type smallint but expression is of type text` — naming one column when the problem is the whole list. Cast every value in the first row (`CAST(NULL AS int2)`, `CAST(2001093004 AS int4)`, ...) and the remaining rows coerce to it. Hit 2026-08-04 replaying 256 `player_gamelogs` rows across 106 columns, 57 of them null on every row; the rollback-only dry run caught it before the real apply.

## A green suite is not evidence a writer can execute

**A writer that names a column which does not exist passes the whole suite, because `test/global.mjs` loads the SAME `db/schema.postgres.sql` that is missing it.** The two halves of the check fail together, so a green suite is not evidence the writer can execute against any database — and the number is reassuringly large while it happens. On 2026-08-04 `dd48ce077` shipped `generate-league-format-player-seasonlogs.mjs` writing `points_added_net_rank`, `points_added_net_position_rank`, `points_added_net_per_game_rank`, `points_added_net_per_game_position_rank` and `points_added_net_cap_dollars`; none of the five existed, 2947 tests passed, and the commit was pushed and deployed. It would have thrown `column ... does not exist` on the generator's next run and taken the stats pipeline with it (`libs-server/stats-pipeline.mjs`). The gap is that no spec runs that generator, so nothing ever executed the insert. **When a commit adds a column to an insert object, check the column exists in `db/schema.postgres.sql` — a `git show HEAD:db/schema.postgres.sql | grep` costs one command** — and prefer running the generator itself over trusting the suite — where it has a `--dry` flag, which builds the full insert and logs samples without writing. **Check for the flag rather than assuming it: only 98 of the 240 scripts have one, and it is absent from several of the highest-risk generators.** A 2026-08-05 validation pass reached for it on `generate-rosters`, `generate-league-formats`, `calculate-league-careerlogs`, `process-projections`, `project-lineups`, `import-rotowire-practice-report` and `generate-nfl-team-seasonlogs` and **none of the seven had it**, so the intended validation could not run as written. The fallback that needs no execution and no writes: extract the insert payload's keys and check each against `information_schema` for the target table, plus the `onConflict` target and the `merge()` list. That is what found three nonexistent columns in `generate-player-snaps` (2026-08-05, `6ba0d1d02`). Note this is the exact inverse of the deploy-lag rule in [the shipping guide](ship.md): there, committed code was ahead of a deployed schema; here, committed code was ahead of the schema file that both production AND the suite derive from, which is why neither could see it.

**The data-view sibling of that gap is the BUILDER/EXECUTOR split: every spec here calls `get_data_view_results_query` and none calls the default export, so the `SET LOCAL` prelude that runs on every cache MISS has no oracle at all.** On 2026-08-19 extracting the per-query budget into a `DATA_VIEW_WORK_MEM` constant moved the quotes off the SQL literal, emitting `SET LOCAL work_mem = 1GB`, which Postgres rejects outright with `trailing junk after numeric literal`. It reached production behind a green 4227-test suite, a green `check-data-view-sql-validity`, a clean `preflight:deploy` and green CI — every one of which reads the BUILDER's output, where the prelude does not appear. A warm redis key also answers before the prelude is ever emitted, so the whole class is invisible to any probe on an existing saved view. `test/data-views-session-settings.spec.mjs` closes it by ROUND TRIP against a real server (proven red at `260af0c6c~1` on both the timeout and the `|| 40000` fallback arm); when you touch anything in that prelude, that spec is the gate, not the goldens. The general rule this shares with the paragraph above: **extracting a value into a constant moves the SQL quoting decision to the interpolation site**, and a string that is still perfectly good JavaScript is the one shape no static gate here can distinguish from valid SQL.

**`db:exec`'s `CONCURRENTLY` guard greps the whole FILE, so the word in a comment refuses a file that must stay transactional — and the suggested fix is dangerous there.** The guard exists because `CREATE/DROP INDEX CONCURRENTLY` cannot run inside a transaction block, and it prints `Re-run with --no-transaction`. But it cannot tell a statement from prose: on 2026-08-03 a file whose header said "no `CONCURRENTLY` anywhere, because TRUNCATE empties both tables first" was refused, and that file was a `TRUNCATE` plus two `ADD COLUMN`s plus an index swap — precisely the shape that must be atomic. Taking the suggestion would have run a destructive statement with no rollback. Reword the comment to avoid the literal token (say "no non-blocking index build is needed here") rather than passing `--no-transaction`, and state in the header that the transaction is required. Reach for `--no-transaction` only when a real `CONCURRENTLY` statement is present and every statement is independently re-runnable.

## The apply window, and candidate schemas

**Applying DDL to production opens a window in which ANY other session's `yarn export:schema` can commit your change for you — the one-commit rule is not yours alone to keep.** The recipe says apply, export, and sweep land in one commit precisely so master never has a schema declaring a column its code cannot name. But `yarn export:schema` dumps the whole live database, so between your apply and your commit, an unrelated cluster that exports for its own reasons will pick your column up and ship it without your sweep. That is not hypothetical: on 2026-07-29 the `nfl_games."timestamp"` -> `kickoff_at` retype was applied and its sweep still in progress when `872cfb8f` (an unrelated `projections` rename) regenerated the schema, and master went red on six tests — two in `historical-injury-index-sql.mjs`, four inserting the old column in `test/teams.reserve.spec.mjs`. The retyping session had done nothing wrong and had not yet committed anything. Two consequences worth planning around: keep the apply-to-commit window as short as you can and do not start a long consumer sweep with the DDL already applied if you can sequence it otherwise; and when it does happen, recognise the shape immediately — a schema/code disagreement on master that you did not commit — because the sync-all pre-push guard then refuses every push to the repo INCLUDING the commit that repairs it, and clearing it needs `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh` (never a bare `=1`, never a direct push). The corollary for the exporting session: `yarn export:schema` is never a private act in a shared tree, so read the diff for columns that are not yours before committing it — though note the exporting session cannot solve this for you, since an export that refused to carry foreign DDL would produce a schema file disagreeing with the live database, a worse failure than the one it prevents. The window closes only at the applying end. **Which DDL opens it: renames and drops, not additive changes** — with one exception that is not about the DDL at all. A new table or column makes the schema a superset of what the code needs, so nothing fails to resolve; a rename removes something committed code still names. The exception is an additive column that widens a table's GRAIN, where the damage is done by the BACKFILL rather than by the `ALTER`: adding `pff_player_seasonlogs.season_type` on 2026-08-14 was harmless until 12,616 scoped rows were written, at which point the deployed emitter's `left join ... on pid and season_year` — correct against the old grain, and unchanged — began matching three rows per player and every `player_pff_*` data-view column fanned out 3x in production. The `ALTER` and the deploy were minutes apart; the fan-out window was the twenty minutes between the backfill and the deploy, and no gate can see it because the committed code is right and the deployed code is right for the schema it was written against. **Sequence a grain-widening backfill immediately before its deploy, never as a separate step afterwards**, and check the redis cache for entries written inside the window (`/data-views/*` payloads whose pid list has duplicates). The same 2026-07-29 window fired three times in one afternoon and only once did damage — the `kickoff_at` retype above — while the same mechanism carried two other clusters' new tables to master harmlessly. Left unrepaired it is not merely a red CI: production ran the conformed schema against stale code for an hour, and the two live GET routes naming the dropped column (`api/routes/players.mjs`, `api/routes/stats.mjs`) began returning 500s once real traffic reached them. This is strictly stronger than the deploy rule further down — a deploy can lag safely, a commit cannot.

**The way to sequence it otherwise: build a CANDIDATE SCHEMA and sweep against that, so production is untouched until everything is green.** Load the committed schema into a scratch database on the `:5433` container, apply your `db/adhoc` files to it, then dump it through `scripts/export-schema.sh`'s own flags and `awk` post-processing (see the "Building a candidate schema by hand" note below — a raw `pg_dump` is not a drop-in substitute and fails as a mocha hang). Copy that over `db/schema.postgres.sql` in a throwaway worktree and run the whole cluster there: consumer sweep, full suite, `check-data-view-sql-validity`, the ratchet, eslint, prettier, and golden regeneration. Only then apply to production, `yarn export:schema`, commit, and deploy — a window of minutes with no debugging inside it, instead of hours. The 2026-08-05 shorthand cluster (204 renames + 9 drops, 434 files) ran this way and its apply-to-deploy window was **eight minutes**; it also caught three defects that the apply-first order would have found in production instead — a PL/pgSQL trigger body that would have failed every `league_formats` write, a silent absent-key on the roster read path, and a data-view param emitting a dropped column. Two things this does NOT get you: `audit-schema-conformance.mjs` ignores `LEAGUE_SCHEMA_FILE` and reads the tracked path (hence copying over it in the worktree — setting the variable reports the TRACKED numbers, which reads exactly like a migration that did nothing), and the candidate dump will differ cosmetically from production's in `CHECK`-constraint array spelling when the two `pg_dump` versions differ, which is not drift. **And a third: a candidate schema makes your LOCAL suite green on code that CI cannot run.** CI reads the tracked `db/schema.postgres.sql`, so if you commit schema-dependent code in one commit and the export in the next, the first commit is red on GitHub no matter how green it was locally — and because the red-main pre-push guard then blocks every league push fleet-wide, the fix sitting in your very next local commit cannot push itself. That happened on 2026-08-13 with `league_pauses`: the guard queried a table the tracked schema did not declare, ~35 specs failed on `relation "league_pauses" does not exist`, and clearing it needed `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh`. **Ship the DDL, the export, and the code that depends on them in ONE commit** — the same one-commit rule the note above states for the apply, for the same reason, at the other end.

**And the sweep has to LIVE in the worktree, not merely be run there — an uncommitted schema-dependent sweep sitting in the shared checkout breaks every sibling's suite run, silently and for as long as it sits.** The one-commit rule and the candidate-schema recipe together leave the sweep with nowhere legitimate to be: it cannot be committed before the export, and the shared tree is where it lands by default. That default is the hazard. `test/global.mjs` loads the TRACKED schema, so any writer naming a not-yet-created column fails 42703 for anyone running the suite in the main checkout — measured 2026-08-18 on the auction-economy cluster, where `find_or_create_league_format` inserting a pending `valuation_salary_cap` took `test/leagues.teams.add.spec.mjs` from 10 passing to 0 passing / 2 failing, via `db/fixtures/league.mjs`, which nearly every league spec runs through. A sibling sees a red run whose cause is invisible in their own diff — the same shape as the `dist/` and `yarn build` traps above, on the suite instead of the bundle. So do the EDITS in the throwaway worktree from the start, or hold them as a patch (`git diff -- <paths> > …`) and keep the shared tree clean; if you must park mid-cluster, revert the sweep out and restore it later rather than leaving it in place. Verify the patch reconstructs before you rely on it — apply it in a scratch worktree and diff every file against the tree you are about to revert, since a bare `git diff` silently omits any untracked file the cluster added.

## Build-and-swap, statistics, grants, staging

**A build-and-swap that RENAMES the old table instead of dropping it turns `check-schema-conformance-ratchet` red, and the baseline cannot absorb it.** Retaining the old table under a new name is the right call for a large migration — `db-exec.sh` runs a file as one non-interactive transaction and exits, so there is no post-commit recovery short of a full restore. But the conformance baseline keys every violation on `table.column`, so the rename mints brand-new keys for the SAME non-conforming columns the baseline already carried, and the ratchet reports them as new debt. The 2026-07-31 keeptradecut restructure retained `keeptradecut_rankings` as `keeptradecut_rankings_pre_valuations` and the ratchet went to exit 1 on `.d`, `.qb` and `.v` — none of which was new. The blast radius is the whole repo, not your cluster: a red master makes the sync-all pre-push guard defer **every** push to `mistakia/league`, so unrelated sessions' commits pile up behind a gate whose cause is invisible in their diffs (four were parked within six hours). Two rules. Do **not** `--rebaseline` — the entries vanish when you drop the table, so you would write stale ones and bury a real regression landing in the same window. And plan the retention window in hours, not days: the drop is what clears it, so verify fast and drop, or post a bulletin naming the cause so siblings do not debug your gate.

**`CREATE TABLE ... AS SELECT` produces a table with no statistics — `ANALYZE` it in the same file.** The planner sees a fresh CTAS relation as tiny regardless of its real size, so a swap that puts 2.3M rows behind a name the API reads on every page load ships with plans derived from nothing until autovacuum eventually gets to it. The 2026-07-31 restructure's DDL omitted this and it had to be run by hand immediately after the apply. Any build-and-swap file should end with `ANALYZE <new_table>;` before the rename, alongside the constraints and grants.

**`REVOKE SELECT ... FROM league_reader` on a new table LANDS AND IS INERT — that role is a member of `pg_read_all_data`, which no per-table revoke defeats.** This matters because the revoke is what someone writes when a table holds something sensitive, and every observable says it worked: the statement succeeds, and the table's ACL genuinely carries no `league_reader` entry (`{league_writer=arwdDxt/league_writer}`). The role still reads every row, because `pg_read_all_data` is a built-in that grants SELECT on every table in every schema independently of per-table ACLs — and `league_reader` is what `base db query league` and every read-only analysis session connect as. Confirmed 2026-08-15 adding `manager_waitlist_submissions`, which holds candidate PII from non-members. Two consequences: **do not state in a table comment or a task that a table is readable by one role only** without checking `pg_auth_members` first, and note that `ALTER DEFAULT PRIVILEGES FOR ROLE league_writer ... GRANT SELECT ON TABLES TO league_reader` is standing, so a new table is readable on arrival even before you consider the built-in role. Narrowing this means dropping the membership and granting per-table SELECT, which changes what every read-only session in the fleet can see — a fleet-wide decision, not a per-table one.

**A staging table left in `public` on production breaks `yarn export:schema` for EVERY session, not just yours.** `pg_dump` takes `ACCESS SHARE` on every table it can see, in one `LOCK TABLE` naming all of them, so a scratch table owned by a role the export role cannot lock fails the whole dump with `permission denied for table <staging>` — not a partial export, no schema file written, and the error names a table that has nothing to do with whatever the exporting session was working on. A 2026-07-29 projection backfill loaded six `projection_backfill_*` tables as `postgres` and every subsequent export failed until they were dropped. Two rules: create bulk-load staging with the same role that runs the export, or drop it in the same session that created it — and never leave it in `public` across a commit boundary. If an export suddenly fails naming a table you have never heard of, this is why; `\dt public.*` and ask whose it is rather than debugging your own change.

## Sweeping consumers after a rename

**Column renames must sweep query call sites, not just the DDL.** A rename lands green while leaving code that still names the old column, because most such references only fail when their code path actually executes. The 2026 `year`/`seas_type` -> `season_year`/`season_type` conformance left four seasonlog and careerlog generators still filtering on `nfl_games.year` and `ng.seas_type`; each threw Postgres 42703 at runtime and had silently aborted every scoring and league format seasonlog build until it was found by a backfill months later. After renaming a column, grep the old name across `scripts/`, `libs-server/`, `jobs/`, and `api/` and run the affected generators once, rather than trusting the schema export to be the whole change. Beware unqualified object-literal predicates (`.where({ year, seas_type: 'REG' })`) — they read as local variables and do not grep like column references.

**The rename's other half: an UNQUALIFIED predicate that was fine before can become AMBIGUOUS after, and the failing query is one nobody edited.** Conforming a column to a name a joined table ALREADY carries collapses the accidental disambiguation the old name provided, so Postgres rejects the whole statement with 42702 `column reference "<new>" is ambiguous`. The 2026-08-05 season_grain conform hit this in `libs-server/restricted-free-agency-bids-query.mjs`, whose builder filtered a bare `.where('season_year', year)`: its three callers join `restricted_free_agency_nominations`, which had been conformed to `season_year` by an earlier cluster, so the predicate was unambiguous only while the bids table still said `year`. That single line was **83 of 165 suite failures** — a shared query builder multiplies one defect across every caller, which is also why the failure count read like a scattered regression rather than one site. Note the sweep itself is what introduces it, so no pre-rename grep of the old name can find it: the check is to list each renamed table's join partners and grep for unqualified predicates naming the NEW column. Loud on execution, so the suite catches it — but only where a spec exercises the path.

**A routes-scoped alias grep does not see the websocket layer.** When a rename ends a wire alias-back, `api/routes/**` is the obvious place to sweep and it is incomplete: three of the nine `year`-to-`season_year` alias-backs removed on 2026-08-05 lived in `api/sockets/auction.mjs`, on the broadcast path that hands bid and transaction shapes to the client. Sweep `api/sockets/` alongside `api/routes/` for anything that shapes a response.

## The consumer gates, and what each cannot see

**`db/gates/check-renamed-column-consumers.mjs` is the gate for that sweep, and its two halves are wired differently on purpose.** GATE 1 — every `'<table>.<column>'` literal in server code must resolve against `db/schema.postgres.sql` — needs no rename list and no base ref, so it cannot drift and cannot go red on a sibling's in-flight migration; it runs in CI. GATE 2 answers the harder question: did THIS change remove a column whose old name a consumer still reads. It diffs the schema against a base ref, so **run it by hand per cluster** and give it the pre-cluster revision:

`yarn check:cluster --base <pre-cluster-ref>` runs it; `node db/gates/check-renamed-column-consumers.mjs --gate 2 --base <pre-cluster-ref> --unadjudicated` is the direct form when you want the unadjudicated set.

**Give it a ref that resolves, and check that it did.** Handed a base ref git cannot resolve, this gate prints a one-line `SKIPPED: could not read db/schema.postgres.sql at <ref>` in the middle of its output and then exits **0** with `GATE OK` — so a typo, or a ref that has since been garbage-collected, reads as a passed gate from every angle except the one line. `yarn check:cluster` resolves the ref itself and treats an unresolvable one as a missing prerequisite, which is the only reason a run through it cannot be fooled this way.

It is deliberately NOT in CI. A gate finding turns master red, and a red master defers **every** session's push to `mistakia/league`; gate 2's findings also need per-site adjudication by someone who knows the cluster, which CI cannot do.

**The thing to understand before trusting a gate-2 green: it is anchored on the affected TABLE, not on the column name.** A silent defect here is a query selecting an affected table WHOLESALE (no explicit projection, and a `.select('*')` wildcard counts) whose row loses the old key with no error while a consumer still reads it — an explicit projection naming a dropped column raises 42703 and is loud instead. Findings are adjudicated per `(table, column)` in `renamed-column-consumer-adjudications.json`, which records the QUERY site list reviewed so a new query site is reported rather than inherited. **That promise does not extend to READ sites, which is where this class of defect actually lives** — see the SPA paragraph below before writing an adjudication reason.

**Anchoring on the table buys reachability for FROM-target queries and loses it for JOINED ones — a table reached through `.join`/`.leftJoin` is invisible to gate 2, no matter how literal its name is.** This is stronger than the table-name-in-a-constant caveat and was undocumented until 2026-08-06. The candidate set comes from `db('<table>')` FROM-target literals only, so a query that says `db('rosters_players').leftJoin('transactions', ...)` puts `transactions` outside the gate's reach entirely. That is how `72346e579`'s rename of the transactions salary column shipped a live defect: `libs-server/get-league-rosters-from-database.mjs` never appeared in the candidate set — at `--base 62ca45544` the gate produces 36 sites for that pair and that file is not among them — so the pair was adjudicated already-swept off a single producer, players arrived with `value: undefined`, and `NaN || 0` at `libs-shared/roster.mjs:97` rendered every team's salary space as the raw $200 cap. The gap is general: 22 join-only sites across the same window. **A gate-2 green does not mean a joined consumer was checked.**

**That REACH gap is now covered by `check-knex-column-resolution`, with a number rather than an inference — 175 of 178.** Measured 2026-08-07 by instrumenting the resolver to separate tables that entered scope through a join from the FROM target: **178 (file, table) pairs where the table is join-reached, 175 with at least one resolved column reference**, leaving 3 uncovered (`generate-seasons.mjs::seasons`, `process-nfl-plays-player.mjs::player`, `resolve-player-match.mjs::player_aliases`). Two caveats worth carrying. The instrumentation has to be gated to the primary scan — the negative controls re-run `run_scan` with a source override and contaminated the first reading by 5x. And this covers REACH only: the silent wholesale-key-loss class is gate 2's, and reach and class are independent, exactly as the paragraph below establishes.

**But do NOT close that by widening `from_re` to join literals — it was measured on 2026-08-07 and does not work.** The obvious remedy reads as a one-line change and this guide recommended it for a day. At `37cc9f36b~1` with `--base 8f1abd79d~1`, adding `.join`/`.leftJoin` to `from_re` takes the candidate set from 259 to 284 sites and reopens **37 adjudications** — the exact cost the gate's own header predicts — while still reporting the live defect it was aimed at **zero** times. The reason is that the defect was never gate 2's class: `compute-roster-slot-metrics.mjs` carried explicit projections at both sites (`.select('tid', 'pid')`, `.select('r.tid', 'g.pid')`), so gate 2 skips them correctly. Gate 2 catches the SILENT loss of a key from a wholesale row; a stale column in a predicate is the LOUD 42703 class, which is gate 1's question. Generalising: **before widening a gate's reach, check that the defect you are aiming at is in that gate's CLASS** — reach and class are independent, and a reach fix aimed at a class miss costs a full re-adjudication and buys nothing.

**`db/gates/check-knex-column-resolution.mjs` is the gate for that class, and it is the fourth anchor: a column reference that names no table LITERALLY, resolved through the statement that binds it.** Gate 1 reads only `'<realtable>.<column>'` literals, which leaves the three shapes this codebase writes constantly — an ALIAS-qualified `'r.year'` where `r` is bound by `.join('rosters_players as r', ...)`, an object-shorthand `.where({ lid, year })` that reads as a local variable, and a BARE STRING `.where('status', x)` that names no table at all. It builds each statement's alias environment from its FROM target, its `.from(...)` calls and every join, then resolves each reference against `db/schema.postgres.sql`. An unqualified or bare reference is resolved ONLY when exactly one table is in scope; with a join present the name is genuinely ambiguous and guessing a table would invent findings, so those are counted as unchecked and printed. It needs no rename list and no base ref, so it is CI-eligible on gate 1's terms and is in the CI step; `yarn check:cluster` runs it with no prerequisite. Its ten negative controls run on every invocation and **four of them assert the gate stays SILENT**, because half of what it does is decide a token is not a column reference.

**The bare-string half has two traps worth knowing before you extend it.** The predicate family's FIRST argument is a column and every argument after it is a VALUE — `.where('type', 'TRADE')` binds a string second — while every argument of the list family (`.groupBy`, `.onConflict`, `.merge`) is a column. Reading past argument 0 for the predicate family resolves DATA as columns, silently, on a corpus where transaction types and season types are all lowercase strings. And a bare reference to an OUTPUT ALIAS the statement declares for itself is correct SQL that must be excluded: `.count('* as count')` then `.orderBy('count')` resolves against the projection, not the table. On this corpus that exclusion is the difference between **9 findings and 1** — the 8 it removes are all that shape. Because an exclusion removing 8 of 9 findings is indistinguishable from a collector that finds nothing, one of the four silence controls asserts exactly it; do not add such a filter here without the paired control.

**It carries no coverage-floor number, and the reason generalises to every gate here that is tempted by one.** It shipped with three — 200 files, 800 statements, 1500 references — and they were deleted on 2026-08-07 as redundant rather than ratcheted. The controls already cover the case they were written for: each of the first four has to FIND real corpus material of its shape before it can mutate it, so **emptying the corpus, making statement extraction return nothing, or making alias binding always fail turns all four red with NO MATERIAL** — measured all three ways. What the floors could not see is the failure that is actually reachable, ONE root going dark, because `walk_files` treats an unreadable directory as empty: moving `jobs/` aside leaves the three floors printing `GATE OK`, since `jobs` is 4 statements of 1493. They were also 22%, 54% and 45% of live coverage, loose enough that a scan could silently halve and still pass, and loose for the ordinary reason a hand-maintained number always ends up loose — an exact match turns unrelated commits red. Coverage is asserted instead **per corpus root**, derived from `ROOT_EXPECTATIONS`: every root must contribute at least one file and at least one knex statement, except `libs-shared`, which must contribute exactly zero because it is isomorphic and reaches the SPA bundle. That last one is an architectural assertion rather than an exemption — a knex statement there is a defect. Nothing in the declaration is a measurement, so ordinary churn moves nothing, and this is the same conclusion `check-api-response-shapes` reached from the other direction: when a control has to work anyway, a hand-maintained minimum adds nothing to the catastrophic case and fires on the ordinary one.

Its first run on master found **four live 42703s that every other gate was green over**, which is the argument for it: `teams.year` in `compute-optimal-metrics.mjs` (the sibling file in the same directory as the one `37cc9f36b` had just fixed, same generator, same cluster, missed by the same sweep), `nfl_team_seasonlogs.year` in `filter-prop-pairings.mjs`, `league_scoring_formats.scoring_format_id` in `load-simulation-data.mjs` (whose own sibling function 130 lines up writes the correct `.where({ id: ... })`), and `users.reset_token` in `POST /auth/reset-password` — a column that has never existed on `users`, so that route had been throwing on every call. All four were repaired rather than adjudicated, so the gate ships with an **empty adjudication surface**: there is no `knex-column-resolution-adjudications.json`, and the absence is the correct end state rather than an omission.

**Its UNCHECKED count is not a coverage note — it is where the 42702 class lives, and on 2026-08-18 it held two live production 500s.** The gate resolves an unqualified reference only when one table is in scope and files the rest as ambiguous, so it prints the number and asks nothing about it; 70 today. Resolving those 70 the other way — counting how many IN-SCOPE tables carry the name, and reporting a count above one — found `GET /api/leagues/:leagueId/draft` 500ing for every caller on an unqualified `count('trade_id')` over a `trades_picks` -> `trades` join the key conform had given a shared name, and `PUT /leagues/:id/poaches/:poachId` 500ing the same way on `poach_id` across `poaches` -> `poach_releases`. Two things about running that sweep. The gate does **not collect a PROJECTION argument at all** — `select`, `count` and the other aggregates are read only for the aliases they DECLARE — so `.count('trade_id as trade_count')`, which is the draft defect's whole shape, is invisible to it even before the ambiguity question; a sweep has to add that shape itself. And its false positives are exactly the inline-subquery ones below: 8 candidates over `api`, `libs-server`, `scripts`, `jobs` and `private`, 2 real, 6 nested builders whose columns bound to the outer table. Anything that resolves a bare name in a multi-table statement can also ask the 42703 question for free (zero carriers rather than two); that returned nothing here.

**Its one false-positive shape: an INLINE subquery, whose columns it binds to the ENCLOSING statement's table.** `db('player').where(function () { this.where({ formatted_name }).orWhereIn('pid', db('player_aliases').select('pid').where({ formatted_alias })) })` is correct SQL, and the gate reports `player.formatted_alias` — because the nested builder never becomes its own statement in the scan, so its column lands in the outer table's environment. On 2026-08-17 that turned master RED fleet-wide (sync-all `red_main_skip` defers EVERY league push, not just the offender's). **Fix it by HOISTING the subquery into a named binding** — `const alias_pids = db('player_aliases')...` then `.orWhereIn('pid', alias_pids)` — which the gate resolves correctly; the emitted SQL is byte-identical, verified by comparing `toString()` of both forms. Prefer that over an adjudication: the first entry in an empty adjudication file should not be a case the code can simply express in a form the gate reads. Two things generalize. **A gate finding on a line you believe is correct is a claim to test, not to suppress** — here the SQL was right AND the finding was worth acting on, because a form the gate can read is strictly better. And when CI fails, **read WHICH STEP failed before concluding anything**: this defect was masked for a full run by a transient `Clean install` failure (`invalid key: core.autocrlf` cloning the `workerize-loader` git dependency), so the suite and every gate never ran and the first re-run looked like a flake re-run. A green install is a precondition for any gate verdict, and an infra failure and a real one are indistinguishable from the run's status alone.

**A MODULE LOAD is not an oracle for a repointed writer, and neither is eslint — both stay green over a call site whose import you deleted.** The natural cheap check when you repoint N writers onto a shared helper is "do all N still load", and it answers nothing: an ES module with `record_projection_history` removed from its `#libs-server` destructure imports fine, lints clean under `yarn eslint`, and leaves the identifier simply UNDEFINED until the write path executes — which for an importer needs the network, so no test reaches it. Measured 2026-08-26 on the nine projection-history writers: deleting the named import from `private/scripts/import-pff-projections.mjs` produced `LOADS` and eslint exit 0, and only a source BINDING check went red. That check is three predicates per file, and all three are load-bearing: the file CALLS the helper, IMPORTS it, and no longer names the old table — the third is what catches a revert, since a file that never adopted the helper passes the first two vacuously by not calling it. This is the same shape as the payload-key-across-a-function-boundary miss above, arriving through the IMPORT rather than through the payload, and it is worth knowing before a repoint because a load probe is what most sweeps reach for first. Note where it leaves `private/`: no gate reads it, the suite never loads it, and its writer needs a vendor session to run — so the binding check plus a round-trip probe of the SHARED helper under `tmp/` is the whole available coverage, and the helper is what makes that enough.

**`private/` is in NO consumer gate's corpus, so a rename touching the PFF or odds importers has no gate at all — and every gate still prints `GATE OK`.** `ROOT_EXPECTATIONS` here is `api`, `libs-server`, `libs-shared`, `scripts`, `jobs`; `check-renamed-column-consumers` and `check-rename-alias-residue` scan the same roots, and the only gate that reaches into `private/` is `check-plays-column-repoint`. This is the code analogue of the `yarn test:private` note in [the test guide](test.md) — that paragraph establishes private SPECS are local-only, and the stronger fact is that private SOURCE is unreachable by the consumer gates entirely. Measured 2026-08-07 on the residual position/team conform, where the writers for three of the seven renamed columns live in `private/` and a full green gate sweep said nothing about any of them. The oracle that works is the candidate-schema recipe above plus, for a writer no spec executes, a throwaway round-trip probe under `tmp/` that calls the real exported function against the candidate database — `log_unresolved_player` reverted alone raises 42703 naming both the insert and the `do update set` halves, which is the only thing that distinguishes a moved payload key from a well-formed one that cannot execute. **When a cluster touches `private/`, budget for hand-verification and do not report a gate sweep as coverage of it.**

**`app/` is in NO consumer gate's corpus either, and a rename the SPA reads survives every one of them — the 2026-08-18 uid-retirement batch 4 shipped three live component reads of the retired column.** `ROOT_EXPECTATIONS` is `api`, `libs-server`, `libs-shared`, `scripts`, `jobs`; `check-renamed-column-consumers`, `check-knex-column-resolution`, `check-rename-alias-residue` and `check-league-schema-consumers` all scan those roots, and the suite drives the API over HTTP and never loads a component or a reducer. So the `Poach` Record declaring and reading `uid`, the poach-notice confirm passing `poach.get('uid')` (a null id on the write path), and the restricted-free-agency auction winner check reading `bid.get('uid')` against a `bid_id` wire all shipped green and surfaced only by re-sweeping `app/` after the deploy. The remedy is the same source-scan shape this guide recommends for `app/` elsewhere: a spec that scans `app/` for the retired accessor shapes and fails on any — `test/app.retired-uid-identifier.spec.mjs` is the worked form, proven red at the pre-fix revision. **Budget a re-sweep of `app/` for every rename, and do not report a consumer-gate sweep as coverage of the SPA.**

**That spec is HALF a gate, and the half it is missing is the one that took production down on 2026-08-18 — do not read the paragraph above as saying the class is covered.** It matches READS of the retired name (`.get('uid')`, `['uid']`, `.uid`, `hasIn([...'uid'])`), so it is structurally blind to a Record that declares `uid: null` or destructures a bare `uid,` — and a rename sweep that RETIRES the old key without declaring the new one leaves the Record carrying NEITHER spelling, which is exactly the shape the follow-up commit `46fdd72c6` created. An Immutable Record silently drops what it does not declare, so `league.league_id` was `undefined` at all ten read sites: the sidebar rendered "League not connected" and the draft saga requested `/api/leagues/undefined/draft`, which 500s. Five more Records were in the same state (`Trade`, `Waiver`, `Source`, plus the trades reducer keyed on `t.team_id`, a column the trades wire has never carried). The blindness is MEASURED, not inferred — the spec passes at `f2c17d6a3~1` with three Records broken, and the full suite reads an identical 4185 passing at both that control and the fix, because no spec anywhere loads a Record, a reducer or a field registry. So a green `app/` source-scan plus a green suite is not evidence about a renamed surrogate key on the SPA; the gate that would cover it asserts each wire-built Record DECLARES the id its reducer keys on, three ways (declaration, factory destructure, constructor call).

**That gate now EXISTS — `test/app.record-declares-reducer-key.spec.mjs`, landed 2026-08-18 — and the "no spec anywhere loads a Record" claim above is history rather than current state.** The resolver hook (see the `app/core` importability passage in [the SPA guide](spa.md)) is what made it writable: the spec LOADS each Record instead of reading its text, so a missing key is a constructed instance that does not carry the field — the browser's own observable — rather than a string absent from a file, which is precisely the blindness the source scan could never close. Four legs over the 10 `app/core` domains carrying both a reducer and a Record: a roster floor, then declaration / factory destructure / constructor call for every entity id the domain's wire factory consumes, then reducer agreement. Calling the factory is not redundant with the declaration — the factory is an INDEPENDENT enumeration of the field list, so a field can be declared on the Record and still dropped between the wire and the store.

The fourth leg is what catches `t.team_id`, and it needs no type inference: an id read off an object the SAME call hands to the domain's factory must be a field that Record declares. The discriminator is the factory's own destructure — `create_trade({ trade_id, ... })` says a trade carries `trade_id`, while `create_season({ wildcard_round, ... })` consumes no id at all, the honest signal that a Season is built FROM a league object, so `seasons` is reported out of reach instead of reported as a finding.

**Proven RED at `f2c17d6a3~1` on all six findings**, including `trade/reducer.js:107`. One limit worth knowing before you trust that pattern elsewhere: the `League` case could NOT be reached by reverting its file, because at that revision `app/core/leagues/league.js` still imports the `@constants` webpack alias which `169c4bfc5` later migrated — so the module fails to load for an unrelated reason and the red proves nothing. That is the extraction-destroys-the-proof trap this guide records above, arriving through an ALIAS MIGRATION rather than a refactor, and it is easy to misread as a working control. It is covered by mutation instead (delete `league_id` from the declaration to reproduce the `46fdd72c6` state, which fires all three legs). **When a revert-to-broken control fails on module resolution rather than on the defect, check whether an unrelated migration moved that file's imports before concluding anything.**

**A LOUD LOG IS NOT AN ORACLE — a writer can scream a complete Postgres error into an ENABLED debug namespace hundreds of times a night while `report_job` records `is_successful = true`, and the run's verdict is the only thing that decides whether anyone finds out.** This is the inverse of every silent-failure trap above and it is easier to miss, because the diagnostic everyone reaches for is already there and already correct. `scripts/import-players-sleeper.mjs` passed a renamed-away `start` key into `createPlayer` (the column became `nfl_draft_year` in `9631a948c`, 2025-06-16, and this guide was never swept); `libs-server/create-player.mjs:101-106` logged the full knex/pg 42703 naming `"start"`, with a stack, under a `create-player` namespace the importer itself enables — **579 times a night for over a year** — while the caller's per-row catch log-and-continued, `run()` returned `shortfall: null`, and `report_job` wrote success. No signal ever fired. Not one `player` row was created by any scheduled job in that window, on a table with no creation timestamp, so even the outage's duration was unprovable after the fact (the provable form is `player_pid_serial_seq` against the max embedded pid serial). Repaired 2026-08-17 in `87a6cc39a`. The durable rule: **a job's oracle is what its `run()` RETURNS, not what its writer prints** — no volume of correct logging substitutes for a condition, and a per-row catch that logs and continues converts every writer fault into a silent one at the run level. Give a scheduled writer a disposition partition whose buckets sum to the loop's iteration count with no remainder, so a disposition falling on the floor is itself a shortfall.

**`check-knex-column-resolution` is structurally blind to that class, and it is a CLASS miss rather than a reach one — `scripts/` was already in its corpus.** Re-run at `5bc8d7630` on 2026-08-17 it printed `GATE OK` over 953 files, 1554 statements and 4928 resolved column references, with all ten negative controls red, while the live 42703 above raised on every creation. The reason is that `start` was never a knex column reference at any point: it is an object-literal KEY in a function-call argument that reaches the insert through a spread **two files away**, in `createPlayer`. Every gate here resolves a column reference at the write site, so a payload key crossing a function boundary into a spreading writer is outside all of them. `createPlayer` is the only cross-file "spread the caller's payload into an insert" shape in the corpus, and it has nine call sites. Note also that `ROOT_EXPECTATIONS` (`db/gates/check-knex-column-resolution.mjs:177-183`) is `api`, `libs-server`, `libs-shared`, `scripts`, `jobs` — **`private/` is absent**, so 27 private scripts' knex statements are resolved by nothing at all, and `private/scripts/import-players-ngs.mjs` carries a dormant instance of the same defect (`nfl_status` against the real `roster_status`, at both a `createPlayer` and an `updatePlayer` site).

## The alias-residue gate

**`db/gates/check-rename-alias-residue.mjs` is the third gate, and it covers that class from the other side — run it on every rename cluster.** It anchors on the **alias-back site**, which needs neither a FROM-target literal nor a distinctive word, so it works for `value` exactly as well as for `rid`. The discriminator is that the alias TARGET name is a column the table actually LOST in the schema diff, which separates a rename alias-back from ordinary join disambiguation (`waivers.waiver_id as wid`) and takes the corpus's alias literals down to a handful. It reads both anchor forms — a qualified `'<table>.<new> as <old>'` and an unqualified `'<new> as <old>'` resolved from the enclosing `db('<table>')` statement (including one held in a builder binding), which is not pedantry: `libs-server/get-roster.mjs:48` writes the unqualified form and a qualified-only scan misses one of the two producers. The BARE side reads the matching four shapes — qualified, unqualified, wholesale `'*'`, and (since 2026-08-20) a statement with NO projection call at all — so both a `select('*')` producer and a `db('t').where({...})` awaited directly count against an aliasing one. Findings come in three classes with their own verdict questions — SPLIT PRODUCERS (aliased at one site, bare at another: the shape `72346e579` left on the transactions salary column), ORPHANED ALIAS (the new name is ALSO read as an in-memory key somewhere, so two vocabularies disagree: the `practice.*` shape), and UNIFORM (correct today, reported as a standing hazard). Adjudicate per `(table, column, file)` in `rename-alias-residue-adjudications.json`; an entry suppressing nothing is itself a finding — **but only when the run's base ref put that entry's column in the lost set, and until 2026-08-07 that qualifier was missing.** Every unused entry was reported STALE with the remedy "the site is gone, so the entry must go too", which made staleness a property of the caller's `--base` rather than of the tree: at `--base 62ca45544` (243 lost columns) all 15 entries were used and the gate read OK, while at `8f1abd79d~1` (27) and `c801b5a11` (0) all 15 read as stale over sites all live in the working tree. Acting on that output deletes load-bearing suppressions. An entry outside the run's lost set is now **NOT EXERCISED** — printed with a count, no verdict — so read that count before treating a green run as an audit of the file: covering all 15 needs a base ref spanning every rename window they were written for. `yarn check:cluster --base <ref>` runs it. **Unlike gate 2 it treats an unresolvable base ref as exit 2, not as a pass.**

**A UNIFORM verdict from this gate was untrustworthy until 2026-08-06 and is not any more — but the reason it was is the durable lesson, because the same asymmetry is easy to reintroduce.** An adversarial review falsified the oracle three ways on the day it shipped. The bare-producer half read only QUALIFIED `'table.column'` literals while the alias half read two anchor forms, so a producer projecting the row WHOLESALE (`select('*')`, or an unqualified bare projection) contributed nothing and a genuine SPLIT PRODUCERS case was reported as UNIFORM — "every producer aliases back, correct today" — with an empty bare-producer list. An alias-back against an imperative builder (`const query = db('x')`, then `query.select('col as alias')`) resolved to no table and was dropped silently. And `REGISTRY_PATH_MARKERS` matched `'data-view'` as a substring of the whole path, excluding 132 files including 13 real query emitters. All three are fixed, along with six smaller defects — comment prose counted as alias sites, a case-sensitive fast path, a partition-terminator miss that hid six tables, and a default `--base` that guaranteed exit 1. **The general rule: when a gate anchors on a pairing, the two sides must read the same shapes, and an asymmetry between them fails toward a confident green.** On the real corpus the repair reclassified six of fifteen findings out of ORPHANED ALIAS into SPLIT PRODUCERS, naming four bare producers no run had printed; none was a live defect, all four were opened and read the physical name.

Three things about it worth carrying. **The stale-adjudication rule is a real backstop, mutation-proven:** broadening `REGISTRY_PATH_MARKERS` to exclude every file still turned the gate red through 15 stale entries, so an already-adjudicated column cannot go quietly dark even when the scan is fully blinded. **`--base` is required and has no default** — there is no invocation that silently diffs against nothing. And **silence is still not total coverage**: an alias literal returned from a HELPER rather than written inside a `db('<table>')` statement resolves to no table and goes unreported, which is live at `libs-server/data-views/add-defensive-play-by-play-with-statement.mjs:72-73` (`'season_year as year'` / `'season_type as seas_type'` off a `to_inner_select_expr` helper — the path exclusion is gone, the sites are still invisible). 70 unqualified literals in the corpus resolve to no table today; the run prints that number, so read it.

**A DECLARED blind spot is not a sized one, and this gate's projection-less case was worth 21 producers against the 1 it named.** The header carried "a statement with no projection call is NOT counted as a bare producer" as a known limitation for two weeks, which reads as an acknowledged rounding error and was not: `db('rosters_players').where({...})` awaited directly returns the row WHOLESALE under the physical names, so it is a bare producer on exactly the same footing as `select('*')`, and the corpus holds 21 such reads of that one table. Closing it on 2026-08-20 moved nothing — 15 findings, 9 ORPHANED / 6 SPLIT, 0 unadjudicated, **0 adjudications reopened** — because widening the BARE side adds no ALIAS sites, and the residue set and every `(table, column, file)` key derive from the alias side alone. The whole cost was producer lines, 10 to 86, absorbed by capping the list at 8 beside a count.

**The reason to close it anyway is that a blind spot on one side of a pairing can FLIP a verdict under ordinary cleanup.** The `rid` alias on `rosters_players` rested entirely on the single wholesale producer `scripts/calculate-franchise-tag.mjs`. Giving that one statement an explicit projection instead of `rosters_players.*` is routine tidying that no reviewer would question — and it would have dropped the finding from SPLIT PRODUCERS to ORPHANED ALIAS while ~19 wholesale producers stayed live, swapping the reviewer's verdict question away from the one that caused the transactions salary-column defect. For a rename whose new name has no in-memory key reads, the same shape lands on UNIFORM, which is the false-green the 2026-08-06 fix above exists to prevent. So the durable rule is stronger than "the two sides must read the same shapes": **a producer count that can reach zero through cleanup was never a measurement**, and a gate whose class depends on a boolean over that count inherits the fragility.

**A control whose material lives in the CORPUS can be starved by someone else's cleanup — manufacture it instead.** The same commit restructured this gate's strip-proving control, which had asserted `unstripped_literals > stripped_literals` over the real tree: 345 against 341, a margin of FOUR carried entirely by two prose comments in `scripts/process-projections-for-league-format.mjs`. Deleting those comments is legitimate cleanup and would have taken the control green — exiting the gate **2**, with the failure reading as a broken strip over a strip that works perfectly. It is now a self-sufficient PAIR that makes its own prose from real material: take one corpus file's source, append a comment containing an alias literal, and assert both that the alias-SITE count is UNCHANGED and that the raw literal count is STRICTLY GREATER. An identity strip fails the first half (the injected alias becomes a site), a dead extractor fails the second (both counts go to zero), and no edit to the tree can starve either. The corpus-prose delta still prints, as an informational number rather than an assertion. **When a control's denominator comes from the corpus, ask what one ordinary commit could do to it.**

**The fourth anchor is not in any gate and has to be run by hand: the PRODUCER-anchored sweep.** It is the one that actually worked on the `player_salary` migration, which found ten consumer sites — six of which survived a green 3304-test suite. Sweep `<identifier>.<field>` where the identifier is an instance of the class whose field moved, and separately enumerate every consumer of that class's collection getters (`Roster` `.all`/`.active`/`.players`/`.get`). It anchors on the producer rather than on the column name, so it needs neither a greppable token nor a spec. It is deliberately not gate code because it cannot self-derive its input: the alias gate derives its whole list from the schema diff, while this one needs a known moved field and a known class, so encoding it would mean hand-maintaining a class-to-field registry that drifts silently. **Treat it as a required step of any rename cluster that moves a field on a shared class.** Budget for the grep shapes that missed during that migration: `get('value')` does not match `get('value', 0)`, `value:` does not match the object shorthand `value,`, and one pattern enumerating `getExtensionAmount` callers found 2 of 9.

This replaced a hardcoded stoplist of common English column names (`total`, `year`, `value`, `team`, `score`, `start`, ...) that the bare-identifier scan needed to stay usable. That stoplist suppressed exactly the names renames concentrate on, and silently: `72346e579` renamed `scoring_format_player_projection_points.total` and the gate returned 129 findings with not one of them `total`, over a defect that wiped a year of projection values and exited 0. **Never re-introduce a name filter to quiet this gate** — adjudicate the sites. And take the negative control seriously: delete one adjudication, confirm its sites reappear, put it back. That is the only thing separating "no findings" from "cannot see findings", and this gate has already failed that distinction once.

**The SPA is the surface this gate reports WORST, and a reason that overclaims about it has already cost a production defect.** Findings anchor on a `db('<table>')` query site; `app/` has none, so the SPA read list is not table-aware at all — it is one global list of "places this name appears in `app/`", stapled identically onto every table that ever carried the column. On the season_grain cluster that meant `spa_read_site_count: 198` for all 17 tables holding `year`: a constant, not a measurement. `read_sites` then hid even that, falling back to same-file server reads whenever the query file read the column itself. The reviewer saw a number and no filenames, wrote "every flagged read is `current_season.year`, a request parameter, or a same-named column surviving elsewhere", and that claim was false — `dashboard-draft-picks.js` was grouping picks on `'year'` and `draft-pick-sheet.js` was reading `.get('year')` off draft rows. The team page headed every pick `undefined` from the apply until `de3e0bb32`, with the gate printing `GATE OK` throughout.

Since `1974ccb88` each finding carries **`spa_high_signal_sites`**, always listed and never suppressed: SPA reads whose shape is an accessor (`.get('x')`) or a bare field argument (`groupBy(picks, 'x')`, matched in `app/` only, since the SPA has no table anchor to bound the noise). Property and index reads stay out — 182 of `year`'s 201 SPA sites were `.year`, and 145 of those `current_season.year`. On that cluster the high-signal list is **four lines** naming both live defects. Read it, and **never write a reason asserting something about read sites you did not open** — the entry records query sites, so such a claim is unfalsifiable on every future run.

Two things deliberately NOT done, both tested and rejected. Gating adjudication validity on the SPA site list: one ordinary line of SPA code (`row.get('year')`) reopened all 22 pairs and every one of the 236 findings, which defers every session's push behind a red master. And a standalone SPA sweep script: it works only with a tight per-cluster base ref (4 sites) and collapses over a six-month window (142 sites, dominated by redux store keys — `state.getIn(['app', ...])`, `player_map.get('value')`), so it would need the base-ref plumbing this gate already has. Note the gate change is PREVENTIVE only: it does not reopen an adjudication that is already wrong.

**`yarn check:cluster` pinned test-container gates to the container in `b0fbdb61b` — before that they inherited ambient `LEAGUE_DB_*`.** The runner probed `:5433`, declared the prerequisite met, then spawned the gate with a bare `process.env`, so a profile exporting `LEAGUE_DB_PORT=15432` (the `base db` league tunnel) sent it elsewhere. ## Surfaces no gate reaches

**Measuring whether an index on a PARTITIONED table is used: never grep `pg_stat_user_indexes` by the index's declared name, and never read the parent index's `idx_scan`.** Both return a confident zero over an index the planner is hammering, which is the direction that reads as permission to drop it. Two independent reasons. The parent index on a partitioned table accumulates NO scans — every scan is charged to the partition index — so its `idx_scan` is 0 forever. And partition indexes are named after their KEY COLUMNS rather than after the parent, so the name you know does not appear in the catalog at all. Measured 2026-08-22 on `nfl_plays`: `idx_nfl_plays_fantasy_points` exists once with 0 scans, while its 27 partitions are named `nfl_plays_year_<year>_year_seas_type_week_bc_pid_psr_pid_trg__idx` and carry **941,275 scans between them** — a grep for `%fantasy_points%` returns the parent alone and reads as a dead index. Resolve the real names first (`SELECT indexname FROM pg_indexes WHERE indexdef LIKE '%<your predicate>%'`), then aggregate `idx_scan` across the partitions. The same applies to a partial index's predicate: a site converted from `WHERE x <> 'A'` to `x IN (...)` stops using it, because Postgres cannot prove the implication.

**A rename does NOT reach into PL/pgSQL function bodies, and no grep of this repo can find the ones it breaks.** Postgres rewrites the parsed trees behind views, indexes and constraints on `ALTER TABLE ... RENAME COLUMN`, so those follow the rename automatically — but a function body is stored as TEXT. It keeps compiling, stays invisible to every code-tree sweep because it lives in the database rather than in a file, and throws only when something calls it. The 2026-08-04 boolean-prefix sweep found `archive_completed_import_jobs()` inserting into `external_league_import_job_history (..., success, ...)`, which the same migration renamed to `is_successful`; nothing in the suite calls it, so the failure would have surfaced on the next 30-day archive run. **That example is now HISTORY, not a live instance — both the function and the table were dropped on 2026-08-08 (`6fd30fa41`), so do not expect to find either in `pg_proc` or the schema.** The rule it illustrates is unchanged and was re-proven by that drop: the same text-body property means `DROP TABLE` does not fail on or rewrite a function naming the table either, so the drop had to take the function first or leave it compiling and throwing at call time. Check `pg_proc` as part of any rename, not just `scripts/`/`libs-server/`/`jobs/`/`api/` — `SELECT proname, pg_get_functiondef(oid) FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace WHERE n.nspname = 'public' AND p.prolang = (SELECT oid FROM pg_language WHERE lanname = 'plpgsql')`, then grep that text for the old names and ship a `CREATE OR REPLACE` in the same DDL file. Note the schema dump does contain these bodies, so a sweep that greps `db/schema.postgres.sql` catches them too — but only if you think to include it, since it is not code.

**Building a candidate schema by hand: reuse `scripts/export-schema.sh`'s post-processing, or the suite hangs instead of failing.** `test/global.mjs` honors `LEAGUE_SCHEMA_FILE`, which is the right way to run the full suite against a post-migration schema without touching the shared tree's `db/schema.postgres.sql` — but a raw `pg_dump` is not a drop-in substitute for the committed file. The export script does two fixups after dumping (`awk 'NR==17{print "SET search_path = public;"} !/^\\(un)?restrict /{print}'`): it re-adds the `search_path` the dump itself clears at line 15, and strips the `\restrict`/`\unrestrict` meta-commands pg16 emits, which the `pg` driver cannot parse. Omit the first and the schema loads but every unqualified seed fails with `relation "player" does not exist`; omit the second and the load dies on `syntax error at or near "\"`. Both present the same way — mocha sits at 0% CPU producing nothing, because `--reporter min` prints only at the end — so it reads as the documented connection hangs or as a broken change, not as a malformed input file. On 2026-08-04 that cost a 40-minute run and a second one after it. Dump with the identical flags (`--schema-only --clean --no-owner --if-exists --no-tablespaces`), pipe it through that same `awk`, and give the run its own database. **Use the container's `pg_dump`, not the host's, when the host binary is older than the container's Postgres** — a local Homebrew `pg_dump` (v14, hit 2026-08-16) refuses the scratch dump with `aborting because of server version mismatch` against the PG16 container, and the rehearsal stalls before it starts. `docker exec -u postgres league-test-pg pg_dump -U league_test --dbname=<db> --schema-only --clean --no-owner --if-exists --no-tablespaces` matches the server version.

**An `onConflict([...])` target list is a column reference that does not look like one, and no gate here covers writer SQL.** A rename sweep that updates the inserted object keys and misses the upsert's conflict target produces valid-looking JS that Postgres rejects at execution with `column "<old>" does not exist`. The damage is worse than a plain failure when the writer follows the `delete().where({ lid })` then `batch_insert` shape this guide uses everywhere: the delete commits, the insert throws, and the table is left EMPTY rather than stale. On 2026-07-30 conforming `league_player_season_projection_values.year` to `season_year` updated the insert keys but left `onConflict(['pid', 'lid', 'year'])` on both new period tables; `process_league lid=1` aborted with the season table emptied, so `market_salary_adj` (renamed to `projected_positive_salary_at_available_cap` on 2026-08-18) and the `'0'` payload key vanished from `get-players` for a full cron cycle — blanking the adjusted-salary readout on league-home, the auction nomination panel and the selected-player panel. Both `yarn lint` and `check-data-view-sql-validity` were green throughout, because the former does not type-check SQL and the latter only EXPLAINs data-view column SQL, never `scripts/`. Add `onConflict` to the post-rename grep alongside `.where({ ... })`, and treat the next scheduled run of the affected writer as the real gate — not the deploy, which reports success either way.

**A BARE column reference inside a `.merge()` expression is ambiguous, and Postgres rejects the whole statement — insert half included.** The DO UPDATE expression's namespace holds both the target table and `excluded`, so `db.raw('total_checks + 1')` raises 42702 `column reference "total_checks" is ambiguous` rather than resolving to the stored value the author meant. This is not a rename hazard like the paragraph above — it is wrong the day it is written, and it fails on the very first INSERT, when no conflicting row exists at all. So the table is left EMPTY rather than stale, which is the tell: a tracking or counter table sitting at exactly zero rows is this defect until proven otherwise. `libs-server/draftkings/draftkings-tracking.mjs` shipped that way on 2025-10-01 and `draftkings_category_activity` held zero rows for ten months, at roughly 2,900 rejected statements a day. Qualify every bare column in a merge raw with the table name (`draftkings_category_activity.total_checks + 1`); reaching for `excluded` instead is a different statement, and for a "keep the old value unless ..." CASE it is the wrong one — `excluded` would wipe the field on every no-op check.

Two things made it survive. The writer wrapped the upsert in `try { } catch (err) { log(...) }`, so the failing path and the healthy path had the same observable and the importer reported success — the [[user:guideline/surface-pipeline-failures.md]] shape where diligent error REPORTING hides a failed run. And the log line was unreachable: `debug` matches a namespace EXACTLY, so the `draftkings` in the pm2 `DEBUG` list does not cover `draftkings-tracking`. That is a distinct failure from the `debug.enable` clobbering documented in [the scripts guide](scripts.md), and the two look identical from the outside — verified 2026-08-04 by instrumenting `debug.enable` across the real worker import graph, where no `enable()` call fires at all and the environment's set survives intact. When a namespace is silent, check membership before reaching for the clobbering story. **Finally, note where the evidence lived: 5,722 occurrences in the Postgres log and nothing anywhere application-side.** The database log is the oracle of last resort for any writer that swallows, and its rotation boundary is not the defect's onset — the "started 2026-08-02" reading here was weekly logrotate, and the same error is in every archive back to `.log.10.gz`.

**The same rename runs the other way too, and a PARTIAL fix is more dangerous than none — because its commit message reads as complete.** `972690b57` is titled "Fix generate-player-snaps onConflict: year -> season_year on renamed player_gamelogs" and did exactly that, while leaving `year` and `opp` in the INSERT PAYLOAD. So the writer went on raising 42703 at `checkInsertTargets`, and anyone grepping the log for whether the rename had been swept found a commit that says it was. What made it survive two weeks rather than one run is the script's own shape: `main()` catches the throw, logs it through `debug`, and calls `process.exit()` — so `generate-player-snaps` exited **0** while writing nothing, every night, and no exit-code oracle, no test and no signal could see it. `opp` was doubly wrong and doubly invisible: the query selects `opponent_nfl_team`, so the destructured `opp` was `undefined` and bound as `DEFAULT` before the column name was ever rejected.

Three rules. Read a rename fix against the writer's whole statement — payload keys, `onConflict` target, and `merge()` list are three separate column references and a commit that names one of them has not necessarily touched the others. Never accept a generator's exit code as evidence it wrote (`grep` the output for the insert count instead). And when you fix such a writer, add the spec in the same commit and confirm it goes RED at the pre-fix revision — that is the only thing that proves the coverage is real.

**This paragraph named `test/scripts.generate-player-snaps.spec.mjs` as that proof until 2026-08-05, and THE FILE DOES NOT EXIST.** Whether it was never committed or was lost, the effect is the same and it is the worst possible shape: the one place anybody would look to check whether this writer is covered asserted that it is. It is not, and nothing else executes the insert — which is how `generate-player-snaps` went on naming three columns that do not exist (`year`, `opp`, `pos` against `season_year`, `opponent_nfl_team`, `player_position`) under a fully green 3166-test suite, raising 42703 on every run while `main()` caught the throw and exited 0. Fixed in `6ba0d1d02`, and the spec was written on 2026-08-05 (`e88f9650c`) — it is now real, and it is proven red 4/4 at `6ba0d1d02~1` with that exact error. **Before citing any spec here as a gate, confirm the file exists** — `ls test/<name>.spec.mjs` — because a named-but-absent spec reads as coverage from every angle except the filesystem. The spec also shows the shape this class needs: it EXECUTES the insert, because a test that inspects the payload object passes at the broken revision — the payload was well-formed JavaScript naming columns that do not exist, and only the round trip tells those apart.

**As written on 2026-08-05 it could not see a TRANSPOSITION of `quarter` and `down_number`, which is the failure the alias migration risked most, and the reason is worth generalizing: its fixture set the two columns to the SAME value on every play.** A fixture that gives two columns identical values makes them interchangeable in the output, so swapping them — the natural failure of a word-boundary replace across `qtr`/`dwn`/`wp` — left the spec 4/4 green. It was widened on 2026-08-06 (`e765a6b07`) to run five plays whose quarter and down distributions differ in SHAPE (quarter 1/1/2/1 against down 2/1/1/1) plus one play below the neutral win-probability band, and it now asserts the `q${quarter}_snaps_off`/`_def` computed keys, `snaps_neutral`, the early/late down split and `snaps_low_prob` — proven red under that transposition, with the four older tests still passing. Two things generalize. **A computed key built by template literal from a renamed variable is the shape no grep and no column-existence check can reach**, so it is the specific thing a spec has to pin. And when a fixture holds two renameable columns at one value, it has no power to distinguish them no matter how many assertions it carries — vary them into distributions of different shape, or the coverage is nominal.

**The computed-key class bit TWICE in one cluster on 2026-08-16, and the second instance failed OPEN — which is why a spec, not a sweep, is the only gate for it.** The side-prefix conform renamed `off_personnel`/`def_personnel`, and `libs-server/parse-personnel.mjs` reads them as ``play[`${side}_personnel`]`` with `side` of `'off'`/`'def'`: the lookup went undefined and the loop's `continue` wrote NOTHING, silently, on a path two live importers use. The position-code conform then renamed `max_roster_*`, and `Roster.has_position_capacity` read ``league[`max_roster_${pos.toLowerCase()}`]``, so every position limit read `undefined`, `!limit` meant "no limit configured", and the check passed everything — a route answering 200 where it must answer 400. Neither is reachable by a name sweep, a column-existence check, or any consumer gate; both were caught only by specs that EXECUTE the path.

Two rules. **Before a rename cluster, grep for backtick-built column names** (`` `${ `` inside a property access) across `libs-shared`, `libs-server` and `app` and treat each as a manual site. And **replace the concatenation with an explicit map rather than fixing the string** — `starter_slot_league_columns` and `max_roster_league_columns` in `libs-shared/constants/roster-constants.mjs` are the shape, and the first one's comment already recorded this exact bug before the second one repeated it. A derived key is a rename that no tool can see; a map is one a reviewer can.

**Retiring a SENTINEL VALUE has the same blind spot one level up, and a consumer sweep that greps the sentinel in SQL predicates will miss the path that actually breaks.** A rename moves a NAME, so the sweep looks for a name; retiring a sentinel moves a VALUE, and the value survives in memory as an object KEY long after the query that produced it is gone. Planning the retirement of `projections_index.week = 0` on 2026-08-26, a full consumer inventory found every `where('week', 0)` site and none of the four reads of `player_row.pts_added[0]` in `scripts/process-projections.mjs`, which are both the numerator and the denominator of `market_salary`. That key exists only because the row-producing loop seeds from `first_projection_week_to_recompute`, which returns `current_season.week` — zero in the offseason. Moving the loop to week 1 without supplying a season key makes the numerator `undefined`, `Math.max(undefined, 0)` is `NaN`, `Math.round(NaN * undefined) || 0` is `0`, and every available player prices at $0 — reproducing the 2026-08-04 outage exactly, through code containing no week predicate at all. The plan's own new oracle could not see it either, because it watched the table the migration created rather than the quantity the incident destroyed. **When a plan retires a sentinel, sweep for the sentinel as an in-memory key (`x[0]`, `x['0']`, `x.ros`) alongside the SQL predicate, and point the oracle at the DOWNSTREAM quantity the sentinel feeds, not at the storage the plan is changing.**

**The computed key's sibling is a computed ALIAS, and it moves the WIRE key rather than the lookup — twelve blank-cell defects in one cluster, none of them reachable by any gate.** `create_field_from_nfl_team_seasonlogs` and `create_field_from_pff_player_seasonlogs` build the emitted alias from the column name (``select_as: () => `nfl_team_seasonlogs_${column_name}` ``), while the SPA hardcodes `player_value_path` as a string literal. So renaming the physical column silently moves the response key out from under the frontend: the query is valid, the API returns 200 with data, and the cell renders empty. The 2026-08-17 counting-stat conform moved thirteen of these; `test/data-view-player-field-parity.spec.mjs` caught the ONE on the pff family and the other twelve had no parity spec at all — they were found only by enumerating every `player_value_path` in `app/core/data-views-fields/` against the rename map, which is now a required step of any cluster touching a table whose field factory computes its alias. Note the COLUMN ID (`player_pff_fg_ep_kicker`) must NOT move with it: that one is persisted in saved views, and only the value path is derived.

**The reason those twelve had no parity spec was a stated EXEMPTION that was simply wrong, and it cost a second instance five days later.** `test/data-view-player-field-parity.spec.mjs` skipped the scoring-format-logs family on the grounds that every definition there carries a `select_as`, which the player-table rule skips because a key built from a PARAMETER has no single alias to compare against. That reasoning does not transfer: both factories in that family build `select_as` from the column name alone and take **no arguments**, so there is exactly one alias per column and CALLING it is an exact oracle rather than a restatement of the derivation. On 2026-08-17 the long-tail token conform moved the four `scoring_format_player_seasonlogs` rank columns and left their `player_value_path`s behind, blanking every rank column in the default data view; the exemption is removed and the assertion is live as of `2691ab1f4`. **Check the ARITY of a `select_as` before concluding a family is unassertable** — a zero-argument one is checkable, and the exemption is the thing to test, not to inherit.

**That sweep also shows why `\b<old>\b` is the wrong pattern for a rename.** The conform correctly moved the server definitions, the fields index and the goldens, and missed all four value paths, because the value path is the column name plus a suffix — `points_rnk_from_seasonlogs` — and a word boundary does not match between `points_rnk` and the `_` that follows it. Any renamed name that is a PREFIX of a longer identifier is invisible to a word-bounded sweep. Grep `<old>_` as well as `\b<old>\b`.

**And the third member of the family is a computed COLUMN ID, which is worse than either, because the id is the thing that must never move.** `app/core/data-views-fields/projected-table-fields.js` interpolates ONE `base_name` variable into both the persisted id and the `player_value_path` (``[`player_season_projected_${base_name}`]``), so the shorthand there reads as an ordinary variable assignment rather than as an identifier a held-out list would cover — the 2026-08-17 counting-stat conform's own commit message names the persisted-id class as a deliberate hold-out, and the hold-out covered the server file, where the ids are literals, and missed this one. It moved `pass_yds` and `rush_yds` while the server definitions, the SEASON_PROJECTIONS system view and the fields index all correctly kept the short spelling, so `app/views/pages/data-views/index.js` threw `Field not found for column_id` before reading a row: a blank SEASON_PROJECTIONS for every user (signals 125880/125881), with the five untouched siblings explaining why only indices 3 and 7 failed. No gate could see it — the goldens read the SERVER registry and stayed green, and `test/data-view-player-field-parity.spec.mjs` covers `player-table-fields.js` only. `test/data-view-projected-field-id-resolution.spec.mjs` now resolves every id that file BUILDS against the shared index, asserting RESOLUTION rather than spelling so a legitimate rename of both sides still passes, with a floor on the declarations it found so a refactor of the `base_name` key cannot leave it iterating nothing. **Before a rename cluster, grep for an id or a value path built by interpolation, not just for the literal name** — that is one `` `${ `` inside a bracket key or a template, and it is the only form of this class that reaches production as a blank page rather than a blank cell.

**`\b` fails at BOTH ends of an old name, and a residual sweep that guards only one end reads clean over the other.** `_` is a word character, so `\b<old>\b` matches neither `pff_field_goal_ep_kicker` (old name PREFIXED) nor `points_rnk_from_seasonlogs` (old name SUFFIXED). The 2026-08-17 long-tail conform hit both and only guarded the first: its residual scan searched `[A-Za-z0-9_]<old>` after the pff site was caught by the suite, and never searched `<old>[A-Za-z0-9_]`, so four `player_value_path` literals in `scoring-format-logs-table-fields.js` survived a sweep, a green suite and a full gate run, rendering every rank column of the default data view as an empty cell while the API returned the values correctly (fixed in `2691ab1f4`). **Sweep the residual set as `[A-Za-z0-9_]<old>` AND `<old>[A-Za-z0-9_]`, not as `\b<old>\b`** — the suffixed form is the more likely of the two here, because this codebase names derived keys `<column>_from_<table>` and the server aliases them from the column name.

Re-running the suffixed form across a whole rename list is cheap and mostly returns the conformed NEW names (which contain the old one as a prefix by construction), so read the hits rather than the count: what you are looking for is a stale literal, and a local variable or helper name wrapping correct SQL (`pos_rnk_map` over a `.select('points_position_rank')`) is cosmetic rather than a defect.

**A blind exact-name sweep corrupts three classes that all look exactly like column references, and the first pass of the 2026-08-17 conform hit every one before being reverted.** The recipe says "sweep by exact name"; from the counting-stat batch onward that is necessary and not sufficient, because three populations spell a league column and are not one.

- **Vendor field names.** `scoring.pass_td` and `scoring_settings.pass_td` are Sleeper scoring-settings keys, `BOX_SCORE_STAT_FIELDS` keys in `libs-server/pfr-gamelog-agreement.mjs` are Pro Football Reference box-score fields, `item.pass_yds` is the PFF projection payload. Each sits on one side of a vendor→league mapping whose OTHER side is the real column, so renaming the vendor half breaks the integration while everything still resolves and nothing throws until that importer next runs. The tell is a sibling key in the same object that is NOT in your rename map (`pass_att`, `pass_cmp`, `rec_yds` beside `pass_yds`) — that is a foreign vocabulary, not a partially-conformed one.
- **Persisted data-view column ids.** `create_projected_stat(projections_index_base('passing_yards'), 'pass_yds')` takes the PHYSICAL column first and the persisted COLUMN ID second; its siblings `'pass_comps'`, `'rush_atts'` and `'pass_tds'` keep their shorthand for that reason. Renaming the id breaks every saved view carrying it. The goldens are the oracle — this one was caught by four query fixtures going red, not by review.
- **Synthetic examples of shorthand.** `test/db.schema-conformance-interior-token.spec.mjs` fabricates `yds_gained` and `deep_pass_att_percentage` as names that read CLEAN under a bare-name rule. Conforming them makes the spec assert the opposite of what it exists to show.

The durable form is a sweep script carrying an explicit held-out list with a reason per entry, and the judgement rule from the prose-sweep section applies unchanged here: decide per `(table, column)`, never per name. Run the data-view goldens before believing any sweep — they are the only cheap oracle that discriminates a column id from a column.

**The red-at-the-broken-revision rule has a consequence worth stating outright: EXTRACTING a pure function to make it testable destroys the proof.** The extracted file does not exist at the broken commit, so the spec fails there on module-not-found rather than on the defect — a red that proves nothing, and one that reads exactly like a real one in a terminal. This matters because extraction is the obvious move when a consumer cannot be imported, and it is frequently suggested as the preferable one. The two goals are in direct tension: a spec either covers the code that was broken, or it covers code you wrote after the fact. Prefer a spec over the unmodified file even when that means checking the SOURCE rather than the behavior.

**The same rule is unreachable in the other direction when the DDL moved, which is the ordinary case for coverage added AFTER a rename cluster — and the substitute is a mutation control that reproduces the design the cluster REJECTED.** A fixture pinning a column the cluster minted cannot go red at the pre-fix revision on the defect, because the physical column does not exist there: the run fails on a missing column, which proves the schema moved and says nothing about whether the fixture can see the defect. Reading that red as the required proof is the trap, since it is a real red in a terminal. Mutate forward instead — apply the alternative the cluster considered and rejected, and confirm the fixture fails on it. `test/data-view-queries/player-pff-pass-plays-value-path-result-equivalence.json` is the worked example: repointing `player_pff_pass_plays` at the `routes` column (the repoint that would have kept saved views rendering while silently changing the number) turns it red with `pff_pass_plays_0: null`, which is the blank-cell shape itself rather than a proxy for it. Note the fixture has to be result-equivalence rather than query-match for this to work at all — a blank cell is an executed-result property, and the SQL is valid in both worlds.

That is what `test/roster.salary-consumer-contract.spec.mjs` does, and it is the shape to copy when the consumers are unreachable from mocha. `33721c0b9` swept four `.value` reads off a `Roster` player — `get_cutlist_total_salary`, the restricted-free-agency dialog's `get_active_charge`, `settings-teams-team`, and the cap-violation detail line — all live breakage from `8643dc8a7`, and **the full suite was green at 3304 passing with every one of them in the tree**. None could get a behavioral spec cheaply: two are JSX, `app/core/selectors.js` imports through the `@libs-shared` webpack alias, and the script's read sits inside a log line. So the spec parses `app`, `scripts`, `libs-server`, `libs-shared`, `api` and `jobs` with babel, resolves which local bindings hold a roster player (from `roster.get(pid)`, from a collection getter, and through the for-of, `.entries()`, reduce and callback forms that carry one), and fails on a `.value` read off any of them. Proven red at `8643dc8a7` naming all four sites and green at `33721c0b9`. Two things that generalize. It is name-anchored on the ROSTER rather than on `.value` — `value` is a common property and grepping it is useless, which is the argument the rename exists to settle — and it asserts a floor on files scanned, since a resolution change that walked zero files would otherwise pass vacuously forever. It also found a FIFTH site both sweeps missed and still live on master: `auction-targets.js` read `rosterSlot.value` off `team.roster.get(pid)`, rendering a rostered player's salary as undefined in the auction list (fixed in `498247ea0`). Four sweep commits and a green suite did not find it; the source scan did on its first run.

**The companion hazard runs the other way: DROPPING a unique constraint breaks every `ON CONFLICT` that names it, on code you have not deployed yet — so the outage lands between the apply and the deploy, not after it.** `ON CONFLICT (a, b, c)` requires a unique index on exactly those columns, and Postgres resolves it at execution, so the moment the constraint goes the still-running old code fails every upsert with `no unique or exclusion constraint matching the ON CONFLICT specification`. The apply is instant and the deploy is human-gated, which makes that window hours rather than seconds. This nearly shipped on 2026-08-04: the plan for the kicking/DST scoring columns called for adding `league_scoring_formats.config_digest` and dropping the 23-column `league_scoring_formats_config_unique` in ONE file, which would have failed every `find_or_create_scoring_format` call — live external-league import included — until someone got around to `yarn deploy`.

The fix is to make the two oracles OVERLAP rather than hand off: add the new unique index in the first file and drop the old constraint in a second one applied immediately after the deploy verifies. Both spellings of the upsert resolve for the whole window, so there is no moment where deployed code cannot find its conflict target. Two things to get right. Gate the second file on what the HOST is running (`ssh league 'cd /root/league && git rev-parse --short HEAD'`), not on what is committed or pushed — this is the same "a cluster is done when it is DEPLOYED" rule in [the shipping guide](ship.md), and here it is load-bearing rather than hygienic. And treat the second file as an immediate post-deploy step rather than as cleanup, because the overlap is not free in the other direction: a retained constraint is strictly stricter than the digest that replaced it, so once the new code is live it rejects rows the new oracle considers distinct. Reproduced on a scratch database — an insert differing from an existing row only in `defensive_touchdowns` raised a duplicate-key violation on the retained constraint that `ON CONFLICT (config_digest)` did not catch, which is a 500 for a commissioner editing a DST value. The window is unavoidable; which half of it is dangerous is your choice, and the post-deploy half is both shorter and narrower.

## Deriving the old-name list

**Do NOT derive the old-name list by grepping `db/adhoc` for `RENAME` — that corpus is not the complete record of applied renames.** At least three clusters were executed as expand-contract instead: `ADD COLUMN`, backfill, then `DROP COLUMN` on the old name, sometimes spread across several dated files, with **zero** `RENAME` statements anywhere. `db/adhoc/2026-05-28-format-id-migration.sql` is the clearest case — 18 `ADD COLUMN`, 17 `DROP COLUMN`, 0 `RENAME` — and it is how `scoring_format_hash`/`league_format_hash` became `scoring_format_id`/`league_format_id`; `2026-06-10-adp-format-dimension.sql` (`adp_type` -> `adp_format_id`) and the `2026-05-31` nfl-coaches pfr-id re-key have the same shape. A `RENAME`-anchored grep is structurally blind to all of them, so any sweep built on one is working from a floor rather than a complete list, and the gap is invisible: the old name simply never appears in the derived list and nothing reports a miss. The heuristic "file drops a column without renaming one" recovers most of them but still assumes both the add and the drop landed in `db/adhoc` at all. **The reliable derivation is diffing `db/schema.postgres.sql` against an earlier revision of itself** (`git log --oneline -- db/schema.postgres.sql`, then diff across the window) — the schema export is the source of truth, so a column that left it is a rename or a drop regardless of which SQL verb effected it. Related caveat, since it bit the same sweep: a script's CLI flag names do not reliably track its columns in either direction — `resolve-player-match.mjs` was renamed with its columns and `import-plays-nfl-v1.mjs` was not, so check each script's argv parsing directly rather than inferring.

**The expensive defect in a prose/plan corpus is not a renamed column — it is a plan specifying a table or mechanism a later migration eliminated.** A 2026-07-30 sweep of the 261 open league task entities found two of these, and a name-anchored sweep cannot see either, because every identifier in them is internally consistent and merely describes a world that no longer exists. `plan-pff-archive-ingest` specified `CREATE TABLE pff_game_id_map` — the table `ee48e5d5` eliminated into `nfl_games.pff_game_id` — so implementing it as written would have re-added what the conform removed, along with an `esbid_resolved` flag that has nowhere to live. `334-add-bestball-adp` specified `ALTER TYPE adp_type ADD VALUE`, the exact `ALTER TYPE` blowup the `adp_format` dimension was built to eliminate; the correct step is a find-or-create on the axis tuple and involves no DDL at all. Both plans were internally coherent and would have passed any grep. The only thing that surfaces them is reading what a plan _builds_ against the current schema, not just what it _names_. Related: `points_added` did not rename, it **split** into `points_added_earned`/`points_added_net` with ranks only on the earned side, so a rename-shaped fix (one old name, one new name) silently picks the wrong semantics.

**Judging a prose sweep per `(table, column)` is not a refinement of the name-only sweep — it is the difference between fixing and breaking.** The same 2026-07-30 sweep hit five independent cases where the shorthand survived on one surface and died on another, four of which would have been actively damaged by a global rename. **Two still hold as of 2026-08-07 and are the ones to reason from**: `psr_gsis`/`trg_gsis` still exist while `psr_pid`/`trg_pid` became `passer_pid`/`target_pid` (same conform, same table, opposite outcomes); and `seas_type` survives as a **data-view param name** even though the column is `season_type`, so the tasks asking for `seas_type` column params are correct as written.

The `pff_id` pair was the third until 2026-08-07 and is now CLOSED, which is itself the lesson repeating: `pff_player_facet_gamelogs`, `pff_player_facet_seasonlogs` and `pff_player_seasonlogs` all moved to `pff_player_id`, joining the `player.pff_id` rename that had gone first. Leaving one spelling beside three others was its own audit class, so the asymmetry this guide cited as durable lasted about five weeks. Re-check a pair against `information_schema` rather than citing this list.

The other two have since moved, which is itself the lesson — an asymmetry is a fact with a shelf life, so re-check the pair rather than citing this list. The 2026-08-05 season_grain cluster CLOSED the seasonlog split: `scoring_format_player_seasonlogs.year` and `league_format_player_seasonlogs.year` were cited here as surviving while `player_seasonlogs.year` became `season_year`, and all three now carry `season_year`, so the join that was correct on one side and stale on the other is uniform again. And `rnk` was cited as a bare surviving column; there was no bare `rnk` on either table — the surviving form was the SUFFIX, in `points_rnk` / `points_pos_rnk` / `points_per_game_rnk` / `points_per_game_pos_rnk` on `scoring_format_player_seasonlogs` and `pos_rnk` on `scoring_format_player_gamelogs`. The 2026-08-17 long-tail conform closed all five to `_rank` / `position_rank`, so this instance is spent and only the lesson survives it.

**Budget for the fact that dropped league column names include ordinary English words.** Matching the derived old-name list against prose returned hits in 185 of 257 task files, almost entirely from `to`, `new`, `off`, `def`, `h`, `v`, `rec`, `int`, `order`, `desc`, `col`, `pl`, `prop`, `pts` and `round` — all genuinely dropped columns, all unusable as bare patterns. Two filters made the corpus tractable without losing signal: require a **code context** (the token inside backticks, or dot-qualified as `table.column`) and carry an explicit stopword set for the English collisions. That cut 185 files to 29 candidates, which matched what manual review found. A complementary pass that needs no stopwords at all: extract every `table.column` pair from the corpus and check each against the parsed schema — it is the only pattern that catches the ambiguous names (`year`, `timestamp`, `week`) that a global list must exclude.

**Validate a sweep pattern against a site you already know exists before trusting its zeros.** A grep that returns nothing is indistinguishable from a grep that cannot match, and the second failure is invisible precisely when it matters most. A 2026-07-29 sweep for `year`-to-`year` join predicates returned a confident zero because the pattern required the two column literals to be adjacent (`.on('a.year', 'b.year')`) and so missed every three-argument form (`.andOn('a.year', '=', 'b.year')`) — which is how this codebase actually writes join predicates. The false negative hid a `teams`↔`users_teams` coupling entirely, and was caught only by re-running the pattern against a known-existing site. This is the same failure class as a proving join missing a discriminating column, but located in the sweep rather than in the data: in both cases the error is invisible in the aggregate and only a positive control exposes it. Any sweep whose zero would let you skip work needs that control. Corollary: a table with rows and a reported consumer count of zero should be disbelieved until the bare table name has been grepped too — table names held in constants (`const HISTORY_TABLE = '...'`) defeat reference-shaped matchers.

The SQL spelling of the same trap fails in the opposite direction — it matches EVERYTHING, and the count looks plausible. **A `LIKE` pattern against URL-encoded text is almost always wrong, because `%` is both the encoding's escape character and `LIKE`'s wildcard.** `url LIKE '%splits=%5B%5D%'`, written on 2026-08-05 to isolate short URLs carrying an empty `splits=[]`, is read by Postgres as "contains `5B` then `5D`" and so matched all 423 `splits` URLs including every non-empty one — reported as `423`, which is a believable number for a filter that is silently a no-op. Classify a URL query string in code (`new URL(...).searchParams`), not in `LIKE`; if you must do it in SQL, escape the literal percent (`LIKE '...' ESCAPE`) and validate the pattern against a row you know is in the class and one you know is not.

**A table-name-anchored count is not blast radius when a wrapper module fronts the table.** One step further out than the constants case, and it does not need a constant to bite: if the only code naming a table is a module that exports functions taking the grain columns as NAMED PARAMETERS, the object keys a sweeper must change live in that module's CALLERS, which never name the table at all. No matcher keyed on the table name can reach them at any level of care. On 2026-07-29 `league_notifications` was scoped as a 2-site cluster on exactly that basis — 2 sites do name the table, both in `libs-server/league-notifications.mjs` — but its two exported helpers take `{ year, event_timestamp }` and four scripts call them at **14 sites**, so the real sweep was 5 files. Note the count was not wrong on its own terms; `entry` accurately reports query sites to open. What failed was reading it as work. The cheap discriminator, worth running before sizing any rename: grep for exported functions in `libs-server` that query the target table AND take the grain column as a named parameter, then add those modules' importers to the sweep surface. Run against the remaining `season_grain` class it flags `libs-server/simulation/*` (~20 such functions chained several layers deep, spanning `rosters_players`, `playoffs`, `matchups`, `teams`, `seasons`), `libs-server/get-roster.mjs`, and `libs-server/context-docs/*`. Refine before trusting it: a `year` parameter is a rename site only where it becomes an object KEY (`.where({ year })`), not where it is a bound value (`.where('t.year', year)`) — so that list is files to open, not a work count, and treating it as one would repeat the original mistake.

## Retypes

**A retype's blast radius escapes a wrapper even when a rename does not.** Same cluster, and the asymmetry is the point. A rename can be contained inside the module that builds the query — only if you accept a translation layer there, which the no-shims rule forbids. A retype cannot be contained at all: callers pass the old representation and pg rejects it at the bind (an integer bound to `timestamptz` is a type error, not a coercion), so every caller is in scope regardless of how the query is written. When folding a retype in with a rename to save an apply window, size the cluster on the retype.

**No CONSUMER gate here can see a retype, because every one of them resolves column NAMES and a retype does not change one.** `check-renamed-column-consumers`, `check-knex-column-resolution`, `check-rename-alias-residue` and `check-league-schema-consumers` all anchor on a name that must resolve against the schema; after a retype it still resolves, the SQL is still valid, and every one of them is green. That was correctly diagnosed as the wrong question rather than a reach to be widened, in the sense the "reach and class are independent" note above means — **and the answer was a gate that asks a different question, which now exists: `db/gates/check-retyped-column-arithmetic.mjs`.** It derives its subject from a schema TYPE diff (columns that moved numeric -> temporal, name unchanged) and reports code still treating them as epoch seconds, in two families — an epoch value BOUND against a retyped column in a predicate, which Postgres rejects, and a READ of one flowing into `dayjs.unix()`, `Number()` or a numeric comparison, which never throws at all. It takes `--base <pre-cluster-ref>`, is in the `check:cluster` manifest, and at `34a7a40f5~1` it independently finds nine of the thirteen below. Do not read the paragraph that follows as saying the class is still uncovered; it is the incident that motivated the gate. The 2026-08-07 timestamptz cluster shipped **thirteen** broken consumers behind a full green sweep: three loud (signals 124812/124813/124804) and **ten SILENT**, because node-pg returns a `Date` where the code expected epoch seconds and nothing throws — `Number(date)` is milliseconds, `dayjs.unix(date)` is a year-58,000 date that passes `.isValid()`, and `epoch < date` coerces and is simply always true. Two ran in production for days behind jobs that exit 0: `process-extensions` skipped every league while logging "not yet reached" for a deadline nine days past, and `process-projections`' freshness oracle threw on its own bind while `main()` swallowed the throw and `report_job` recorded success. Repaired in `34a7a40f5` / `848f99825` / private `fb066f1`.

**Give that gate the pre-DDL ref, not the consumer-FIX ref — `34a7a40f5~1` is the wrong base for it, and the wrong base reads as a broken gate.** The nine-of-thirteen figure above is a statement about the CODE at that revision, and the gate's subject comes from the SCHEMA diff; `34a7a40f5` is the consumer sweep, which lands after the DDL, so the schema at `34a7a40f5~1` already carries the timestamptz columns and the diff against today is EMPTY. The run then says `no numeric -> temporal retype in this window`, has no read site left to mutate, and exits 1 on `negative control STAYED GREEN` plus every adjudication reported stale — which reads exactly like a gate that has stopped working, and the response it invites is deleting the adjudications. The right ref is the DDL apply, `805d8a5d6~1`, where the same tree yields 17 retyped columns, zero findings and all seven controls red. **The base ref for a TYPE-diff gate is the schema commit, while the base ref for a consumer gate is the cluster start** — they are different commits whenever the sweep is not in the same commit as the apply, and only this gate takes the first one. Measured 2026-08-08.

**An empty type-diff has a SECOND cause the paragraph above does not cover — an ADDITIVE-only cluster — and the gate now tells the two apart itself.** A cluster that only ADDS a column can never move one numeric -> temporal, so the subject is legitimately empty, there is no read site to mutate, and the control cannot run. Until 2026-08-16 that reported `negative control STAYED GREEN` and exited 1 over a cluster with nothing wrong, which is the same output a wrong base ref produces — and the remedy that failure invites, deleting the adjudications it reports as stale, is destructive.

The gate now discriminates on the WIDER schema delta (`derive_schema_delta`), because an additive cluster moves the schema while a base ref sitting past the whole cluster typically does not. Three outcomes, each verified against a real ref:

| Window                                  | Verdict                                                  | Exit             |
| --------------------------------------- | -------------------------------------------------------- | ---------------- |
| A real numeric -> temporal retype       | subject listed, controls run                             | 0 or 1 as before |
| No retype, but the schema moved         | `NO SUBJECT` — not applicable                            | 0                |
| No retype and no schema movement at all | `TOOLING ERROR` — your base ref is probably past the DDL | 2                |

**The third row is the one that keeps this honest**: the wrong-base case still fails, so the fix did not buy a green by loosening. Note the discriminator is not a proof — a base ref landing between two commits of the same cluster shows movement and can still be wrong — so the `NO SUBJECT` banner names the ref and says confirming it is the DDL commit is yours to do. The three verification refs are recorded in the gate's own header; re-run them if you change its verdict logic.

Three things to carry from it. **The silent class cannot raise a signal by construction**, so triage will never find it — only a gate or an executed run will. **A `db.raw` template string was in no gate's corpus at all** — `check-league-schema-consumers` gate 3 extracted raw SQL and EXPLAINed it, but only over user-base shell scripts and API call sites, which is how a stale `transactions.timestamp` inside a `concat_ws` survived every gate. **That is now closed**: gate 3 has a third transport reading `.raw()` literal arguments and template-literal SQL constants across `scripts/`, `libs-server/` and `jobs/`, bound to league by the file's `#db` import — a transport statement, not a filename. The run prints both numbers. When two functions in one domain disagree about the unit of the same column, the one that disagrees with the DB is the defect, and `getDraftDates` had even written the convention down in its own JSDoc.

**A RETYPE GATE'S FINDING COUNT IS NOT THE CLUSTER'S BLAST RADIUS, and reading it as one is how the 2026-08-08 lifecycle retype nearly shipped two silent data-corruption defects.** `check-retyped-column-arithmetic` reported 13 findings over 6 files for the fifteen-column lifecycle retype; the real consumer surface was roughly 90 changes across ~50 files. The gate was not wrong — every one of its 13 was real — but its class is a resolvable epoch expression in a predicate or a read, and **four other classes carry the same defect while lying outside it by construction**. Budget for all four on any retype:

- **INSERT PAYLOADS.** A payload is neither a predicate nor a read. 24 sites across 18 files here — trade accept/reject/cancel, waiver submit/cancel, RFA bid submit/cancel, poach submit/process, tag cancel. All fail LOUDLY, so the cost is a stopped write path rather than bad data, but an unswept one takes the app's whole transactional surface down. Note several were reached only through a DERIVED variable (`const timestamp = Math.round(occurred_at.getTime() / 1000)` feeding `processed: timestamp` 160 lines later), which no grep of the epoch idiom finds.
- **THE SPA.** `SCAN_ROOTS` omits `app`. Beyond the obvious `dayjs.unix()` renders, the expensive shape is a value the SPA sends BACK as a query bound: `getScoreboardUpdated` returned `0` when no plays were loaded, which becomes `where updated > 0` against timestamptz and breaks the live scoreboard on the FIRST register of every session. A column can be SPA-visible through the write path even when nothing in `app/` renders it — do not conclude "not SPA-visible" from a read sweep alone.
- **MIXED-UNIT MERGE STREAMS, and these are the dangerous ones.** A Date pushed into a stream of epoch seconds that is then sorted or compared numerically. Both instances were SILENT and neither was adjacent to anything the gate flagged: `walk-transactions.mjs` compared `earliest_trade * 1000` on a value that is now a Date, so the synthetic pre-trade ownership window was never created and every pick traded before its endowment lost its first leg; `refresh-extension-state.mjs` pushed `restricted_free_agency_bids.processed` raw into a reset stream keyed on epoch seconds, misordering every extension-ladder reset. The second one's own comment asserted the opposite, accurately when written — a dated unit claim in a comment is exactly the thing a retype falsifies.
- **WRITE-BOUNDARY AND RAW-SQL CONVERSIONS BECOMING DOUBLE CONVERSIONS.** `to_timestamp(?)` wrappers and `TO_CHAR(TO_TIMESTAMP(col), ...)` were correct against an epoch integer and are now either a type error (`function to_timestamp(timestamp with time zone) does not exist`, which fails the whole statement) or a float misread (`invalid input syntax for type double precision: "58450-09-27..."`). Grep `to_timestamp` and `epoch_to_timestamptz` against the retyped columns as its own sweep step.

Two procedural rules follow. **Read the sibling lines around every site the gate names** — the five `walk-transactions` findings it reported all had an unflagged `sort_ts:` assignment one line above, and the worst defect in the file was 40 lines below them. And **treat an ordering-shaped test failure as a possible real defect until you have bisected it**: five lineage failures reading `expected 2 to equal 1` looked exactly like specs asserting a stale contract, and reverting only that file against HEAD is what proved they were not. The full suite against a candidate schema, compared against a control run at HEAD, is the oracle that found both silent defects — no gate did.

**A `varchar` -> numeric retype is a THIRD class, and `check-retyped-column-arithmetic` does not cover it — its subject is numeric -> temporal only.** What breaks is narrower than the timestamptz class and louder: an ordinary bind survives, because Postgres coerces an unknown-typed parameter to whatever the column now is, so `week = $1` with `'7'` keeps working. What does NOT survive is a consumer that CASTS to the old type explicitly, since the cast pins the operand and the comparison becomes a type error rather than a coercion. On 2026-08-25 `0a846bbdb` narrowed `league_player_projection_values.week` to `smallint` and recorded "No companion code change" on the strength of verifying the WRITER, whose string-keyed week still coerced; the reader in `libs-server/data-views-column-definitions/player-projected-column-definitions.mjs` wrapped its join in `CAST(<week_reference> AS VARCHAR)` behind a `cast_join_week_to_string` flag, and every data view carrying `player_week_projected_points_added*` returned 42883 `operator does not exist: smallint = character varying`. **So the sweep for this class is a grep for explicit casts to the OLD type, not for the column name** — the name still resolves everywhere, which is why the four consumer gates stay green. `check-data-view-sql-validity` is what caught it, and only because the emitted SQL was genuinely invalid; a cast living outside data-view emission would have had no gate at all. Note the flag was correct at its other call site, where `league_format_player_projection_values.week` really is still `character varying(10)` — a per-table flag, so retyping one table leaves the other's use load-bearing.

## Proving joins and unit semantics

**Check a proving join for its own false matches before believing what it proves.** A join used as evidence — "this table's data all exists over there, so the drop is lossless" — is itself a query that can be wrong, and when it is, the error hides in the aggregate. On 2026-07-29 two separate approved instructions rested on joins missing a discriminating column. The `schedule` drop was to be preceded by backfilling 2 "unique" `surf` values; the finding behind it joined on `(season, week, v, h)` without `season_type`, and since `schedule` holds no preseason at all, its regular-season week-1 rows had matched **preseason** week-1 rows for the same teams. Both values already existed on the correct rows, and performing the approved backfill would have invented surface data for two games the source never described. The tell was never visible in a count — it took looking at the individual rows the join had paired, and re-matching on `(season, teams, nearest date)` to absorb the OAK/LV code drift and postseason renumbering that broke the naive form.

**A retype must preserve UNIT semantics, and re-deriving a number with a different query shape does not test the population it was scoped to.** Two lessons from one defect, both live for the remaining retype clusters. First: `b09fdbce` restated `to_timestamp(gm."timestamp" - 7*86400)` as `kickoff_at - interval '7 days'` and described the forms as equivalent. They are not — a day-unit interval on a `timestamptz` is calendar arithmetic in the session timezone (production is `America/New_York`), so across the November fall-back it spans 169 hours. Hour units are absolute; day, week, and month units are not. When a retype moves epoch-integer arithmetic onto a `timestamptz`, state offsets in hours (`interval '168 hours'`, pinned in `8684b569`) and assert the calendar form is ABSENT, or the drift is invisible: it fires for one week of every season and no other, which is a seasonal artifact rather than a uniform widening. Second, and the more general one: the impact of that drift was first measured at **155 flipped rows and re-derived with a differently-shaped query that agreed**, but both shapes omitted the `player_gamelogs gl_inner` join the CTE actually performs, so both measured a population the CTE never sees — the real figure is **5**, and 580 of the 616 "extra" changelog rows belong to players with no gamelog for the game whose window they fell into. Independent derivation only catches an error the derivations do not share, and scoping is exactly what two readings of the same SQL will share. It is also not what a positive control fixes by default: the control used here (a game on the fall-back date) validated the timestamp arithmetic, which was never in doubt. Aim the control at the step that could be wrong, and anchor it on the artifact you are making the claim about — name a row, predict its value, then look for it in the output table. Doing that surfaced both the corrected count and an unrelated defect, because the predicted row was not in the table at all.
