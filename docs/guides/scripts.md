# Write or Change a Script or Job

**When to read this:** Read before touching `scripts/`, `jobs/` or a crontab.

A scheduled writer that fails silently is the standing failure here: exit codes, logs and `report_job` all report success independently of whether anything was written.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

## Logging: debug.enable and namespaces

**A `debug.enable()` call REPLACES the enabled namespace set — it does not add to it.** So a helper's own instrumentation is silently unreachable unless the entry-point script lists its namespace. `record-league-format-projection-value-history` logs the change rate that is the entire cost model for the projection-value history store, and it had logged **zero times** in production — including through the run that seeded 468,930 rows — because neither `process-projections.mjs` nor `process-projections-for-league-format.mjs` named it in their `debug.enable(...)`. Nothing fails; the metric just does not exist, which is the worst shape for an instrument whose job is to detect silent degradation.

**The remedy is NOT "name the namespace at the entry point".** ESM evaluates every import before the importing module's body, so a `debug.enable` at the module scope of any imported file runs BEFORE the entry point's own line — and since enable REPLACES the set, the last import to run owns the process. Naming everything at the entry point also decays: it is a list of your transitive dependencies' namespaces, maintained by hand, and nothing tells you when it goes stale.

**This guide also claimed a logger, once clobbered, "cannot be turned back ON", making the entry point structurally unable to repair the set. That is false on `debug` 4.4.3 and should not be reasoned from.** `enable()` after a logger is constructed re-enables it correctly — `enabled` is a lazily-recomputed getter keyed on the namespace string (`node_modules/debug/src/common.js`). What DOES latch is the getter's SETTER: any assignment to `log.enabled` pins an override that every later `enable()` is powerless against. Nothing in this tree assigns it. Measured 2026-08-23; the original observation was real but the mechanic inferred from it was not.

The prop write path was dark in production for exactly this reason, and it cost five deploys and three wrong diagnoses on 2026-08-03. `jobs/import-live-odds-worker.mjs` imports the draftkings, pinnacle and prizepicks scripts in that order; `import-prizepicks-odds.mjs` ran last and set the namespaces to its own three, naming neither the worker nor `insert-prop-markets`. The worker's own unconditional `debug.enable('import-live-odds-worker')` then ran after it and restored exactly one namespace — its own — which is precisely why the worker logged normally while everything else stayed silent and every configuration change looked correct. Removing that line without replacing it took the worker's stderr to **total silence**, a strictly worse state that shipped to production for an hour.

**Never call `debug.enable` directly. Call `enable_debug_namespaces()` from `#libs-shared/enable-debug-namespaces.mjs`, which UNIONS instead of replacing.** It reads the current set back out and re-enables it alongside the new one, so import order stops mattering and no entry point has to enumerate anything. `local/no-bare-debug-enable` makes the bare form a lint error; it carries no baseline, because the sweep went to zero. Keep the call at module scope, next to the logger it is for.

Two notes on the helper. Its `DEBUG` check is snapshotted at module load and MUST NOT become a per-call read: `debug.enable` calls `save()`, which WRITES `process.env.DEBUG`, so a per-call read sees the value the helper itself just wrote and collapses the union back to whichever module was imported first. And `libs-shared` is isomorphic — it reads `globalThis.process?.env?.DEBUG`, since the SPA bundle has no `process`.

**The guard this guide previously mandated, `if (!process.env.DEBUG) { debug.enable(...) }`, did not fix the race and is gone.** With `DEBUG` unset every guarded module still calls `enable()` and the last one still wins; the guard only makes an explicit `DEBUG` authoritative. All three pm2 workers set `DEBUG`, which is the only reason the 2026-08-03 fix appeared to work — no crontab does. Measured across every entry point's import graph on 2026-08-23: 31 were still racing, including `jobs/finalize-week.mjs` with 22 of its 25 enablers dark. All 280 call sites, `private/` included, now go through the helper.

**The claim that moving the call into `main()` "silences the script entirely" does not reproduce, and the reasoning behind it was the false mechanic above.** A logger constructed at module scope IS re-enabled by a later `enable()`; a three-module fixture with the entry point's call deferred into `main()` printed all three namespaces, while the same fixture with unguarded module-scope calls printed only one. So deferral is not the hazard — replacement is. The 2026-08-05 zero-byte logs on `audit-keeptradecut-liquidity-coverage.mjs` were real, but whatever caused them, it was not an `enable()` that ran too late. Keep the call at module scope for consistency with the helper, not because `main()` is broken.

The durable fix for anything whose log IS its audit trail — a scheduled job, an oracle, a one-shot repair — is **`console.log`/`console.error` for every outcome line**, reserving `debug` for chatty per-item detail. Namespace resolution is a runtime negotiation with the whole ESM import graph; an oracle's verdict must not depend on winning it. This is the same reasoning already given for `db/adhoc` scripts further down, and it generalises to every `scripts/*.mjs` a crontab invokes. Note the failure is invisible to the test suite (specs assert on return values, not stdout) and to a local run with `DEBUG` set — only running the job the way cron runs it, with a clean environment, exposes it.

**Diagnose this by instrumenting `debug.enable`, never by reading configs.** Monkeypatch it to print its argument and caller, then load the real import graph — it names the clobbering call site in one command. The whole 2026-08-03 detour came from verifying configuration (the pm2 env was correct in `/proc/<pid>/environ` every single time) and inferring behaviour from it, when the observable was one `grep` away: the error log contained exactly ONE namespace, which is a fact about precedence rather than about whether any config was right.

## Naming a traversal

## Key Development Patterns

**`db.raw()` rewrites a literal `?` in your SQL before Postgres ever sees it, and the query still returns rows.** knex parses `?` as a positional bind placeholder — that is the documented feature — so it also fires inside a regex, a `LIKE` pattern, or a JSON operator, where you meant a literal character. There is no error and no warning: the statement executes, returns a plausible row count, and the result reads as data. Measured 2026-08-23 on a name-normalization regex, `'(Jr|Sr|II|III|IV|V)[.]?$'` silently stopped matching and three separate collision measurements were wrong in the same direction before the cause was found — the tell was a suffix-stripping expression returning its input unchanged on a string that obviously ended in a suffix.

Two forms avoid it. Write the quantifier the long way — `[.]{0,1}` for `[.]?`, `{1,}` for `+` is unaffected — which keeps the fragment safe for any caller to pass to `db.raw`. Or, when the SQL genuinely needs a question mark, take a pooled connection and issue it through the driver, bypassing knex's parser entirely (`db.client.acquireConnection()`, `connection.query(sql)`, then `releaseConnection`). Prefer the first for anything exported as a reusable fragment, and say so in a comment beside it: the next editor has no way to see the constraint from the code.

**Asset lineage and team accounting are DIFFERENT TRAVERSALS over one graph, and a value field must state which one it belongs to — a filter argument on a shared field is not a substitute for separate names.** `roster_asset_transformation` models a trade as a one-to-one asset move, which is right for "where did this player end up" and wrong for "what did this team get out of the deal": a team's economic interest does not end when it trades the acquired asset onward, it continues into whatever came back. `grade_trades` reported on TEAMS while traversing ASSETS, and the single field named `current_keeptradecut_value` is what let that pass review for as long as it did — one name answering two questions, so neither answer could be checked against its own definition. The damage ran in **both** directions from that one cause, which is the part worth internalising: 218 of league 1's 456 trade records credited a team with the current value of assets it no longer held, and 87 read zero on a team that had demonstrably converted the asset into something it still holds. An over-report and an under-report from a single defect look like two unrelated complaints in a bug queue.

Two rules follow. **Name the traversal in the field** — the three figures here are `keeptradecut_value_at_trade` (a property of the leg), `keeptradecut_value_still_held` (of the team and the asset) and `keeptradecut_value_proceeds` (of the team and the trade), and the old name was retired rather than redefined precisely because keeping it under any meaning preserves its ability to recur. And **derive a state from the EDGE that ended the team's holding, not from partitioning what is still open**: partitioning leaves a fourth case unnamed, so a team that traded an asset onward whose line then died reads "consumed" beside a non-zero proceeds figure — 306 of 1,484 leg-perspectives sit in exactly that gap. Resolve the transformation TYPE and not `terminated_by`, which covers 742 real trades plus 77 poaches and 49 restricted-free-agency wins.

**A traversal that walks from a trade into LATER trades cannot consume an index built from a filtered leg set, and the failure is a smaller number rather than a null.** `grade_trades` narrows its legs by `trade_uid` in SQL before building the maps it indexes by; a consideration walk that reused them collapsed to the still-held figure on the detail route (trade 171 team 1 reading 20,301 on the list and 0 on the detail page, same data, no error) and lost 21 of 58 records in a year-filtered slice, because consideration chains cross years by construction. Load independently of the filter arguments and apply filtering to the OUTPUT records. Note the shape of the near-miss: the mirror-symmetry check was green throughout, because both perspectives truncate identically — **an invariant that holds on both sides of a symmetry cannot see a defect that is symmetric**, and the measurement harness could not see it either, since it re-queried the view unfiltered. The gate that works is a spec asserting a filtered call and an unfiltered call agree on the same record.

## Jobs, cron and scheduling

**`is_main` is FALSE under pm2, so every pm2-managed job needs `|| process.env.PM2_HOME` or it silently does nothing.** pm2 fork mode execs its own `ProcessContainerFork.js` and leaves `process.argv[1]` pointing at THAT, while `is_main` is a verbatim `===` against `fileURLToPath(import.meta.url)`. So `main()` never runs — and the process does not exit or crash, because importing `#db` builds a knex pool whose reap interval holds the event loop open. pm2 reports a healthy `online` process at steady RSS that has never executed a line of its own logic. `refresh-projection-cache-worker` shipped that way on 2026-08-09 and ran for hours; both live-import workers already carried the clause, which is the only reason they work. **The trap is that reading it from OUTSIDE confirms the wrong thing**: `/proc/<pid>/cmdline` shows `node /root/league/jobs/<worker>.mjs`, because pm2 rewrites the process title, and that is what made `is_main` look like it passed. Measure `process.argv` from INSIDE a pm2 child instead — a three-line probe started under pm2 settles it. The companion symptom is zero-byte pm2 logs, which reads as an observability gap and is not one; a control app started under pm2 on the same host writes its log files normally.

**Cron schedules in `/server/crontab-*.cron`** for different server roles

**`yarn deploy` does NOT update cron — the crontab is a separate deploy.** A code deploy ships the scripts but leaves the schedule and its ARGUMENTS untouched, so a script whose flags changed will keep running under the old ones with no error anywhere. On 2026-07-29 an external-league importer was deployed with new `--import_limit`/`--resync_limit` budgets while the installed crontab still passed a removed `--limit 250`; the job would have run weekly with stale arguments indefinitely. Ship both: `yarn deploy` then `server/deploy-crontab.sh league server/crontab-main`. Note the installed file is machine-built (`base crontab build`, which injects `JOB_SCHEDULE`/`JOB_SCHEDULE_TYPE`), so never hand-edit `~/crontab/*` on the host — and before deploying, diff the installed job lines against the source with the injection stripped, since the crontab directory is shared and carries every session's committed changes, not just yours.

**A league-host cron job has NO `scheduled-command` entity, so never address its signals to one.** The league host runs no `schedule-processor`, which makes a `scheduled-command` entity for one of these jobs inert — and since base's processor executes `enabled: true` entities, creating one for a job this crontab already runs invites a second concurrent execution. Two scripts nonetheless set `SIGNAL_SOURCE = 'user:scheduled-command/league/<name>.md'` against an entity that has never existed, so every signal they raised addressed nothing and triage had no entity to open; both are fixed as of 2026-08-04 (`process-projections.mjs` in `d2bca6f21`, `generate-dst-market-projections.mjs` in `d84b46073`). Pick the replacement shape by what actually invokes the script, and do NOT reach for `cron:` reflexively — naming a schedule that does not exist is its own defect. A job in `server/crontab-main/*.cron` takes the host-cron shape `cron:<job>@league`, matching the fleet's `cron:check-host-resources@database`. A script nothing schedules takes the emitter-named shape `script:<repo-relative-path>` (cf. the fleet's `script:scripts/import-3dep-dem.mjs`), which names the script rather than its scheduler and so stays correct if it is later put on a schedule — that is what the DST generator got, since it is committed deliberately unactivated and appears in no crontab. Either way the failure and success dedup keys both derive from `SIGNAL_SOURCE`, so they move together. The entities under `user:scheduled-command/league/` are a DIFFERENT population: jobs migrated OFF this host onto base's scheduler, carrying `working_directory: /Users/trashman/user-base`. Note that nothing validates a URI embedded in a code string — `base entity validate-references` does not reach it — which is why both defects survived so long.

**A fixed sleep between requests does not rate-limit anything.** It ADDS to network latency rather than bounding a rate, so the achieved rate depends entirely on which host runs the job — and the fast host is always the one that ships. Measured 2026-07-29 on the Sleeper importer with a fixed 120ms sleep: round trip was ~670ms from a workstation (~76 req/min) but ~43ms from the production VPS, which would have run the identical code at ~350 req/min, roughly 4x the vendor's conservative published figure. The workstation measurement looked reassuring and was pure artifact of a slow link, which is the real trap: it is easy to "verify" a throttle somewhere it will never run. Pace against elapsed time instead — hold a `next_request_at` timestamp and advance it from `max(now, next_request_at) + interval`, so the ceiling is deterministic on any host and a slow response cannot bank credit toward a later burst. See `scripts/import-sleeper-external-league-trades.mjs`.

## Writers, upserts and generators

**A timestamp populated on only ONE row of a group makes `Number(null)` → `0` read as "infinitely overdue" rather than as an error — give the group a row of its own.** `restricted_free_agency_bids.announced` was written onto the nominating team's own bid and only that bid, because the announcement is a property of the PLAYER's window and not of a bid row; every competing bid carried `announced = null` for its whole life. `process-restricted-free-agency-bids.mjs` read it per bid, so a competing bid's null coerced to epoch 0, landed roughly 41,000 windows in the past, and came due the instant it was submitted: league 1 processed its second 2026 nomination at 10:10 ET on 2026-08-02 instead of 16:00 ET, three minutes after the winning bid was placed, and cut a player off the winning team's cutlist to make room. Nothing threw, and the script's own shortfall oracle was blind to it in both directions because it filtered `whereNotNull('rfab.announced')` — excluding exactly the rows that were mis-firing.

The structural fix landed 2026-08-02: `restricted_free_agency_nominations` holds one row per `(league_id, player_id, season_year)` carrying `original_team_id`, `nominated_at`, `announced_at`, `processed_at` and `winning_bid_id`, and the bid columns that duplicated them are gone. Read window state through `libs-server/get-restricted-free-agency-nominations.mjs`; the null that could be misread no longer exists, because the field has exactly one home per auction. Note this also removed a live inconsistency the denormalized form had already produced: two of the 166 historical auctions carried disagreeing `player_tid` values across their own bids, from a player traded before the auction ran.

Three rules survive the fix. When a field is populated on one member of a group, resolve it through the GROUP key rather than off the row in hand — and prefer giving the group its own row over agreeing to read the field carefully. Refuse a falsy value explicitly (return `Infinity`) rather than letting it flow into date arithmetic, the same silent-`NaN` family as the `current_season` comparator trap above. And note the suite could not have caught this: `test/scripts.restricted-free-agency.spec.mjs` gave its competing bids an `announced` value they never carry in production, so the fixtures encoded the wrong shape. Fixtures now seed through `test/utils/insert-restricted-free-agency-bid.mjs`, which makes that shape unwritable rather than merely unwritten. When a live incident contradicts a green suite, check whether the fixture builds a row the writer never builds.

**The companion lesson is about the outcome column: never store a presentation string where a code belongs.** `restricted_free_agency_bids.reason` carried whatever English was in scope at settlement — two hardcoded sentences plus `error.message` — so the database's vocabulary was an accident of exception text, and 262 of 280 losing bids across five seasons read `player no longer a restricted free agent`, which is true of every ordinary loss and distinguishes none of them. It is now `outcome`, a closed set defined once in `libs-shared/constants/restricted-free-agency-constants.mjs` (`won` / `matched` / `outbid` / `lost_tiebreak` / `roster_limit_violation` / `player_ineligible` / `processing_error`), with `outcome_detail` carrying a message only for the error case and nothing branching on it. Failures attach their code at the throw site via `libs-server/restricted-free-agency-bid-error.mjs` so no caller matches on message text — a reworded throw would otherwise change the stored outcome silently. Historical rows were reclassified from each auction's resolved state, which recovers the distinction the text never recorded.

**A bare `.merge()` on an upsert asserts EVERY column the insert names, including ones another pipeline owns.** A generator that hardcodes a constant for such a column silently reverts the owner's writes on every run, and nothing fails — the row is simply wrong afterward. `generate-player-gamelogs.mjs` hardcodes `is_active: true` (correct for a player with counting stats) while `player_gamelogs.is_active` is owned by `import-nflverse-weekly-rosters.mjs`, which maps game-day roster status onto it (ACT -> true; INA / RES / DEV -> false). With a bare `.merge()` the UPDATE half reverted every game-day-inactive flag the run touched: regenerating one 2014 game flipped six. Fixed by merging every column except that one — `GAMELOG_COLUMNS_NOT_MERGED` — which keeps the insert value for a new row and leaves an existing one to its owner. (The column was `active` when this was written; the 2026 boolean-prefix conform renamed it to `is_active` in `6ac331d4c`.) Before adding a column to any upsert here, ask which script is the writer of record for it — the INSERT and the UPDATE halves of an upsert do not need the same column set, and for a foreign-owned column they must not have it.

**A second class of column belonged in the same hold-back, and the fix was to remove the cause rather than keep the hold-back: one that re-encodes a value with no controlled vocabulary.** `player_gamelogs.player_position` and `player_seasonlogs.player_position` both copy `player.primary_position`, and until 2026-08-04 none of the three had a canonical value set — `player.primary_position` held 43 distinct values, the gamelog column 39, with `OLB` and `LB`, `T`/`G`/`C` and `OL`, `SS`/`FS`/`CB` and `DB` all naming the same position under different importers' spellings. Merging therefore rewrote a stored value to a DIFFERENT SPELLING OF ITSELF, which reads as a correction in a diff and is churn: a 277-game backfill would have changed the position on 1,183 rows, including 111 `K`->`P` and 87 `P`->`K` flips in opposite directions on the same run. It is no longer held back. The vocabulary is now the 25 values in `libs-shared/constants/position-constants.mjs`, enforced by a `CHECK` constraint on every position column in the schema and by `normalize_position` throwing at each write site, so a merge can only write the value already stored. `is_active` remains held back, for the foreign-ownership reason above. (Both position columns were spelled `pos` when this was written; a later conform renamed them to `player_position`, and `1ac03580e` then dropped `player_seasonlogs.player_position` outright because nothing read it. Only `player_gamelogs.player_position` still exists.) **The general rule survives its instance:** an uncontrolled vocabulary is a reason to control the vocabulary, not a reason to permanently except a column from its upsert.

**Validate a generator change against the PRIOR GENERATOR, not against production — these tables are upsert-only, so production carries rows no current input supports.** The instinct is to diff new output against the live table, and it conflates your change with every accumulated mis-attribution and every newer field nobody backfilled. Measured both ways over the same 277 games on 2026-08-04: prior-generator-vs-new was 21,634 unchanged / 291 changed / 0 added / 100 removed, and every delta was explainable; production-vs-new was 3,503 changed / 1,522 added / 8,240 removed on identical code, with the extra volume being stale `pos` spellings, un-backfilled `receiving_first_downs`, and gamelogs whose supporting play stats no longer resolve to that player. Extract the old file with `git show <commit>^:scripts/<script>.mjs`, import both, and diff their collectors. Then read the production diff separately, as the answer to "what will the write actually touch" — a different and equally necessary question. Note the corollary: a `removed` row in either diff is NOT removed from the database, because nothing here deletes; it just stops being regenerated.

**`player_gamelogs.nfl_team` cannot validate a writer that writes it — use `nfl_play_stats.nfl_team` as the oracle.** The stored team is produced by the code under test, so scoring against it measures the sum of your error and its own, and the second term dominates. Measured 2026-08-04 while replacing the snap-path team fallback: the candidate resolver scored **4.4% wrong against `player_gamelogs`** and **0.021% against `nfl_play_stats`** — nearly every disagreement was the stored value, not the resolver. Game `2016081153` is CAR @ BAL and carried gamelogs for TEN, SF and BUF; Rick Wagner, a Ravens tackle, was stored as CAR. `nfl_play_stats.nfl_team` is the feed's own statement of the PLAYER's team rather than the possession team — a defensive player's tackle rows carry his own side — so it is independent of `nfl_snaps`, of `player_gamelogs`, and of any gamelog writer. Two guards make it usable: drop any oracle row whose team is neither side of its own game (such a value is wrong on its face and cannot be ground truth), and remember it only exists for players who recorded a counting stat, which is exactly the population a snap-only gamelog is NOT in — so it validates the method without being able to repair the rows.

**Comparing `player_gamelogs.nfl_team` against `nfl_games.home_nfl_team`/`away_nfl_team` reports ~33,000 false positives unless BOTH sides go through `fixTeam`.** `nfl_games` keeps the abbreviation the franchise carried at the time (`SD`, `STL`, `OAK`) while `player_gamelogs` stores the conformed one (`LAC`, `LA`, `LV`), so every Chargers game before 2017 and every Rams game before 2016 looks like it has no team in common with its own gamelogs. The raw predicate returns 33,224 rows and reads as mass corruption; the normalized one returns 477, and the pre-2015 remainder is entirely relocation drift with no defect in it at all. The failure is worse than a wrong number because it is directionally convincing — the raw counts cluster in exactly the old seasons where you would expect legacy data problems. Normalize before counting, and treat "team is neither side of the game" as a genuinely useful corruption predicate only in its `fixTeam` form.

**`is_main` has two real failure modes, and a RELATIVE PATH is not one of them — that claim was false and has already propagated into a plan.** Node resolves `process.argv[1]` to an absolute path before your code sees it, so `node db/adhoc/repair-something.mjs` enters `main()` exactly as the absolute form does. Do not reason from this paragraph's earlier version. What DOES break it: **`is_main` is false under pm2**, so a pm2-managed job silently never runs; and a **symlinked path** diverges because `import.meta.url` is realpath'd while `argv[1]` is not, which fires on macOS `/tmp` paths. Both are silent, print nothing, and exit 0 — indistinguishable from a run that had no work to do. Everything under `db/` — `adhoc`, `gates`, `tools`, `archive` — calls `main()` bare (`db/gates/check-schema-conformance-ratchet.mjs`, `db/gates/check-data-view-sql-validity.mjs`) — follow that, and treat a one-shot data repair that produced no output as unproven rather than as a no-op. Related: give such a script `console.log`, not `debug` — a repair that writes thousands of rows while printing nothing has destroyed its own audit trail, and an audit trail must not depend on namespace resolution at all. (`enable_debug_namespaces` removed the clobbering that used to be the sharper form of this argument; the rule stands on its own without it.)

**A cross-table invariant is only real if the producer writes both tables in ONE transaction — and every writer here autocommits statement by statement.** A consumer that treats "row A implies row B" as impossible will throw the moment it reads between a producer's two writes, and the evidence is gone by the time anyone looks: both rows are present and correct, so the error message describes a state that no longer exists and reads as data corruption rather than a race. On 2026-08-02 `calculate-team-daily-ktc-value` died on `no restricted free agency signing found for HOU__2026-08-02` because `process-restricted-free-agency-bid.mjs` inserted the RFA tag transaction while its CALLER marked the bid `succ` in a separate statement afterwards. Note this was not luck: a 17:00 ET announcement plus `restricted_free_agency_window_hours=12` minus `restricted_free_agency_processing_lead_hours=1` puts the processing deadline at 04:00 ET, which is the exact minute the valuation job's cron fires, so the two collided on every announcement in that window. Fixed by committing the transaction insert and the bid marking together (`db.transaction`), which the consumer's read ORDER then makes sufficient — it reads `transactions` first, so a visible tag guarantees a visible signing; reversing those two reads would reopen the hole with the producer still atomic. Two rules: when a consumer asserts a cross-table invariant, verify the producer commits both sides atomically before trusting the assertion, and when splitting a success outcome across statements, guard the later one (`whereNull('processed')`) so a throw raised after the commit cannot roll the record back to the broken state. The suite cannot see any of this — a serial test never interleaves — so the gate has to be a test that pins WHERE the write happens, not one that checks the end state.

**A knex `.select()` that omits a column the code later reads yields `undefined`, and an index lookup keyed on that `undefined` MISSES silently — so a whole code block can be dead for years without ever erroring.** This is the same absent-key/no-diagnostic family as the `mapDispatchToProps` and Immutable `Record` traps above, but on the server and far more expensive, because the symptom is not a wrong value in one field — it is an entire branch that never runs. The 2026-08-02 follow-on triage of the same `calculate-team-daily-ktc-value` incident found its `db('transactions').select('tid', 'pid', 'type', 'timestamp', 'year')` never selected `uid`, while the loop below keyed the trade lookup on `trades_index[transaction.uid]`. Every lookup was `trades_index[undefined]`, so the trade-application block had never executed. Trade transactions are type `TRADE`, which the roster switch ignores, so that block was the _only_ thing moving a traded player: 349 players across 196 accepted trades had never changed teams, and fixing the one-word select changed 11,614 of the table's 12,346 rows (mean absolute 12,565, max 104,325). Nothing failed for years — the map lookup returned `undefined`, the `if (trade && ...)` guard read it as "not part of a trade", and the script exited 0 every night. Two rules. When a query feeds an index lookup, check that the key column is in the `.select()` list, since a missing one is indistinguishable from a legitimate miss at the call site. And prefer an explicit throw over a truthiness guard on a lookup that is supposed to hit — `if (trade && !processed[trade.uid])` cannot tell "this transaction is not a trade" from "I never selected the key", which is exactly what let this survive.

**The caller-side twin of that trap: a key the CALLEE does not destructure is dropped in silence, and a fallback path can hide it for years.** `import-plays-playerprofiler.mjs` called `getPlay({ esbid, qtr, dwn, yards_to_go, yard_line_100, ... })` while `libs-server/get-play.mjs` destructures `quarter` and `down_number`. JavaScript discards the two it does not name, so the lookup constrained only game, teams, distance and spot — never unique — and `getPlay` returned null on essentially every play. Nothing threw, because the script had a second attempt that added `seconds_remaining_quarter`, and that attempt carried 2023 and 2024 on its own. The defect only surfaced when Sumer Sports began writing `seconds_remaining_quarter` for 2025 with a clock a few seconds off this feed's: the hidden path stopped working, the match rate fell to 0.840, and 2025 lost roughly a sixth of its charting. A probe of 1,200 unmatched plays resolved **0** under the key set the code actually used and 1,062 once `quarter` and `down_number` were really applied. Two rules. When a call site and its callee use different names for the same concept (`qtr`/`quarter`, `dwn`/`down_number`), the rename is the bug surface — read the callee's destructure rather than the call site's intent. And treat a progressive-fallback matcher as a place defects hide: if the loose attempt is silently never succeeding, the tight one is doing all the work and its assumptions are load-bearing without anyone having decided that. Order tiers tightest-first and count which tier resolved each row, so a tier that stops contributing is visible in the run's own output.

**The same replay had two more silent roster holes, and the pattern is general: a transaction type that MOVES a player but is absent from the switch leaves the roster permanently wrong, with the strays hidden inside `ignored_tran_types`.** `POACHED` was handled as an add to the poaching team while nothing removed the player from the team he was poached from, so he contributed his full value to a team that no longer held him for the rest of history. At the 2026-08-11 snapshot the replay carried **291 players against the 243 actually rostered**, 50 of the 54 strays having been poached, which moved a team's Article XXII deposit by up to $37 in a $2,000 pool. Fixed in `00fe563b3` as the one-roster-per-player invariant — remove the player from every roster before any add — rather than a `POACHED`-only removal, so a future add whose departure the log does not state cannot reopen it.

Two rules, and the second is the expensive one. **Reconcile the replay's roster against an independent point-in-time source rather than assuming it** — `roster_asset_holding` scoped with `period_start <= date AND (period_end IS NULL OR period_end > date)`, which is a different walker over the same log and disagrees where either is wrong. Scoping it to holdings open TODAY instead manufactures phantom disagreements for anyone who joined after the date, which reads exactly like a defect. And **fixing one half of a two-sided flow can activate a DORMANT bug in the other half**: `SUPER_PRIORITY`, the reclaim an original team makes once the poaching team releases the player, was equally unhandled and equally invisible — with the poach unapplied the player never left, so nothing had to bring him back. Shipping the poach fix alone would have silently deleted two players from their rosters (fixed together, `1d413e3f8`). Reconcile the full residual to zero before calling such a fix done; "54 strays down to 2" is not the same claim as "the rosters are right".

**A fraction column typed `numeric(p,p)` — scale equal to precision — cannot represent 1.0, and the ceiling is invisible until the day a single row reaches 100%.** All the digits sit after the decimal point, so `numeric(5,5)` spans only ±0.99999 and a legitimate `1.0` raises `numeric field overflow`, which aborts the entire `batch_insert` rather than the one row. `league_team_daily_values.ktc_share` was `numeric(5,5)` and survived only because league 1 has 12 teams and its maximum share was 0.52125; the moment the 2026-08-02 fix started emitting rows for zero-value teams, the 2020 league-inception day where one team held all the ranked value produced a share of exactly `1.00000` and would have killed the job on every run. Widened to `numeric(6,5)`, which keeps the five decimal places and adds the one integer digit. When adding any share/rate/percentage column, give it a precision strictly greater than its scale.

**A safety flag that `main()` never reads off `argv` fails OPEN, so the run that was supposed to write nothing writes everything.** `import_plays` in `import-plays-playerprofiler.mjs` declares `dry_run = false` as a parameter and branches on it, while `main()` calls `import_plays({ filepath: argv.filepath, year: ... })` and never passes it — so `--dry_run` is accepted by yargs, changes nothing, and the "control run" a plan described as writing nothing would have executed a full `update_play` pass over an already-imported season under an untested matcher. Nothing errors: yargs takes any flag, the parameter default is the unsafe value, and the branch is simply never taken. This is the caller-side twin of the dropped-callee-key trap above, made worse by direction — for a `--limit` the failure is a no-op, but for a dry-run flag the default IS the destructive path. Two rules: trace a flag from `argv` to its consumer rather than confirming the parameter exists, and give a dry-run verify an oracle that a write would move (a row count on a season with known-missing values) — a count taken where the writer is fill-only and the data is already complete is identical under both branches and proves nothing. Watch the spelling too: `--dry_run` parses to `argv.dry_run` and `--dry-run` to `argv['dry-run']`, so a script reading one silently ignores the other. Do not reach for `max(changed_at)` in `play_changelog` as that oracle: checked 2026-08-22, the table holds **zero** rows for `source='playerprofiler'`, so "it did not move" is vacuous for this importer. An oracle whose population is empty reports success under both branches.

**An importer that derives its season from its own input has no oracle for "I imported the wrong season", and the job log will report success indefinitely.** `import-plays-playerprofiler.mjs` read a season-pinned URL out of config and took the season from the file it got back, so once the config held the prior year's URL every run re-imported an already-complete season, wrote nothing new, cleared its match-rate floor and recorded `is_successful=true` — for months. The blank 2025 column that finally surfaced it was several layers away from the cause. The rule: when a script's season is derived rather than passed, assert the derived season against an independent expectation (`current_season.last_completed_season_year`, or the `--year` argument when one is given) and fail loudly on a mismatch. A run that imports the wrong season correctly is indistinguishable from a healthy one on every signal the job itself emits.

**An importer that matches a vendor entity on a literal string from the FEED will stop matching the day the vendor rewords it, and the only symptom is a null foreign key on rows that keep arriving.** `import-betmgm-odds.mjs` resolved a game by `fixture.name.value.includes(' at ')`; BetMGM renamed its fixtures from `<away> at <home>` to `<away> @ <home>` some time after 2024-01-05, and from that day every game market was written as a FUTURE — `esbid` null, and later `season_year` falling through to `current_season.year` instead of the game's. It ran that way for two and a half years. Nothing could see it: the fetch succeeded, the markets inserted, the row count was healthy, and `esbid` is nullable because a genuine futures market has no game. The tell was only visible by comparing eras — 2024-01-05 rows read `Dallas Cowboys at Washington Commanders` and resolved, 2026 rows read `Seattle Seahawks @ Tennessee Titans` and did not. Match on the vendor's structured fields where they exist, accept every spelling you have historically seen when you must parse a name, and treat a separator as feed content rather than as a constant.

**The oracle for a resolver is the count it LINKED, not the count it fetched — and when a nullable foreign key is the output, "linked zero" has to be a failure rather than a number nobody reads.** The same run reported 134 fixtures and 724 markets on every channel it had while linking 0 of 127 real matchups, because no channel counted linkage at all. It now prints `fixtures=/matchups=/linked_games=/markets=` and throws when the feed carries game fixtures that resolve to zero games — a condition that was continuously true for two and a half years and would have fired on the first run. Any importer whose job is to attach foreign rows to local ones needs the attach rate in its own output; a total that only counts what arrived cannot distinguish a working resolver from one that has been dead since a vendor edit.

**The runs ledger reads "never ran" for a script whose `main()` skips `job()`, so absence from `jobs` is not evidence a writer is idle.** `import-betmgm-odds.mjs` called the importer directly from `main()` instead of going through `job()`, which is the only thing that calls `report_job`. The ledger therefore held nothing for `BETMGM_ODDS` after 2024-01-05 while the importer went on writing rows into 2026 — and the investigation that finally opened it began from "this source has not run", which was false. `import-caesars-odds-v4.mjs` and `import-betrivers-odds.mjs` both have the right shape: `main()` parses argv, calls `job(...)`, and lets `job` own the try/catch, the `report_job`, and the rethrow. Before concluding a job is dormant, check whether its entry point can report at all, and cross-read the table it writes rather than the ledger alone.

**A `--esbid`-style narrowing flag has to filter the collection the writes are derived FROM.** The same script's flag filtered only `unique_esbids`, which feeds the routes / dropbacks / snap loads, while every gamelog was built from an unfiltered `playStats` — so it wrote the whole week and logged one game. It also compared a numeric column against a yargs `type: 'string'` option, so the filter matched nothing and reduced the auxiliary loads to zero games while the full-week write proceeded regardless. Two rules for a scoping flag on a backfill tool: filter the source collection, not a derived index, and throw when the scope selects nothing rather than falling through to the unscoped write.

**No future-week roster slice is ever served, so one that exists can only drift — and a `rosters.find(r => r.tid === tid)` over a week-DESC list silently picks it.** `get-league-rosters-from-database` returns every week of the year ordered `week` DESC, so a bare `find` on `tid` resolves to the HIGHEST week, never the one the client renders (`getRosterRecordByTeamId` clamps to `min(fantasy_season_week, final_week)`, as does every other consumer — the scoreboard and matchup selectors, `simulate-matchup`, and `load-team-starters`, which computes future lineups from the CURRENT roster pool rather than reading a future slice). On 2026-08-03 that attached a team's live restricted free agency bids to a week-1 slice nobody reads while the week-0 roster it renders charged the pre-bid salaries, so the bid dialog quoted a max bid of -$75 against a $200 cap — $52 under the truth, with no error anywhere, because `Roster` prices `bid ?? value` and the bids simply never arrived. The same family as the absent-key traps above: the `find` returns a real roster, just the wrong one.

The slice should not have existed at all. `generate-rosters` takes `current_season.week + 1`, and `current_season.week` reads **0 for the entire offseason**, so the forward slice is materialized the day the previous season ends and then freezes at whatever week 0 held that night. It is now held until Week 1 is within `FORWARD_SLICE_LEAD_DAYS` of `regular_season_start` (which is itself two Tuesdays before the opener), and the orphan-slice oracle reports any populated week beyond the one a run is responsible for. Two rules: qualify a roster lookup by week, never by `tid` alone; and when a job derives a target from `current_season.week`, check what that expression reads in the offseason before trusting it.

## Script exit and lifecycle

**A script that imports `#db` does not EXIT when its work finishes — the knex pool keeps the event loop alive, so wall-clock duration is not run duration.** The work completes, the last `console.log` sits unflushed in a pipe, and the process lives until something kills it. This is the default outcome of an ad-hoc invocation, not a rare event: a 2026-08-04 census of league-production found **four** leaked `node` processes aged 10 to 56 days, every one a hand-typed `node -e` or a `tmp/*.mjs` throwaway, two of them ad-hoc data-view scripts. The 56-day one had held a Postgres backend authenticated as `league_user` — a role DROPPED in the 2026-07-01 rename — because Postgres never re-checks a role on an already-open session, so no timeout and no credential change could ever have reclaimed it. The same trap corrupts measurement while you are still at the keyboard: in that session two timing scripts appeared to hang for 7 and 15 minutes and were nearly diagnosed as slow query CONSTRUCTION, when construction took 98ms and the queries took 44s — the rest was the process refusing to exit behind a `| tail` that therefore printed nothing. End any script that opens a handle with `await db.destroy()`, and add an explicit `process.exit(0)` when a redis client is also open (`redis_cache` from `#libs-server` holds its own socket, which `db.destroy()` does not close). When a script prints nothing and seems slow, check `ps -o etime= -p <pid>` and its open sockets before believing the work is slow.

## Season constants

**`current_season.week` reads 0 for the whole offseason, and `isReserveEligible` uses that as a deliberate switch — so QUESTIONABLE is reserve-eligible today and will not be once Week 1 starts.** The last clause of `libs-shared/is-reserve-eligible.mjs` makes ANY `game_designation` qualify when the week is 0, because in the offseason there is no game to be active for; in the regular season only OUT and DOUBTFUL qualify. This reads as a bug and is not one — `submit-reserve.mjs` passes the live `current_season.week`, so no QUESTIONABLE player can reach injured reserve during the season. It cost a gated investigation on 2026-08-03 because the spec asserting it hardcoded `expect(result).to.equal(false)` with no frozen clock, which is right in-season and fails every offseason. Anything asserting on a designation whose answer depends on the season phase must pin the clock on BOTH sides; `current_season.week` is a live getter, so `MockDate.set` inside the test works and a clock-derived expectation is never necessary. Same family as the `--recursive` and golden-template traps: a value that is correct half the year looks like a stable one.

**`current_season.nfl_seas_week` names the week AFTER the one being played in PRESEASON, so any importer defaulting its week to it silently works an unplayed week.** It is `now.diff(regular_season_start, 'weeks')` truncated toward zero, then mapped through the `week < 1` ladder in `libs-shared/season.mjs:189`. With `regular_season_start` at 2026-08-25, a `now` of 2026-08-15 is -10 days, which truncates to -1 and returns **2** — while PRE week 1 games were in progress that afternoon. The window `diff == -1` spans Aug 11-18 and maps to week 2; PRE week 0 (the Hall of Fame game) falls inside the window that maps to week 1. Nothing throws: the importer fetches a week whose games have not started, skips all of them, and reports success, so an exit-code oracle and a `games_skipped` count both read healthy. This is why `import-plays-nfl-v1`, `import-nfl-games-nfl` and `import-plays-nfl-pro` all take `--full_season`, which sweeps every week of a season type instead of trusting the getter (2026-08-15). Before defaulting anything to this value in a PRE context, sweep the weeks or pass one explicitly; the getter is still unfixed.

**PRE week 0 is a real week and it is FALSY, which breaks every `x && { week: x }` guard it reaches.** Three live instances surfaced in one afternoon on 2026-08-15: `import-nfl-games-nfl.mjs`'s `format()` dropped `week` from the payload and failed the `nfl_games.week` NOT NULL constraint with 23502; the same function's `score.homePointsTotal && {...}` silently dropped a legitimate shutout of 0, leaving the column at whatever it already held; and `import-plays-nfl-v1.mjs`'s `week = week || last_week_with_stats` rewrote an explicit week 0 so the Hall of Fame game could never be imported through a week loop. Use `!= null` for any numeric field whose zero is meaningful — it still skips the pre-game nulls — and note that only preseason exposes this, so a guard that has been correct for years is not evidence. When one turns up, sweep the whole payload rather than the reported field: extract the insert's column list and check each against `information_schema`.

**The season-type flag is spelled three different ways across the four scripts of one pipeline, and the wrong spelling silently runs the default instead of erroring.** Walking a preseason repair end to end on 2026-08-26 needed all three: `import-plays-nfl-v1.mjs`, `import-plays-nfl-pro.mjs` and `import-gamelogs-ngs.mjs` read `argv.seas_type` (`--seas_type`); `process-plays.mjs` reads `argv.seasType`, so it needs the KEBAB `--seas-type` and carries an in-code note that reading `argv.seas_type` there was itself a silent bug; `generate-player-gamelogs.mjs` and `generate-player-snaps.mjs` take `--season_type`. The trap underneath is that yargs' camel-case expansion maps `--season-type` but NOT `--season_type`, so an UNDECLARED underscore flag parses to a key nothing reads and the run proceeds on its default — REG everywhere except `generate-player-snaps`, whose `main()` defaults to ALL. The cost is measured, not hypothetical: a 298-game preseason-inclusive backfill lost all 47 of its PRE games this way, each throwing `no play stats for esbid` into a `main()` that caught the throw and exited 0 (the comment at `generate-player-gamelogs.mjs:66`, which is why that script now declares the alias and a `choices` list). Read the script's own `initialize_cli` before passing the flag, and never carry a spelling across scripts.

Never reconstruct an `nfl_week_id` locally. Use canonical helpers in `libs-shared/nfl-week-identifier.mjs`: `current_nfl_week_identifier()`, `current_nfl_week_params()`, `last_completed_nfl_week_identifier()`, `last_completed_nfl_week_params()`, `nfl_week_offset_params({ offset })`. **Pick the half that matches the direction of your question**: the current pair is the week in play or next up and is what salaries, projections, betting markets, practice reports and schedules want; the last-completed pair is the most recent week with results. They are equal during the season and a whole season apart for the six offseason months, so a wrong choice is invisible from August to February. See `docs/data-views-system.md` "Live current_season semantics" for the choke-point rules.
