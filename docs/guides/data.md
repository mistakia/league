# Add or Change a Data-View Column

**When to read this:** Read before touching a column definition, a param registry, a field factory or a golden.

Column ids and params are persisted in saved views and short URLs, so a rename here is a migration. Four hashes behave differently under one.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

---

## Param coverage: saved views and short URLs

**Run `check-saved-view-param-coverage.mjs` as part of that gate list, not as an afterthought — a renamed PARAM key is the one failure this whole recipe otherwise misses.** The suite, the SQL-validity gate and the goldens all pass over it, because the defect lives in `user_data_views.table_state` rather than in any file. The 2026-08-05 cluster renamed 18 keys in `nfl-plays-column-params.mjs` and shipped without a matching rule in `data-views-saved-view-migration.mjs`, silently dropping filters on **45 saved views** (`qtr` 25, `dot` 7, `route` 7, `dwn` 5, `wp` 5) — found only after the deploy. The rule for that file is stated at length further down; what was missing was running the check at all, so treat it as a required gate whenever a cluster touches a param registry.

**Both param-coverage gates are KEY-anchored, so neither can see a renamed param VALUE — and a value rename has no gate at all.** `check-saved-view-param-coverage` walks `Object.keys(node.params)` and `check-data-view-url-param-coverage` walks `parsed.searchParams.keys()`, so both stay green across a value rename whether or not any migration rule exists. Running their negative controls does not help: those prove the gates work on KEYS. This is the reach-versus-class distinction stated in [the schema cluster guide](schema.md), arriving on the surface where it is easiest to miss, because a plan that says "run both param gates" reads like coverage. The 2026-08-08 run-direction rename hit it — `team_rush_left_end_dvoa` and its four siblings are VALUES of the `dvoa_type` param on `team_unit_dvoa` (`app/core/data-views-fields/team-dvoa-table-fields.js`), not param keys and not column ids, so `LEGACY_URL_PARAM_ALIASES` was the wrong remedy too: that map aliases top-level `table_state` keys, and an entry for a value would have been inert. The working shape is a VALUE map in `data-views-saved-view-migration.mjs` (`SCORING_FORMAT_HASH_TO_ID` is the precedent — it is likewise a value mapping) plus wiring it into `parse_table_state_from_url`, since the URL path runs only the nfl-week migration and would otherwise rewrite nothing at all. The gate has to be a spec proven red at the pre-fix revision; `test/data-views.dvoa-type-value-migration.spec.mjs` is the shape, asserting through the two public entry points rather than importing the rename map so its red is a value that was not rewritten rather than a missing export. **Before trusting a gate a plan names, check that your defect is in its class — three column-shaped things live in `table_state` (param keys, column ids, param values) and only the first two have gates.**

**Its sibling `check-data-view-url-param-coverage.mjs` covers the OTHER data-view surface, and it is the one a rename forgets — a shared short URL cannot be rewritten, so a missed key there is permanent.** The saved-view gate checks the params nested inside a column; this one checks the top-level query-string keys of the production `urls` table against `SHARE_LINK_URL_SCHEMA` plus `LEGACY_URL_PARAM_ALIASES`. The distinction that made the June 2026 `splits` -> `row_axes` rename fail is that **a URL query string carries no version field**, so it never enters the versioned migration chain in `libs-shared/data-view-storage/migrations.mjs` — the rename did ship a `v2_to_v3` rule and 188 of 682 production URLs still rendered at the wrong grain for six weeks, three of them emitting unexecutable SQL. Run it alongside the saved-view gate on any cluster touching a top-level `table_state` key:

`yarn check:cluster` runs it, supplying the production environment itself and skipping loudly when the tunnel is down.

The only remedy for a reported key is a permanent entry in `LEGACY_URL_PARAM_ALIASES` (`app/core/data-views/parse-table-state-from-url.mjs`); there is no migration to write, because the link is immutable. Two things worth copying from it. Its accepted-key sets are **imported rather than grepped**, which is the direct fix for the failure that blinded the saved-view gate — a presence-grep cannot tell a consumer from prose about one, so a comment naming a legacy key made that key unreportable. And its URL population is **five routes, not one**: `/leagues/:lid/players-table` is a `<Navigate>` redirect preserving `location.search`, so scoping to `/data-views` alone misses 159 of the 863 URLs. Its negative control is deleting the `splits` alias and confirming the gate reports it — take that as seriously here as everywhere else in this guide.

**Two ways a rename hides from the gates you are running.** First, **a golden cannot catch a miss its emitter SHARES**: if the emitter still produces the old name and the golden still expects it, they agree and the fixture passes — two goldens survived the 2026-08-05 sweep that way, and one was `skip_query_match`, so it could never have failed on SQL at all. After regenerating, grep the goldens for every old table-qualified name; that grep, not the suite, is the gate. Second, **the audit cannot show you the members it did not flag**: renaming some members of an obvious sibling set splits it. `wins`/`ties` are four characters and flagged while `losses` is six and invisible, so four tables were about to ship `regular_season_wins / losses / regular_season_ties`. When a class renames part of a set, check the whole set against `information_schema` rather than against the audit output.

## Oracles and goldens

**An executed-result oracle is only as good as where its expected values came from.** The result-equivalence fixtures are the gate meant to catch semantics that valid SQL cannot, but their `expected_rows` are hand-written, and one authored by reading the current output is a screenshot rather than an oracle. `game-opponent-range-year-offset-fanout-result-equivalence.json` asserted `game_is_home: true` for a subject team its own `seed` SQL places at `away_nfl_team` in both games, so it executed happily and blessed an inverted flag alongside four query-match goldens. Derive an oracle's values from the fixture's seed data, and note that `update-data-view-snapshots.mjs` only rewrites `expected_query` — regeneration structurally cannot repair an oracle, so a wrong one must be hand-corrected.

**A regenerated data-view golden cannot catch a rename you missed.** `scripts/update-data-view-snapshots.mjs` overwrites `expected_query` with whatever the current code emits, so a golden regenerated from buggy code agrees with the buggy code and the suite goes green over a live defect. This is not hypothetical: the 2026-07 plays/snaps conformance left `build_role_union_period_cte` emitting `nfl_plays.year` against the renamed table — a 42703 on every data view carrying a rate type — and eight regenerated goldens blessed it. Auditing the regeneration diff does not help either, because that only proves each _change_ was intended; it says nothing about an old name that stayed _unchanged_. After regenerating, grep the goldens for the old names directly (they escape quotes, so match `nfl_plays\\".\\"<old>`), and treat executed result-equivalence — not query-match — as the gate.

**A golden carrying `skip_query_match: true` asserts NOTHING about its SQL — regenerating one is bookkeeping, not coverage.** The mocha harness branches on that flag: when set, it logs the SQL diff to the working-tier catalog for hand review and continues, so `expected_query` is inert and the fixture cannot fail on a query change. The trap is that every other signal still looks like coverage — the file lives in `test/data-view-queries/`, `data-view-test-cli.mjs` _does_ compare it and prints `✓ Queries match!`, and `--update` rewrites it — so a session fixes a defect, regenerates the one golden that exercises the shape, sees green, and has added no gate at all. On 2026-07-31 the week-row-axis fix landed against exactly this: `keeptradecut-value-year-week-split.json` was the only golden in the corpus requesting a `week` param, and it carried the flag at the time. **No golden carries `skip_query_match` today** — `08cd28937` (2026-08-11) un-skipped and regenerated all 29 — so the trap is currently dormant, but the harness branch is live and a fixture reintroducing the flag reopens it. Check the flag before treating a fixture as your gate; when it is set, the coverage has to be a spec asserting on the generated SQL (or a result-equivalence fixture), and the honest proof is that the new test **fails at HEAD** — run it in a clean worktree at HEAD and confirm it goes red before trusting it green in your tree.

**A query-match golden asserts NOTHING about a table-alias HASH — both comparison paths normalize every hash away before comparing.** `test/utils/compare-queries.mjs` (the mocha spec) and `normalize_sql_for_comparison` in `libs-server/format-sql.mjs` (the CLI, `scripts/data-view-test-cli.mjs`) independently rewrite each distinct 32-character hash to a POSITIONAL `table_0`, `table_1`, ... So a change that moves an alias while leaving the join structure alone is invisible to all 256 goldens, and to `--all`, which reports `✓ Queries match!` over it. Measured 2026-08-15: neutralising the `as_of_month_day` contribution to `generate_table_alias` changed a fixture's emitted alias from `t2802b353...` to `t8bc93b1f...` and the CLI still passed it.

**The costly corollary is about REGENERATION, and it reads as your change moving an alias when it did not.** `scripts/update-data-view-snapshots.mjs` compares under the same normalization, so it never rewrites a golden whose ONLY drift is a hash — which means a committed fixture can carry STALE table-alias hashes indefinitely, from whatever change last moved them. The moment that fixture regenerates for an unrelated reason it absorbs the current hashes too, and the diff shows an alias move your change did not cause. Measured 2026-08-19 on `player-rush-yards-after-contact-per-attempt-from-plays-year-offset-range.json`, where two aliases moved in a commit that only renamed accumulator columns: instrumenting `generate_table_alias` showed the input key BYTE-IDENTICAL between the working tree and a HEAD control, and the control computed the same new hashes while reporting `0 updated`. **The discriminator is one command** — regenerate the same fixture in a control worktree at HEAD; `0 updated` plus the new hashes means the committed ones were already stale. Reading the move as yours sends you hunting a change to the alias derivation that does not exist.

**But `0 updated` ALONE does not settle it, and the sentence above reads as though it does.** The regenerator cannot rewrite a fixture whose only drift is a hash — that is the whole point of the preceding sentence — so `0 updated` at HEAD is exactly what you get whether the committed hash is stale or current, and the control never prints a hash for you to compare against. What settles it is emitting the SQL in both trees and reading the literal alias: import `get_data_view_results_query` from `#libs-server/get-data-view-results.mjs`, pass the fixture's `request`, and match `/t[0-9a-f]{32}/g` against the working tree and a HEAD worktree. Note it returns `{ data_view_metadata, query }` rather than a builder, so `String(result)` is `[object Object]` and yields a 15-character "SQL" that reads as an empty query rather than a wrong unwrap. Used 2026-08-23 on `player-fantasy-points-from-plays-week-split-per-week-result-equivalence.json`, where HEAD emitted the same `t9b050d8a...` the working tree did while the committed fixture carried `t689a3101...` — stale, and the 25-character length delta between the two trees was exactly the predicate that change removed.

**The METRIC alias is the opposite case and it bites a rename: `m_<12-hex>` derives from the column EXPRESSION, so it MOVES when a column is renamed, and neither comparison path normalizes it — both rewrite 32-character hashes only.** So a golden that was textually swept to the new column name still fails on an alias nobody edited, and the failure reads as a broken rename rather than as bookkeeping. Seven goldens failed exactly this way in the 2026-08-18 `recv` -> `receiving` conform, where the sweep had correctly rewritten every `nfl_plays.recv_yards` and the only residue was `m_3cfbf16a44c1` -> `m_2205f2f1663c`. **Regenerate the affected goldens rather than patching them by hand** (pass the DB env to `scripts/update-data-view-snapshots.mjs` and name the fixtures explicitly), then grep for the old column names as the actual gate. The two hashes fail in opposite directions and it is worth holding both: a moved TABLE alias is invisible and needs a spec to pin it, while a moved METRIC alias is loudly visible and needs regeneration.

**A THIRD alias property bites a rename and it is the quietest of the three: a `select_as` becomes a real SQL identifier, and Postgres TRUNCATES one past 63 bytes with a NOTICE rather than an error.** `select-string.mjs` emits `${select_as}_${column_index}`, so the emitted name is the alias plus two or three bytes. Past the limit the result carries a key the client never asks for and the cell renders blank in production — while the suite stays green, because `test/data-view-player-field-parity.spec.mjs` compares the client `player_value_path` to `select_as()` with BOTH sides untruncated and they agree on a name the database will never return. Measured on `league-test-pg` 2026-08-18: `select 1 as "rest_of_season_projected_points_added_positive_including_cap_savings_0"` answers `NOTICE: identifier ... will be truncated to "..._including_cap_sa"`.

The trap is that a conformance rename makes names LONGER, so a vocabulary campaign walks toward this limit rather than away from it — the longest alias in the tree was 56 bytes until the 2026-08-18 `adj` retirement, whose literal spelling would have emitted 70. That family's aliases drop their `projected_` token to fit; the DB column (53 bytes) and the persisted column ids are unaffected and must NOT be shortened for this, since only the derived alias overflows. **When a rename lengthens a column, measure the ALIAS separately from the column** — they have different limits and only one of them is a Postgres identifier.

The gate is a byte-length assertion in that same parity spec, budgeted at 60 rather than 63 so an alias cannot fit at a single-digit column index and truncate once a view carries ten or more columns. It asserts its own denominator, so a matcher that stops matching cannot report compliance. Two aliases were already over budget when it was written (`nfl_team_seasonlogs_receiving_yards_after_catch_over_expected` and its `_per_reception` sibling, both 61 bytes, from the `recv` conform) and are held out in a dated list that FAILS once an entry is no longer over budget — so a repair forces the entry out instead of leaving a standing exemption.

What the normalization DOES preserve is the alias COUNT and its position, so an alias COLLAPSE — two columns falling onto one join — turns a golden red **only where a golden requests both columns together**, which is a much weaker guarantee than this guide claimed until 2026-08-19. Measured that day: `player_opportunities_from_plays` and `player_total_expected_points_added_from_plays` had been collapsing onto one alias for as long as both existed, because `generate_table_alias` hashed their role columns as a SET while emitting them as an ORDERED `COALESCE`. The shared CTE carries ONE subject-id expression, decided by whichever column came second in the request, so one of the two was always crediting the wrong player — on 60,547 plays in 2023+ alone, since `passer_pid` and `target_pid` are both non-null and different on every pass. **No golden went red, because no golden requests both.** Fixed in `289b88483` by hashing the declared order; `test/data-views.role-column-order.spec.mjs` pins it. The durable rule: a collapse is only visible to the goldens if some fixture happens to pair the two columns, so when two columns share an alias by construction, the gate is a spec asserting the aliases DIFFER, not the corpus. The invisible half is a hash that merely MOVES: that silently invalidates every cached redis entry and every saved view keyed on it, with no test anywhere able to see it. If you need to pin that a hash did not move — which is the check that makes a new column param safe to ship — assert the literal alias in a spec (`test/data-views.keeptradecut-as-of-month-day.spec.mjs` pins `t1e3e92b5fa3914d2c8f61e0ded52116e` for the unset keeptradecut column) or diff the emitted SQL against a worktree pinned to an explicit pre-change hash. This is the same family as the `skip_query_match` trap above: the fixture looks like coverage, `--all` prints a tick, and the property you care about was never compared.

**There is a FOURTH hash and it is neither normalized nor value-derived: the batched CTE NAME, `rate_<period>_<12hex>` (and its `per_period_` twin), which `compute_group_key` derives by hashing `JSON.stringify(sig)` — so it moves when a FIELD NAME in that signature object changes, not only when a value does.** That is the opposite failure from the table alias, which hashes the role list's VALUES via `join('_')`. Renaming `pid_columns` to `role_columns` on 2026-08-20 therefore moved 34 goldens while moving zero table aliases and zero metric aliases, and the plan's verify — written on the alias rule — had declared any moved golden there a defect. It is not: classify the differing tokens before believing either verdict. That run was **316 CTE names and nothing else**, and the CTE name is internal to one statement rather than a cache key, so the churn costs nothing. The general form: three of these hashes read different inputs (values, expression text, the whole signature INCLUDING keys), so "did my rename move a hash" has three different answers and only one of them is a defect.

**Beware the inverse grep error: a pattern that matches as a SUBSTRING of a longer identifier, making dead code look live.** The documented hazard above is a pattern that cannot match; this is one that matches too much, and it reads as confirmation rather than as a zero. Grepping the goldens for `week_timestamp` to check whether a join was exercised returns 11 files — nearly all of them hits on the _table_ name `nfl_year_week_timestamp`, which contains the column name as a substring. Anchoring on a delimiter (`\.week_timestamp`, `"week_timestamp"`) returns 3. Anchor a reachability grep that way and confirm the emitted SQL, not just the file list.

**The third variant is the worst, because delimiter-anchoring does not fix it: the token is complete and correctly spelled, but appears in a DIFFERENT SYNTACTIC ROLE than the one you are testing for.** A column name that is also a data-view column id, a wire key, or a constant will be in the bundle no matter what the code does with it, so its presence proves nothing about the migration you are verifying. On 2026-08-06 a frontend deploy meant to clear the roster-salary rename was "confirmed" by `grep -oh player_salary` over the deployed `dist/` returning 130 hits across ten chunks — with a positive control that passed. The claim was worthless: `player_salary` predates the migration as a data-view column id, which the bulletin tracking that deploy had explicitly warned about. **Anchor on the syntactic role, not on the token**: the migration moved Immutable reads, so the discriminating patterns are `get("player_salary")` and `get("player_salary",0)` (14 and 4 hits, the second being exactly the `notSetValue` form the source uses) against **zero** `get("value")`. Positive form present in the shapes the source actually has, negative form absent — that pair is the proof, and either half alone is not. Corollary: when a bulletin or task note tells you a specific verification is invalid, it is recording a trap someone already fell into; read it before choosing your oracle, not after.

As of 2026-05, the anchored count was **zero** and the join was genuinely unreachable: `group_tables_by_supported_row_axes` intersects the request `row_axes` against the column's `source.grain` identity, so a `player_year`-grain column never saw a `week` axis and its week branch could not execute. A plan had been written to fix a type error in that branch. **That is no longer true** — the keeptradecut restructure declared `supports_row_axes: ['year', 'week']`, which made the branch live and put the column into three goldens. The grep technique is the durable lesson here; the counts are dated.

**Never conclude a column is absent from a pattern-filtered `information_schema` query.** The same failure class as the grep note below, in the one place it reads as authoritative. On 2026-07-29 a session checked whether `projections` retained dated history with `information_schema.columns WHERE table_name='projections' AND column_name ~ 'time|date|year|week'`, got no timestamp back, and reported that no point-in-time projection history existed anywhere. The column is `generated_at`, which contains none of those four substrings. It is `NOT NULL` and part of the unique key, so the table had been appending 4.69M rows across 2,064 daily snapshots for two years. The wrong conclusion drove a design decision -- projections demoted to live-only, their benefit "asserted rather than measured" -- that had to be reversed. List a table's columns in full before concluding a capability is missing; a pattern filter is for reading convenience on a table you already know, never for proving a negative.

**Grep proves the absence of a string; only EXPLAIN proves the query is valid.** The golden-grep above is necessary but not sufficient, and on 2026-07-27 it missed a live defect twice. Correlated-subquery predicates are emitted as raw SQL against a generated CTE alias, so they appear _unquoted_ and _hash-named_ — `t22c9a76f62c8a62fec52ad076663a982.year IN (2024,2025)` — and match neither `nfl_plays\\".\\"<old>` nor any table-qualified pattern. A reviewer sweeping for `prop_markets_index.year` plus a fixed alias list that omitted `pmi.` likewise returned a confident zero on `pmi.year` in `update-market-settlement-status.mjs`, which had thrown 42703 on every game finalize for four days.

The gate that does work is now committed as **`db/gates/check-data-view-sql-validity.mjs`**, and it must run per cluster on any grain-column rename:

`yarn check:cluster` runs it once the `:5433` container is up (`yarn test:db:up`).

It provisions its own database on the shared :5433 container (so it cannot collide with a sibling's suite run), loads `db/schema.postgres.sql`, generates SQL for all 551 data-view columns across the plain and `year_offset` range shapes, and `EXPLAIN`s each of the 1102 statements in about five seconds.

**A predicate that is merely REDUNDANT still changes the plan, so "defense in depth" on a scope predicate can cost more than the pruning it was added for.** The output-aggregator period CTE scoped `nfl_games` and joined `nfl_plays` on `esbid` alone, so a single-year view scanned all 27 `nfl_plays` partitions -- 2.6M intermediate rows, 16.1s cold (signal 126307). Pushing the year onto `nfl_plays` and the cohort alias prunes to one partition and made it SLOWER: the planner flipped to a 35,198-iteration nested loop reading 5.98M buffers against 179K, 6.3s against the unpruned 5.6s warm. Dropping the now-implied `nfl_games` predicates -- keeping only what the fact table cannot express, since `player_gamelogs` has a season year and no season type -- landed it at 3.3s. Measured back to back on production 2026-08-21; `d262fdb72`. Two rules fall out. Emit each scope component on exactly ONE relation, the one whose partitions you need pruned, and prove the duplicate's absence is safe on DATA (plays and games agree on `(season_year, season_type, week)` for all 1,487,212 rows) rather than on reasoning. And judge a pruning change on `EXPLAIN (ANALYZE, BUFFERS)` of the real statement, never on the partition list alone: pruning is visible, the join-shape flip that eats the win is not.

**`withMaterialized` is an OPTIMIZER FENCE, not a performance hint, and on a small CTE it only blinds the planner.** The knex call emits `WITH x AS MATERIALIZED (...)`, which stops Postgres seeing through to real statistics. On the `player_year_teams` identity bridge that cost a rows=1 estimate against an actual 2,411, and the outer join became a nested loop rescanning all 2,411 rows once per player — 28,129 loops, ~67.8M comparisons, 8.3s of an 8.7s data view (signals 126228, 126446). Dropping to plain `.with()` measured 7.0s -> 0.22s with byte-identical results, 2026-08-23, `1b5575346`. The fence is right where it was designed for — the big play-by-play and period CTEs, which are expensive and feed hash joins where the estimate does not matter — and wrong on a small bridge CTE, where nothing needs fencing. It arrived at 19 call sites wholesale in the identity-model migration rather than being chosen per site, so treat an existing `withMaterialized` as a default someone inherited, not as a decision someone made.

Two things make this safe to change and easy to get wrong. **Plain `WITH` is adaptive**: Postgres inlines a CTE only at a SINGLE reference and materializes it otherwise, so switching does not risk re-evaluating a multiply-referenced CTE — verify with a two-reference control that still shows `CTE Scan` nodes, since a single-reference test alone cannot distinguish the two rules. And **the emitted keyword is load-bearing for your gates**: the CTE-dedupe spec anchored on the literal string `"player_year_teams" as materialized` and returned a confident 0 after the change rather than reporting a re-emission. Anchor a CTE-count gate on the DECLARATION (`"<name>" as (`), and prove it still reports by disabling the dedupe guard.

**When a view is slow and there is no fix you are willing to buy, ACCEPT it in `ACCEPTED_SLOW_QUERIES` rather than muting the signal or letting it re-emit forever.** The registry lives in `libs-server/data-views/execute-data-view-request.mjs` beside `data_view_query_signature`, is keyed by that signature, and RAISES the emission threshold for that one shape — it is a ceiling, not a mute, so a run above the ceiling still emits. That distinction is the point: "known to cost 6.6s" and "degraded to 14s" are different facts and only the second wants triage. The first entry is signature `da81f8407752c611` (signal 126506), a wide 7-year player-year view at 6,593ms with 23 outer joins and 7 CTEs where every scan is index-driven and the largest leaf is under 200ms — nothing left to rewrite, and the only remaining fix was narrowing the view, a product decision. Two properties to know before you add one. The ceiling **cannot buy silence under load**: this class of query measured 4,992ms idle against 10,840ms contended, so a static number that covered the loaded case would also hide a real regression, and 8000 was chosen to cover the idle steady state only. And an acceptance **lapses on its own**, because the signature is derived from query SHAPE — edit the view and the hash moves, the entry stops matching, and the shape reports again until someone re-accepts it. Every entry carries the trade-off that was declined and a `review_after`, so an accepted cost gets revisited instead of inherited.

**Those two shapes are the WHOLE of its coverage, and the output-aggregator paths are not among them.** It emits the plain and year-offset-range shapes only, so every `output: { period, aggregation }` request — every rate, count and mean, and the multi-year team-play wrap — is outside it. A GATE OK says nothing about them. On 2026-08-20 hand-EXPLAINing the aggregation shapes found three defects the gate was green over, one of them a live 500 on 17 of 17 columns. When you touch the aggregator, write a throwaway probe that builds each (column, period, aggregation) you care about and `EXPLAIN`s it; the full 42x18 cross product runs in about the same time the gate itself takes. Run ad hoc on 2026-07-27 it found six defects that 232 goldens and a fully green 2214-test suite did not; on its first committed run it found two more, both pre-existing (`player_pro_bowl_selections` naming a physical column that does not exist, and a `NaN` interpolated raw into the keeptradecut `year_offset` range SQL).

**Run it from a clean worktree at your HEAD, not from the shared tree — it reads the working tree, so a sibling's uncommitted edits are indistinguishable from your defects.** The script imports the column definitions live and loads `db/schema.postgres.sql` off disk, both from whatever is sitting in the checkout. So a sibling mid-cluster — emitter already renamed, DDL still `PENDING`, schema export not yet regenerated — makes the gate fail on _their_ transient inconsistency, reported against column names that have nothing to do with your change. On 2026-07-31 a schedule-route cluster ran the gate and got `GATE FAIL: 8` on `espn_team_win_rates_index.nfl_team does not exist`; HEAD had the correct `key_columns: { team: 'team' }` and the `nfl_team` was an uncommitted edit belonging to the live time-series-feeds session, staged ahead of its own `db/adhoc/2026-07-31-conform-espn-win-rates-feeds.sql`. The findings were real SQL failures and entirely not the running session's — and read as a pre-existing defect worth reporting. The tell is a finding on a table your cluster never touched; the check is `git status` plus `git show HEAD:<emitter>` against your tree. Get the honest number the same way you would for a build: `git worktree add ~/user-base/tmp/<name> HEAD`, symlink `node_modules`, run there, `git worktree remove`. It costs one command and the gate still provisions its own database, so it cannot collide.

**A bare import that is not in this repo's `package.json` still resolves — from user-base's ROOT `node_modules`, one level up — and no gate here catches it.** Node walks parent directories, so a package absent from `repository/active/league/node_modules` is found at `/Users/<you>/user-base/node_modules` and everything looks fine from the real checkout. It breaks only where that ancestor is missing: a worktree under `/tmp`, a CI checkout, a production host. `league-import/espn.mjs` imported `node-fetch` this way until 2026-07-31, and a `/tmp` worktree therefore killed the **whole suite at load** with `ERR_MODULE_NOT_FOUND` before a single test ran — while the SQL-validity gate and individual golden specs still passed, because neither loads `test/importer-espn.spec.mjs`. So `/tmp` appeared to work right up until you asked for the number that mattered.

That import is gone (the file now uses Node's global `fetch`), and `node-fetch` was the only such package — every other unresolved bare specifier in the tree is a webpack alias or a Node builtin. A worktree at `/tmp` runs the full suite green today. The recipes above still say `~/user-base/tmp/` because it costs nothing and keeps the scratch under one root; that is preference now, not a constraint. What is worth keeping is the check: **before adding an import, confirm the package is in this repo's `package.json`** — a parent-resolved dependency produces no error, no lint failure, and no gate finding on the machine you develop on.

**Read its findings by reachability, not by how broken the SQL looks.** Every finding carries a tier — `system_view` (ships in a default view, so it is on a page-load path), `saved_view`, `golden`, `catalog_only` — and the report sorts by it. Ranking the 2026-07-27 findings by severity alone inverted the call: a dormant seasonal path was ranked BLOCKER above `GET /api/markets/players/:pid`, which had been returning 500 on every call for a year. A `catalog_only` failure still fails the gate; the tier orders triage, it does not excuse anything. Feed the `saved_view` tier from production with `--saved-view-columns` (see `check-saved-view-param-coverage.mjs --column-ids`).

To validate a single golden by hand, extract its `expected_query` and run `EXPLAIN` against the container directly (`docker exec -u postgres -i league-test-pg psql -U league_test -d league_test`; the `postgres` and `league_writer` DB roles are GRANT targets and cannot log in, so `-U league_test` is the only usable login role).

**A renamed column PARAM silently drops the filter — sweep saved views at apply time, not authoring time.** `apply_play_by_play_column_params_to_query` iterates the param registry and skips any key it does not recognise, so a param renamed code-side leaves every saved view still persisting the old key with a filter that is quietly ignored: no error, no failed test, just a wrong answer. `db/gates/check-saved-view-param-coverage.mjs` finds them against production:

`yarn check:cluster` runs it against production when the tunnel is up.

The remedy for anything it reports is a rule in `libs-shared/data-views-saved-view-migration.mjs`, which rewrites persisted params at read time. A one-shot SQL migration written when the rename is AUTHORED cannot cover a view saved between that check and cutover — which is precisely the hole the 2026-07-24 plays/snaps saved-view migration left. This check found 196 orphaned occurrences across 13 saved views from a 2025-07-24 rename that shipped with no saved-view migration at all.

**That rule runs CLIENT-side, so the fix is not live for users until a FRONTEND deploy — a backend deploy changes nothing.** `run_migrations` is reached only from `app/core/data-views/sagas.js` (via `libs-shared/data-view-storage/storage.mjs`), so the rewrite happens in the browser before the request is sent. `yarn deploy` ships the module to the hosts and no user is helped. Sequence `yarn build && yarn deploy:dist && yarn deploy:sourcemaps`, and confirm the map reached the bundle by grepping the deployed directory on the host for a legacy KEY that exists nowhere else (`ssh league "cd /root/league/dist && grep -oh 'avsk:.\{0,22\}' *.js"`), with a positive control. One upside of the client-side placement: the migrated request carries the new keys, so it hashes to a fresh redis key and no cache purge is needed. Confirmed 2026-08-05 fixing the 18 shorthand param renames (`038e45768`).

**Two traps in the coverage check itself, both of which make a CORRECT fix look broken.** Its recognition test is a presence-grep whose tokenizer requires three characters or more, so a two-character legacy key (`wp`, `cp`, `ep`, `db`) could never match and reported as an orphan with a correct rule in place; it now imports `MIGRATED_PARAM_KEYS` from the migration module and recognises migrated keys exactly. And a param whose key doubles as its column may legitimately KEEP its key while its column moves — resolution is `column_name || param_key` and saved views persist the key — so `dot` is still a live registry key even though its column is now `depth_of_target`. Adding a rename rule for that shape CREATES an orphan rather than fixing one; check the registry before writing a rule.

**A third trap ran the other way and was far worse: until 2026-08-05 the check tokenized COMMENTS, so prose naming a legacy key marked it recognised and the gate could not report it at all.** The two traps above make a correct fix look broken, which is loud. This one made a broken state look fixed. The presence-grep cannot distinguish a consumer from prose ABOUT a consumer, and the prose that names a legacy key is by construction written in exactly the files it scans — so the migration module's own incident note (`across 45 saved views (qtr 25, dot 7, route 7, dwn 5, wp 5)`) plus an aside in `player-fantasy-points-from-plays-column-definitions.mjs` between them made `qtr`, `dot`, `route` and `dwn` permanently unreportable. The comment documenting the incident is what blinded the gate to the incident. Verified by deleting the `qtr` rule and re-running: still `GATE OK`, over 289 occurrences across 25 saved views. Comments are now stripped before tokenizing, which costs nothing legitimate because a legacy key requires a rule and `MIGRATED_PARAM_KEYS` recognises those exactly.

**So never accept a green from this check without a negative control.** Delete one live rename rule, re-run, confirm it reports, and put the rule back — it takes two minutes and it is the only thing that distinguishes "no orphans" from "cannot see orphans". That is the same positive-control discipline this guide already requires of any sweep whose zero would let you skip work, and this gate had gone un-controlled since it was written.

**`await` on a knex QueryBuilder EXECUTES it, so an async helper that returns one hands you rows and every SQL-shape assertion silently passes over an array.** A builder is a thenable, so `const q = await build_query()` resolves the builder itself rather than returning it, and `q.toString()` is then `'[object Object]'` (or `'[object Object],[object Object]'` for a result set). Assertions written as `expect(sql).to.include(...)` fail with a message about `[object Object]` that reads like a broken expectation rather than a broken harness; assertions written as `expect(sql).to.not.include(...)` **pass vacuously**, which is the dangerous half. This cost two separate detours on 2026-08-05 — first in a new builder spec, then again in an ad-hoc verification script where it produced `per-game stage emitted: false` for a feature that was working correctly and nearly sent the session to debug the emitter. Have the helper return the builder inside a wrapper (`return { query: build_period_cte(...) }`) or make it synchronous; a helper whose only async work is resolving inputs should resolve them first and return the builder plainly.

**A verifier that reads a GENERATED file is only as current as the last generation — its OK is vacuous until you regenerate.** `scripts/verify-named-format-catalog.mjs` iterates `libs-shared/named-format-catalog.mjs`, which is written by `yarn generate:formats`. On 2026-08-05 that file was eight weeks stale, so a newly added named format was absent from it entirely and the verifier reported `OK` while asserting nothing whatsoever about the new format. Regenerating first turned the same command into two real errors. This is the same family as the negative-grep and `skip_query_match` traps above, with the staleness living in an input artifact rather than in a pattern: before trusting a green from any generated-input gate, confirm the thing you are verifying actually appears in the generated input (`grep -c <new-id> <generated-file>`), then run the negative control. Note the control itself can be vacuous for a third reason — prettier reformatting can break a mutation pattern, so a `perl -0pi` control that reports "no failure" may never have applied; verify the mutation landed before reading its result.

**`apply_scope_to_query` resolves physical column names by table name; do not hardcode them.** `libs-server/data-views/physical-season-columns.mjs` maps physical tables to their conformed `season_year` / `season_type` columns, and `apply_scope_to_query` consults it by default, so an emitter that simply omits `season_year_column` gets the right name instead of the vocabulary `year`. Any cluster that conforms a physical table an emitter targets must register it there — `test/libs-server.physical-season-columns.spec.mjs` scans `libs-server` for `apply_scope_to_query` call sites and fails the suite when a table one of them names carries `season_year` but is absent from the map. Note the criterion is that an emitter targets the table, not that the table carries the column: 70 base tables carry `season_year` and only the handful an emitter names belong in the map. A call site passing a variable rather than a literal cannot be resolved statically, so those are pinned in a reviewed list and a new one fails until it is reviewed. Tables with no season-type column at all (`nfl_snaps`, the `nfl_plays_*` participant tables) are declared explicitly and throw rather than falling back, so a `seas_type` predicate against them is a loud error rather than a runtime 42703.

## Regenerating goldens

When a rename does turn up a bad golden: **fix the code first, regenerate second, EXPLAIN third.** Regenerating first only re-blesses the defect. And declare `key_columns: { pid, year }` on any data-view source whose CTE projects `season_year` — `param-utils.mjs` silently defaults `year_column` to `'year'` when a source omits it, which is a rename that no grep of the source tree will ever surface.

Before regenerating, prove the golden is the thing that is wrong. A golden that disagrees with your change may be encoding semantics you just broke: on 2026-07-27 a `.year BETWEEN` predicate that was invalid without a year split turned out to be **valid and load-bearing** with one (the CTE projects `season_year as year` only when a year row axis is present), and the golden that failed was the only signal. The fix was to guard the predicate on `year_reference`, not to regenerate. Confirm the delta is exactly what you intended by reversing your change on the generated string and checking it reproduces the old golden byte for byte.

**String-level reversal only works for a change that SUBSTITUTES text — for one that adds structure, reverse the code instead, in a worktree at HEAD.** A change that appends a UNION arm, a CTE, or a join cannot be undone by deleting the matching text: on 2026-07-30 two new role-union arms were stripped by splitting the generated SQL on `union all` and dropping the arms naming the new roles, which also deleted the trailing `) as "role_union" inner join "nfl_games" ...` that belonged to the last arm, and the "reversal" then differed from the golden at char 0 on several fixtures. The rig looked like it had found a problem when it had only mangled the SQL. The reliable form costs one command: `git worktree add ~/user-base/tmp/<name> HEAD`, symlink `node_modules`, run the golden spec there against its own database, and confirm it is **fully green**. That proves the committed goldens encode current-master behaviour, so every failure in your tree is your change alone — which is the claim you actually need before regenerating, and it holds no matter what shape your change takes. Pair it with reading the first divergence point of each failing golden to confirm the inserted text is only what you added.

**A golden that embeds a clock-derived value must be a template, not a literal.** `expected_query` is run through `libs-server/process-expected-query.mjs`, which evaluates it as a template literal with `current_season`, `constants`, `all_years`, `last_3_years`, and `next_week` in scope (`next_week` mirrors the `next_week_opponent_total` branch of `get-data-view-results.mjs`). Any golden containing `${` is also skipped by the regeneration script, so templating is what protects a fixture from being re-blessed. `pff-team-grades-next-week-opponent.json` was a literal `"week" = 0` until 2026-07-28, when the date rolled over, the derived week moved to 1, and the golden broke on master with no code change; it is now `"week" = ${next_week.week}`.

**Regenerating in the SHARED tree blesses whatever a sibling session is mid-change on, and the diff reads as your own change doing something inexplicable.** The advice below -- name your fixtures, check `git status` -- catches an unintended FILE and cannot catch a fixture whose content absorbed another session's uncommitted emitter. On 2026-08-21 a period-CTE change regenerated 45 goldens in the shared checkout; 36 carried the intended predicate move and the rest also lost a `player_years` join and moved a table-alias hash, both belonging to a live sibling's in-flight bridge work. **The discriminator is one command, and it reads opposite to the stale-hash note above: regenerate the same fixtures in a worktree at HEAD.** `0 updated` there means the committed goldens match HEAD exactly, so every delta in your tree is code -- yours or a sibling's -- and `git status` on the whole repo tells you which. The fix is to regenerate in a worktree holding only your own files, the same recipe this guide already prescribes for the SQL-validity gate, applied to fixtures.

**`scripts/update-data-view-snapshots.mjs` now REFUSES a bare unfiltered run** — it prints "Refusing to regenerate every mismatching fixture" and exits, so you must either name the fixtures or pass `--all` deliberately. (This guide said it rewrites everything by default; that has been fixed in the script.) Pass filenames (`node scripts/update-data-view-snapshots.mjs some-fixture.json`) — with `--all`, it will also bless unrelated drift from a sibling session's uncommitted edits in this shared tree.

**It SKIPS template fixtures and reports it in a line that reads like success — `12 template-skipped` — so a sweep that regenerates cleanly can still leave goldens carrying the old predicate.** A fixture whose `expected_query` interpolates a live value (`${current_season.nfl_seas_type}`) is never rewritten, and the run summary counts it beside the successes rather than as work left undone. Measured 2026-08-22 converting the `<> 'NOPL'` deny-lists: two sweeps regenerated 96 and 36 fixtures and left **three** template-skipped ones still red, one of which additionally needed its `rate_aggregate_<hex>` CTE name updated by hand. **Treat the template-skipped count as a to-do list, not a footnote**: after regenerating, grep the whole corpus for the old predicate (`grep -rl "not .play_type. = .NOPL" test/data-view-queries/`) and expect zero. Hand-editing them is correct and unavoidable — the interpolation is what protects them from being re-blessed against a moving clock. Always `git status -- test/data-view-queries/` after regenerating and revert anything you did not intend to touch. The script runs outside `test/global.mjs` and so has no clock mock of its own; both it and the suite honor `LEAGUE_MOCK_DATE`, which pins the clock for a regeneration or a verification run.

**Checking the updated COUNT is not enough — a fixture can regenerate to the right file list and the wrong CONTENT, because the script reads whatever the target database currently holds.** The advice above ("check the updated count against `git status`") catches an unintended file and cannot catch a corrupt one. On 2026-08-18 the pts conform regenerated four goldens by name; `git status` showed exactly those four, and one of them — `create-a-query-for-season-projected-stats.json` — had absorbed every scoring weight collapsing to `* 0`, because the run happened after a schema reload had dropped and recreated the tables and `league_scoring_formats` was no longer seeded. A blessed golden asserting a zeroed scoring format would have passed the suite forever. **Diff each regenerated fixture at TOKEN level and confirm the only changes are the ones your change explains** (`diff <(git show HEAD:<f> | tr ',' '\n') <(tr ',' '\n' < <f>)`) — these files are single-line JSON, so a line diff is one useless hunk and the eye cannot audit it. When a fixture comes back with unrelated deltas, revert it and regenerate against a properly seeded database rather than blessing what you got.

**It DOES connect to the database for some fixtures, and without the connection env it silently regenerates only part of the corpus.** The script is widely described as pure `.toString()` on the query builder — true for most fixtures, false for the ones whose emitter resolves a format through `#db`. Run bare on 2026-08-05 it wrote 11 fixtures and printed `error <name>: role "league_test" does not exist` for 10 more, then reported a normal-looking summary line; re-run with `LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 LEAGUE_DB_DATABASE=<your-db>` it wrote 20. The per-fixture errors scroll past above a summary that reads like success, so a rename sweep can regenerate "all" the goldens and leave half of them stale. Always pass the DB env, and check the updated count against `git status -- test/data-view-queries/`.

**It needs `NODE_ENV` too, and without it the script does not run at all** — `config/index.mjs` loads `config-${NODE_ENV}.json`, so a bare invocation dies on `ENOENT: config/config-undefined.json` before touching a fixture. That failure is loud, but it arrives as a config path nobody recognises rather than as a missing flag, and the natural reading is that the checkout is broken. The full working form is `NODE_ENV=test LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 LEAGUE_DB_DATABASE=<your-db> node scripts/update-data-view-snapshots.mjs <fixture>.json`. Confirmed 2026-08-19.

**Regenerating goldens cannot fix a fixture's `setup` SQL — those are hand-edited.** Result-equivalence fixtures carry raw statements like `INSERT INTO nfl_games (esbid, season_year, week, season_type, v, h) VALUES (...)` in their setup block. `update-data-view-snapshots.mjs` only rewrites `expected_query`, so a rename sweep that regenerates every affected golden still leaves the setup SQL on old column names, and the fixture then fails at seed time rather than at compare time. The 2026-07-29 `nfl_games` conform hit exactly this in 9 fixtures. After any rename, `grep -rn "INSERT INTO <table>" test/data-view-queries/` as a separate step.

**Grep the goldens for the BARE quoted projection, not just the table-qualified form.** The emitters produce both shapes, and a sweep keyed to one silently misses the other. The documented pattern `nfl_games\".\"<old>` finds table-qualified references, but CTE builders like `rate-type-per-game.mjs` project `"h" as "team"` with no table prefix — so 7 affected goldens looked clean under the table-qualified grep and were caught only when the suite failed on them. Sweep both: `\\"<old>\\" as \\"` as well as `<table>\\".\\"<old>`.

**Verify a clock-derived golden across a week boundary, not just against today.** Regenerating until green only re-blesses whatever the clock says now. Run the suite at several mocked instants spanning PRE/REG/POST — e.g. `LEAGUE_MOCK_DATE=2026-09-22T12:00:00Z LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=5433 TZ=America/New_York NODE_ENV=test TEST=all node_modules/.bin/mocha --exit --require test/global.mjs --reporter min test/libs-server.data-view-queries.mjs`.

Format identities (`league_scoring_formats.id`, `league_formats.id`) are opaque -- snake_case slugs for the named catalog, `gen_random_uuid()` for the long tail. Never reintroduce a content-derived hash as an identifier -- see `user:guideline/schema/avoid-content-derived-identity.md`.

## Scoring formats and columns

**The two tables now dedup differently, and the scoring one is the exception.** `league_formats` still uses a `UNIQUE` index across its full config tuple, so adding a roster metric there is a normal additive `ALTER TABLE ADD COLUMN` plus an index rebuild. `league_scoring_formats` cannot: its tuple reached 44 columns when kicking and DST scoring became configurable on 2026-08-04, against a Postgres `max_index_keys` of 32, so the full-tuple index is no longer buildable at all. Dedup there is `config_digest`, a `GENERATED ALWAYS AS (md5(...)) STORED` column with a unique index on it alone, and the upsert's conflict target is `ON CONFLICT (config_digest)`. `id` is untouched and nothing references the digest, which is what keeps this outside the guideline's prohibition.

**`libs-shared/scoring-columns.mjs` is the single source for what a format can score, and adding a scoring column means adding a registry entry — not editing five lists.** It replaced four enumerations that had to agree by hand: `base_fantasy_stats` / `kicker_fantasy_stats` / `defense_fantasy_stats` in `constants/stats-constants.mjs`, `SCORING_COLUMNS` in `find-or-create-format.mjs`, the unique tuple, and `scoring_field_labels`. All of those now derive from it, `calculate-points.mjs` loops it, and `test/libs-shared.scoring-registries.spec.mjs` asserts it against the exported schema in both directions — including that every registry column appears in the digest expression, since an omission there silently merges two distinct formats onto one id with no error anywhere.

Three things about the registry that are not obvious from reading it. The three stat lists are **derived, not deleted**: they feed `all_fantasy_stats`, which `format_base_gamelog` uses to filter which columns are persisted to `player_gamelogs`, so an entry losing its `stat` silently stops that column being written. An entry may carry a `stat` with no `column` (`field_goals_made` is deliberately never scored -- it is the total the five distance bands partition, and scoring both double-counts) or a `column` with no `stat` (the two DST thresholds parameterise a rate rather than reporting a value, so they must stay out of `all_fantasy_stats`). And **`default_value` is load-bearing in two places, not documentation**: `find-or-create-format.mjs` fills an absent config key from it rather than writing `null`, and `calculate-points.mjs` falls back to it when a `league` object does not carry the column. Both exist because every new column is `NOT NULL` and many callers hold a partial config -- the named format definitions declare only the base columns, and the external-league mapper structurally cannot carry kicking or DST keys. Drop either fallback and the failure is silent in opposite directions: an explicit NULL on write (an explicit NULL does NOT fall back to the column DEFAULT), and every kicking and DST stat scoring zero on read.

**Kicking scores PER-YARD at 0.1 in production, not in 3/3/3/4/5 distance bands.** The old code branched on `if (stats.field_goal_yards)` and the band arm was unreachable whenever that stat was populated, which it always is -- 2025 REG kickers: 453 gamelogs with band counts, all 453 also with field goal yards, ZERO with bands alone. The backfill therefore sets the per-yard rate to 0.1 and every band to 0, and "correcting" it to the bands would silently cut every kicker's score. Scoring is now additive (bands plus the per-yard term) so a banded league sets the bands and zeroes the rate. `test/libs-shared.scoring-format-equivalence.spec.mjs` checks all 65 production formats against a fixed stat-line corpus and is mutation-checked.

**Before sourcing a from-plays role off an `nfl_plays` pid column, MEASURE that column against production — it has been effectively empty three times out of three, and the role passes every gate while returning nothing.** The pid column is the obvious source and the cheap one, so the instinct is to reach for it and move on. But the join is valid, the SQL EXPLAINs, the suite is green, the goldens regenerate, and the column simply produces no rows: return touchdowns resolved 4 of 732 valid stat rows, two-point conversions 2 of 2,221, field goals 0 of 931 and extra points 2 of 1,210. Two of the three read as obviously fine beforehand — a two-point conversion IS a rush or a pass, and a field goal obviously has a kicker — which is exactly why reading the schema is not a substitute for counting. The measurement is one query:

```sql
SELECT ps.stat_id, count(*) AS valid_stat_rows, count(p.<pid_column>) AS rows_with_pid
FROM nfl_play_stats ps
JOIN nfl_plays p ON p.esbid = ps.esbid AND p.play_id = ps.play_id
WHERE ps.is_valid = true AND ps.stat_id IN (<ids>)
  AND p.season_year = 2025 AND p.season_type = 'REG'
GROUP BY 1 ORDER BY 1
```

Scope it on `nfl_plays` rather than joining `nfl_games` — the games join times out through `base db query`. When `rows_with_pid` is near zero, the role has to take the `nfl_play_stats` attribution shape plus the EXISTS gate widening, which is what `libs-server/data-views/nfl-play-stats-attribution.mjs` exists for; its header carries the per-role evidence.

**A registry-driven scoring path and a hand-written one must have their COVERAGE compared by a spec, because nothing else can see the gap.** `calculate-points.mjs` scores every column in `libs-shared/scoring-columns.mjs` by construction — it loops the registry — while the from-plays path hand-writes each term into a generator. So a column nobody remembered to add scores correctly on one path and silently ZERO on the other, with no error, no failing golden and no red gate. `passing_completions` was in that state for as long as the from-plays path has existed: 2 of the 65 production formats score it at 0.50 and 0.20, so a 350-completion quarterback was under-reported by up to 175 points a season. It was found by writing a spec, not by any gate. `test/libs-server.fantasy-points-path-parity.spec.mjs` is the shape to copy — assert the coverage MAP rather than an executed residual (the suite's seeded database has no real season, so a residual measures the fixtures), require every gap to be declared with a reason, and carry a positive control so a matcher that stops matching cannot report perfect parity over a path scoring nothing.

**That spec no longer reads source text — it IMPORTS `from_plays_scored_columns`, which the scoring module derives from its two role tables.** So a column is covered exactly when a term or a role names it, and moving code cannot change the map. What that replaced is worth keeping in mind whenever a gate is built on matching rather than on data. The spec used to read two files by PATH and run three regexes over them, which coupled it to file layout in a way nothing declared: the import graph does not change, no module fails to resolve, and the matcher simply stops finding terms that still exist and still work. Extracting the generators into their own module (`815f092d6`) hit exactly that, and only the positive control made it visible. Worse, its broadest pattern was any single-quoted lowercase token, so any unrelated string could have counted as coverage — the same over-permissive tokenizer that made `check-saved-view-param-coverage` unable to report the orphans it existed to find, and the reason a matcher-based map needs a negative control that a derived one does not.

**Adding a scoring column to the from-plays path means adding a term to a role in `libs-server/data-views/fantasy-points-scoring-expressions.mjs`.** The three roles `nfl_plays` names with a pid column (passing, rushing, receiving) carry declarative `terms`; the seven `nfl_play_stats`-sourced roles carry a `scoring.columns` list. Terms have three `kind`s — `rate` (`<expr> * <value>`), `flat` (`<value>`, for a role whose join already restricts each row to one event), and `conditional` (a `CASE`) — plus an `always` flag for terms emitted even at 0. **Those exist to reproduce the previous hand-written output character for character, not as a general expression language**: the split between always-emitted and emitted-only-when-nonzero is what keeps 248 goldens from moving, so match an existing term's shape rather than inventing one. Read values as `scoring_format[column] || 0`, deliberately not through the registry's `default_value` fallback — a format row missing a column must keep emitting 0 here or existing SQL changes.

## Join-group identity and caching

**A CTE identity key that derives its membership from a param registry loses members silently when the registry changes, in a commit that never touches the key.** `get_stats_column_param_key` builds the from-plays table alias by enumerating `Object.keys(nfl_plays_column_params)`. `year`, `week` and `seas_type` were registry members until `64a28f9dc` replaced them with the composite `nfl_week_id` — so the alias key stopped distinguishing them, and two `*_from_plays` columns differing only by year hashed identically, landed in one join group, and shared one CTE built from whichever column seeded the group (`group_column_params` in `get-data-view-results.mjs`). The second column rendered the first's values under its own header: no error, no failing test, a wrong answer. It survived from March to July 2026 because the one golden exercising the shape (`player-target-share-from-plays-different-params`) had blessed SQL containing no predicate at all for its second column's year, and 114 saved views carry per-column `year` on a from-plays column. Fixed 2026-07-31 by keying `year`/`seas_type` explicitly, emitted only when present so unscoped columns keep their hash — the reason exactly one golden changed. Two rules: when adding or removing a member of a param registry, grep for code that enumerates its keys rather than reading it by name, since those consumers change behaviour with no diff of their own; and when a param is both user-facing and resolved a layer up (here `year`, expanded into `nfl_week_id` by `resolve_params_contribution`), it still needs to be in any identity hash, because the scope layer runs after grouping has already collapsed the columns.

**The same collision arrives without any registry: a table that stores several PERIODS in one column needs the period in its alias key.** This one is now HISTORY rather than live shape — the projection period split gave each period its own table, and two different tables cannot share a join group, so the class is retired rather than guarded. It is kept because the mechanism recurs wherever one table holds several periods. `league_format_player_projection_values` then kept `'0'`, a numeric week, `'ros'` and `'ros_net'` in one `week` column, and each period column pinned its own sentinel in `extra_predicates` / `attach`. Its alias keyed only on year/week/seas_type, so two period columns in one view hashed identically, collapsed into one join group, and that join carried only the SEEDING column's predicate. Measured at `50f63cf5a`: `[week, ros]` emitted `week = 'ros'` for both columns and `[ros, week]` emitted `week = '0'` for both, so one of the two rendered the other period's value under its own header — `market_salary` had the same shape. Nothing caught it because no golden exercised any rest-of-season projected column at all, and each column is provably correct when requested ALONE, which is how anyone would test it. Fixed 2026-08-04 in `67278d518` by keying the alias on the period. Two rules: when a column pins a discriminator its siblings do not share, that discriminator belongs in the alias key, not just in the join predicate; and test a join-group defect with the columns TOGETHER and in both orders, since the single-column case passes either way and the order decides which value wins.

**The time scope has THREE spellings and each reader knows a different subset, so a view can carry a scope that no reader can see.** `nfl_week_id` is decomposed onto `params.year` / `params.week` by `resolve_nfl_week_params`; `year` (with optional `seas_type`) is read directly; `single_nfl_week_id` is neither, and until 2026-08-21 it reached no reader at all — `resolve_view_scope` matched only `nfl_week_id`, and `get_year_range` / `get_week_range` matched only the decomposed `params.year` / `params.week`. It is not a rare param: it is what the dfs-salary and betting-market column families carry. A view whose ONLY scope was that spelling therefore looked completely unscoped, so the year row axis fell through to the full 2000-current default and `apply_scope_to_query` no-opped on every source — 13,079,985 intermediate rows and 76s on the saved DFS-salary week view (signals 126229/126343). All three now go through one reader, `resolve_explicit_nfl_week_ids`, which deliberately does NOT fall back to the current week the way `resolve_nfl_week_ids` does: a scope reader has to distinguish "names no weeks" from "names the current one", or it imposes a scope on a view that declares none. **When you add or touch a scope param, enumerate its readers rather than its writers** — `has_explicit_time_scope` and `compute_effective_scope`'s `has_year_like` are two more that must agree, and disagreement there is silent in both directions.

**That gap had no golden coverage and could not have had any: not one fixture in the corpus requests `single_nfl_week_id`.** The corpus reaches for `year` and `nfl_week_id`, so the whole third spelling — including every dfs-salary and betting-market default — was outside the goldens, outside result-equivalence, and outside the SQL-validity gate (which emits the plain and `year_offset` shapes only, never a week split). A green corpus said nothing about it. `test/data-views.single-nfl-week-id-row-axis-scope.spec.mjs` is the gate now, and it carries a control per assertion so a matcher that stops matching cannot report compliance. Before treating the corpus as coverage for a param, `grep test/data-view-queries/` for it — a zero there means the gate you are about to trust is vacuous.

**An empty view scope silently disables the `participation_status` signal, and nothing reports it.** The auto-injection gate in `get-data-view-results.mjs` requires a non-empty REG-only `query_context.nfl_week_ids`, so a week-split view that declares no scope the resolver can see emits no signal at all — the client then cannot tell active-but-zero from on-bye from did-not-play, and every one of those cells renders blank. This is the second-order cost of the scope gap above: the fan-out was the loud symptom, the missing signal was the quiet one, and it was fixed only incidentally. When a gate keys on view scope rather than on the request, an unscoped view is not a wider query — it is a query with the feature switched off.

**A discriminator in `source.extra_predicates` does NOT reach the year_offset range path, which emits its own correlated subquery instead of reading the join.** `player_year_offset_range_select` / `team_year_offset_range_select` take `extra_predicates` as an explicit ARGUMENT (`libs-server/data-views/param-utils.mjs`), so a source that declares one and a `main_select_string_year_offset_range` override that does not forward it produce two different scopings of the same column — the join is pinned and the range subquery is not. It fails silently in the worst direction for a `latest_by_year: true` override, whose `ORDER BY <year> DESC LIMIT 1` then picks whichever discriminator value happens to sort last: adding `season_type` to `pff_player_seasonlogs` on 2026-08-14 would have let the text columns (`unit`, `player_position`, `grade_position`) render from a scoped row where every column but `routes` is null, a blank cell rather than an error. **The tell is a golden that regenerates to NO CHANGE** while its siblings all gain the new predicate — `player-pff-unit-range-offset-latest-season.json` was the only one of nine that did not move, which is what surfaced it. When you add a predicate to a source, grep that file for `year_offset_range_select` and forward it.

**A `-999` sentinel RATE cannot tell a wiped year from a year that legitimately has no source, and reading it as damage points at a destructive "repair".** `league_format_player_projection_values` is written delete-then-reinsert by `(league_format_id, year)`, so a broken run replaces a year with sentinels — which is exactly what a year whose scoring format has no `scoring_format_player_projection_points` rows looks like on its own. The healthy baseline is already ~48% sentinel (unprojected and non-fantasy-position players sit in the pool deliberately), so rate thresholds are useless here. On 2026-08-05 four format-years read as 100% sentinel across all 19 weeks and were reported as conclusively wiped; joining values to source showed all four hold **zero** source point rows, so a correct run produces the same output and there was nothing to repair. The discriminating query is the join, not the rate: ask for a pair that is fully sentinel **while holding source rows**, which is the only shape a wipe can take. Re-running the writer against a sourceless year recomputes the identical sentinels, so "repair by re-running" is a no-op there regardless.

**An all-sentinel oracle over a projection-values table must count WEEKLY rows only, and the period split is what made that structural rather than a predicate.** The period aggregates SKIP the sentinel rather than propagating it, so they land at `0` — a non-sentinel value — even on a run where every real week was sentinel. Counting them leaves "real" values per player on a fully wiped year and silences the check on precisely the failure it exists to catch. Caught by the spec, not by review, when the first draft of `process-projections-for-league-format.mjs`'s oracle did exactly this, and it was written then as a `week ~ '^[0-9]+$'` predicate over one mixed table. Since the periods became separate tables the oracle simply reads the weekly one, so the exclusion can no longer be got wrong — which is the general shape worth taking from this: an exclusion a query has to remember is a defect waiting for the next author, and moving the distinction into the schema retires the whole class.

**A projection rebuild is SECONDS of unbroken synchronous JS, so it can never run inside the API process — and its cost is SEASONAL, which makes the log lie to you.** Measured on production data 2026-08-09: `process_scoring_format_year` blocks the event loop for **244ms** (1,131 players, 22,600 rows; the rest of its ~2.1s wall is IO), while the league-format stage — the 19-week `calculate_projection_values` loop plus the period aggregation that follows it — blocks for **7.6 seconds**. Node is not idle through that; it is CPU. Running it in `server.mjs` would freeze every request, the auction socket and the scoreboard for the duration, which is why the rebuild lives in `jobs/refresh-projection-cache-worker.mjs` rather than in `PUT /leagues/:leagueId` where it started.

The seasonal part is the trap. The cron's `process_league_format` starts its week loop at `first_projection_week_to_recompute({ year })`, which returns `current_season.week` — a high week in-season, so few iterations, and **0 for the whole offseason**, so all 19. Reading `duration_ms` out of `/var/log/league/process-projections.log` with a `tail` therefore returns ~2.4s or ~11.5s for the same format depending only on where in the file you landed, with nothing in the line saying which regime produced it. A design decision was nearly made on the in-season number. Read a WHOLE run, check the timestamps against the current phase, and compare two consecutive runs before quoting a duration — the offseason figures for league 1 are `genesis` ~2.1s and `genesis_10_team` ~11.4s, stable across hourly runs, against ~20 formats at 6-34s each for roughly an eight-minute total run.
