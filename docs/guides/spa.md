# Change the SPA

**When to read this:** Read before touching anything under `app/`.

The recurring class is an absent key with no diagnostic: Records, dispatch maps, wire payloads and styles all fail silently and far from the cause.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

---

## Absent-key traps

**A typo'd action-creator name in `mapDispatchToProps` fails SILENTLY, and it has shipped twice.** Every connected component here uses the object form (`const map_dispatch_to_props = { remove: roster_actions.remove_tag }`), which redux passes to `bindActionCreators` — and that function copies only values that are `typeof 'function'`, skipping everything else without warning. So a reference to a creator that does not exist resolves to `undefined`, gets dropped from the props object entirely, and produces **no connect-time warning, no lint error, and no build failure**. The component renders normally; the only symptom arrives when a user fires the handler, as `TypeError: this.props.<name> is not a function`, reported through `window.onerror` with null `filename`/`lineno`/`request_url` because the browser has no usable stack for it.

The recurring cause is the project's camelCase → snake_case action rename passing over a call site: on 2026-07-30 `remove-tag-confirmation/index.js` still referenced `roster_actions.removeTag` (real name `remove_tag`, signal #123469) and `stat-qualifier-filter/index.js` still referenced `stat_actions.updateQualifier` (real name `update_qualifier`, never reported — it needs the qualifier filter opened to fire). Note that `PropTypes.func` does not catch it either; the prop is simply absent, and an absent non-required prop is valid.

When touching a dispatch map, verify each referenced name exists on the actions module rather than trusting it — `grep -nE "^\s+<name>[:(]" app/core/<domain>/actions.js`. A same-named saga or a `SCREAMING_CASE` type constant is not the creator: `removeTag` existed as both a saga export and `REMOVE_TAG`, which is exactly what made the wrong name look plausible. There is currently **no automated guard** for this class — but the reason stated here until 2026-08-07 was wrong in the direction that discourages writing one. A connected component does resolve `@core`/`@components` aliases mocha has no harness for, which blocks a BEHAVIORAL spec; it does not block a SOURCE scan. `test/app.connected-component-prop-contract.spec.mjs` covers the adjacent defect that way — a component destructuring a prop no producer supplies — and needs no harness at all. That gate cannot see THIS one: a typo'd creator leaves the map's KEY declared while only its VALUE is undefined, so the prop reads as provided and `bindActionCreators` drops it at runtime. Resolving each dispatch value against its actions module is the fix, and it is the same parse the existing gate already does.

**But "app/core is not Node-importable" is too broad a reading of that, and it has already discouraged coverage that was free to write.** The blocker is the `@`-prefixed aliases specifically. A module importing only `#`-prefixed specifiers and bare package paths resolves natively, because both this repo and `react-table` declare the matching `imports` field in their `package.json` — **101 of the 231 files under `app/core/` are in that group** and need no harness at all. `app/core/data-views/parse-table-state-from-url.mjs` was believed untestable on this basis and carried zero coverage while holding the entire blast radius of the `splits` -> `row_axes` URL defect; it in fact imports under plain `node` unchanged, and `test/data-views.parse-table-state-from-url.spec.mjs` covers it today with no harness. Before concluding a module in this tree cannot be specced, try importing it — `node -e "import('#app/core/<path>.mjs').then(...)"` costs one command and answers definitively.

**As of 2026-08-18 the harness EXISTS and the `@`-prefixed aliases are no longer a blocker at all — `app/core` is 132 of 234 importable from a spec, up from 52, with zero source changes.** `test/webpack-resolve/` registers a `module.register()` hook that gives Node the resolution webpack already performs (`resolve.alias`, `resolve.extensions`, and directory-index via `resolve.mainFiles`), and `test/global.mjs` loads it ahead of every spec — so a spec can simply `import` from `@core/...` the way the SPA does. Records are 10 of 10, actions 37 of 37, field registries 25 of 30. Module-resolution failures across the tree fell 179 to 3.

Three things to know before reaching for it. It is **strictly additive** — every specifier goes to `nextResolve` first and the fallback runs only where Node has already failed — so it cannot change the meaning of an import Node resolves on its own, and it does not implement `resolve.modules` (a bare `core/x` specifier still fails, deliberately, so nothing can shadow a real package). Its alias map is **DERIVED** from `webpack/webpack.config.base.mjs` rather than copied, which is what keeps a second resolution oracle from drifting from the bundle's; `test/app.webpack-resolve-hook-conformance.spec.mjs` asserts that derivation by IDENTITY, because a copied map passes a deep compare on the day it is made. And `IS_DEV` is a **DefinePlugin global**, not an import, so no resolver can supply it — `register.mjs` sets it (plus `APP_VERSION`/`MACHINE_IP`) from the PRODUCTION config's values, and without it every reducer reaching `app/core/constants.js` throws ReferenceError on load.

**What the hook does NOT unblock, measured: jsdom buys ZERO additional modules.** 132 of 234 with it and without. The 90 `window is not defined` failures become 90 identical `Cannot access 'initialState' before initialization` failures on exactly the same 90 files, because behind the DOM tier sits a native-ESM circular-import wall webpack never hits — babel-loader transpiles ESM to CJS, where a circular read yields `undefined` instead of a TDZ throw, so the bundle works and Node does not. Reducers stay 15 of 36 and sagas 0 of 34 regardless. Do not reach for jsdom (or happy-dom) expecting the reducer and saga tiers; that is a module-format problem wearing a DOM costume, and it is the same shape as the two false premises this item already burned — a change measured against one constraint that was never the whole blocker.

**An Immutable `Record` SILENTLY DROPS any key its declaration does not list, so a new API/database field reaches the client as `undefined` no matter how correctly it is plumbed everywhere else.** `new League({...})` copies only declared keys; `createLeague` additionally destructures an explicit field list, so a field must be added in BOTH places (`app/core/leagues/league.js`) plus the constructor call. Nothing warns: not lint, not the build, not PropTypes, and not the reducer — `create_default_league` can set the value, `getLeague`'s `SELECT *` can return it, and the Record discards it between them, which is exactly what makes the plumbing look correct. On 2026-08-02 the five new `seasons` playoff-format columns were wired through the API, the selector and the shared primitive but never declared on the Record, so `get_playoff_seeding` received `playoff_team_count: undefined` and threw — inside `mapStateToProps`, which renders the standings page and the league-home dashboard blank. Same family as the `mapDispatchToProps` trap above: an absent key, no diagnostic, symptom far from cause. When adding a column the SPA reads, grep `app/core/<domain>/<model>.js` for a sibling field and confirm it appears three times, and prefer degrading in the selector over throwing — a throw in `mapStateToProps` is a blank page, and it is also the state of every league between a frontend deploy and a not-yet-applied migration.

**A league field reaches the SPA on TWO payloads, and wiring only `get-league.mjs` leaves it inert for exactly the people who are logged in.** `GET /leagues/:leagueId` is the obvious wire and it is half of one: the leagues reducer rebuilds the whole record from the `/api/me` payload on `AUTH_FULFILLED` (`state.set(l.uid, createLeague({...l}))`), and `GET_LEAGUE_FULFILLED` does the same from the other route, so whichever response lands last wins and a field present on only one is absent, present, or racy depending on timing. `api/routes/me.mjs` builds its own `db('leagues')` query and inherits nothing from `libs-server/get-league.mjs`. On 2026-08-13 the league-pause fields shipped on `get-league.mjs` alone, so an anonymous visitor saw the pause banner and every member did not — the inverse of the usual auth-shaped bug. Attach on both routes from ONE implementation (`get_pause_state_by_league_id` is the shape: the single-league reader delegates to the batch one) rather than writing the query twice.

This is the same absent-key family as the traps above, with one addition worth internalizing: **no server spec can see it.** The suite drives the API over HTTP and never loads a reducer, so `/me` returning a correct-looking league passes everything; only a browser against a real store shows the field never arriving. The gate that does work is a spec asserting the field on BOTH route payloads (`test/league-pause.spec.mjs` § "pause state on the league wire"), which is cheap and needs no harness — copy it when adding a league field the SPA reads.

**Two more members of that family sit on the REQUEST path, and on 2026-08-12 both shipped in one feature — each independently enough to make a new button do nothing.** They are worth knowing together because the plumbing looks complete at every site a reviewer would grep.

**An api service function's return value is merged FLAT into the fetch init, so a `method` nested one level down is silently dropped and the request degrades to a GET.** `api_request` does `merge(default_options, apiFunction(opts), ...)` and then `fetch(options.url, options)`, so `{ url, opts: { method: 'POST' } }` sends a GET — valid JavaScript, no lint error, a clean build, and the only symptom is a 404 from a route that answers POST. Every other entry in `app/core/api/service.js` spreads `...POST(data)`; copy the sibling rather than hand-writing the options. `test/app.api-service-verb-contract.spec.mjs` is the gate.

**`create_api_actions` and `create_api_action_types` are BOTH required, and exporting only the first leaves every reducer case as `case undefined`.** The creators are what a saga calls; the type constants are what a reducer switches on, and they come from the second helper spread into the domain's `<domain>_actions` object. Export the creators alone and `actions.X_FULFILLED` is `undefined`, so the saga dispatches a real string that matches nothing: the store never updates and a FAILED case can never set its error. With `ignore_error: true` on the saga — the shape used wherever a refusal renders inline — that combination gives the user no feedback whatsoever. `test/app.action-type-registration.spec.mjs` asserts the pairing across every `app/core/**/actions.js`.

The general rule both teach: **an `rg` count proves a token is present, not that it is wired.** Both defects satisfied a plan whose per-step verify was a grep count, and neither is reachable from the server suite, which drives the API over HTTP and never loads a reducer. A client-path change needs a browser pass on `yarn dev:live`, or a source-scan spec of the kind above — and note that both gates here had to discriminate on POSITION rather than presence, since the broken form of the first one contains the word `method` and would pass any grep for it.

**`player_map.get(key, default)` is not a null guard, and it reads exactly like one.** Immutable substitutes `notSetValue` only when the key is ABSENT; a key present with an explicit `null` returns `null`. Several reducer branches write explicit nulls when clearing a field — `DELETE_RESTRICTED_FREE_AGENCY_TAG_FULFILLED` sets `bid` and `restricted_free_agency_conditional_releases` — so `get('restricted_free_agency_conditional_releases', [])` handed the RFA dialog a null it then iterated, crashing the page for a real user on 2026-08-01 (signal #123965). Coalesce with `|| []` / `?? 0` when the field is one a reducer clears; a 2026-08-01 sweep of the other array-defaulted reads (`championship_round`, `deltas`) found no second live instance, but nothing prevents the next one. Clearing a field to the empty shape the API already returns — every players route coalesces this one with `|| []` — is the better half of the fix, since it keeps client state in the shape every read site expects.

**`current_season` is a `Season` INSTANCE, so a module-level constant reached through it is `undefined` — and as a comparator's `notSetValue` that yields `NaN`, which `sort` reads as "equal".** `libs-shared/constants/index.mjs` re-exports both the instance and a pile of bare constants, so `current_season.default_points_added` looks like every other `current_season.*` read and resolves to nothing; the real export is `default_points_added` (`-999`) from `source-constants.mjs:104`. The draft board sorted on it (`app/views/pages/draft/draft.js`) and 274 of the 396 players in the 2026 rookie class have no `pts_added['0']`, so their comparisons returned `NaN`, those rows held their arrival order, and the page shipped looking unsorted with no error anywhere. Same family as the three traps above — an absent key, no diagnostic, symptom far from cause — but the mechanism is namespace confusion rather than a dropped prop, and `NaN` is the worst of the group because a comparator swallows it silently instead of throwing. The sibling auction selector had it right the whole time (`app/core/selectors.js:47,253`). Before reaching for a constant on `current_season`, confirm it is a `Season` property (`libs-shared/season.mjs`) and not a bare export — and treat any `notSetValue` feeding arithmetic as worth checking at runtime, since a wrong one cannot fail loudly.

**The `teams` store is keyed by YEAR and nothing loads a year but the app's own, so a page rendering any other season shows blank teams — and a page that dispatches none of four specific actions shows blank teams in EVERY season, including the current one.** `get_team_by_id_for_year` falls back to `new Team()` (`app/core/selectors.js:84`), which renders as empty rather than throwing, so this is the same absent-key/no-diagnostic family as the traps above with an even quieter symptom: a `TeamName` that is simply not there. Two independent halves, and the second is the one that surprises. `load_teams` (`app/core/teams/sagas.js`) takes `year` from `get_app` and ignores its caller, so it can only ever populate the app year — but it is also only ever _reached_ from `LOAD_TRANSACTIONS`, `LOAD_WAIVERS`, `LOAD_MATCHUPS`, `LOAD_ROSTERS`, `LOAD_TEAMS`, `SELECT_YEAR` and `AUTH_FULFILLED`. A new page that dispatches none of them gets no teams at all: the restricted free agency history shipped on 2026-08-02 with every team blank in all six seasons, and the current-season case looked identical to the historical one, which is what made "the store has no 2024 teams" read as the whole story. `load_teams_for_year` now takes an explicit year for this; watch your page's load action from `team_sagas` rather than assuming another page's fetch has warmed the store, and note the request-history key is `GET_TEAMS_${leagueId}_${year}` while `initTeams` fetches with no year at all, so the current season's key is literally `..._undefined`. The same hole exists for players — a historical roster names players no league page has ever loaded — with `load_missing_roster_players` as the pattern to copy.

**`PlayerName` renders a FRAGMENT of two siblings, not one element, so its container's `display` decides whether a player's own status/tag chip stays attached to it.** The second element (`.player__name-label`) carries the PSP/cutlist/status/`PlayerTag` chips. In a block parent it starts its own line — a tagged player put his PUP or Q chip on a row beneath the position badge. In a flex row it is a separate flex item that can wrap away from the name it belongs to, so a list of players needs each one in its own wrapper, not the bare component. `.player__name` also carries `flex 1`, which makes it expand to fill any flex parent unless overridden. None of this is visible in the JSX at the call site, which reads as a single component. When laying out more than one `PlayerName`, or one beside other content, wrap each in its own flex element and override `flex` on both children.

**A custom request header needs naming in `Access-Control-Allow-Headers`, and the omission is invisible in production while breaking every browser verification pass.** Anything outside the CORS-simple set (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type` with a form/text value) makes the browser preflight, and a preflight the API does not answer for that header means the request never reaches the route at all — no server log, no status code, just `TypeError: Failed to fetch` on the client. Production cannot see it: `api/index.mjs` serves the SPA same-origin with the API, so nothing preflights there and the header sails through. Dev is cross-origin (`localhost:<webpack port>` against `MACHINE_IP:8082`), so the failure is confined to exactly the oracle this repo mandates for a client change. On 2026-08-22 `x-contribution-claim-token` was added to the contribution read path and the status page rendered its not-found branch for a submitter holding a perfectly valid token, while the same request over `curl` returned 200 — which reads as a client bug and is a one-line server omission. The discriminating check is the preflight itself, not the real request: `curl -I -X OPTIONS <url> -H 'Origin: <dev origin>' -H 'Access-Control-Request-Headers: <your header>'` and read the `Access-Control-Allow-Headers` line that comes back. Note the fix belongs in the header allow-list rather than in moving the value to a query parameter — a query parameter dodges the preflight and puts whatever it carries into access logs, `Referer` headers on any outbound link, and browser history.

## Styles and layering

**`app/styles/normalize.css` carries a global `input { -webkit-appearance: none }`, so a hand-rolled checkbox or radio renders with NO box, NO tick and no intrinsic size — and `accent-color` cannot fix it.** The rule is there to normalize text inputs, and it strips the platform rendering from every `input` in the app as a side effect. The symptom is a control that is present in the DOM, focusable, keyboard-operable and fully functional, while being invisible — the same absent-symptom family as the traps around it, and it reads as a styling mistake in the component rather than an inherited global. `accent-color` is the natural reach and is inert, because it only applies to natively-rendered controls. Draw the box explicitly (size, border, and a `:checked` state), and supply the tick as a `background-image` rather than a pseudo-element: `input` is a void element, and generated content on one is not reliable across browsers even once appearance is stripped. **Call `prose_checkbox()` from `app/styles/prose-form.styl` rather than drawing it by hand** — that file is the shared form language for the prose pages (waitlist, admission vote, admission vote commissioner) and exists because this trap has already cost two features: the waitlist page drew its own box and wrote the reason down, the commissioner page did not and shipped a 0x0 control that toggled correctly and was invisible, which read as team selection being broken. Note `select` is NOT affected — the rule names `input` only — so a select keeps its native arrow and needs styling only for border and type.

**Two things about that shared file, because getting either wrong reintroduces the very defect it prevents.** It is injected by `stylusOptions.import` and so reaches every stylesheet in the app, which means it must hold **mixins and variables only** — a top-level rule there is emitted once per stylesheet. And the import list lives in `webpack/stylus-options.mjs` because **BOTH `webpack.config.base.mjs` and `webpack.config.prod.babel.mjs` carry their own stylus-loader rule**, with the production one deciding a real build: on 2026-08-15 the new file was added to the base list alone, and since **stylus is SILENT on an unknown mixin — it emits no declarations rather than erroring** — the build succeeded, the CSS shipped stripped, and the deployed rule for the questionnaire's checkbox read `{margin:2px 0 0}` and nothing else. All three pages lost most of their styling at once. Add to the shared module, never to one config.

That defect also shows why a bundle grep is the wrong oracle for CSS. The JS greps all passed, because the JS was fine; the CSS grep that would have caught it searched for `M3.5 8.5l3 3 6-6` and returned nothing, because the SVG in the data URI is URL-encoded (`M3.5%208.5l3%203%206-6`) — a pattern that could never match, reading as a clean result. The check that worked was loading the deployed page and measuring `getBoundingClientRect()` on the control, which is available anonymously on `/waitlist` and covers every page sharing the mixin.

**Every floating surface takes its z-index from the named scale in `app/styles/variables.styl` — a bare number is the bug, and `yarn check:z-index-scale` fails CI on one.** MUI stacks dialogs, popovers, menus and autocomplete popups all on ONE layer (1300) and breaks the ties by DOM order, which works only as long as no app surface is raised above 1300. This app hand-rolls its nav drawer, its context menu and several dropdowns, so their values shared that space with MUI's under no declared ordering, and every collision was historically fixed by nudging one surface upward — each nudge silently jumping over every MUI layer in between. `6d8490f78` raised the selected-player drawer to 1400 to clear the nav drawer at 1300, which put it above every `Dialog`: from then on the place-bid, sign-free-agent, waiver and poach confirmations opened BEHIND the panel that launched them. Nothing failed — the dialog rendered, took focus and worked, it was just not visible, which is the same absent-symptom family as the traps above.

Two rules the scale encodes and a literal cannot. **A surface that is always opened FROM another surface belongs above everything that can open it** — `$z_popper` sits above `$z_dialog` rather than beside it, because ten confirmation dialogs here contain a `Select` or an `Autocomplete` and a naive "dialogs on top" ordering hides their own dropdowns. And **a value below 100 is local, not global**: it orders siblings inside one component, so the guard ignores it. The scale is injected into every `.styl` by stylus-loader (`webpack/webpack.config.base.mjs` `stylusOptions.import`), so no import is needed anywhere. When a new surface does not fit an existing layer, add a layer to the scale rather than picking a number — the point is that the whole ordering is reviewable in one file.

**The dangerous case is a MUI overlay that carries no literal at all**, since a value living in `theme.zIndex.*` is invisible to any sweep of this repo. `Snackbar` defaults to 1400: it ties the selected-player drawer and loses to every dialog, and it survived the first pass of the guard precisely because there was no number to find. `general.styl` now pins each such component onto the scale, and the guard asserts the pin exists rather than trusting the list — extend `MUI_OVERLAYS_REQUIRING_A_PIN` when the app starts using another one. The remaining blind spot is a stacking-context trap, which is static-undetectable: an ancestor with `transform`, `filter`, `opacity < 1`, `will-change` or `contain` makes a descendant's z-index local regardless of which layer it names. A 2026-08-04 sweep found none — every overlay here portals to `document.body` or is `position: absolute` — so a new one would be a new trap.

## Routes and navigation

**A new route needs an entry in `libs-shared/page-routes.mjs` or it ships `noindex` with the home page's copy.** `app/index.html` carries double-brace tokens that the API's SPA fallback (`libs-server/middleware/render-html.mjs`) fills per request from that table — a crawler never runs the app, so the served HTML is the only head it reads, and a path the table does not know is deliberately treated as a typo rather than given the site defaults under its own canonical. The same table drives the client-side `@components/page-head` effect, which is what keeps the browser tab correct after an in-app navigation, so the two cannot drift. Three things that are easy to get wrong: the tokens must NOT be filled at build time (one bundle serves every route); do not write a brace token into a comment in `app/index.html`, because the dev build keeps comments and it then reads as an unfilled placeholder; and a per-route title sourced from the database must be safe to show an anonymous visitor — league names are, saved data-view names are not, since `user_data_views` has no public flag.

**A full page load and an in-app navigation to the SAME URL do not produce the same app state, so verifying a route by typing its address cannot see this whole class of defect.** `app/views/components/app/app.js` reads the route's league id in a `useEffect` whose dependency list is `[init]` — it runs once on mount, and until 2026-08-14 nothing else could move `app.leagueId`. So `/leagues/1` was correct when loaded directly and rendered the DEFAULT league under that URL when reached by clicking a link: the landing page's only call to action, with a sidebar still reading "League not connected" and no league links at all. Every server-side oracle was green throughout, because the server was never asked. `SELECT_LEAGUE` (`app/core/app/actions.js`, with a `load_league` watcher in `app/core/leagues/sagas.js`) now carries the matched route's league, so the two paths agree.

Two things generalize past the one fix. **Any state derived from the route at mount is a candidate** — a mount-only effect is the shape to grep for, and `app.year`/`app.teamId` are reached the same way — so when you add route-derived state, drive it from the route rather than from `INIT_APP`. And **a browser check has to CLICK the path a user takes**: the two anonymous defects fixed the week before (standings, data views) were both found and verified by direct `page.goto`, which is exactly the method that reads this one as working. Drive the real link with `page.click` and compare against a `goto` of the same URL; a disagreement between them IS the bug.

**`useNavigate()` returns a NEW function identity whenever the matched route changes** — its own deps include the resolved pathname and the match array — so an effect that lists `navigate` in its dependency array re-runs on every in-page navigation, not just on mount. On 2026-08-14 the trade-review page's list-load effect listed it, so toggling a row (which navigates between the two sibling routes `/trade-review` and `/trade-review/:trade_uid`) re-fired `load_trade_review` and dropped the page back onto its full-width spinner every time. Keep `navigate` out of a data-fetch effect's deps: an absolute redirect like `navigate('/', { replace: true })` does not need a fresh identity, so split it into its own effect keyed on `[lid, navigate]` and key the fetch on `[lid]` alone.
