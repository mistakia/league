# Add or Change an API Route

**When to read this:** Read before touching anything under `api/`.

Twenty routers mount before the blanket auth guard, so ownership is enforced per handler. Response schemas are validated in test against a dated hold-out list.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

---

## Request patterns

### API Requests

- Standard pattern: Express route → database query → response
- Authentication via JWT tokens
- Rate limiting on resource-intensive endpoints
- Caching with node-cache for expensive queries

## The pre-guard routers

**Twenty routers mount BEFORE the blanket auth guard, so each of their routes must self-enforce.** `api/index.mjs` mounts `docs`, `status`, `errors`, `stats`, `players`, `projections`, `plays`, `schedule`, `sources`, `auth`, `leagues`, `teams`, `markets`, `percentiles`, `seasonlogs`, `cache`, `data-views`, `u`, `wagers` and `selection-combinations` above the `if (!req.auth) return 401` catch-all, which therefore covers only what mounts after it (`scoreboard`, `me`, `settings`). Most of those routers are legitimately public NFL data, but any route in one of them that reads USER-owned rows needs its own `req.auth` check, and the guard's presence in the file makes it easy to assume otherwise. `GET /api/data-views` had neither an auth check nor a mandatory filter for that reason and returned every saved view on the platform to an anonymous caller until 2026-07-31 (`216c1a5d0`). Its sibling `GET /api/plays/views` still has the identical shape against `user_plays_views`, latent only because that table is empty. When adding a route to any pre-guard router, check whether it touches user-owned data and enforce ownership in the handler.

**`GET /api/wagers/:user_id` was the second live instance, and its shape is worth recognising because the ownership check WAS there — it just could not fire.** The handler computed `public_only = req.auth && req.auth.userId && req.auth.userId !== user_id`, which is correct for an authenticated caller and silently false for an anonymous one, so a caller with no token was treated as the OWNER and received private wagers. Reading that line in isolation it looks like a privacy filter; the defect is only visible once you know the router mounts pre-guard and `req.auth` is therefore routinely absent. Measured before the 2026-08-06 fix (`2f0ca9a0f`): user 1 holds 64,513 wagers, none of them public, every one reachable unauthenticated up to the 1000-row default limit. **A predicate gated on `req.auth` being PRESENT is inverted on a pre-guard router** — anonymous is the untrusted case, not the exempt one, so write the condition so that absent auth falls into the restricted branch (`!req.auth || req.auth.userId !== user_id`).

## Response shapes and swagger

**`db/gates/check-api-response-shapes.mjs` is the gate for that class, and it is the first thing here that reads the swagger response schemas at all.** `api/swagger` declares response schemas across 53 route files and nothing validated a response against them, which is exactly why the `leagues.hosted` window above was invisible server-side and why the season_grain wire question had to be settled by reading routes by hand. Two halves, wired differently on purpose. GATE 1 compares the spec to ITSELF — every `required` name and every `$ref` must resolve against the schema's own resolved properties. It needs no database and no base ref, cannot go red on a sibling's in-flight migration, and cannot produce a false positive. GATE 2 compares the spec to the SCHEMA FILE, for handlers that echo a wholesale single-table read to `res.send`: there the response key set IS the table's column set, so a documented non-column is a field that is never emitted. Run both per cluster; it takes about a second and needs no container.

`yarn check:cluster` runs both gates. `node db/gates/check-api-response-shapes.mjs --gate 1` is the spec-only form, safe anywhere and the one to reach for from a dirty tree.

**Its ORACLE choice is the load-bearing decision, and the intuitive answer is the wrong one.** Executing each route against the test container and validating the body sounds stronger. It is weaker: in a fresh test database nearly every list route answers `[]`, which validates vacuously against `type: array`, so an executed gate runs green across the whole surface while structurally unable to see a renamed column — the failure this guide already records three times. Its power would be bounded by fixture coverage rather than by the spec. For the wholesale-read shape, `db/schema.postgres.sql` states the key set completely, so the static comparison is a COMPLETE oracle for those routes and strictly better than execution. What static analysis cannot do is the rest of the surface, which is why the run always prints the denominator.

**Read the coverage line before the findings — gate 2 reaches 5 of 109 operations, and that is the honest number.** The other 104 have a response the analysis cannot determine: an explicit projection, a join, or a `res.send(rows.map(...))` that builds a new object per row. The run lists every uncovered operation with its reason, because a gate over part of a surface that READS as full coverage is worse than no gate. Two things keep that number honest rather than decaying. The chain analysis is an ALLOWLIST of shape-preserving knex methods, not a denylist of projecting ones — the first draft was a denylist, `map` was not on it, and the gate reported five confident findings against a route whose response carries none of that table's columns; with an allowlist an unrecognised method makes a route uncovered, which is the safe direction. And the NEGATIVE CONTROL runs on every invocation rather than behind a flag: three mutations, each asserted to be reported, and a control that stays green fails the run.

**That control is also what detects the gate going blind, which is why there is deliberately no coverage-floor constant.** The gate-2 control needs a covered route to mutate, so if the handler analysis ever stops finding any, it reports STAYED GREEN and the run exits 1 — the catastrophic case is already covered by a mechanism that has to work anyway. A hand-maintained minimum would add nothing there and would fire on the ordinary case instead: giving a covered route an explicit projection is a perfectly good change that drops coverage by one, and the only remedy would be editing a magic number, which is the ritual `--rebaseline` teaches you to distrust. The same reasoning removed an adjudications file: under the allowlist a covered route's response IS the table's columns, so a documented non-column is a defect by construction and an exception file would have been a hook for a case that cannot arise.

It found the two known stale-doc defects unaided plus three the season_grain cluster had not identified — `Transaction` documenting five non-columns, `PlacedWager` documenting `id`/`status` where the columns are `wager_id`/`wager_status`, and `api/routes/leagues/settings.mjs` referencing a `#/components/responses/Unauthorized` that does not exist. All are repaired (`948e6e5d8`, `e5fe62bd0`) and the gate is green. It also surfaced one finding that was NOT a docs defect: `api/routes/wagers.mjs` filtered `whereIn('status', wager_status)` against `placed_wagers`, which has no `status` column — a live 42703 that `check-renamed-column-consumers` gate 1 could not see, because that gate resolves `'table.column'` literals and this was a bare `'status'`. **That one is now FIXED** in `2f0ca9a0f`, deployed 2026-08-06. The bare-literal blind spot it exposed in gate 1 is **now covered** by `check-knex-column-resolution`'s bare-string half (`6a6521858`), whose first run on master found a live 42703 of exactly this shape: `scripts/validate-charting-import.mjs` called `.whereNotNull('sumer_id')` on `db('player')` where the column is `sumer_player_id`, fixed in the same commit.

**A caution about that fix line, which read `23e73d14b` here until 2026-08-06: it credited a commit that never touched the predicate.** `23e73d14b` edited `api/routes/wagers.mjs` in the same window — it moved `placed_at` onto a `Date` for the timestamptz retype — and `git show 23e73d14b:api/routes/wagers.mjs` still carries `whereIn('status', wager_status)` at line 350. So the file recorded a live 42703 as repaired for as long as the wrong hash stood, which is the same shape as the named-but-absent spec above: every signal says covered except the one that counts. **Verify a fix attribution by reading the commit's diff for the specific line, not by trusting that a commit touching the right file in the right window is the right commit.** One command settles it: `git show <hash> -- <file> | grep <predicate>`.

**The same route held a second defect no name-resolution gate could ever have found: `.where('public', true)` against `placed_wagers.public`, which is a `smallint`.** The column exists, so gate 1, the proposed bare-predicate gate, and any `information_schema` sweep all resolve it happily — it is the bound VALUE that is wrong, and pg rejects it at execution with `invalid input syntax for type smallint: "true"`. That broke every authenticated caller viewing another user's wagers, alongside the 42703 that broke every `wager_status` filter. Two rules. When a rename sweep or a schema conform passes over a route, check the bound value's type against the column's, not just the column's existence — a `smallint` flag read as a boolean is the common shape here, since several older tables spell booleans that way. And note the whole class is invisible to static analysis: only executing the predicate against a real schema distinguishes it, which is why the spec for this route seeds rows and runs the round trip rather than asserting on the query builder.

**Why it survived: this handler catches and returns 400, not 500.** `catch (error) { res.status(400).send({ error: error.message }) }` turns a server-side schema failure into what reads as caller error, so neither the status code nor any error-rate alarm distinguishes "you sent a bad filter" from "this route cannot execute its own query". A route whose catch-all maps every exception to 4xx has no observable for its own breakage; prefer 500 for anything the caller could not have caused, and treat a 400 carrying a Postgres error string as a server defect wearing a client's status code.

**Two swagger traps the gate cannot remove, both of which make a CORRECT-looking repair wrong.** First, **a schema can be defined TWICE under one name and swagger-jsdoc merges the definitions silently** — once in `api/swagger/config.mjs` and again in a route's `@swagger` JSDoc block. `WaiverClaim` and `Transaction` were both in that state until 2026-08-05. So a property the merged spec carries may live in a file you are not reading, and a finding can name a key you cannot find where you are looking. Collapse to one definition rather than editing whichever copy you found.

Second, and more expensive: **a component schema shared by two operations means a documented non-column may be a real emission by the OTHER route.** `WaiverClaim` was the 200 of both `GET /waivers/report` (a wholesale read, so gate-2-covered) and `POST /waivers` (uncovered — it sends the inserted row plus `data.release`, which lives in `waiver_releases`). Acting on the finding, a repair deleted `release`, leaving `POST /waivers` documented as not emitting a field it does emit and contradicting its own 200 example — with no gate able to see it, since that route is uncovered. The remedy is to SPLIT the schema (`SubmittedWaiverClaim`, and `Transaction` / `TransactionWithDraft` before it), never to delete the property from a shape two routes share. Gate 2 now names the sharing operations on every such finding, but the check it cannot do for you is reading what the other route actually sends.

**Not in CI, and gate 2 should stay out.** It reads the working tree's schema file, so a sibling mid-cluster turns it red on findings that are not yours — run it from a clean worktree at your HEAD, exactly as for `check-data-view-sql-validity`. Gate 1 is genuinely CI-eligible now that it is green: spec-only, about a second, no database, and structurally unable to go red on someone else's migration, which is the same reasoning that put gate 1 of `check-renamed-column-consumers` in CI and kept its gate 2 out. `--gate 1` runs only gate 1's controls for exactly that reason.

**CI-eligibility is a property of a gate's CORPUS, not of the gate, so a gate that reads two corpora must be SPLIT rather than excluded whole — and "it passes on a clean checkout" cannot tell you which case you are in.** On 2026-08-18 three gates were wired into CI, each verified green on a clean checkout first, and two turned master red within the hour and were backed out (`c1c9c3f9a`, `21eae672e`). Both failures were environment dependencies that a developer machine structurally cannot see: `check-stranded-vocabulary-literals` walks UP from the checkout for its user-base SQL corpus, which succeeds on any machine where the checkout sits under user-base and has no ancestor on a runner; `check-dropped-table-consumers` shelled out to `rg`, which is on every developer PATH and on no `ubuntu-latest` runner. Neither is visible to any check run locally, so the clean-checkout confirmation the plan asked for was green in both cases and proved nothing.

The vocabulary gate has since been split as this rule prescribes: `check-stranded-vocabulary-literals` carries a `--gate 1` knex half that needs nothing outside the checkout and a `--gate 2` SQL half that needs the user-base corpus, and the cluster manifest names them as two entries — `stranded-vocabulary-literals-gate-1` with `requires: 'none'` and `-gate-2` with `requires: 'user-base-prose'`. **Name the halves separately in the manifest rather than invoking the gate bare**, because a bare invocation makes the whole gate declare itself BLIND on a runner, and the only way to keep such a job green is an allowance keyed on the gate's NAME — which then goes on excusing that gate after it becomes blind for some unrelated reason. The private corpus-gates workflow carried exactly that allowance and no longer needs one.

Two rules. **Verify a CI-bound gate from a `/tmp` worktree with the suspect binary off PATH** — that is the only place both conditions are absent, and it costs one `git worktree add`. And when the dependency turns out to cover only PART of what the gate reads, the fix is a `--gate 1` / `--gate 2` split on the corpus boundary, not removal: the vocabulary gate's knex half needs nothing outside the checkout and had been CI-eligible all along, and it went out only because it ran in the same process as the SQL half, which exited 2 on the absent root after every knex finding had already been computed. Repaired in `6660fec37`; the gate now splits, and the dropped-table gate walks the tree in Node so it depends on nothing but node and the checkout.

**A gate in CI with no negative control is a strictly worse object than the same gate run per cluster**, and the standing "backlog item, not a blocker" verdict was formed about the second case. Per cluster a human reads the output; in CI nobody reads a green, so a matcher that quietly stops matching is indistinguishable from a clean tree. Three of the nine gates now in CI carry none — `check-schema-conformance-ratchet`, `check-renamed-column-consumers` gate 1, and `check-dropped-table-consumers`, whose matcher was rewritten in that same commit.

**The EXECUTED half of that surface is now live in the test environment, as a ratchet: `express-openapi-validator` runs with `validateResponses` on for every request the suite makes, and a response that does not match its operation's schema fails the test that produced it.** It is wired in `api/index.mjs` behind `NODE_ENV === 'test'`, mounted after the JWT middleware and before the first route mount, with the implementation and its reasoning in `api/swagger/response-validation.mjs`. Note this does NOT contradict the ORACLE paragraph above, which rejects execution as a way to check the SPEC against the SCHEMA — a fresh test database answers `[]` and validates vacuously against `type: array`, so gate 2's static comparison stays the better oracle for that question. This answers a different one: whether the server EMITS what it documents, which no static analysis can reach.

**It went on while 41 (operation, status) pairs still mismatched (38 today), behind the dated hold-out list in `api/swagger/response-validation-holdout.json`, and that sequencing is the whole design.** Waiting for the backlog to reach zero means a route added in the meantime drifts undetected for exactly as long as the grind takes — which is how the first attempt at this ended up backed out. Two properties make the list a ratchet rather than a mute button, and both are load-bearing. An entry is keyed on `(operation, status)` and **never on a route**: a route key would suppress a second operation on the same path, which is the `WaiverClaim` shared-schema trap stated above, and `test/api.response-validation-ratchet.spec.mjs` reproduces exactly that shape as a control. And **an entry that stops failing FAILS THE RUN** — the same self-cleaning property the conformance baseline and every `db/gates` adjudications file carry — enforced from a root `afterAll` hook in `test/global.mjs`, so a repair has to remove its own entry instead of leaving a standing exemption. Verified in both directions: a synthetic entry over a passing pair turns the run red naming the entry, and an entry the run never exercised stays silent, so a single-file mocha run does not report the other 37 as stale.

**The stale-entry arm reads a SAMPLE, not a corpus, and until 2026-08-28 that made it able to turn master red with nothing repaired.** `get_response_validation_report` treats an entry as exercisable when `observed_pairs` holds its `(operation, status)`, which answers "did the suite produce a response for this operation" and not "did the suite produce a response that would have tripped this entry". Those two coincide for a static gate — `check-retyped-column-arithmetic`, whose NOT EXERCISED bucket this borrowed, derives its subject set from a `--base` ref and reads the file tree, so a rerun at the same ref sees the same corpus. Here the corpus is whichever rows `test/utils/select-player.mjs` returned, and it draws `ORDER BY RANDOM()`. `GET /api/teams/{teamId}/players` at 200 was reported STALE on run 59544f720 and the identical job passed on a rerun with no code change, which is the shape to expect: **do not delete a hold-out entry on the strength of one red run.**

**The variance was itself the defect, so the fix was repairing it rather than narrowing the check.** Measured over 11 instrumented full runs at HEAD, all 41 entries held on every run, but the absorbed MESSAGE sets under three of them flipped run to run — `GET /api/leagues/{leagueId}/players`, `GET /api/teams/{teamId}/players` and `POST /api/players`, all at 200, all three `pattern_drift`, and no other entry. Both of their messages traced to the `Player` component describing a stricter table than `public.player` actually is:

- `/response/*/roster_status must be string` — the column is a NULLABLE unconstrained `varchar(100)`, and 297 of the 1000 rows in `db/fixtures/test/player.sql` carry null, while the schema declared a non-nullable five-value enum naming neither the null nor `RETIRED`, `CUT`, `NOT_WITH_TEAM`, `UNSIGNED_FREE_AGENT`, `UNDRAFTED_FREE_AGENT` or `RESTRICTED_FREE_AGENT` — every one of which the route emits.
- `/response/*/pid must match pattern` — `PlayerId` demanded exactly four letters per name half and exactly six digits, while the `player_pid_format` CHECK constraint allows ONE to four letters and six OR MORE digits. The offending values were the suite's own `XR-ROOK-` / `XS-SOPH-` fixture players: legal identities the database accepts and the published spec rejected. **The spec was the defect, not the fixture** — renaming those 250 rows was the first repair attempted and it is the wrong one, because a real player with a short name produces the same shape in production.
- Behind those two, `draft_round`, `height_inches`, `weight_pounds`, `jersey_number`, `nfl_draft_year`, `college` and `date_of_birth` were all declared non-nullable over nullable columns, and `primary_position` carried a hand-written 13-value enum over a 25-value CHECK — one that omitted `OL`, `T`, `G`, `C`, `NT`, `EDGE`, `OLB`, `ILB`, `MLB`, `DB`, `P` and `LS`, and listed `DEF`, which is not a legal stored value. `draft_round` surfaced only AFTER the first two were fixed, as a 500 on a route the entry had been absorbing all along.

So whether a given response validated depended on which player the draw returned. The repair is the `Player` component conforming to the table: nullable where the column is nullable, the position and status vocabularies DERIVED from `position_vocabulary` and `player_nfl_status` rather than hand-listed so they cannot drift again, and `PlayerId` mirroring `player_pid_format` — the pattern now also lives in ONE place, with the four inline copies in `api/routes/players.mjs` replaced by a `$ref`. The three entries then read genuinely stale and were deleted. Verified across 15 consecutive full runs: 190 pairs observed, 38 entries, all held every run, zero stale, and the staleness detector re-proven in both directions first (a synthetic entry over the now-passing pair fails the run naming it; an entry for an unobserved pair stays silent).

**The rule that generalises past this incident: a hold-out entry whose violation depends on which fixture row the suite drew is unjudgeable from one run, so do not create one.** When a stale report names an entry you did not repair, read its `messages` before believing it — a message about a NULLABLE column, or a pattern narrower than the column's own CHECK constraint, means the entry only fires on some draws and the report is a lottery result rather than a finding.

**But a single-file run whose spec issues NO HTTP requests fails the whole run, and it reads as your spec being broken.** The zero-pairs arm is a different assertion from the stale-entry one the sentence above describes: with nothing exercised at all, the teardown cannot distinguish "this run made no requests" from "the validator is not mounted", so it fails loudly with `Response validation observed ZERO (operation, status) pairs while the hold-out list carries 38 entries` and a paragraph about middleware mount order. Every source-scan spec in this repo trips it — `test/data-views-socket-param-override.spec.mjs`, `test/data-view-player-field-parity.spec.mjs`, and the rest of the parse-the-source family make no requests by construction. Read the passing/failing COUNTS, not the exit status: `2 passing / 1 failing` where the only failure is the root `afterAll` hook is a green spec. The cheap control is to run any untouched no-request spec alongside yours and confirm it fails identically, or to include one request-issuing spec in the same invocation, which clears the arm entirely.

**Read the coverage line the run prints and do not read a shrinking hold-out as growing safety: COVERAGE EQUALS TEST HIT-RATE.** The validator only ever sees the pairs the suite actually produces — 190 `(operation, status)` pairs on the full run, of which 38 are held out and 152 validate clean. An unexercised route and an error path no test provokes stay unchecked no matter how empty the list gets, so emptying it raises the floor under what the suite already exercises and says nothing about the rest. **It is a floor, not a contract.** The 38 entries fall into four classes: 16 `undeclared_status` (a 423/403/401/400 with no response declared for that status, mostly the league-pause feature's doc gap), 10 `type_drift`, 9 `missing_required`, 3 `undeclared_body`. The `pattern_drift` class is empty — its three entries were the flaky ones, and burning them down is the incident below. Burning them down is ordinary follow-on work, one entry per repair — and before repairing a shared schema, re-read the SPLIT-not-delete rule above, which is the trap this class walks straight into.

**A NEW spec that reaches a previously-unexercised operation is validated from its first run, and a mismatch reaches the spec as a 500 from the ROUTE rather than as a validation message.** The `onError` hook rethrows, so what the spec reads is an ordinary server error carrying no hint that the validator produced it — which reads as the handler being broken and sends you back to a query you have already proven correct. On 2026-08-26 a spec written for `GET /api/projections` failed exactly this way on all four of its authenticated cases while its anonymous case passed, because a fresh test database answers `[]` for the anonymous read and validates vacuously against `type: array` — the same vacuity the ORACLE paragraph above rejects execution for, here disguising which half of the spec is really being checked. The discriminator is `LEAGUE_RESPONSE_VALIDATION_DISCOVER=1`, which swallows the throw and prints the message; there it was one property, `Projection.source_id` enumerating 1-30 while a user projection carries the column default 0 that the PUT path never sets. **Budget a hold-out entry as part of landing any spec that exercises a route the suite did not previously reach** — the pair was unvalidated before your spec existed, so holding it out is no regression, and the entry names the docs repair for whoever burns it down.

**Seeding or re-seeding the list is `LEAGUE_RESPONSE_VALIDATION_DISCOVER=1`, which swallows every failure and prints a proposed list.** It cannot be used to make a red suite green: the teardown assertion fails unconditionally whenever the variable is set. One gotcha it already hit — read the clock at MODULE LOAD when dating entries, because a spec's `MockDate.set` leaks into the teardown hook and the first seeding run stamped every entry 2026-09-01 on a list built 2026-08-18.
