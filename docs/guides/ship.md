# Ship a Change

**When to read this:** Read before committing anything you intend to reach production, and before any deploy.

The arc from commit to CI to push to deploy to post-deploy verification. Most of it exists because a partial deploy and a suppressed CI run both look exactly like success.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

---

## The deploy commands in full

**Build & Deploy:**

- **`yarn deploy:all` — the deploy path. Use this unless you have a specific reason not to.** Runs `preflight:deploy && deploy && build && deploy:dist && deploy:sourcemaps`: pre-flight gate, then backend to both hosts, then the frontend bundle and its sourcemaps. It exists because the individual steps below are each independently skippable and the skip is silent — the recurring production incident here is a PARTIAL deploy, someone shipping `deploy:dist` for the frontend and never running `deploy` for the backend (or the reverse). On 2026-07-16 both backend checkouts sat 6 commits behind since the last `yarn deploy` while the client `dist` had been rebuilt that same day; the app hosts drifted again to 4 behind by 2026-07-29. Running every step in one command is what makes the sequence un-skippable. It is human-gated on purpose — nothing auto-deploys these hosts, because they run the live API and the import workers and reloading them unattended is the wrong risk. Being a superset of a backend-only deploy costs one webpack build and one rsync; take that over reasoning each time about whether your change reaches the SPA.
- `yarn preflight:deploy` - The gate every deploy path runs first, via `deploy` (`scripts/preflight-deploy.sh`). Refuses to deploy from a dirty working tree (`yarn build` would bundle a concurrent session's edits into production), from a HEAD that is ahead of or behind `origin/master` (the hosts `git pull` origin, so an unpushed commit deploys the prior state), or with an unpushed `private` submodule commit (the hosts `git submodule update --init private`, and `private` is a nested submodule that `sync-all` does not push). Read-only — it fetches and compares, nothing else. Safe to run on its own to check whether a deploy would be honest.
  **`deploy:all` is an `&&` chain, so a failure on EITHER host stops it before the frontend steps and ships a partial deploy — the exact incident the entry above says running one command prevents.** `yarn deploy` is `load:main && load:worker1`, and the frontend steps come after it, so a worker-host failure leaves the API reloaded on the new commit and `dist/` untouched. The claim that one command makes the sequence un-skippable holds only for a deploy that gets all the way through; it does not survive a host that refuses. Measured 2026-09-04: `load:main` reloaded `league` at `10ab7caae` and `load:worker1` then died on `digitalocean-0` with `cannot pull with rebase: You have unstaged changes` (its `config-production.json` carries `ssl` blocks in no commit — bulletin #655), and `build`, `deploy:dist` and `deploy:sourcemaps` never ran. Nothing in the output says the frontend was skipped; you have to notice the chain ended early. **So read the TAIL for which step it reached, and when a host you do not need has blocked the chain, run `yarn build && yarn deploy:dist && yarn deploy:sourcemaps` yourself** — that is a real frontend deploy and it is what the partial-deploy rule actually asks of you here.

  **`yarn deploy:all` EXITS 0 WHEN THE PRE-FLIGHT GATE REFUSES, so the exit code cannot tell a completed deploy from one that never ran.** On 2026-08-14 a deploy refused with `HEAD is 1 commit(s) BEHIND origin/master` — a sibling had pushed while the worktree was installing — and reported `exit=0` with a normal-looking tail; the hosts never moved and the change was reported as shipped. Read the OUTPUT (`grep -c 'REFUSING TO DEPLOY'`) and then the hosts, never the status. Two checks settle it: both hosts at `origin/master` (`ssh league "cd /root/league && git rev-parse --short HEAD"`, same for `digitalocean-0`), and — the one that matters more — **the bundle the served HTML references must exist on disk**: `curl -s https://xo.football/ | grep -oE 'main\.[a-z0-9]+\.js'` against `ssh league 'ls /root/league/dist/'`. Checking the served HTML's CONTENT is not enough, because Cloudflare will happily keep serving a deleted `/dist` asset from the edge (the `immutable` note above) and the page renders for you while it is broken for anyone without that cache entry.

## Deploy commands

**And note the deploy ORDER is reload-then-rsync: `deploy` (pm2 reload) runs BEFORE `build && deploy:dist`.** Anything the API caches from `dist/` at startup is therefore captured from the PREVIOUS build. The SPA-fallback middleware (`libs-server/middleware/render-html.mjs`) cached `dist/index.html` on first read and pinned production to a superseded, content-hashed bundle that `deploy:dist` had already deleted — every visitor without an edge-cached copy got a blank app, and the recovery was a second `pm2 reload` after the rsync. It now keys the cache on mtime, covered by `test/api.render-html-middleware.spec.mjs`. When you add anything that reads `dist/` at startup, assume it will see the old build.

- `yarn build` - Build production bundle
- `yarn analyze` - Build with bundle analyzer
- `yarn deploy` - **API + workers only**: on each host, `git pull` from `origin/master`, `yarn install`, and `pm2 reload` the app (main) / import workers (worker-1). Does **NOT** rebuild or rsync the frontend `dist/` bundle. Frontend changes (any file under `app/`, `webpack/`, `libs-shared/` consumed by the SPA, or routes/components) require running `yarn build && yarn deploy:dist` separately — **which is exactly the split that keeps producing partial deploys, so prefer `yarn deploy:all` above.** Reach for bare `yarn deploy` only when you have positively established your change is backend-only (`api/`, `libs-server/`, `scripts/`, `jobs/`). **Push to `origin/master` before running `yarn deploy`** — the servers pull from origin; an unpushed local commit will deploy the prior origin state and leave production on stale code. Both paths now refuse in that situation: `preflight:deploy` moved from `deploy:all` into `deploy` itself, so the quick path carries the same gate and `deploy:all` inherits it through its first step rather than running it twice. It used to be checked only by `deploy:all`, which made bare `yarn deploy` of an unpushed commit a silent redeploy of the prior revision whose output read like success.
- `yarn deploy:dist` - Frontend-only deploy: rsyncs locally-built `dist/` to `/root/league/dist` on the main server (excludes `*.map` — sourcemaps are never served publicly). No API restart. Pair with `yarn build` to refresh the SPA bundle.
- `yarn deploy:sourcemaps` - Ships the build's `*.js.map` files to the **private** path `/root/league/sourcemaps` on the main server (never the public `dist/`). The `/api/errors` route resolves minified client stack frames against these maps server-side (`libs-server/symbolicate-stack.mjs`), so emitted `log_error` signals carry original `file:line:col` instead of minified chunk coordinates. **Always pair this with `yarn build && yarn deploy:dist`** — a frontend deploy that ships new chunk hashes without the matching maps silently degrades symbolication to raw minified stacks for the new chunks. Full frontend deploy: `yarn build && yarn deploy:dist && yarn deploy:sourcemaps`.
- `yarn load:main` - Update code and deps on the main server and `pm2 reload` the API app
- `yarn load:worker1` - Update code and reload worker processes on worker server 1

Deploy targets (SSH hosts): `league` (main: API + frontend), `digitalocean-0` (odds/plays import workers)

## Deploy hazards

**`yarn build` reads the working tree, not the pushed ref — never build a frontend deploy from a dirty shared checkout.** `yarn build` bundles whatever is sitting in the tree, so a sibling session's uncommitted edits ship straight to production. **A dirty tree blocks EVERY deploy path, not just the frontend one** — `preflight:deploy` refuses on a bare `git status --porcelain`, and since it moved into `deploy` itself, a backend-only `yarn deploy` is refused too even though the hosts would only ever `git pull` from `origin/master`. The reason the gate states is about `yarn build`, so the refusal reads as inapplicable to the command you actually ran; it is not. The throwaway-worktree recipe below is the remedy for any deploy from a shared tree that a sibling has dirtied, backend-only included (confirmed 2026-09-03 deploying the data-view admission-gate split, where the tree carried three other sessions' edits). This is not hypothetical: a 2026-07 frontend deploy for the RFA column rename coincided with another session's uncommitted changes to `libs-shared/get-draft-window.mjs`, which reaches the SPA through `libs-shared/index.mjs`. Check `git status` before `yarn build`; if the tree is dirty with work that is not yours, build from a throwaway worktree pinned to the pushed ref (`git worktree add ~/user-base/tmp/<name> origin/master`, symlink `node_modules`, then `yarn build && yarn deploy:dist && yarn deploy:sourcemaps` from there, then `git worktree remove`). Do not stash a sibling's work to clean the tree.

**A fresh worktree does not inherit submodules, so `yarn deploy:all` from one refuses with `private submodule is not initialized; the hosts deploy it`.** The recipe above omits the step: run `git submodule update --init private` in the worktree first (it clones ~fresh, so give it a moment), then verify its HEAD matches the main checkout's before deploying. Confirmed 2026-08-04 on the trade-review rename deploy — preflight caught it cleanly, but it reads as a deploy-config problem rather than a missing worktree step.

**And `git worktree remove` REFUSES to tear that worktree back down, because the `private` init two steps earlier is what makes it a "working tree containing submodules".** The recipe ends on `git worktree remove` and the removal is the step it does not survive: the error is `fatal: working trees containing submodules cannot be moved or removed`, which reads as repo corruption rather than as the documented consequence of the documented previous step. `git submodule deinit -f private` inside the worktree first is NOT sufficient on its own — it clears and unregisters the directory and the plain remove still refuses; `--force` is what completes it. So the teardown is `git submodule deinit -f private` then `git worktree remove --force <path>`, and both need `git -C <explicit-path>` rather than a `cd`, since the Bash tool's cwd reverts after a subshell and a bare `git worktree remove --force` then resolves against user-base, where the parent destructive-op guard blocks it outright. Hit 2026-09-03 on the live-blocks deploy worktree; leaving the worktree behind instead is not free, since it keeps a stale `node_modules` symlink and a registered entry in `git worktree list` for every later session to wonder about.

**And the `node_modules` symlink the recipe calls for points one level deeper than the directory the roots helper names.** `worktree_root`/`node_modules_root` resolve to `$HOME/worktrees` and `$HOME/node-modules`, but the main checkout's link target is `$node_modules_root/league/node_modules`, not `$node_modules_root/league` — the obvious symlink to the latter produces a worktree where `ls node_modules` returns a single entry and every build tool is missing. Copy the main checkout's own target (`ls -ld node_modules` in it) rather than composing the path from the helper's variables. Hit 2026-09-02 on the percentile-field deploy worktree.

**`yarn deploy:dist` ships whatever is already in `dist/` — a clean `git status` does NOT mean it is safe to run.** This is the companion hazard to the one above, and the check for it is different. `dist/` is a build artifact directory: it survives commits, it is not cleaned by anything, and it can hold a sibling session's _finished build of an undeployed change_ while the source tree is spotless. Running `deploy:dist` then ships that change to production early, out of its own sequence and possibly ahead of the schema or push it depends on. This is not hypothetical either: on 2026-07-28 the tree was clean while `dist/` held a built bundle of the rookie-draft hourly-window rework, which had its own gated deploy sequence and must not have shipped early. **Before any `deploy:dist`, compare the local bundle against what production actually serves** — `ls dist/main.*.js` locally against `grep -o 'main\.[a-z0-9]*\.js' /root/league/dist/index.html` on the server. A local hash that does not match production's means `dist/` holds something undeployed; find out whose it is before shipping. If your change is backend-only (`api/`, `libs-server/`, `scripts/`, `jobs/`), skip the frontend steps entirely — `yarn deploy` alone is what you want.

**That hash comparison tells you the bundles DIFFER, not that the SOURCE differs — the build is not reproducible, so it cannot answer the question you are actually asking.** On 2026-08-24 three bundle hashes were in play for provably identical SPA source: production served `main.621f23b7.js`, the shared tree's `dist/` held `main.659d1932.js`, and a clean build from `origin/master` in a fresh worktree produced `main.2ee3061d.js` — while `git log <deployed-sha>..origin/master -- app/ libs-shared/` was **empty**. Read on hashes alone that reads as "master has undeployed frontend work" and argues for a `deploy:dist` that ships nothing but churn. **The oracle is `dist/build-manifest.json`, which names the commit the deployed bundle was built from**: `ssh league "cat /root/league/dist/build-manifest.json"` returns `{"sha": ..., "built_at": ...}`, and `git log <sha>..origin/master -- app/ libs-shared/` then answers whether a frontend deploy is warranted at all. Reach for the manifest first; the hash comparison remains useful only for its original narrow purpose, catching that `dist/` holds a build somebody else has not shipped.

**A pm2 RELOAD re-executes the app with the environment pm2 already holds — it does not re-read `server.pm2.config.js`.** So a commit that makes a NEW environment variable mandatory breaks the very deploy that ships it, and the config file naming the variable is no defense: `yarn deploy` reloads, the reload re-executes new code against the old environment, and the API refuses to boot. Only `pm2 delete server && pm2 start server.pm2.config.js --env production` re-reads the config file. `preflight-deploy.sh` gate (4) catches this one instance for `LEAGUE_REDIS_HOST`, but the rule is general and the next mandatory variable will need its own gate.

The sequence matters and is not the obvious one. The host's checkout supplies the config, so the new `server.pm2.config.js` has to be ON the host before the delete-then-start — but `load:main` is `git pull && yarn install && pm2 reload`, and its reload is exactly the operation that fails. Do the host half by hand for that one deploy: `git pull`/`checkout` to the ref, `git submodule update --init private`, then delete-then-start, then run the normal deploy for the frontend once gate (4) passes. **Confirm the dependency actually exists before restarting** — a delete-then-start into a variable pointing at nothing leaves production down rather than degraded (for Redis: `ssh league "redis-cli -h 127.0.0.1 ping"` should return `PONG`).

**A delete-then-start drops every live websocket**, where a reload lets clients reconnect. That makes it a different decision during a live auction, and the auction's own reconnect handling is what decides whether it is survivable — see [auction.md](auction.md). Performed 2026-09-03 at 23:02 UTC into the live League 1 auction on the c2cd9f013 deploy: 0 restarts, mode poll ticking, zero `auction is paused` refusals afterwards.

**Pin the build to a REF you resolved, and re-resolve nothing by name afterwards.** `git pull` on the host takes whatever `origin/master` means at that instant, and `sync-all` pushes on a debounce, so a ref you read minutes earlier can gain commits before your pull — including ones another session is parked on a ruling for. On 2026-09-03 a host pull intended to land `c2cd9f013` landed `7b081d08b`, six commits later, carrying an unruled change to touchdown values (#641) that the deploy had explicitly promised to exclude. Caught before the restart, so nothing served it, and the remedy was `git checkout <the-pinned-sha>` on the host. Use the sha everywhere — `git worktree add <path> <sha>` and `git checkout <sha>` — never the branch name, and re-verify on the host with `git merge-base --is-ancestor <excluded-sha> HEAD` before restarting anything.

**A pin leaves the host DETACHED, and the next deploy cannot recover from that on its own — so pinning is a two-part operation and the second part is somebody else's problem unless you do it.** `git checkout <sha>` on the host detaches HEAD, and `load:main` opens with `git pull`, which refuses on a detached HEAD with "You are not currently on a branch" and exits 1. That failure is benign in the moment — measured 2026-09-03, it aborted before installing or reloading, so production was untouched — but it lands on whoever deploys NEXT, presenting as a broken deploy pipeline rather than as the residue of a pin they did not perform and have no reason to suspect. Restore the branch as soon as the pin has served its purpose: `git checkout master && git merge --ff-only <sha>`, which fast-forwards cleanly because the pinned sha is an ancestor. If you are pinning to exclude a commit that is awaiting a ruling, the honest end of that procedure is not the deploy — it is putting the host back on `master` once the ruling lands.

## Verifying a deploy

**Verifying a frontend deploy over HTTP: assets live under `/dist/`, and every path OUTSIDE `/dist/` returns `index.html` with a 200.** The SPA catch-all means `curl https://xo.football/main.<hash>.js` answers `200` with 11KB of `index.html` rather than the bundle — so a verification that only checks the status code passes identically whether the asset exists, is stale, or was never deployed. On 2026-07-29 a `kickoff_at` frontend deploy was "confirmed" three ways by this shape: the new bundle, the superseded bundle, and a `.map` all returned 200, which read as success, success, and a public sourcemap leak. All three were `index.html`. Check `content_type` and body, not `%{http_code}` — the real URLs are `https://xo.football/dist/main.<hash>.js` (`application/javascript`, ~376KB). Read the referenced hash out of the deployed page (`curl -s https://xo.football/ | grep -oE 'src="[^"]*"'`) rather than guessing the path.

Since 2026-07-30 the `/dist` mount is `fallthrough: false` with its own 404 handler (matching `/static` and `/docs`), so **a missing asset under `/dist/` now 404s instead of falling through to the catch-all.** Before that fix an absent chunk was answered `200 text/html` with index.html's body, and the browser parsed `<!doctype html>` as JavaScript and reported `SyntaxError: Unexpected token '<'` with no filename and no request_url — naming neither the asset nor the deploy that dropped it (signal #123576). This changes the sourcemap check's observable: `/dist/main.<hash>.js.map` now returns **404**, where it previously returned `text/html`. Both results prove the same thing — maps are not publicly served, because `deploy:dist` excludes `*.map` — but the passing observable is now a 404, not an HTML body. A `.map` that returns `200 application/json` is still the real leak to watch for.

**Counting OLD identifiers in the deployed bundle is not a valid post-deploy check for a data-view column-id rename, and it reads as a FAILED deploy when the deploy is correct.** `libs-shared/data-views-saved-view-migration.mjs` runs CLIENT-SIDE, so every legacy id in `COLUMN_ID_RENAMES` and every legacy key in `PARAM_KEY_RENAMES` is a map KEY that MUST ship in `dist/` — that is the whole point of the map. After the 2026-08-18 `recv` conform the deployed bundle carried 18 live `nfl_team_seasonlogs_recv_*` strings and all 18 were migration keys; a plan whose verify step read "the bundle carries the new ids against ZERO old" would have called a correct deploy broken. This is the same syntactic-role trap recorded above, in the one place a rename plan reliably reaches for it. **The discriminating oracle is the live WIRE read as a pair** — the deployed API returning the new keys WITH VALUES and zero old keys — not a bundle grep.

**Confirm a shipped bundle by executing its behavior, not by grepping the source for the fix.** "The new source contains the fix" and "the deployed bundle no longer has the defect" are different claims, and only the second is what a deploy verifies. For a defect that is a silent no-op rather than a crash — a comparator returning `NaN`, a filter matching nothing — nothing in the logs or the status codes will ever distinguish them. The durable check is to fetch the bundle production actually serves, extract the minified construct from it, and run it against a real production payload: the 2026-07-29 `kickoff_at` gamelog sort was confirmed by pulling `(e,t)=>new Date(t.kickoff_at)-new Date(e.kickoff_at)` out of the served JS and sorting a live 61-row response with it, showing the old comparator yielded `NaN` and the shipped one ordered correctly. Note that `/api/players/:pid/gamelogs` has **no `ORDER BY`** — the server returns rows unordered and the client comparator is the only thing sorting them, which is why this class of defect is display-only yet fully invisible server-side.

**Probing an API route unauthenticated proves NOTHING about whether it deployed: the blanket 401 at `api/index.mjs` answers identically for a route that exists and one that does not.** `curl -X POST https://xo.football/api/leagues/1/pause` returning `401 {"error":"Authentication required"}` reads as "the route is live and gating correctly" — but on 2026-08-13 the negative control `/api/leagues/1/pause-nonexistent` returned the exact same 401, so the check was vacuous. `/api/docs/swagger.json` is auth-gated too, so reading the deployed swagger for a new component fails the same way. Two checks that DO discriminate: read the host's git HEAD plus the pm2 process uptime (`ssh league "export PATH=\$HOME/.nvm/versions/node/<v>/bin:\$PATH && pm2 list"` — pm2 is not on a non-interactive PATH), and exercise a behavior that differs from the default, which for the pause meant opening one on a DORMANT league (league 2, zero teams in the current year) and watching the same anonymous POST flip 400 -> 423 -> 400 across pause and resume, never touching league 1 with its live draft. This is the same shape as the `/dist` catch-all trap above, relocated to the API.

**Reading a source file to learn what is deployed reads the SHARED CHECKOUT, and master moves under you between your deploy and your grep.** This is the source-vs-artifact rule above in its git form, and it is easier to miss because the file you open is real, current, and says what you hoped. On 2026-08-29 a session confirmed a deployed data-view code path by grepping `libs-server/data-views-column-definitions/player-projected-column-definitions.mjs` in the local tree, found the season arm routed to `season_projections_index`, and reported production healthy. That map was an UNDEPLOYED commit another session had landed on master minutes earlier; the deployed file contained the string zero times. `ssh league 'cd /root/league && grep ...'` is the oracle, and `git log <deployed-sha>..origin/master` tells you whether the question was even askable locally.

**A deploy ships whatever `origin/master` holds, not the commits you wrote.** Same session, same day: verifying that your OWN commits were pushed is not verifying what the deploy carries. `yarn deploy:all` pulls origin on both hosts, so every sibling commit that landed since the last deploy ships with yours — including one guarded only by a bulletin. Run `git log <currently-deployed-sha>..origin/master` before deploying and read every line; if a commit is not yours, find its owner before shipping it. A bulletin cannot protect an undeployed commit sitting on master, because it only reaches sessions that started after it was posted.

**And an owner's go-ahead covers the RANGE they read, not the range you eventually ship — so re-read `git log <deployed-sha>..origin/master` immediately before the deploy, not once at the start.** Asking an owner costs a round trip, and master keeps moving through it. On 2026-09-01 a session cleared two dfs-salary commits with their author, and by the time it came back to deploy, master had also taken an 88-file MUI removal — `Button`, `IconButton`, `ButtonGroup`, `Dialog`, `Accordion` and the icon sprite all swapped for the app's own primitives, plus follow-ups re-anchoring stylesheet rules the conversions orphaned and one commit whose message is "fix three defects the conversion introduced, found by review". None of that was in the range anyone had cleared, and nothing in `yarn deploy:all` would have named it. The tell is cheap and the cost of skipping it is shipping a stranger's unverified refactor under your own deploy: diff the range again, and if it grew, the new commits need their own owner's answer before you proceed. The same applies to a bundle you built earlier in the session — check `git log <manifest-sha>..origin/master -- app/ libs-shared/` before `deploy:dist`, or you either ship work nobody cleared or silently revert work somebody did.

**Executing the deployed behavior is necessary and not sufficient: the INPUT has to be able to tell the old rule from the new one, and real production data usually cannot.** A behavioral check runs the shipped code against real rows, agrees with expectation, and reads as the strongest possible verification — while proving nothing, because the two rules return the same answer on that input. On 2026-08-09 the Amendment XL wildcard-berth deploy was "confirmed" by seeding league 1's real 2025 standings through the deployed `get_playoff_seeding`: the field came out `7, 12, 4, 2` under `head_to_head_berth_count = 2` and `7, 12, 4, 2` under a forced 0, so the run was vacuous. It is not a quirk of one season — the record ladder and the points-for ladder agree in **six of league 1's seven seasons**, because the best records below the byes are usually also the highest scorers, so picking any single real season had about a one-in-seven chance of discriminating. The fix is to run the check as a PAIR against a control with the feature disabled and require the two to DIFFER, which turns "did it work" into a question the run can actually answer; sweeping all seven seasons then found 2021 as the one real discriminator, and a synthetic case built to disagree (best records below the byes are also the worst scorers) pinned the exact predicted split. This is the fixture-with-two-identical-columns trap from the testing section, relocated to a verification oracle over production data, where it is harder to see because nothing about the data looks contrived.

**A component's strings are NOT in `main.js` — routes are code-split, so grepping the main bundle for your change returns a confident zero on a deploy that fully succeeded.** This is the false-negative twin of the trap above, and it fires on the cheapest check anyone reaches for first. On 2026-08-03 a verified-good deploy of the restricted free agency nomination card answered `0` in `main.js` for `until bids close`, `until the window opens` and `Nomination needed`, while the CSS class name `restricted-free-agency-nomination` WAS present — the class reaches main through the style import, the JSX strings live in the lazy route chunk. The three strings were all in `5453.9c112e32.chunk.js` and `8274.c17f0b54.chunk.js`. So grep the whole deployed directory rather than the main bundle, and read the host as the oracle: `ssh league "cd /root/league/dist && grep -l -- '<string>' *.js *.css"`. Sweep `*.css` too — extracted stylesheets are their own chunks, so a style-only change appears in no `.js` file at all. The same run also re-proved the documented "validate a negative pattern first" rule: `rfa-nomination__compact` returned nothing because the real class is `rfa-nomination--compact`, and a double-underscore guess is indistinguishable from a missing deploy.

**Cloudflare sits in front of xo.football, so a probe of an already-published asset URL can be an edge hit rather than origin truth.** `/dist` assets are served `Cache-Control: public, max-age=31536000, immutable`, so once an edge node has a hash-named asset it keeps answering `200` for it long after `deploy:dist` deleted that file from `/root/league/dist`. On 2026-07-30 the superseded `main.f1d67453.js` and its chunks still returned `200 application/javascript` from the edge (`cf-ray` present) while all three were provably `deleted` on the host. So an edge `200` proves nothing about what origin holds, and "the old bundle is still being served" is the expected reading, not a failed deploy. A probe is origin-truthful when its URL is one the edge has never cached a success for — a brand-new content hash, or a path that does not exist — which is why the `9999.deadbeef.chunk.js` and `.map` 404 checks above stay valid. For anything about origin state (did a file actually ship, did it actually get deleted) read the host directly: `ssh league 'ls /root/league/dist'` or `grep` in that directory, and treat that as the oracle over any `curl`.

**A frontend deploy does not reach a tab that never reloads, and a GOOD reconnect makes that indefinite.** The bundle a browser is running was fetched once; nothing on the deploy path replaces it. So a user who leaves a tab open receives no frontend fix, and the better the socket reconnect works the longer that lasts — a `pm2 reload` drops every socket, the client reconnects a few seconds later on the JavaScript it already holds, and the page looks entirely healthy while running code from hours ago. Verified 2026-09-03 on the auction: team 6 has joins at `23:01:24` and `23:33:01`, each four seconds after a pm2 boot with no page load in between, while the bundles fixing his reported bug landed at `23:02:49` and `23:33:28`. Two deploys passed his tab and he still had the defect. **So a host-side artifact check settles what SHIPPED, never who RECEIVED it** — every oracle in this guide reads `/root/league/dist`, and all of them stayed green through both deploys. When a named user reported the bug, confirming the fix means confirming their client reloaded, and the log tell is a join that is NOT adjacent to a restart.

**The client-side remedy for that is now shipped, and its two traps are the reason it is not three lines.** `app/core/stale-build.js` records the `dist/build-manifest.json` value read at boot as the build the tab started on and re-reads later to compare, because the bundle deliberately carries no sha; `StaleBuildNotice` renders a dismissible chip and NEVER auto-reloads. Both of the following fail in the direction that looks like success, so preserve them when touching either file.

**The reconnect signal arrives a full webpack build BEFORE the new manifest exists, so an immediate check reads the OLD one and concludes the tab is current.** `deploy:all` is `yarn deploy && yarn build && yarn deploy:dist`, and `deploy` ENDS in `pm2 reload` — the socket drop that announces a deploy therefore precedes the rsync by the length of a production build. This is measurable in the incident above: the two reconnects at `23:01:24` and `23:33:01` came 85 and 27 seconds before their bundles landed. So a reconnect arms a bounded re-check SCHEDULE (`RECHECK_DELAYS_MS`), never one read, and the same ordering makes `WEBSOCKET_RECONNECTED` unusable as a bare trigger for anything that asks what is deployed.

**And `/dist` is served `immutable`, so a plain re-read of the manifest never reaches the network.** The mount sets `max-age=31536000, immutable` for every file under it, and build-manifest.json is the one member that changes under a stable url. Measured 2026-09-04 in a browser: a repeated default `fetch` reports `transferSize: 0` and returns the boot value for the life of the tab, while `cache: 'no-store'` transfers on every call. `api/index.mjs` now serves that one file `max-age=60, must-revalidate` (`libs-server/dist-cache-control.mjs`), but the client still sends `no-store` plus a cache-busting query parameter, because it cannot depend on a header it does not control and Cloudflare answers this path `DYNAMIC` only by default. Do NOT reach for a `Cache-Control` REQUEST header instead — it is outside the CORS-simple set and unlisted in `Access-Control-Allow-Headers`, so it preflights and fails in dev while working in production.

**A data-view fix is not live for users when the deploy lands — redis keeps serving the pre-fix value to whoever requests the same payload, and the entry can outlive the deploy by DAYS, not hours.** `api/routes/data-views.mjs` caches the whole result set under a hash of the request body (`where`/`columns`/`sort`/`offset`/`prefix_columns`/`row_axes`), with the TTL the columns' `get_cache_info` agree on. **Do not assume 12 hours.** The tiers in `libs-server/data-views/cache-info-utils.mjs` run `ONE_DAY` / `TWO_DAYS` / `ONE_WEEK` / `THIRTY_DAYS`, and the from-plays family routinely lands on `one_week` — a 2026-08-04 scan of production found live keys at ~599,000s remaining out of 604,800. So "the deploy was more than 12 hours ago, the cache must have turned over" is an unsafe inference and has to be replaced by reading the key. The cache is in redis, so `pm2 reload` does not clear it and there is no bypass parameter. This cuts both ways on verification: a probe with a payload nobody has requested before gets a fresh key and honestly executes the deployed emitter, while re-running the exact payload the page sends can return a pre-fix entry and read as a failed deploy. After fixing a column, verify with a deliberately novel payload, then check whether a stale entry still exists for the real one — `ssh league "for k in \$(redis-cli --scan --pattern '/data-views/*'); do redis-cli --raw get \"\$k\" | grep -q <column_name> && echo \"\$k \$(redis-cli ttl \"\$k\")\"; done"` — and delete only the affected keys if any hold the old value. Confirmed 2026-07-31 on the `player_league_extended_salary` extension-ladder fix, where a single key held the column and it was the verification probe's own fresh entry.

For a SAVED view, skip the scan and compute the key directly — it is exact, and TTL alone cannot tell you a key's age without knowing which tier it came from. Feed the stored `table_state` to `get_data_view_hash` over `{where, columns, sort, offset, prefix_columns, row_axes, user_id}` (`user_id` is `null` for anonymous; it does not change the hash for a view with no viewer-scoped column), then `redis-cli exists` / `ttl` that one key. Note the script must live INSIDE `/root/league` for the `#libs-server` import map to resolve, and `get_data_view_hash` is a DEFAULT export. Used 2026-08-04 to clear the from-plays alias-collision deploy: the view's key held no entry at all, so no purge was needed.

The same on-host trick is the way to verify a column's emitted SQL in production without a credential: `/data-views/debug` bypasses redis but requires an admin bearer token (`userId === 1`), whereas importing `get_data_view_results_query` from `#libs-server/get-data-view-results.mjs` and printing `query.toString()` executes the deployed emitter honestly, generates no load, and writes nothing.

**The same redis cache INVERTS the verification advice for a CLIENT-side data-view defect: a novel payload hides the bug, and only the real one reproduces it.** The paragraph above says probe with a payload nobody has requested so the deployed emitter honestly executes; that is correct for a column's SQL and exactly wrong for anything in the SPA's request/response handling. On a cache MISS the request is queued and `handle_non_auth_request` (`api/sockets/data_view.mjs`) collapses a second request from the same client into the first, so only one result comes back; on a cache HIT both answer immediately and overlap. A 2026-07-31 defect that rendered every row of a saved view twice — two requests per direct link (`app/core/data-views/sagas.js`), plus a reducer keying its append decision on `request_id`, which is the VIEW id and not a per-request identity (`app/core/data-view-request/reducer.js`) — reproduced at 2x on a warm cache and was perfectly clean on a cold one, on the same view minutes apart. Verify a client-path fix on the payload the page actually sends, after warming it, and treat "it looked fine on a fresh probe" as no evidence at all.

Two related traps when counting rendered rows in a browser to prove such a thing. **The SPA delivers data-view results over the WEBSOCKET, not `POST /api/data-views/search`** — that route exists and answers correctly, so a network capture filtered to it shows nothing and reads as "no requests fired". Hook `WebSocket.prototype.send` and a `MessageEvent.prototype.data` getter, both of which apply to an already-open socket, rather than patching the `WebSocket` constructor (too late by the time you can evaluate). And **the table renders ~25 rows per scroll and pads the end with empty `.row` elements**, so a raw `querySelectorAll('.row').length` overcounts; key the duplicate check on the player NAME cell, never on the row-number cell, which is generated per rendered row and is unique by construction — that mistake returns a confident zero duplicates over a table that is entirely duplicated.

**When you write a grep to prove a defect is ABSENT, validate the pattern against an occurrence you know exists first.** A negative grep that cannot match is indistinguishable from a clean result, and it reads as proof. Concrete instance from 2026-07-30: `remove:[a-zA-Z_$]{1,4}\.removeTag` was used to assert the fixed bundle no longer contained the broken dispatch map, and it reported `absent` on both the fixed AND the broken chunk — the minified namespace is `h.CB`, whose `.` is not in the character class, so the pattern could never match anything. The check was vacuous in exactly the direction that looks like success. Anchor negative checks on the bare identifier with surrounding context (`grep -ohE '.{28}removeTag.{12}'`) and read the hits, rather than encoding a guess about the minified shape into the pattern.

## Deploy topology and submodules

**Deploy tree topology:** the main host runs a **single** `/root/league` clone. The long-lived PM2 app (`server.mjs`, registered from `/root/league` via the absolute `script` path in `server.pm2.config.js`) and all scheduled scripts (crontab invokes `/root/league/scripts/*.mjs`; SSH-in wrappers `cd /root/league`) share that one tree; `digitalocean-0` mirrors the shape for its import workers. `yarn deploy` = `yarn load:main && yarn load:worker1`, each a `git pull` + `yarn install` + `pm2 reload` on its host. (Historically the main host carried a second `/root/league/source` pm2-deploy tree; in 2026-07 a `pm2 start` from the wrong tree silently served a months-old bundle, so the layout was collapsed to one tree and pm2-deploy was dropped — see `user:text/league/league-server.md` § Deployment Topology.)

**Submodule policy:** Only `private` is initialized on the production servers. The `data` submodule is **dev-only** — it is a large git-lfs reference dataset and git-lfs is not installed on production. Never run plain `git submodule update --init` (without an explicit path) on a production server; always target `private` specifically. The `load:main`, `load:worker1`, and `load:logrotate:main` scripts use `--init private` for this reason.

**A commit that bumps the `data` gitlink breaks `yarn deploy` on every host, and `submodule.data.active=false` does NOT prevent it.** `git pull` defaults to `fetch.recurseSubmodules=on-demand`, which fetches any submodule whose gitlink CHANGED — and under git 2.43 that path does not consult `submodule.<name>.active`, so the hosts (which have `active=false` set and an empty `data/` directory, exactly as the policy above intends) still tried to reach `git@github.com:mistakia/league-data.git` and failed. It presents identically to the `private` case below: the superproject fetch prints a reassuring `d429910ed..ba25f64c9 master -> origin/master`, then `fatal: Could not read from remote repository` / `Errors during submodule fetch: data`, the merge never runs, and the `&&` chain skips `yarn install` and `pm2 reload`. The host simply stays where it was. Hit 2026-08-05 on `1ccd93480`, which refreshed the glossary coverage reports and bumped the gitlink as a side effect; the fix is `git config fetch.recurseSubmodules no` in each host's checkout, now set on `league`, `digitalocean-0` and `base-storage`. Nothing is lost by it — `load:main` and `load:worker1` already run an explicit `git submodule update --init private`, so recursive fetch was never what supplied the one submodule production needs.

**An unpushed `private` commit breaks `yarn deploy` for EVERY session, and the error names neither the cause nor the repo you are working in.** `private` is a nested submodule that `sync-all` does not recurse into, so a commit there reaches origin only if someone pushes it directly. Push the gitlink bump to `origin/master` without pushing `private` and the host's `git pull` aborts with `fatal: remote error: upload-pack: not our ref <sha>` / `Errors during submodule fetch: private` — the superproject fetch SUCCEEDS and prints a reassuring `master -> origin/master`, but the merge never runs, so the host stays on the old commit and the `&&` chain skips `yarn install` and `pm2 reload` entirely. Nothing says "your deploy did not land"; check `ssh league "cd /root/league && git rev-parse --short HEAD"` rather than trusting the deploy output. This is not necessarily your commit — on 2026-08-03 a Sleeper-importer deploy hit it on an unrelated session's vendor-proxy commit, which had been referenced by pushed `master` for hours. Verify `git -C private rev-list --count origin/main..HEAD` is 0 **before** deploying, not after the failure, and when it is not, `git -C private push origin HEAD:main` — the commit is already public by reference, so leaving it unpushed is the broken state, not the safe one.

**Running a `db/adhoc` script by copying it onto a host blocks EVERY later deploy, from the moment that script is committed.** It is the same abort shape as the submodule cases above and it originates entirely on the host, so nothing local predicts it: `preflight:deploy` passes clean — the tree is clean, HEAD equals `origin/master`, `private` is pushed — and then the host's `git pull` refuses with `error: The following untracked working tree files would be overwritten by merge` naming the adhoc paths, `Aborting`. The `&&` chain stops at the first host, so `yarn install`, `pm2 reload`, `build`, `deploy:dist` and `deploy:sourcemaps` all never run and both hosts stay exactly where they were. Hit 2026-08-25, where three `2026-08-24-*wheatley*` scripts had been copied to `/root/league/db/adhoc` on 2026-08-24 to run the identity split against production, and `47098bafe` then added those same paths to the repo — the deploy had been failing on it for every session since, unnoticed because nobody had deployed in between.

The fix is to move the host copies aside, but **compare before you move**: `git -C "$L" rev-parse "master:db/adhoc/<file>"` against `ssh league "cd /root/league && git hash-object db/adhoc/<file>"`. Equal blob hashes mean the merge restores the identical bytes and removing the host copy is provably lossless; unequal means the host copy carries edits made during the live run and is somebody's work, so surface it rather than clobbering it. All three matched in the 2026-08-25 case. The durable prevention is to not leave the script behind at all — run it from the deployed checkout after it is committed and pulled, or delete the copy when the run finishes, because an adhoc file is written once and run once and has no reason to persist on a host as untracked state.

**Running a script host-side against the live database:** `NODE_ENV=development` does not work — `config/config-development.json` names a LOCAL database (`127.0.0.1` / `league_development`) with a blank password, so `#db` connects nowhere useful. Use the production config (sops-decrypted at load) redirected onto the `base db` league SSH tunnel:

```bash
NODE_ENV=production LEAGUE_DB_HOST=127.0.0.1 LEAGUE_DB_PORT=15432 node scripts/<script>.mjs
```

The tunnel's local port comes from `config.databases.instances.league.tunnel.local_port` in user-base and is what `base db query league` already uses, so a working `base db query league` means the tunnel is up. Never pass a credential on the command line.

## CI, and what a green master does not mean

**Before reaching for `PUSH_TO_RED_MAIN`, check whether the red is a FLAKE and just re-run the job — that clears the block for everyone instead of pushing past it.** `PUSH_TO_RED_MAIN` is the remedy when master is genuinely broken and your commit is the repair; it is the wrong tool when CI failed on a known-flaky shape, because it leaves master red and every other session still deferred. Know before you reach for it that the block is not permanent: the guard stops deferring once the branch has been red for `RED_MAIN_STALE_HOURS` (default 1) and pushes the queue with a loud warning. So the override buys minutes, not rescue, and a queued fix that cannot push itself is a wait rather than a deadlock. The tell that you are looking at a flake is in this guide already: a duplicate-key violation (`rosters_players_pkey`, `transactions_pkey`) is the documented downstream symptom of an EARLIER test exceeding its budget, whose abandoned queries then collide with the next test's fixture reset — so the named spec is the victim, not the cause. Confirm by running the same spec locally against the same tree; if it passes, `gh run rerun <run-id> --failed` is the whole fix. Hit 2026-08-07, where sync-all was logging `red_main_skip league` and holding six commits from three sessions behind one flaked `test/players.routes.spec.mjs` case at `7345a655a`; the re-run went green and the queue drained on the next cycle. Read the sync telemetry to find out you are in this state at all — `telemetry/sync/<date>.jsonl` in user-base records `red_main_skip <repo>`, and nothing else announces that your push is being deferred rather than simply not having happened yet.

**A green master is NOT evidence your commit was tested, and a missing `Test` run is NOT flakiness — GitHub scans the ENTIRE commit message for `[skip ci]`, body included, so you cannot WRITE ABOUT the token without triggering it.** This was recorded here as an unexplained intermittency until 2026-08-08, when three consecutive misses resolved to one cause with no residue. `Test` is a bare `on: push`, the workflow is `active`, and every commit in that window whose message contains the literal token anywhere got no run while every commit without it got one — a perfect correlation across eight shas.

**A missing `Test` run has a SECOND cause with the identical observable, and the token explanation fits it perfectly — so grepping your own message clears the documented cause and leaves you with nothing.** On 2026-08-26 the push carrying `0e36b85d9` produced a CodeQL run and no `Test` run at all, on a message carrying no token; GitHub Actions was in a `major_outage` and three league runs sat queued for over an hour while `Test` was never created for that sha. Both causes present as "CodeQL ran, `Test` did not", which is the one observable the paragraph above teaches you to read as a suppressed run. Check the platform before concluding anything about your commit — `curl -s https://www.githubstatus.com/api/v2/summary.json` and read the `Actions` component. During an outage there is no verdict to wait for and no gate to debug: say so, post a bulletin so siblings do not each debug their own gate, and decide on the local suite.

Two ways the token lands in a message nobody meant to skip.

- **A merge commit inherits it from the branch.** `git merge` writes a `merge.log` body listing the merged commits' subjects, so a single branch commit ending in `[skip ci]` propagates the skip to the merge — and the merge is the commit that lands the whole cluster. `3501e4f27` merged the timestamptz retype (16 production column retypes, ~50 consumer files) and was skipped this way, by the subject of `4ed9f92de` quoted in its own body. **Check `git log -1 --format=%B` of the merge before pushing it**, not the subject line. Note what propagates and what does not: `merge.log` lists the merged commits' **subjects**, so a token in a branch commit's **body** cannot reach the merge — which is why the 2026-08-18 vocabulary-gate merge was safe despite a branch commit carrying one. Do not rely on that reasoning alone, though; write the merge message with an explicit `-m` so no branch subject is quoted at all, and settle it on the observable that matters — whether `Test` actually RAN on the merge sha (`gh api "repos/mistakia/league/actions/runs?head_sha=<full-40-char-sha>"`), not on a grep of the message.
- **Explaining the token invokes it.** Twice, a commit written specifically to RESTORE a suppressed run defeated itself by naming `[skip ci]` in its prose. `41dd78ffc` was an empty commit whose body reads "The preceding commit carried [skip ci]"; `10407feaf` reads "this commit carries no [skip ci]". Both were skipped. Describe the mechanism without the literal — "carried a skip token" — or the remedy commit becomes another instance of the disease.

The cost is quiet: the retype cluster reached production with nothing having run the suite in CI, and the only evidence it worked was a local run. Two standing consequences. Reading the branch's latest CI status answers a question about someone else's commit, so **query the runs API for your own head sha** (`gh api "repos/mistakia/league/actions/runs?head_sha=<sha>"`) when it matters that your change was exercised; a lone run with event `dynamic` is CodeQL, and CodeQL running is not a proxy for `Test`. **Pass the FULL 40-character sha** — `head_sha` is matched exactly, so an abbreviated one returns an empty `workflow_runs` array at exit 0, which is indistinguishable from the suppressed-run state this very check exists to detect (`git rev-parse <short>` first; confirmed 2026-08-14, where two commits that each had a green `Test` read as having no run at all). And an **empty commit is a poor CI trigger** — it changes no paths and, as above, tempts you into writing the very token you are undoing; prefer sequencing the real work so the head commit carries content.

**A run's `conclusion` is not a verdict on your change until you know which STEP failed — `Clean install` fails often enough that a red run frequently means the suite never executed at all.** The workflow installs before it tests, and that install clones `workerize-loader` from GitHub, so a transient `Failed cloning the repository` / `invalid key: core.autocrlf` / exit 128 turns the whole run red having exercised nothing. Reading only `status`/`conclusion` off the runs API then reports a fully-green change as broken. Read the failing step (`gh run view <id> --log-failed | tail -40`) before attributing, and note the two attributions are opposite actions: an install failure is a re-run (`gh run rerun <id> --failed`), a `Test` failure is yours to fix. **The branch's red and YOUR commit's red can also be different causes at the same time**, which is the trap this cost on 2026-08-17: commit `498254b40`'s own run died in `Clean install` on the clone, while master's red in the same window was a real `check-knex-column-resolution` failure from an unrelated commit — so a bulletin correctly saying "the red is a real gate failure, not the flake" was about a different run than the one being read, and reporting either as the other is wrong. Settle it per sha, per step.

**Read which WORKFLOW is red before which step, because the red-main pre-push guard blocks on ANY workflow's newest run — so a CodeQL failure defers every league push while `Test` is green.** `cli/lib/pre-push-guard-red-main.sh:125` queries `gh run list --limit 20 --json conclusion,databaseId,createdAt,workflowName`, drops runs with no conclusion, groups the rest BY WORKFLOW, and blocks if the newest completed run of any one of them is a `failure`. This repo runs `Test` and `CodeQL` on the same pushes, so either can hold the queue on its own and a green one does not offset a red one.

**So `gh run list --limit 1` is the wrong check, even though it looks like the right one.** Both workflows are created by the same push and share a `createdAt`, so the single row it returns is whichever the API happens to order first — which on 2026-09-04 was a green CodeQL sitting above a red `Test` at the same second, reading as a clear branch while the guard was actively deferring. Pass `--limit 5` and read the workflow column, or skip the inference entirely: **`red_main_skip <repo>` in `telemetry/sync/<date>.jsonl` is the only thing that reports the block as it happens**, and it is what settles whether a repair has actually cleared the queue or has merely been committed. A fix that is committed but unpushed leaves the branch red by definition, which is the bootstrap case below.

**A REPAIR COMMIT CANNOT PUSH ITSELF, and `PUSH_IMMEDIATELY` does not help.** The guard defers on the very red the repair clears, so "it will go out on the normal cycle" is false for exactly the commit that matters most. The two overrides are not interchangeable: `PUSH_IMMEDIATELY=<repo>` bypasses only the carve-out quiet-window debounce, while `PUSH_TO_RED_MAIN=mistakia/league` is the one that bypasses this guard. Reaching for the first when you need the second reads as "queued, will converge" and never moves. Hit 2026-09-04, where the MUI-ratchet repair sat locally through two `PUSH_IMMEDIATELY` attempts while `red_main_skip league` kept firing.

**And do not withdraw the bulletin when you COMMIT the repair — withdraw it when the push lands.** The same day, #667 was resolved on a locally-green ratchet while origin/master was unchanged and the queue was still deferring, which tells every session the block is gone at the moment it is not, and sends the next one to debug their own gate. The withdrawal condition is `red_main_skip` having stopped, or a green run on the new head sha; it is never a local test result.

On 2026-08-17 CodeQL failed on a GitHub-side SARIF UPLOAD outage — the analysis itself completed clean (2100 of 2100 files, 0 findings) and died on `No server is currently available to service your request` — and every session's push was deferred behind it with nothing whatsoever wrong in any commit. `gh run rerun` returned 503 too, so it could not be cleared from the fleet at all; it resolved on its own. Two consequences. The documented flake-versus-real triage assumes the red is `Test`, so run it only after confirming the red run IS `Test` — `gh run list --limit 5` prints the workflow column. And when the block is a foreign-workflow infra failure and your own commit is time-critical (an applied-but-uncommitted DDL window is the case that matters), `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh` is the right override rather than waiting out the guard's one-hour ceiling — post a bulletin naming the cause so siblings do not each rediscover it. Note sync-all runs on a ~1-minute cycle and takes a lock, so an override invocation collides with the scheduled one and has to be retried into a gap; the scheduled run carries no override and will keep deferring.

**A green `yarn verify` means neither "this will push" nor "CI will pass" — the local gate set is a strict SUBSET of the two gates ahead of it, and both gaps were hit in one session on 2026-09-01.** `scripts/verify.mjs` is a list of checks somebody added to that file; the pre-push guard and `.github/workflows/test.yml` are two other lists, and nothing keeps the three in step. The failure mode is the worst-shaped one available: every check you know how to run is green, and the work either cannot leave the machine or lands on a red master.

- **The pre-push guard runs `prettier --check` over the pushed RANGE, and `verify` does not run prettier at all.** One stray blank line in `app/views/components/confirmation/confirmation.js`, committed hours earlier by a different slice, blocked every league push fleet-wide for fifteen minutes — thirteen commits from two sessions, on a repo whose `yarn verify` passed all fifteen checks. The guard is diff-scoped over the whole range, so ANY commit in your unpushed stack can be the blocker and it is usually not your most recent one. Check it directly rather than inferring it from `verify`: `git diff --diff-filter=ACMR --name-only origin/master..HEAD`, filter to `.js/.mjs/.cjs/.jsx/.ts/.tsx/.json/.css/.scss/.md`, and `npx prettier --check` that list. Note `.styl` is NOT in the guard's set, so a stylesheet can never be the cause.
- **CI runs gates `verify` does not.** `db/gates/check-schema-conformance-ratchet.mjs` is invoked at `.github/workflows/test.yml:88` and appears nowhere in `scripts/verify.mjs`, so a non-conforming new column reddens master while every local check stays green. Same day, `users.data_view_export_max_rows` did exactly that.

**The inverse is also true, and it is the one that makes you raise a false alarm: a RED local `yarn verify` does not mean your push is blocked.** The guard verifies a CLEAN worktree of the committed SHA, while your local run reads the shared working tree — so anything uncommitted or untracked in that tree can fail your run and cannot possibly fail the guard's. On 2026-09-02 a sibling's untracked `db/_probe-types.mjs` failed the `dead code (knip)` check locally; the guard's verdict for the same HEAD was `pass` at 17 checks, because the file does not exist in a fresh checkout. Both readings are internally consistent and only one is about what will push. The authority is the guard's own state, not a re-run: read `$worktree_root/league/.verify-state/verdict-<sha>` for your HEAD and `verify-<short-sha>.log` beside it. This matters beyond your own wait — a bulletin announcing a fleet-wide push block over a local failure sends every sibling to debug a gate that is green, which is exactly what was posted and then withdrawn that day.

The second one compounds a trap the section above already names: because GitHub attributes a run to the HEAD commit of the push, the red is reported against whoever pushed last rather than whoever introduced it. A frontend-only commit touching no `db/`, no `libs-server/` and no schema was named by both the run and its signal for a schema violation two commits earlier. Read the failing STEP and the finding it prints before attributing a red to your own change — and when it is not yours, post a bulletin naming the real cause, because the signal will keep pointing at the wrong commit.

## A cluster is done when it is DEPLOYED

**A cluster is not done when its sweep lands — it is done when the sweep is DEPLOYED.** Every gate above examines the working tree or master; none of them can see what production is actually executing. So an applied DDL plus a correct, committed, undeployed consumer sweep leaves production running stale code against a conformed schema, and the whole suite stays green while it does. This is not hypothetical: on 2026-07-29 production was 20 commits behind with `practice` already conformed to `season_year`/`season_type` while the deployed `historical-injury-index-sql.mjs` still queried `practice.seas_type` — a 42703 waiting on that script's next cron fire in early September. Treat the DDL apply and its consumer deploy as one unit, and before declaring a cluster complete check what production is on:

```bash
ssh league "cd /root/league && git rev-parse --short HEAD"           # against origin/master
ssh digitalocean-0 "cd /root/league && git rev-parse --short HEAD"   # odds/plays import workers
ssh base-storage "cd /home/user/league && git rev-parse --short HEAD" # seasonal Underdog ADP ingest
```

**When you verify what production is running, read the HOST — grepping the shared checkout answers about master, which has moved.** A `git rev-parse` on the hosts is only half of it; the moment you go on to ask _what the deployed code does_, the natural next command is a `grep` in the local tree, and that tree is master, not production. On 2026-08-29 a session verifying a partial cutover grepped `player-projected-column-definitions.mjs` in the shared checkout, found the new period-table mapping at lines 117-118, and reported the deployed data-view arm as already correct. It was not: `ssh league 'cd /root/league && sed -n "113,122p" <file>'` returned the OLD function, and the mapping it had found belonged to an undeployed commit that landed on master between its deploy and its grep. Nothing in the output names a host, so the reading is plausible and wrong in the reassuring direction. Prefix the command with `ssh league 'cd /root/league && ...'` for any claim about deployed behaviour, and for a frontend claim grep the built bundle (`ssh league 'grep -oh "<pattern>" /root/league/dist/*.js'`) rather than the source — `dist/` is the artifact users receive, and it can lag the source in the same tree.

**Check all THREE checkouts — `base-storage` is the one that bites.** It is a functional code checkout running a production importer, and no deploy step touches it: it is outside the `yarn deploy` fan-out entirely. **It is no longer unattended, though — since 2026-07-29 it fast-forwards itself hourly at `:40` (`~/bin/update-league-checkout`, logged to `/var/log/league/update-league-checkout.log`) and again immediately before the seasonal ADP import.** So a nonzero behind-count here is expected to self-clear within the hour, and the thing to check is whether the currency job is still RUNNING — read that log rather than treating any drift you observe as a manual remediation. Confirmed working 2026-08-07: a checkout 6 commits behind converged on its own 12 minutes later. **Do not read the "238 commits behind" below as a current figure** — it is the pre-automation incident, and quoting it as live state is a mistake that has already been made once.

On 2026-07-29 it was 238 commits behind: its `find_player_row` still named `player.formatted` after the rename to `formatted_name`, so every player lookup threw. Because the Underdog best-ball ADP importer catches per-player lookup failures and counts them as unmatched, the run produced zero inserts, exited 0, and reported success **daily for three weeks** while writing nothing — the rename's blast radius reached a host the sweep never considered, and the exit-code oracle could not see it. A rename sweep that checks only `league` is not complete. See [[user:task/league/keep-base-storage-league-checkout-current.md]].

Note the cron schedules make this class of defect latent until the season starts (`0 9 * 1,2,9-12 2` for the injury index), which is the same shape as the prop-settlement 42703 — offseason silence is not evidence that a sweep landed.

**"A deploy can lag safely" is true only for BACKEND consumers. Rename a column the SPA reads and the deploy lag is a live user-facing outage, while every server-side oracle stays green.** The API does not break: routes here `SELECT *`, so the response simply carries the new key and `/api/status` keeps answering 200. The browser breaks, because the deployed bundle still reads the old key. On 2026-08-05 the boolean-prefix sweep renamed `leagues.hosted` to `is_hosted`, and between the apply and the frontend deploy a logged-in user lost Auction, Draft, Matchups, Schedule, Standings, Stats, Transactions, Waivers, Restricted Free Agency, Trade Review and the whole team section — the menu gates on `Boolean(league.hosted)` (`app/views/components/menu/menu.js`). The blast radius runs well past the menu because an Immutable `Record` drops the undeclared key at the reducer boundary, so `app.js`'s auction banner, `league-team`'s summary panel, `trade-action` and `editable-league` (both of which then treat the league as external) and every roster action surface degraded together — the same silent absent-key family documented above.

So for any rename touching a column the SPA reads, **the frontend deploy is part of the apply, not a follow-up**: sequence `yarn build && yarn deploy:dist && yarn deploy:sourcemaps` immediately behind the DDL rather than at the end of the cluster, and treat a 200 from the API as no evidence whatsoever. The cheap check for whether you are in this case is to grep `app/` for the old bare name before applying — if the SPA names it at all, the window is user-visible. Note this inverts the usual priority: the commit is what must not lag for backend consumers, but for SPA-visible columns the _deploy_ is the urgent half.

**And it is not safe for a BACKEND consumer either when that consumer is a SCHEDULED writer — which is a second window, independent of the apply-to-commit one, and about CRON rather than about exports.** The paragraph above narrows the exception to the SPA, and that reading is what makes a cron collision look impossible. `process-projections` runs hourly at `:30` and takes ~9 minutes; on 2026-08-18 the pts conform applied at roughly `:35`, INSIDE a live run, and three league formats (`sfb16_sleeper`, `standard_10_team`, `standard_12_team`) failed at 05:38-05:39 on the still-deployed old code with `column "pts_added" does not exist`. Nothing about the apply was wrong — the DDL, the export and the sweep all landed in one commit exactly as the recipe requires — and the window was minutes, not hours.

**No data was lost, and that was a property of the script rather than luck**: `process-projections.mjs` calls `record_league_format_projection_value_history` BEFORE its `delete()`-then-`batch_insert`, so each throw aborted its format ahead of the delete and all three kept a full 23,835 populated rows, stale by one cycle. Had the same throw landed between the delete and the insert, those formats would have been EMPTIED — the documented delete-then-reinsert failure, reached without anyone writing a bug. So: **enumerate `server/crontab-*` for writers touching the renamed table before choosing an apply moment, and time the apply to land immediately AFTER a scheduled run completes rather than at an arbitrary minute.** The next run repairs the staleness on its own, so the recovery is to verify rather than to intervene; check the log for `FAILED` lines and confirm the following run writes a non-zero count for every format.
