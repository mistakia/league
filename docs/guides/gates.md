# Write or Maintain a Gate

**When to read this:** Read before adding a gate, a registered check, a ratchet or a negative control.

What separates a gate from a check, why every gate needs a control that can go red, which corpora are CI-eligible, and how adjudication files stay self-cleaning.

Extracted from `CLAUDE.md`, which keeps the one-line rule and routes here.

---

## Never key a gate on a field the gated actor can write

A gate decides whether to enforce by reading something. If the actor being
gated can change that something, the gate is advisory — it will be turned off
by whatever it was built to stop, and it will look green while it happens.

Paid for on 2026-08-23 by `contribution-guardrails.yml`. It enforced the
guarded-path list only on pull requests carrying a `contribution` label, and the
GitHub App it constrained held `pull_requests: write` — which includes label
management. The App deleted the label from its own pull request (HTTP 200) and
the check went from fail to pass on an unchanged diff. Re-keyed on the author
login, which GitHub assigns at creation and the App cannot edit.

Two things to check when adding a gate:

- **Who can write the discriminator?** Enumerate it against the actor's actual
  permission set, not its intended use. A permission grants everything it
  grants, and label management rides along with pull-request write.
- **Is the discriminator assigned or asserted?** Author, commit SHA and event
  type are assigned by the forge. Labels, titles, branch names and body text are
  asserted by whoever opened the thing. Prefer assigned.

The same reasoning applies to any control keyed on pull request title, body, or
requested reviewers — all of them are writable with `pull_requests: write`.

## Lint and JSDoc ratchets

**Code Quality:**

- `yarn lint` - Run ESLint. Carries `local/no-bare-container-jsdoc`, which bans `@param {Object}` / `{Array}` / `{Map}` / `{Set}` / `{Function}` / `{Promise}` — capital `Object` is the TypeScript `Object` interface, so such a tag reads as documentation while guaranteeing an error at every property access through it. Lowercase `{object}` with `@param x.y` sub-tags is the correct idiom and is not flagged. It is a **ratchet**: `eslint-rules/bare-container-jsdoc-baseline.json` carries a per-file allowance for the 1,175 pre-existing occurrences, a file absent from it is allowed zero, and fixing a file means lowering its entry.
- `local/no-week-reconstruction` - Bans re-deriving `current_season.active_fantasy_week` inline: `Math.max(current_season.week, 1)` in either argument order, and `current_season.week || 1` / `?? 1`. **Baseline-free**, like `no-bare-debug-enable` and for the same reason — the sweep that introduced the getter went to zero, so the honest enforcement is zero, and it covers `private/` because a stateless rule over an unchecked-out submodule reports nothing rather than failing over files it cannot see. Autofixable. It deliberately does NOT flag `Math.max(current_season.week - 1, 0)` (the prior week), `Math.max(current_season.nfl_seas_week, 1)` (a wrong value rather than an unnamed right one), or any receiver other than `current_season`. It anchors on the receiver by name, so an aliased import defeats it; that is accepted, since this is a ratchet against re-growth rather than a proof of absence.
- `local/no-week-zero-sentinel` - Bans week `0` as a season-long sentinel on the data-view PARAM path: `week || 0` / `?? 0`, `week = 0`, `const min_week = 0`, `week === 0`, and `Math.max(week, 0)` in either argument order. **Scoped by path** to `libs-server/data-views-column-definitions/`, `libs-server/data-views/` and `libs-server/get-data-view-results.mjs`, and that narrowness is what lets it be an error with no baseline file — `week === 0` legitimately means the offseason in `get-roster.mjs`, `context-docs/rosters.mjs` and `is-reserve-eligible.mjs`, and the PRE opener in the `nfl_games` and `practice` data. A repo-wide version would be a list of exceptions, which is a much weaker thing. It carries exactly **one** named exemption, `player-projected-column-definitions.mjs`, whose two `params.week || 0` sites still address real stored rows; that file is owned by the projections storage-layer retirement, and the exemption is deleted when that lands. The rule found both of those sites on its first run.
- `yarn check:jsdoc-baseline` - The ratchet's downward half, in CI. Fails when a baseline entry allows MORE than the file contains — the slack a later regression would be reabsorbed into silently.
- `yarn prettier` - Format code with Prettier. **The script is `prettier --write .` — it rewrites the WHOLE tree and ignores extra args, so `yarn prettier --check <file>` still reformats files you never touched (2026-08-15: dirtied two `scripts/social-cards/*.html` this way).** Scope with the direct binary: `npx prettier --check <files>` / `npx prettier --write <files>`.
- `yarn test --reporter min` - Run all tests with Mocha
- `yarn test --reporter min test/filename.spec.mjs` - Run specific test file
- `yarn check:types` - The incremental `//@ts-check` tier (see below). In CI.
- `yarn measure:seams` - Advisory seam count plus ts-check coverage. Never a gate.

## The ts-check ratchet

**The `//@ts-check` tier is OPT-IN per file, and the pragma IS the ratchet.** Nothing in this tree is type-checked until a file carries `// @ts-check` on its first line, so adding one is the whole adoption action; `tsconfig.json` sets `checkJs: false` and includes the server roots so an opted-in file can resolve its imports while everything around it stays silent. `yarn check:types` regenerates `db/schema-types.d.ts` from `db/schema.postgres.sql` and fails if the committed copy disagrees, then runs `tsc`. It, `db/gates/check-ts-check-ratchet.mjs`, and `db/gates/check-knex-table-types.mjs` are all in CI. **`check-ts-check-ratchet` is CI-ONLY — no `yarn check:*` target runs it, so adding a file with the pragma and seeing a fully green local tree tells you nothing.** Run `node db/gates/check-ts-check-ratchet.mjs` before pushing any commit that adds one, and list the file in `db/gates/ts-check-adoption.json`; adoption is a reviewed line, not a silent one. This is the same class as the schema-conformance ratchet below and carries the same fleet-wide cost — on 2026-08-27 a new `//@ts-check` module turned master red, which made the sync-all pre-push guard defer **every** push to `mistakia/league` until it cleared, and the queued fix could not push itself out (`PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh` is the escape). The check takes under a second. Five things to know before touching it:

- **Row types are GENERATED, never hand-edited** — `node db/tools/generate-schema-types.mjs` after any DDL change. It emits two files: `db/schema-types.d.ts` (one interface per table) and `db/knex-tables.d.ts` (the knex `Tables` augmentation). A rename moves the type under every consumer; that is the entire value, and a hand-written shape would be a second schema that decays.
- **`db('<table>')` already resolves to its row type — do NOT hand-annotate the return.** The augmentation declares the table-to-row mapping once, so `db('player').select('pid', 'first_name')` types as `Pick<PlayerRow, 'pid' | 'first_name'>[]` and a misspelled read is TS2551 with the correct spelling, in every checked file, with no `@returns` anywhere. Writing one anyway is how you get a _wrong_ annotation: the hand-written `@returns {Promise<PlayerAliasesRow[]>}` on a two-column select claimed columns the query does not return. Reach for a hand typedef only where the shape is genuinely bespoke — a computed result, a join whose alias narrowing knex cannot follow, `db.raw()`.
- **`db/knex-tables.d.ts` is listed EXPLICITLY in tsconfig `include`, and that line is load-bearing.** Every other pattern there ends in `*.mjs` and so matches no `.d.ts`; an augmentation outside the program applies to nothing while `yarn check:types` keeps exiting 0 over a tree that is no longer covered. `check-knex-table-types.mjs` holds it, asserting the behavior as a red/green pair and the `include` wiring separately, because the pair builds its own config and stays green when the repo's has lost the line.
- **Put the pragma AFTER a shebang.** Above one, `#!` becomes illegal on line 2 and **tsc then reports ONLY that parse error and suppresses every semantic diagnostic in the whole program** — a short output at exit 2 reads exactly like a clean tree. An adoption measurement once read "31 of 32 files clean" and was entirely this artifact.
- **`noImplicitAny` is load-bearing, not a strictness preference.** With it off, an unknown property on an INFERRED type resolves to `any` instead of being reported, which silently un-covers every destructure over a locally-built array. Its cost is bounded to opted-in files by `checkJs: false`.
- **Adopting a file means adding it to `db/gates/ts-check-adoption.json`.** The ratchet checks that list against the tree both ways, because `tsc` is structurally blind to a file that has been UN-adopted: deleting one comment makes a type error vanish and `check:types` still exits 0 (measured). A file that loses its pragma fails, and a file that gains one fails until it is listed.

## Where a file under db/ belongs

**`db/` is split by LIFECYCLE, not by subject matter — read `db/README.md` before adding a file to it.** Everything under `db/` is "about the schema", so subject matter separates nothing; what separates them is whether a file is ever edited again and whether it carries a verdict.

| Directory  | Rule                                                                                  |
| ---------- | ------------------------------------------------------------------------------------- |
| `adhoc/`   | Dated `YYYY-MM-DD-<slug>`, written once, run once, **never edited**. History only.    |
| `gates/`   | Pass/fail verdict AND an entry in the `check:cluster` manifest. State file beside it. |
| `tools/`   | Durable, and **must not** carry a verdict wired to a run.                             |
| `checks/`  | Registered data checks. Carry a verdict that **must not** fail their own run.         |
| `archive/` | Tooling whose cluster closed. Kept for reference, not run.                            |

**A standing DATA condition is a registered check, not a cluster gate — `db/checks/registry.mjs` is where it goes, and `yarn check:cluster` is where it must not.** The two carry opposite dispositions and that is the whole reason they are separate: a cluster gate makes a FINDING fail the run, which is right for "did this push break something", while a data check's exit code carries DETECTOR HEALTH only — a finding rides a self-closing signal and a red run means the check could not answer. Putting a data check in `gates/` is what makes a standing condition nobody introduced defer **every** session's push to `mistakia/league`, which `db/gates/check-conflated-player-rows.mjs` does today. The line: **a gate is triggered by a CODE change; a check watches a STANDING condition.** A conflated player row can arise with no code change at all.

**A check is also where an oracle goes when its subject is a COLUMN whose data has not arrived yet, and the un-gradeable bucket is what keeps it from passing vacuously.** `betting-market-game-prop-column-resolution` is the worked example. league `6e724c02c` turned on an inner `nfl_games` join for six player game-prop columns that had emitted none at any clock, and a newly-enabled inner join that is wrong presents as an EMPTY column — no error, no failing test, no log line, and no natural discovery. The structural half is a spec (`test/data-views.betting-market-grain.spec.mjs`, all six columns under four clocks), but whether the join RESOLVES needs real markets, and CI's throwaway database holds none — so the question can only be asked in production, on the weekly run. Three things about its shape generalise:

- **The measure is an INTERSECTION over a UNION, not resolved-over-expected, because `min_rate` is one-sided.** Losing a game-grain join does not empty the column, it makes it SEASON-WIDE — thirty players become three hundred, the naive rate reads 10.0, and a floor of 1.0 waves it through. Grading `|reference ∩ resolved|` over `|reference ∪ resolved|` makes 1.0 mean the two sets are IDENTICAL, so a dropped player and an invented one both fail. Measured: the join-removed mutation resolves 5 players for a 3-player week and the naive measure calls it healthy. **Whenever a check compares a produced set against an expected one under a one-sided threshold, ask which direction the threshold cannot see** — it is usually the direction the defect actually takes.
- **The live week is emitted UNCONDITIONALLY, carrying a denominator of 0 when no props exist for it.** `classify_check_rows` reports a zero-denominator row as un-gradeable rather than clean, so the operator sees NOT EXERCISED and never a pass. Deriving the rows only from the markets that exist would leave a season with no props ABSENT from the scan, which reads as silence rather than as a question not yet answerable — the same vacuous green this guide warns about everywhere else, relocated into the row builder.
- **The PREVIOUS season is in scope, and that is what makes the check non-vacuous today.** A detector whose whole population has not arrived cannot be shown to work, and the first run that could tell you anything would be the first run that matters. The 2025 corpus grades 21 week-units at 4 to 33 players each, so the join is proven to resolve in production on every weekly run while the 2026 unit waits to become answerable on its own — no calendar reminder, no code change.

Adding one is a row in `db/checks/registry.mjs` carrying its query, grain, optional precondition, threshold, calibration prose and repair command; `scripts/run-data-checks.mjs` runs the whole registry weekly, `libs-server/data-check.mjs` grades it, and `db/checks/parked.json` holds every suppressed finding under a required `adjudicated` or `baselined` disposition. Findings travel on ONE convention — a `log_error` signal with a pinned `fingerprint_override` of `data-check-findings-<check_id>`, `data-check-parked-stale-<check_id>` or `data-check-ungradeable-<check_id>`, each paired with a resolve on the clean branch — so a check removed from the registry must have all three keys closed in the same change or any open row becomes permanently un-closeable. They are three keys rather than one because the conditions can be true independently, and dedup collapses a second emit under an already-open row into a no-op. The design rules are canonical in `user:guideline/software/design-data-checks.md`; the registry's header carries the mechanical how-to-add.

**Adding a row to `db/checks/registry.mjs` breaks a test in a file your change does not name.** `test/data-checks.spec.mjs` pins the registry LENGTH (`expect(registry).to.have.lengthOf(N)`), so a new check fails a spec that appears in no diff you wrote, in a directory you had no reason to open. Nothing in the registry's own header says so and no gate warns. On 2026-08-23 two checks registered in `3431fc0ab` turned master red exactly this way, and because a red master makes the sync-all pre-push guard defer **every** push to `mistakia/league`, the remedy commit was itself stranded behind the failure it fixed — the guard's own stale-hours lift cleared it an hour later, and a deploy window was lost. Update the pin in the same commit as the check, run `yarn test:local` before pushing, and post a bulletin if you do turn master red. The pin is deliberate and worth keeping: it is what stops a check being deleted silently.

**Measure a new gate's finding count on the current tree, and disposition every finding, BEFORE you add its manifest row.** A gate is written against a defect class, so the interesting question while writing it is whether it can SEE the class — and the count it returns over the standing tree is a different question that nothing prompts you to ask. Get it wrong and the manifest row makes `yarn check:cluster` permanently red on debt nobody in the push introduced, which is the same failure `check-conflated-player-rows` embodies and which defers **every** session's push to `mistakia/league`. The two honest landings are a green gate with each pre-existing finding recorded in an adjudications file beside it, or a deliberate red with the repair tracked and a bulletin posted; both need the number first. `check-call-site-param-contracts` measured 69 findings over 58 sites on arrival, none of them false positives and none of them in the lane that built the gate — landed green with all 58 adjudicated as tracked debt, so the gate fails only on what is NEW. Do not skip the disposition step and adjudicate in bulk: the reason line is what stops the file becoming an allowlist, and the count is what tells you whether you are landing a gate or a backlog.

If you would ever edit it, it is not an adhoc migration. If it answers pass/fail but no runner invokes it, it is a gate nobody runs — the failure this repo keeps repeating. If it exits non-zero by design on standing debt, it is a tool and wiring it into CI produces a permanently red master, which defers **every** session's push to `mistakia/league`. Before relocating anything under `db/`, check the path depth: most of this tooling resolves the repo root as `path.join(__dirname, '..', '..')` and then filters scan directories through `fs.existsSync`, so a move to a different depth silently empties the scan set and reports zero findings at exit 0. The five directories are deliberately at the same depth.

**The same path-depth rule decides WHERE you can run `yarn check:cluster` from, and a worktree under `.claude/worktrees/` is the wrong depth.** `check-cluster-gates.mjs` hardcodes the six user-base prose roots as `../../../<dir>` relative to the repo root, which resolves to user-base only from a checkout at `repository/active/<name>`. From `repository/active/league/.claude/worktrees/<slug>` the same relative paths land back inside the repo, all six read as MISSING, and the runner correctly refuses with `TOOLING ERROR: 6 root(s) do not exist`. **There is no `--root` override** — the flag exists but is ADDITIVE, so passing user-base explicitly adds a seventh root and leaves the six broken ones exactly as they were. The remedy is to run the gate from a worktree created at the right depth (`git worktree add repository/active/league-<slug>`), not to pass paths. Confirmed 2026-08-26, where the "pass absolute `--root` paths" workaround was tried first and does not work.

## Declare the corpus, or GATE OK means two things

**A gate that cannot SEE a file cannot go red on it, so a gate whose declared corpus is partly unread is making a narrower claim than its verdict line.** Use `db/gates/scan-corpus.mjs`: `resolve_corpus` splits declared roots into read and unread, `format_corpus` prints a `CORPUS` block naming each with a reason, and `verdict_suffix` qualifies the success line. The cluster runner turns the `CORPUS INCOMPLETE` marker into an **OK (PARTIAL)** verdict, checked BEFORE the exit code, because the exit code is the misleading half in exactly this case. Three synthetic controls drive that rule alongside the six already there.

**Do NOT test root presence with `existsSync` or `statSync` — an uninitialized git submodule is a present, EMPTY mountpoint.** `git worktree add` and a CI checkout without `submodules:` both produce that shape, so an existence check reports the root as scanned and the gate prints an unqualified `GATE OK` over nothing. This is not hypothetical: the first version of `scan-corpus.mjs` used `statSync` and passed `private` as scanned against a worktree at HEAD. Emptiness is the condition that matters. Where a gate knows its own per-root file count, pass it — the count is what the gate actually read and it outranks any filesystem guess.

**But that rule holds for the corpus REPORT only, and a gate that also ASSERTS something about its roots must resolve the corpus TWICE.** The two resolutions answer different questions — counts answer what this run read, the filesystem answers whether the root exists at all — and feeding a counts-derived missing set into a coverage assertion makes that assertion's input identical to its own failure condition, which disables it silently. `check-knex-column-resolution` did exactly that in `73a4c82f5`: it resolved the corpus with counts and handed the resulting missing set to `evaluate_root_coverage` as the exclusion list that assertion skips. A zero-file root lands in a counts-derived missing set by construction, so the exclusion list was precisely the set the coverage guards fire on. Every root that could fail was skipped before it was tested, both file-count branches went dead on every run, and the path-depth regression they exist to catch went back to exiting 0. **Nothing in the output changed** — no verdict moved, no line appeared or vanished — which is why it took a review rather than a run to find, and is the whole reason this is written down. The repaired shape is two resolutions with one source each: what was READ stays counts-driven and is what the `CORPUS` block and `verdict_suffix` claim, while whether a root EXISTS comes from the filesystem through a named `coverage_exclusions()` that takes no counts and is the only source of that set. Give that function exactly two callers — `main` and the control that drives it — so rewiring it back to counts fails the control instead of passing quietly. A control that reaches for `resolve_corpus` itself pins the MODULE's behavior rather than this gate's CHOICE, and stays green over that rewiring.

The corollary is the case the counts view gets backwards. **An ALL-unread corpus is not a narrowed verdict, it is the path-depth failure itself.** Every scanner under `db/` resolves the repo root as `path.join(__dirname, '..', '..')`, so a file moved to a different depth reads zero files in every declared root — which a counts view reports as a corpus that is merely incomplete, and qualifies. `check-knex-column-resolution` now fails on it instead.

**`private/` is the standing instance, and no workflow checks it out** — there is no `submodules:` key anywhere under `.github/workflows`, so on the runner it is an empty directory. Declaring the corpus does not fetch it and is not meant to; it makes the narrowing visible, so a green in CI and a green locally stop being the same claim. The cost of the old silence is concrete: `private/test` was still updating `seasons.year` long after the conform renamed the column to `season_year`, because every consumer sweep that would have caught it ran over a corpus `private/` was not in. The blind spot now has an owner: `check-private-tests.mjs` (in this manifest, and in CI's `private-tests` job) runs the suite where `private` is present and reports `CORPUS INCOMPLETE` where it is absent, so a green locally and a green in CI stop being the same claim.

**A declared root whose extensions cannot match is worse than an undeclared one.** `check-z-index-scale` listed `private` while reading only `.styl`/`.js`/`.jsx`; that submodule is 64 `.mjs` files, two `.json` and a cron, so the root contributed a permanent zero that read as coverage. It was removed rather than reported missing forever. Print the per-root file count so a root that stops contributing is visible rather than silent.

**A NOT EXERCISED bucket is only sound where "exercised" is decided by a CORPUS, and it is a lottery where it is decided by a SAMPLE.** The bucket exists so an adjudication the run could not have reached is not reported as stale, and `check-retyped-column-arithmetic` can answer that honestly because its subject set comes from the `--base` ref and its corpus is the file tree — rerun at the same ref, same answer. The response-validation hold-out borrowed the same shape and the same vocabulary, but its corpus is whatever `(operation, status)` pairs the SUITE happened to produce, over fixtures drawn `ORDER BY RANDOM()`. Producing a response for an operation is not evidence that the run reached the violation the entry names, so an entry could read stale on an unlucky draw and fail the run over a repair nobody made — which defers **every** session's push. Before you give a gate a NOT EXERCISED bucket, ask what decides membership: a declared input and a tree is fine, a sample is not. The instance, its measurement and its repair are in [api.md](api.md).

## A coverage threshold is a decision about who you keep losing

**A floor on a match rate, fill rate or any other coverage ratio is a standing decision to lose whoever falls under it, and setting it from a MEASURED rate is the version that looks most defensible and is worst.** The residual gets laundered into a number that reads like calibration, the gate goes green forever, and nobody is ever named. The importer keeps dropping the same rows every week for as long as the feed exists.

The ESPN line win-rate feed ran this exact arc. Unmatched players were dropped before insert, which lost the row AND the denominator that would have said how many were lost, so no fetched-vs-matched figure existed at all. A backfill then measured 236/240 and the obvious next move was to set the floor from it. **The rate was removed instead, and the gate now fails on a single unresolved row and names it.** Forcing that rule red immediately surfaced a real player nobody had listed, blocked because two players share his name and the fallback route could not choose. A 0.8 floor would have hidden him permanently.

Two conditions make the strict rule affordable, and without them it is just a broken job:

- **Keep the unresolvable row rather than dropping it.** Write it with a null foreign key. The published data and the denominator both survive, and the failure becomes about a missing link rather than missing data. A gate that forces the run to discard good rows will be relaxed, correctly, the first time it fires.
- **Split the verdict by REMEDY, not by severity.** A data failure — wrong season, collapsed table, a percentage at the wrong scale — means the numbers are wrong and must not land, so it blocks the write. A coverage failure means the numbers are right and one identity link is absent, so the rows land and the run fails afterwards. Collapsing the two into one boolean forces a choice between discarding a correct season over one new player and going green on a feed that is quietly shedding rows. Name the distinction on the verdict object (`write_blocked`) rather than recomputing it at the call site, so the two cannot drift apart.

A ratio is the right shape only where the population genuinely has an unrecoverable tail. Where the residual is small, finite and fixable — which is the usual case for identity matching against a roster you control — enumerate it.

## The cluster gate runner

**The cluster gates run as ONE command — `yarn check:cluster`.** Every durable gate below is in its manifest (`scripts/check-cluster-gates.mjs`), ordered cheapest-first, and a gate whose prerequisite is missing SKIPS LOUDLY naming what it needs rather than being silently absent from the run. Add `--base <pre-cluster-ref>` to include the gates that diff against a base revision; `--list` prints the manifest and each gate's oracle without running anything. This exists because the recurring failure here was never a gate returning the wrong answer — it was a gate nobody ran, and the invocation list living only in this guide is what made skipping one invisible. The 18 renamed param keys that dropped filters on 45 saved views are the standing example, and this guide's own verdict on them is that what was missing was running the check at all.

It fails on more than findings. **A gate that declares an always-on negative control must print one, and a control reporting STAYED GREEN fails the whole run even when that gate exited 0** — which turns the "never accept a green you have not shown can go red" rule from a convention each gate keeps privately into something checked from outside. The runner's own verdict rule is driven by synthetic controls on every invocation, for the same reason.

**The control block's HEADER is declared in `db/gates/negative-control.mjs`; the per-line phrasing is not.** The runner's BLIND rule reads `NEGATIVE_CONTROL_MARKER` and its cannot-report rule reads `CONTROL_STAYED_GREEN_MARKER`, both imported from that module rather than spelled independently at each end. A gate printing a control block prints the header verbatim — `format_negative_controls` does it for you — and must reserve `STAYED GREEN` for a control that did not fire. This exists because the undeclared token bit inside the runner on 2026-08-24: `check-ts-check-ratchet` ran four healthy controls under its own `CONTROL WENT RED: <name>` spelling, the string `NEGATIVE CONTROL` appeared in that file only in a source comment, and the runner reported the gate BLIND and failed `yarn check:cluster` over a gate whose controls were all firing. The fix was the gate conforming plus the marker being declared, not the runner learning a third spelling — every added spelling makes the fourth cheaper. The same defect had a second instance, found by the sweep and fixed with it: `check-stranded-vocabulary-literals` derived its verdict WORD from what each control EXPECTED rather than what it did, so a control that went green printed `[FAIL] WENT RED` — a firing control on the one surface a reader checks first — and the gate never emitted the token the runner reads as cannot-report. **Derive a control's printed verdict from its OUTCOME, never from its expectation.** One residue is deliberate: `check-renamed-column-consumers` prints its gate-1 header only when the control set is non-empty, which fails toward BLIND and is the right direction.

**A gate whose oracle is NAME-SHAPED must carry a DECOY control — an input where the naive implementation fires and the correct one does not.** Every incident above is a vacuous green, and every rule above is built to catch that direction. The opposite direction is not covered and costs just as much: a gate that reports confident false positives gets read as broken, and the response a broken-looking gate invites is weakening it, which is the same expensive move a BLIND verdict invites. The controls a gate writes naturally all prove it can SEE a defect; none of them prove it can tell a defect from a look-alike, so that property survives no refactor. `check-call-site-param-contracts` resolves the import edge rather than the callee's bare name, because this tree defines `download_csv` and `import_for_year` as unrelated locals in three different importers on two different parameter vocabularies, and a name-keyed sweep of it measured roughly 50% false positives. Its decoy control drives exactly that shape and goes green the moment the resolution is rewired back to name matching. Write the decoy against the specific look-alike your corpus actually contains, not a synthetic one.

**A gate's machine-readable output owns stdout alone, and the always-on control block is what breaks that rule.** The two conventions collide by construction: a control that must print on every invocation meets a `--json` flag whose payload must be the only thing on stdout. `check-rename-alias-residue` printed its `NEGATIVE CONTROL` block to stdout ahead of the payload, so `--json` never parsed for as long as the flag had existed, and nothing noticed because no runner passes it — the cluster manifest invokes the gate bare. Route the control block to **stderr**, which satisfies both ends at once: stdout under `--json` carries the payload and nothing else, the block still reaches a terminal on every run, and the runner is unaffected because it reads `stdout + stderr` concatenated. Do NOT reach for the other repair and suppress the block under `--json` the way the CORPUS block is suppressed — that hides a `STAYED GREEN` on a `--json` run, which is the one direction a control must never fail. When you add `--json` to a gate, exercise it: pipe it through a parser rather than eyeballing it, because the failure is a leading line a human reads straight past.

**Do not audit gate health by grepping for a control marker — the per-line spellings still diverge and no gate declares which it uses.** `check-league-schema-consumers` prints `RED as expected`; `check-knex-column-resolution` and `check-stranded-vocabulary-literals` print `WENT RED`; `check-league-fixture-reset-coverage` prints `RED (good)`. So a sweep anchored on one form returns a confident **0** against a gate using the other, which reads as "the controls stopped firing" over a gate whose controls are all firing — the expensive direction, since the response it invites is going to weaken a working gate. Hit 2026-08-18 reviewing the vocabulary gate, where `RED as expected` returned 0 at BOTH revisions being compared. This is the same validate-your-pattern-against-a-known-present-match rule this guide already states for sweeps, relocated to reading a gate's own output. Read the runner's `CONTROL`/`VERDICT` table, which normalises across gates, rather than grepping the gates' prose.

**Four things it cannot decide for you, and they are the whole judgment half of a cluster.**

- **A skipped gate is not a passed gate.** The run says so in its summary; believing it is on you. Same for the gates it names as carrying no negative control, whose greens are unproven by construction. Read that list off the run rather than from here: it moves whenever a gate is added or earns a control, so any number written down on this page is wrong by the time someone reads it — the `6 of 18` this sentence used to carry had drifted to four uncontrolled out of twenty-four. **Check WHY a gate is uncontrolled before treating it as debt**, because the uncontrolled set today is not a coverage gap: every member is a per-cluster, apply-time instrument whose header names the incident it was built from and the moment it has to run — two of them against PRODUCTION, where a control would have to fabricate production state. Their standing green in a bare cluster run was never the claim; the claim is what they report when a cutover points them at the surface they were written for. A gate meant to run continuously and carrying no control is real debt. One meant to run at apply time is not, and writing it a synthetic control buys nothing the next cutover will not do better with a real map.
- **Whether a finding is a defect or accurate history.** A doc site describing what a rename DID is correct; only live instruction counts. That call needs someone who knows what the cluster did, which is the deciding reason none of this is in CI.
- **Which findings to read first.** `check-data-view-sql-validity` ranks by reachability tier, not by how broken the SQL looks; ranking by severity once put a dormant seasonal path above a route that had been 500ing for a year.
- **Whether the green is yours.** Several gates read the WORKING TREE — its schema file, its prose, its column definitions — so a sibling mid-cluster turns them red on findings belonging to nobody in your push. When the shared tree is dirty, run from a clean worktree at your HEAD.

  **The same shared tree produces a false GREEN, and that direction is worse, because the green is what licenses REMOVING an adjudication.** A red you did not cause is noise you investigate; a green you did not earn is a repair you believe happened. On 2026-08-28 a commit removed five `check-call-site-param-contracts` adjudications and reported `22 OK, 0 findings` from `--base HEAD` — but two of the five covered `jobs/import-live-odds-worker.mjs`, whose repair was sitting UNCOMMITTED in the shared tree, authored by another session. The commit shipped the removals without the repair, so HEAD alone reported both as live findings for anyone who ran the cluster next, and the commit message named only the three entries it had actually earned. Read `git status` before removing an adjudication, and confirm the repair is in a commit — an adjudication removal is the LAST step of a repair, and the working tree cannot tell you whose repair it is. Removing entries is exactly where a stale-adjudication report tempts you to regenerate the file wholesale, which is the move that launders a sibling's in-flight work into your commit.
  **But PLACE that worktree at the same depth as the main checkout**, because `check-league-schema-consumers` declares corpus roots that reach OUT of the repo (`../../../guideline/nfl`, `../../../text/league`, `../../../cli`) and resolves them against its own repo root. From a worktree anywhere else — `/tmp`, or the `<repo>-worktrees/<slug>` convention — all seven external roots resolve to nothing and the gate reports `TOOLING ERROR: 7 root(s) do not exist`, which reads as a real regression in a gate your diff never touched. This is the path-depth rule above applied to the whole repo rather than to a file moved within `db/`. Either place the worktree three directories below the user-base root (`repository/active/<slug>`, matching `repository/active/league`), or pair-run the cluster — once with your change stashed, once with it applied — and compare the two outputs rather than the absolute verdict, which is the only form that stays honest from an arbitrary path.

  **A right-path run with the ROOTS OMITTED fails in the opposite direction — quietly, and looking like a broken gate rather than a bad invocation.** The external roots are ARGUMENTS, not a hardcoded path, so a bare `node db/gates/check-league-schema-consumers.mjs` from the correct directory raises no tooling error at all: it silently narrows the corpus to the seven in-repo roots and reports every adjudication belonging to an omitted tree as `stale_adjudication` — roughly forty of them, each reading "no longer suppresses anything, so remove the entry". Worse, the negative control drops to `GATE FAIL: the negative control did not go red`, because a control asserting a `.sql` finding cannot fire over a corpus holding no `.sql` files. Both signals point at the gate; neither is about the gate. The adjudications file records the staleness half of this ("a scoped run is a debugging aid whose stale reports mean nothing") but you only read that file once you already have findings, and it does not mention the control. Reach for the roots the cluster runner passes — `USER_BASE_ROOTS` in `scripts/check-cluster-gates.mjs` is their single source — or just run `yarn check:cluster`. **Do NOT delete a single adjudication on the strength of a scoped run**, which is the destructive move this failure mode invites.

**A pin that names SOME of the overrides is not a pin, and the runner's did for two years of `LEAGUE_DB_*` growth.** `PRODUCTION_ENV` and `TEST_CONTAINER_ENV` set host and port so a pinned gate cannot be aimed elsewhere by the operator's profile — the 2026-08-06 incident their comment records. But `db/index.mjs` honours five overrides, not two, so `LEAGUE_DB_USER`, `LEAGUE_DB_PASSWORD` and `LEAGUE_DB_DATABASE` walked through the pin untouched. Exporting `LEAGUE_DB_DATABASE` to satisfy `check-private-tests` — the one gate that requires it, and whose own error text tells you to set it — therefore redirected every pinned gate to that database as well: on 2026-08-28 two data-view coverage gates reported `TOOLING ERROR: database "league_test_privsuite" does not exist` and `check-conflated-player-rows` went BLIND, three verdicts manufactured by the environment on gates the change never touched. The runner now DROPS the whole five-key family before applying a pin, so a pinned gate's connection cannot be influenced by the shell at all, while `requires: 'none'` gates keep `process.env` and `check-private-tests` still receives what it needs. **When you widen the set of environment variables a component honours, grep for every place that pins them** — a partial pin fails in the direction that looks like a broken gate, and its loud form is the lucky one. The quiet form is an ambient `LEAGUE_DB_DATABASE` naming a `league_test_<slug>` that DOES exist, which runs a pinned gate against a stale schema and reports a green over it.

And it stops at the repo boundary: a cluster is not done when its gates are green, it is done when the sweep is DEPLOYED. Nothing here can see what production is executing.

**Running the cluster from a CI job needs an oracle of its own, and the two obvious ones are both vacuous.** A job step written as `yarn check:cluster 2>&1 | tee gate-output.txt` reports **tee's** exit status, not the runner's, so the verdict is discarded and the job goes green over a log whose last line says a gate could not report. Reaching for the log instead and grepping for the ABSENCE of `CORPUS INCOMPLETE` fails the same way in the other direction: absence is what you also get when the gates never ran at all. Both were live in the first version of the private-corpus job, and the second is this guide's own confident-zero rule reproduced inside the thing meant to enforce it. Assert POSITIVELY on the runner's output and make each assertion name something that must be PRESENT — the control block exists and every control held, no `OK (PARTIAL)`, findings and tooling-error counts read off the summary line, and any gate allowed to be blind allowed BY NAME so a newly blind gate still fails the job. Then mutate the captured log once per assertion and confirm each mutation is rejected; an oracle nobody has shown can go red is not an oracle. Use `set -o pipefail` or drop the pipe entirely if you keep one at all.

## The schema-conformance ratchet

**Run `node db/gates/check-schema-conformance-ratchet.mjs` before pushing any commit that adds a table or column — it is CI-only, so a fully green local suite tells you nothing about it.** The ratchet is a separate CI step and nothing in `yarn test`, `yarn lint`, or the SQL-validity gate exercises it, so the first signal is a red master. On 2026-08-02 a new `scoring_format_projection_calibration` table shipped with columns `n`, `r`, `slope` and `position` — three bare names of five characters or fewer plus a reserved word — against a local suite that was green at 2600 passing. The cost is not yours alone: a red master makes the sync-all pre-push guard defer **every** push to `mistakia/league`, so unrelated sessions pile up behind a failure invisible in their diffs, and clearing it needs `PUSH_TO_RED_MAIN=mistakia/league cli/sync/sync-all.sh`. The check takes about a second. When it fires on a table you just added, that is new debt and the fix is renaming the columns — **never `--rebaseline`**, which is reserved for a deliberate audit widening. Full-word snake_case; no bare name of five characters or fewer (an underscore is what conforms `slope` -> `fit_slope`); no reserved words (`position`, `timestamp`, `order`, `desc`, ...). Post a bulletin naming the cause if you do turn master red, so siblings do not debug your gate.

**For an ADDITIVE table or column you can check conformance BEFORE applying, and the recipe is one `cat` — no scratch database, no worktree.** The ratchet reads the tracked schema file, so the usual reading is that you must apply, export, and only then find out. But `audit-schema-conformance.mjs` takes `--schema-file` and only PARSES SQL text, so concatenating your pending `db/adhoc` file onto the current schema produces a candidate the audit reads correctly: `cat db/schema.postgres.sql db/adhoc/<file>.sql > tmp/candidate.sql`, then `--schema-file tmp/candidate.sql --table <new_table>`. (Strip the `-- STATUS:` banner line; it is a comment, but leaving it in a file you might later confuse for the real one is the hazard.) This works only because the change is additive — a rename or drop needs the full candidate-schema recipe above, since the audit must see the columns GONE. Used 2026-08-15 to land a 186-column `pff_player_gamelogs` at zero violations on the first apply, where the alternative was renaming columns in production after the fact.

**And it MISREPORTS a `CREATE TABLE` whose body carries an INLINE constraint, which is the third failure mode of the same shortcut and the one that fires in the direction that wastes time.** The two above are vacuous greens; this one is a confident RED over a clean table. The audit's parser walks the `CREATE TABLE` body as a column list, so each line of a multi-line `CONSTRAINT ... CHECK (...)` is read as a column: `player_field_override` audited at 6 violations on 2026-08-17, three `quoted_camelcase` and three `shorthand`, every one of them named **`AND`** — the continuation lines of two CHECK expressions. A finding whose column name is a SQL keyword is the tell. `pg_dump` moves constraints out into separate `ALTER TABLE ... ADD CONSTRAINT` statements, so the real exported schema never has this shape and the ratchet is right where the shortcut is wrong. Rehearse on a scratch database instead and audit a real dump of it — load `db/schema.postgres.sql` into a throwaway on the `:5433` container, apply the adhoc file with `--single-transaction -v ON_ERROR_STOP=1`, then dump it through `export-schema.sh`'s own flags and `awk` (see "Building a candidate schema by hand" above) and audit THAT. It costs three commands, it proves the DDL is valid SQL as a side effect, and it is the only form that reports what the ratchet will. The same run then gives you the negative control the recipe otherwise lacks: drop one token from `db/tools/schema-token-vocabulary.mjs`, confirm the audit names the exact column, and put it back — a zero over a table the parser never reached is otherwise indistinguishable from a zero over a clean one.

**That recipe reads a new TABLE and is BLIND to a new COLUMN on an existing one, because the audit parses `CREATE TABLE` bodies and does not read `ALTER TABLE ... ADD COLUMN` at all.** So the concatenated candidate reports `total violations: 0` over a column it never parsed — a vacuous green in the one direction that reads as permission to apply. The `pff_player_gamelogs` success above is a `CREATE TABLE`, which is why it worked and why the gap went unnoticed. Measured 2026-08-16 adding `manager_waitlist_submissions.edited_at`: the candidate file audited clean, the apply went in, and the ratchet then failed on the tracked schema for a column the pre-check had passed. Nothing was harmed — the ratchet is the backstop and the fix was a vocabulary line — but the pre-check bought nothing. For a new column, either write the candidate as the post-change `CREATE TABLE` body (edit the table's block in a copy of the schema file rather than appending an `ALTER`), or skip the shortcut and use the scratch-database recipe, which dumps real post-DDL `CREATE TABLE` text. **The general rule: before trusting a `--schema-file` audit, confirm it can SEE your change** — `--table <name>` prints the table's columns, so a column missing from that listing was never checked.

Two things about the finding itself, both of which generalise past this column. `edited_at` was reported as `[shorthand]` on the token `edited`, which is a real English word and the same lifecycle-participle class the vocabulary already carried in `announced` / `created` / `deleted` / `processed` / `submitted` / `updated` — it was simply absent, which is the inversion-to-FLAG property working as designed, not a finding about the column. Adding the one reviewed line is the fix; renaming a real word to appease the list is not, and neither is `--rebaseline`. And check the repo-wide total afterwards (664 here, unmoved) — adding a token can only REDUCE findings, so a total that moves means the addition unmasked or hid something else.

**Two gotchas that only appear once you are iterating against that candidate.** The `shorthand` rule is a POSITIVE token vocabulary (`db/tools/schema-token-vocabulary.mjs`), so a legitimate new football word is reported exactly like real shorthand — 29 tokens fired on that table, and `punting`, `elusive`, `breakaway`, `assists` and ordinary English plurals were all simply absent from the list. That file's header states the intended response: a genuinely new word costs one reviewed line, and the ratchet property is the inversion to FLAG, not the list being complete. So triage each token — rename the ones that are truly shorthand (`qb` -> `quarterback`, `a_gap`/`b_gap` -> `center_guard_gap`/`guard_tackle_gap`, and `off_ball` -> `second_level`, since `off` means OFFENSE elsewhere in this schema) and add the real words. Do NOT `--rebaseline`, and do not rename a real word to appease the vocabulary. And **a rename made to satisfy one rule can trip another**: spelling `hangtime` as `hang_time` cleared `shorthand` and immediately raised `timestamp_type`, because the column now ended in `_time` while typed `numeric`. Re-run the audit after every rename rather than only at the end. Adding tokens can only REDUCE findings elsewhere, so check the repo-wide total is unmoved (664 here) to confirm you left no stale baseline entries.

**A conformance COUNT is a reading off an INSTRUMENT that is versioned in this repo, so a number measured on a branch cut before an audit change is taken against a different ruler — and it looks exactly like stale arithmetic in the plan.** `db/tools/audit-schema-conformance.mjs` gains rules over time; a worktree branched before one of those commits runs the narrower audit and reports a smaller total, with nothing in the output naming which instrument produced it. On 2026-08-08 the footballoutsiders retirement measured 25 total violations against a plan that said 45, and the session wrote a `[correction]` onto the task entity declaring the plan's arithmetic stale. The plan was right: the branch was cut at `41dd78ffc`, which predates `cc50e2a49` (widened the audit past its three blind spots) and `e15841c77` (rebaselined for it), so `external_id` and `timestamp_type` did not yet exist as rules. After merging master the numbers landed exactly as planned — 45 before, 21 after, 24 cleared. Worse than the wrong number was the near-miss: `--rebaseline` run on the narrow instrument had written a 1-entry baseline, which merged would have silently dropped 20 real violations. **Merge master and re-measure before citing any conformance number, and never rebaseline from a branch you have not just merged** — the same "verify before you act on any specific identifier here" rule this guide opens with, applied to the measuring device rather than to the measurement.

**The ruler moved again on 2026-08-08: `60495ef2d` took the audit from 16 to 24, and every one of the 8 is `external_id`.** It closed the third and worst blind spot in `conforms_external` — a bare two-token `/^[a-z0-9]+_[a-z0-9]+_id$/` that applied no vocabulary check to EITHER token, so any `qualifier_noun_id` conformed by construction. That one is categorically worse than the two `cc50e2a49` repaired: those made a column INVISIBLE, so the count was an acknowledged floor, while this one reported non-conforming columns as CLEAN — five of the eight are `gsis_it_id`, a name the audit's own `known_bad_external_ids` roster already listed and the permissive shape was overriding. The entity-type vocabulary is now DERIVED from the schema's own table-name tokens rather than hand-listed as `player|team|game|league|site`, so a new entity type conforms on arrival. **Decompose a widening's delta by TABLE as well as by rule when you report it** — 8 findings by rule is 7 tables by table (`nfl_games` carries two), and this program has already shipped a by-rule total into three artifacts as if it were a by-table one. `test/db.schema-conformance-external-id.spec.mjs` is the regression test for the class, and it is the shape to copy for this tool: it spawns the real audit against a synthetic schema through the new `--schema-file` flag, so it pins reported OUTPUT rather than an internal shape a refactor could move. Note that flag does NOT change the `LEAGUE_SCHEMA_FILE` caveat in [the schema cluster guide](schema.md) — the tool still ignores the environment variable, and the ratchet gate still spawns the audit without the flag, so a candidate schema must still be copied over the tracked path.
